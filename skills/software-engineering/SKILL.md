## 1. 选择主流程

依据用户要完成的工作选择一条主流程；咨询、评审与实施保留原意。先读取该流程，再按问题读取所需主题索引、规则或方法章节。无需读取全部知识，但须保留当前判断所需的前提、例外和关联内容。跨流程复用已有事实与决定，仅补充变化部分。

| 当前任务 | 主流程 |
|---|---|
| 获取需求信息，把模糊诉求转为可执行需求；分析需求冲突、变更或验收标准 | [需求澄清与验收](references/workflows/requirements.md) |
| 设计或评审系统架构、模块边界、数据与消息方案 | [架构、领域与集成设计](references/workflows/architecture.md) |
| 新增或修正功能；局部设计、接口实现、错误处理或性能优化 | [设计与实现变更](references/workflows/implementation.md) |
| 审查差异、提交、接口或实现方案 | [代码与变更审查](references/workflows/review.md) |
| 设计测试、选择验证层次、分析测试失效或补充回归 | [测试策略与验证](references/workflows/testing.md) |
| 解释错误、性能退化、失败测试或生产症状；定位根因并在授权范围修复 | [故障与缺陷诊断](references/workflows/diagnosis.md) |
| 保持行为的结构调整；难测代码、遗留系统演进或兼容迁移 | [重构与遗留改动](references/workflows/refactoring.md) |
| 设计或实施集成、流水线、配置与发布；评估迁移、回滚和发布风险 | [集成、构建与发布](references/workflows/delivery.md) |
| 设计 SLI/SLO、监控、容量和恢复能力；评估过载、依赖故障、告警与复盘机制 | [运行目标与可靠性](references/workflows/operations.md) |
| 估算与分解工作、协调依赖、技术决策；调整团队流程或分析工程效率问题 | [工程计划、协作与改进](references/workflows/planning.md) |

## 2. 建立判断依据

- 保留最小工作上下文：目标与授权、事实及位置、假设/未知、要保持的契约、决定、验证结果。不强制另建文档。
- 只询问会改变下一步的缺失信息；能够独立完成的工作继续进行。关键未知保留条件分支，勿编造业务指标、平台保证或已执行检查。
- 先用当前需求、代码、契约或观测证明问题，再用规则选择方法。来源支持方法，不能代替项目证据。

## 3. 执行与交付

- 按影响范围、不可逆性、不确定性和恢复成本调整深度。直接完成低风险任务；不强制模式、图表、打分、会议或全套阶段。
- 对每个采用建议说明适用条件及主要代价，保留最小可行方案。没有实质问题可以明确无须改变。
- 选择能验证关键行为的检查；报告实际结果和未检查范围。评审不自动改代码，发布或生产操作遵守用户已有授权。
- 多流程衔接时传递事实、未决项、兼容契约和验证证据；不把上一流程的假设升级为事实。

## 4. 知识边界

规则区分原书观点、多源综合与工程适配；互相冲突时比较目标、前提和证据，不按书籍数量或出版时间投票。专项语言、平台、安全标准或法规需要当前权威依据，不能由历史示例推出。

SWEBOK 仅用于维护时查漏，不是每次任务的阶段表。本包按声明范围提供判断方法，尚未通过真实工程案例评价；建设检查的结果不等于工程效果承诺。需要回查版本与来源时读取[来源目录](references/sources.md)。
