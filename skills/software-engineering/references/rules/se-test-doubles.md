## 1. 判断问题

这个替身在帮助观察，还是在制造虚假通过？

## 2. 条件与证据

适用：

- 测试需要控制难触发、慢、不可用或有危险副作用的依赖
- 对象协作协议本身是应验证的行为

不适用或需调整：

- 被测目标自身不能被替换后仍声称已验证其实现
- 值对象或简单确定性计算通常无需 mock
- 不能仅凭替身通过宣称第三方 API 真实兼容

必要证据：

- 被测系统的明确边界
- 外部接口契约与实际版本
- 需要控制的间接输入或观察的间接输出

## 3. 操作与取舍

1. 先说明此次证明对象是局部逻辑、协作协议还是完整集成；能通过稳定公开结果判定时优先这样做。
2. 确有必要时选择提供输入的 stub、简化实现的 fake 或观察交互的 spy/mock；只约束契约相关的调用、顺序和次数。
3. 对第三方能力优先在自有薄适配层后替换；用针对实际第三方版本的集成或学习测试检验适配假设。难触发异常可以替身模拟，但不把它当作真实依赖行为的证据。
4. 将替身覆盖与真实边界验证分开报告，升级依赖时复查假设。

- 状态验证通常较少耦合实现；交互验证适合无可查询结果或协议顺序有业务含义的场景
- 增加适配层需有边界收益；不为每个第三方值类型制造包装

## 4. 验证与反例

- 被验证的生产逻辑确实执行
- 断言不约束与契约无关的内部调用
- 替身协议有来源，真实边界另有验证或明确缺口

反例：把支付适配器替成永远成功的 fake 后声称已验证支付 SDK 参数和错误转换，实际测试从未运行该适配器。
