## 1. 判断问题

测试为何频繁随无关改动一起坏掉？

## 2. 条件与证据

适用：

- 测试难读、失败诊断弱、无关重构引起大量修改
- 需要新增或整理有持续维护价值的自动化测试

不适用或需调整：

- 不能以一测试一个断言的字面规定拆碎一个完整业务结果
- 为了消除少量重复而引入复杂测试框架得不偿失

必要证据：

- 测试表达的业务条件
- 最近的实际失败类型与维护原因
- 夹具数据和断言是否与该条件相关

## 3. 操作与取舍

1. 以行为、条件和结果命名测试；保留最小有辨别力的数据，让关键输入与预期关系就地可见。
2. 断言本场景相关的结果；移除无语义必要的顺序、展示形式和内部步骤约束，但保留属于契约的格式要求。
3. 只有重复确实造成维护问题时抽取有意图的构造器或断言帮助函数；不要把关键预期藏进通用基类。
4. 检查失败消息是否说明期待、实际与上下文；复杂测试辅助逻辑单独验证，避免把同样错误复制进产品和测试。

- 共享工具减少重复，但会隐藏夹具与增加理解跳转
- 多断言可以描述同一结果，过多不相关条件会掩盖后续失败

## 4. 验证与反例

- 维护者可看出失败保护的行为
- 与契约无关的实现调整不会要求重写大量测试
- 故意改变关键结果时诊断足以区分预期与实际

反例：测试整份内部对象快照，新增一个与当前业务无关的缓存字段就导致几十个测试失败；这些失败没有增加回归信息。
