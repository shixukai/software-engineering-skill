## 1. 判断问题

模块是否确实需要独立进程或服务？

## 2. 条件与证据

适用：

- 正在拆分应用、选择部署拓扑或设计远程接口

不适用或需调整：

- 同进程模块边界足以满足需求，且没有独立部署、资源或故障隔离收益

必要证据：

- 跨边界调用频率、数据量与延迟目标
- 独立部署、伸缩、组织或故障隔离需求
- 可观测、版本兼容与运行维护能力

## 3. 操作与取舍

1. 分别画出逻辑模块和物理部署边界，避免把一个领域对象直接变成一个远程服务。
2. 比较同进程模块、整个应用多实例、必要的服务拆分；为每条远程边界列出明确收益。
3. 对必要的远程接口按业务操作控制往返次数，同时设计部分失败、超时、兼容和资源上限。

- 分布边界可提供独立性，但引入延迟、部分失败、数据协调和运维负担。
- 粗粒度远程接口减少往返，也可能增大负载和耦合；不能不加区分地批量传输全部对象。

## 4. 验证与反例

- 每条远程边界的收益与责任清楚
- 高频路径的往返、负载和失败预算可检查
- 同进程实现作为可行基线被比较过

反例：把每个类放进独立服务，期望自动提高性能，实际将一次本地调用变成多次同步网络等待。
