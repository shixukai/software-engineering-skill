## 1. 判断问题

哪些状态必须一起成立和提交？

## 2. 条件与证据

适用：

- 多个相关对象在并发修改下必须共同满足业务规则
- 需要领域聚合或评估事务边界

不适用或需调整：

- 无共同不变量的只读投影或简单记录，不强制套用聚合体系

必要证据：

- 业务不变量与失败后允许的中间状态
- 状态所有者、访问路径和并发写入者
- 事务能力、冲突频率及跨边界协调要求

## 3. 操作与取舍

1. 把必须同时成立的不变量列成可检查条件，再确定最小合理修改边界。
2. 指定维护不变量的聚合根或等价机制，防止外部更新绕过约束。
3. 边界内选择能维护规则的事务与并发控制；若规则频繁跨边界，重新检查模型或明确协调协议。
4. 跨边界异步更新必须说明延迟、失败、补偿或人工处置；业务要求立即原子性时不能用“最终一致”跳过要求。

- 边界太大会增加锁争用和加载成本，太小会把不变量推入昂贵协调。
- DDD Reference 的跨聚合异步建议是模型设计方向；具体一致性承诺仍受业务要求约束。

## 4. 验证与反例

- 并发执行时不变量仍成立或事务明确拒绝
- 全部修改路径经过同一约束机制
- 跨边界失败恢复与可见中间状态符合验收

反例：为追求小聚合把共同额度拆开，各对象单独验证均通过，合计却超过业务上限。
