## 1. 判断问题

算法变体是否需要独立替换或演进？

## 2. 条件与证据

适用：

- 多个算法实现具有共同契约但时间、空间或业务策略不同
- 算法变化反复迫使上下文改变

不适用或需调整：

- 单一稳定算法且封装不能改善理解
- 变体之间没有可保持的共同契约

必要证据：

- 变体的输入、输出和状态需求
- 选择策略的责任归属
- 是否需要运行时替换

## 3. 操作与取舍

1. 明确算法公共契约和每个变体的语义差异
2. 上下文保留业务编排，策略负责算法；选择方明确知道差异
3. 只传策略必要的数据，比较参数传递与回调上下文的耦合
4. 验证默认策略、替换与共享状态；无需动态替换时考虑更简单的函数或静态机制

- 可独立替换算法，但增加对象与选择责任
- 统一接口可能产生未使用参数；回传整个上下文又增加耦合
- 函数或静态机制为工程适配，需按当前语言核实

## 4. 验证与反例

- 所有变体通过共同契约检查
- 上下文无需知道算法内部数据结构
- 策略状态与生命周期符合使用方式

反例：每个布尔分支都建一个策略类会把局部判断变成分散的对象网络；共享有请求状态的策略实例还可能相互污染。
