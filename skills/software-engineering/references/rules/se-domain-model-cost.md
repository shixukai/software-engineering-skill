## 1. 判断问题

事务脚本、表模块或领域模型哪种更合适？

## 2. 条件与证据

适用：

- 组织新业务逻辑或已有组织方式阻碍修改

不适用或需调整：

- 已有简单实现清楚稳定，仅因模式偏好要求重写

必要证据：

- 规则数量、相互依赖、重复与变化模式
- 团队建模能力和数据访问工具
- 现有实现与迁移成本

## 3. 操作与取舍

1. 简单的单一业务动作先评估事务脚本；记录集工具主导时考虑表模块。
2. 当规则跨多个用例重复、复杂变化需要共同维护时，再评估承载行为的领域模型。
3. 服务层只承担有依据的应用边界、事务协调或用例编排；明确领域规则归属。
4. 允许不同区域采用不同方式；以修改代价而非类数量检验选择。

- 领域模型有表达与复用收益，也有学习、映射和间接调用成本。
- 独立服务层可能提供稳定接口，也可能仅增加转发代码。

## 4. 验证与反例

- 一个代表性变化能说明所选组织方式的价值
- 共享规则只有明确责任主体
- 无只为模式完整而存在的层

反例：只有简单记录增删查的工具，为每张表增加实体、领域服务、仓储和应用服务，维护成本大于规则收益。
