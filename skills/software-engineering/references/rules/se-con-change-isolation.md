## 1. 判断问题

这次变化应该被哪个边界吸收？

## 2. 条件与证据

适用：

- 同一业务规则或外部依赖的改动波及多个模块
- 明确存在独立变化的需求或昂贵的未来迁移

不适用或需调整：

- 只有模糊的将来可能，没有可描述的变化场景
- 增加间接层比未来局部重构更贵

必要证据：

- 当前调用与数据依赖
- 变化原因、预期频率及不确定性
- 现在隔离与以后迁移的成本

## 3. 操作与取舍

1. 列出本任务涉及的变化，把共享变化原因的实现放在一起
2. 设计只暴露调用者所需概念的接口，隐藏存储、供应商或算法细节
3. 用一个可信变化场景追踪影响，检查是否仍穿透到无关模块
4. 保留最简单可满足现有需求的方案，昂贵的灵活性须说明收益

- 隔离变化会增加接口和间接调用
- 低概率但后续迁移极难的变化值得提前考虑；低成本局部重构可以延后

## 4. 验证与反例

- 变更影响集中在预期边界
- 公共行为和依赖契约保持可验证
- 不存在只有一个固定值的无用途配置项

反例：两个字段恰好同为字符串，不足以建立通用字段框架；它们可能因完全不同的业务原因变化。
