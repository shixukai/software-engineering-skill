## 1. 判断问题

当前一步是在改结构还是改功能，失败后如何定位？

## 2. 条件与证据

适用：

- 调整既有结构以便理解或降低修改成本

不适用或需调整：

- 预期行为已经改变却仍称为纯重构
- 长时间不可运行的整体重写被包装为安全重构

必要证据：

- 需要保持的可观察行为及允许的接口变化
- 快速反馈测试或有边界的工具保证
- 最后可用基线

## 3. 操作与取舍

1. 明确结构改动与功能改动各自意图，允许在任务中交替但每步保持清楚
2. 先建立受影响行为的反馈，再作小步变更
3. 每步运行适当检查，失败就检查最后一步或回退
4. 按评审收益决定提交组织，不把每次意图切换强制变成独立提交

- 小步增加操作次数但缩小定位范围
- 自动重构工具可降低风险，不能未经核实把所有重写当安全
- 无测试时须限制范围并进入遗留代码接缝策略

## 4. 验证与反例

- 各可用检查点保持约定行为
- 行为变化有独立验收依据
- 未覆盖路径和工具限制明确

反例：同时重命名、改变数据模型和修改业务规则后，一次大测试失败无法说明是哪种意图造成的。
