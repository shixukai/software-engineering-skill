## 1. 判断问题

发现的是用户受损、资源风险还是无关噪声？

## 2. 条件与证据

适用：

- 定义监控告警或诊断所需可观测信号

不适用或需调整：

- 无需长期运行监测的一次性工具，不搭建完整告警平台

必要证据：

- 用户结果、关键请求路径和资源限制
- 已有信号、采集与聚合窗口
- 告警责任人和可执行响应

## 3. 操作与取舍

1. 将用户可见症状与内部原因分开，结合外部探测和内部指标。
2. 对服务检查延迟、流量、错误与饱和度；成功与失败延迟分开，关注长尾及重要分组。
3. 呼叫值班人员的告警对应当前或即将发生的用户影响及可执行动作；诊断指标不必全部呼叫人员。
4. 检查采集失效、重复告警、低价值规则和保留成本，维持可理解的监控。

- 更多指标可增加诊断能力，也增加存储、维护和误报。
- 只监控症状无法定位根因，只监控原因又可能与实际用户结果脱节。

## 4. 验证与反例

- 代表性失败会触发正确症状告警
- 告警能到达责任人并指向可执行响应
- 正常但高流量的条件不产生同等级误报

反例：平均延迟稳定且CPU不高，于是判断服务正常，却遗漏少量请求卡住直到超时。
