## 1. 判断问题

哪些概念应共享，哪些应分开？

## 2. 条件与证据

适用：

- 多个团队、子系统或外部系统对同名概念持不同规则
- 复用模型产生冲突或需要规划集成

不适用或需调整：

- 同一规则的轻微命名差异可直接澄清；不据团队人数机械拆分

必要证据：

- 各业务概念的含义、不变量与使用者
- 模型所有权、协作能力、实际共享代码和数据
- 外部契约、变更影响和上下游控制力

## 3. 操作与取舍

1. 先描述现有模型及其适用范围，标出同名异义、共享内容、翻译点和各方责任。
2. 分别比较共享、明确映射与隔离；共享必须有协调和一致性维护机制。
3. 外部模型损害本地含义且不能协调统一时，评估防腐层，显式转换单位、身份、状态和错误。
4. 逻辑上下文与模块、数据库、服务部署分别判断，不规定一对一关系。

- 独立模型减少相互干扰，但转换、重复数据和兼容维护有成本。
- 共享模型减少映射，却让发布与变化需要协调；防腐层不能自动解决业务分歧。

## 4. 验证与反例

- 每个模型有清楚范围与责任
- 跨边界的数据语义、转换、失败和版本责任可追踪
- 边界对应业务和协作事实，不只对应文件夹

反例：把部门组织图直接映射成微服务，既没有模型差异也没有独立性需求，却增加跨服务事务。
