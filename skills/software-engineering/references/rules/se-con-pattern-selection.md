## 1. 判断问题

引入这个模式究竟解决哪个已经存在的设计问题？

## 2. 条件与证据

适用：

- 需比较多个局部设计方案
- 候选模式用于隔离已知变化

不适用或需调整：

- 仅因模式常见、名称高级或目录中有它
- 没有需要的灵活性，直接实现已足够清楚

必要证据：

- 具体变化轴与调用场景
- 候选模式的适用性、协作和代价
- 不采用模式的最小方案

## 3. 操作与取舍

1. 先描述问题和可变部分，再查候选模式的意图
2. 核对参与者、关系和运行协作是否匹配
3. 比较直接代码、现有语言机制和模式实现的成本
4. 命名围绕业务职责；只引入解决当前变化所需的角色

- 模式以间接层换取灵活性，可能增加理解和性能成本
- 模式是设计词汇，不是通用缺陷判据

## 4. 验证与反例

- 方案能指出具体变化被哪个边界吸收
- 采用模式后新增角色均有当前职责
- 删除某个抽象会损失的能力能够说清

反例：一个不会扩展的两分支判断，不会仅因存在 switch 就需要工厂、策略接口和注册中心。
