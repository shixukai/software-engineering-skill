## 1. 判断问题

所谓恰好一次到底覆盖哪些效果？

## 2. 条件与证据

适用：

- 消费消息同时更新状态、发布消息或执行外部动作

不适用或需调整：

- 无状态纯转换且重复无影响，或丢弃语义已被业务接受

必要证据：

- 接收、状态修改、输出、进度或ACK顺序
- 数据库、broker和外部系统的事务参与能力
- 失败重试和恢复协议

## 3. 操作与取舍

1. 画出每次持久状态变化与确认，逐个列出崩溃后会重做还是漏做。
2. 同一事务能力范围内协调进度与效果；跨系统时比较受支持的分布式事务、持久待发送记录加重投、或幂等与对账。
3. 把承诺限定到参与协议的组件；流框架内部保证不能自动覆盖外部通知或其他不可回滚动作。
4. 请求发送与应答等待不要放在必须先提交才能发送请求的同一未提交事务中。

- 跨资源原子提交有协调和可用性代价；本地持久记录加重投引入重复、延迟和维护责任。
- 分布式事务、幂等与补偿解决的失败范围不同，不能互相换名。

## 4. 验证与反例

- 每个崩溃点恢复后不漏必需工作、不重复不可接受副作用
- 确认/提交配置与实际API版本一致
- 保证范围与仍需对账的外部效果写明

反例：处理结果已写入外部系统但消费进度未保存，任务重启重放；框架宣称恰好一次仍产生两次外部副作用。
