## 1. 判断问题

业务描述与实现是否表达同一个规则？

## 2. 条件与证据

适用：

- 领域术语有歧义
- 业务规则复杂、会反复变化或需要领域专家协作

不适用或需调整：

- 无需领域建模的机械性转换或一次性简单脚本；不为术语活动创造额外流程

必要证据：

- 代表性业务场景、规则及反例
- 现有术语、接口和代码命名
- 能解释业务含义的责任人或有效文档

## 3. 操作与取舍

1. 用业务语言复述场景中的动作、状态和约束，列出同名异义与异名同义。
2. 尝试不同表达，检查是否能自然描述规则与例外；不把技术表结构当成业务解释。
3. 在任务授权范围内同步术语、验收示例和实现命名；行为含义变化时同步验证。

- 共享语言减少翻译误差，但需要持续协作。
- 语言在上下文内一致即可，跨领域强行统一会失真。

## 4. 验证与反例

- 关键术语能用业务例子解释
- 规则和例外在需求、测试与接口中含义一致
- 未解决歧义有明确责任与后续核实点

反例：两个部门都说“完成”，一方指审核完成，另一方指履约完成；仅统一字段名会隐藏状态差异。
