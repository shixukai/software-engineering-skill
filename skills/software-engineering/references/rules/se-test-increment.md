## 1. 判断问题

下一步应验证什么，步子需要多小？

## 2. 条件与证据

适用：

- 用户任务允许修改行为，且需要快速探索接口或修复逻辑
- 已采用测试驱动方式，需要控制红灯状态和改动范围

不适用或需调整：

- 没有行为影响的简单修改不强制套用完整 TDD
- 测试设施尚不具备时，不能伪称已运行红绿循环
- 不能把仅为通过一个测试的常量实现当成完成产品

必要证据：

- 目标行为与测试待办清单
- 当前可运行测试和基线状态
- 已知实现路径与当前最大不确定性

## 3. 操作与取舍

1. 先列当前目标必需的测试与改动，选择有信息量且能够完成的下一项。通常从最简有意义成功路径开始；若连操作放置或设施都不确定，可先用极小启动案例建立反馈。
2. 先观察预期失败；实现足以解释当前例子的改动，并运行相关已有测试。实现明显时直接实现，受阻时缩小步幅；抽象不明确时用有区别的第二个例子排除硬编码。
3. 在通过状态清理本次产生的重复和耦合，再推进下一项；新想法先记入待办，超出本次授权的重构单独提出。
4. 结束时核对必须条件、失败处理与剩余项；初始成功路径通过不等于整个功能完工。

- 极小步有助于定位不确定性，但熟悉实现逐字拆步会增加成本
- 最简成功案例与空输入启动案例目的不同，以阻碍反馈的实际问题选择

## 4. 验证与反例

- 每次失败对应当前待办行为
- 增加不同输入后实现仍符合契约
- 必要失败条件与已有回归通过，清楚说明未执行检查

反例：已有清楚算法却强制先返回每个样例的常量，既无学习收益又诱发为测试硬编码。
