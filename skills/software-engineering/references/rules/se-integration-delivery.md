## 1. 判断问题

消息在什么时刻被认为安全，失败后由谁处理？

## 2. 条件与证据

适用：

- 消息丢失、积压或不可处理消息会影响业务

不适用或需调整：

- 可丢弃、可覆盖的短期信号经业务确认无需持久交付

必要证据：

- 发送确认、落盘、复制、接收与消费确认的具体语义
- 消息价值、到期与保留策略
- 队列容量、恢复能力及异常消息处置责任

## 3. 操作与取舍

1. 逐跳标明消息持久化和确认点，核实进程崩溃与存储故障范围。
2. 将无法路由、到期与业务不可处理消息分开记录，按平台能力隔离并保留原因。
3. 给重投、人工修复或丢弃设置责任、上限、监测和去重前提。
4. 按生产与消费差估计积压，设置容量和保留边界；持久队列不能提供无限缓冲。

- 持久化增加I/O、延迟和存储成本；允许丢弃可简化系统，但必须符合业务。
- 死信隔离保存问题供处理，不能单独保证业务完成。

## 4. 验证与反例

- 确认后崩溃的交付行为符合承诺
- 不可处理消息可定位且不会无限阻塞正常消息
- 积压和保留边界有告警与恢复方案

反例：创建死信队列后无人监测或处理，系统不再报错，却把用户请求永久停在隔离区。
