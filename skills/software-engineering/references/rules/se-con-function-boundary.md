## 1. 判断问题

拆分后是否更容易理解做什么及为什么？

## 2. 条件与证据

适用：

- 函数混合业务步骤和低层细节
- 一段实现需要反复解释其目的

不适用或需调整：

- 提取只把原有语句换个近义名字
- 为了行数门槛制造大量无意义跳转

必要证据：

- 函数职责与调用者需求
- 可独立命名的步骤
- 局部状态、控制流和团队阅读习惯

## 3. 操作与取舍

1. 用一句话描述当前函数意图
2. 找出有独立意义且低一层抽象的步骤，以目的命名
3. 保持同层步骤的叙述顺序，必要时把底层细节下移
4. 从调用处复读，若新名称没增加信息就保持内联

- 小函数可表达意图，但分散代码增加导航成本
- 行数是作者偏好或提示，不是普遍正确性阈值

## 4. 验证与反例

- 新函数名无需读实现即可说明职责
- 没有拆坏状态或顺序依赖
- 评审指出理解问题而非只报告行数

反例：将 return total 改成 return returnTotal(total)，只增加一次跳转；一个清晰的长决策表也不应仅为压到若干行拆碎。
