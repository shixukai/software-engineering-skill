## 1. 判断问题

哪些风险需要在哪一层取得证据？

## 2. 条件与证据

适用：

- 制定测试策略或决定改动所需的回归范围
- 单元测试全通过但接口、部署或质量属性仍可能失效

不适用或需调整：

- 没有涉及的风险或边界不扩展成全系统测试工程
- 不能以任意统一覆盖率、测试数量或层次比例代替风险判断

必要证据：

- 本次影响的业务路径与失败后果
- 组件边界、外部依赖和环境差异
- 现有测试覆盖条件、耗时、失效信号及验收要求

## 3. 操作与取舍

1. 列出关键成功路径、等价输入类别、边界、错误状态及安全、容量、可用性等本任务相关的质量要求。
2. 将局部逻辑放到能快速定位错误的窄范围测试；把协议、持久化和组件协作风险放到集成层；保留关键用户路径与部署冒烟验证。
3. 对每项重大风险写明测试或其他验证、执行时机和剩余盲点。探索性与可用性检查按需要保留人工判断。
4. 优先执行快速且决定性的检查，再运行与改动风险相称的较慢检查；评估结果不足时增加针对性证据，不因数量不足重复同一检查。

- 窄范围测试快且定位清楚，却不能证明真实协作；端到端测试覆盖连接，却昂贵且难穷举
- 不同层可覆盖同一业务事实但检验不同失效机制，应消除无新增证据的重复而不是强制每个行为仅测一次

## 4. 验证与反例

- 风险到验证方式可追踪，遗漏与假设已说明
- 重要边界至少有对应证据或明确未验证结论
- 反馈时间与维护成本有实际记录；不宣称覆盖率等于可靠性

反例：所有持久化调用都替换成内存对象，业务单元测试通过，但真实数据库映射或约束错误仍未被检验。
