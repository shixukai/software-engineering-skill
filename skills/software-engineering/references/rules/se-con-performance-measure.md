## 1. 判断问题

当前慢在哪里，慢到什么程度才算问题？

## 2. 条件与证据

适用：

- 用户体验、容量、成本或资源目标未达成
- 拟以更复杂代码换取性能

不适用或需调整：

- 没有目标或测量，仅凭代码外观推断快慢
- 把历史硬件上的百分比当当前收益

必要证据：

- 需改善的指标和目标
- 代表性工作负载、规模及分布
- 环境、版本、测量方式与基线

## 3. 操作与取舍

1. 确认性能问题的实际价值，区分用户等待、吞吐、CPU时间和资源占用
2. 先测端到端基线，再定位消耗或等待位置
3. 比较需求、算法、数据结构、交互和配置的改进机会，再考虑局部调优
4. 控制对照条件与测量开销，选择适合指标的计时方式并记录波动

- 局部CPU时间适合计算热点，端到端延迟须保留等待；不能把书中的CPU计时建议推广为所有场景
- 微基准可定位机制，但可能遗漏真实工作负载成本

## 4. 验证与反例

- 基线可复现且指标与目标相符
- 热点有数据支持
- 结论限定于测量环境和负载，不夸大为普遍加速

反例：把等待外部I/O的接口改写为位运算，可能让微小计算更快而总延迟不变。
