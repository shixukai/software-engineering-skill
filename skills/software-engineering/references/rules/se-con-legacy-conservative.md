## 1. 判断问题

为了获得测试反馈，最少必须改哪些代码？

## 2. 条件与证据

适用：

- 必须先小幅改造才能把遗留代码放进测试
- 当前反馈不足且需要解依赖

不适用或需调整：

- 顺便整理命名、参数、算法和类层级
- 未经验证相信工具对所有语义都安全

必要证据：

- 初始依赖障碍
- 原签名、类型、参数顺序和作用域
- 编译检查、人工核对及回退基线

## 3. 操作与取舍

1. 把建立接缝作为当前唯一目标，其他清理先记录
2. 尽可能保留签名、参数顺序与方法体，不同时引入新业务概念
3. 检查名称遮蔽、绑定和类型转换等隐患，编译只能覆盖其中一部分
4. 取得测试反馈后，再逐步改善结构

- 暂时保留不理想设计以降低无保护改动风险
- 保守变更不等于零风险，须如实记录剩余盲区

## 4. 验证与反例

- 初始差异能逐项对应必要解依赖
- 参数、绑定与执行顺序经核查
- 新测试实际运行到目标且不会触发无意外部操作

反例：为提取一个依赖调用同时新建参数对象并换单位，既扩大改动又让尚不存在的测试无法保护转换错误。
