## 1. 判断问题

一个依赖或租户能否耗尽所有能力？

## 2. 条件与证据

适用：

- 共享线程、连接、进程或依赖可能传播故障
- 关键和非关键功能共用资源

不适用或需调整：

- 没有可识别传播路径的小型简单系统，不机械添加熔断组件

必要证据：

- 共享资源、依赖与故障传播图
- 功能重要性、允许降级行为
- 隔离容量、熔断指标及恢复策略

## 3. 操作与取舍

1. 找出慢依赖和高负载租户消耗的共享资源，按业务损失选择隔离粒度。
2. 比较独立池、并发限额与其他隔离方式，保留管理和恢复通路。
3. 需要熔断时明确关闭、打开和有限探测状态，设置适合失败类型的判定与恢复条件。
4. 降级结果须满足业务含义；拒绝、延后、缓存结果和部分结果分别说明。

- 隔离减少故障传播，也降低资源共享效率并增加容量规划。
- 熔断会主动拒绝请求；阈值不当可误伤健康依赖，恢复探测也需有界。

## 4. 验证与反例

- 单依赖黑洞或单租户过载不耗尽受保护功能
- 熔断状态可观察且能受控恢复
- 降级未绕过必要业务校验或返回虚假成功

反例：称某推荐依赖为非关键，却让其无期限占满主请求线程池，最终核心操作也不可用。
