## 1. 判断问题

什么条件允许这个版本进入下一阶段？

## 2. 条件与证据

适用：

- 搭建或修改集成流水线
- 需要判断某版本是否具备发布证据

不适用或需调整：

- 测试结果只能支持执行版本及对应环境，不自动批准外部发布
- 未完成功能的预期失败不能混成既有回归失败而长期放任红灯

必要证据：

- 各阶段输入制品、检查内容、通过条件与执行环境
- 阻断失败的负责人与修复状态
- 变更风险和必要的人工判断或授权

## 3. 操作与取舍

1. 把快速构建与局部检查放在前面，后接相关集成、验收和质量属性检查；每阶段明确输入输出和阻断条件。
2. 让失败尽早终止该候选版本的晋级并反馈责任人；先判断产品、测试还是基础设施问题，不靠重试覆盖原失败。
3. 区分进行中的新验收与必须持续通过的回归；只有必需检查完成的对应版本可成为待发布候选。
4. 记录执行结果、未执行项与剩余风险；人工验收与生产发布授权保持显式边界。

- 较多关卡提高证据但延长反馈，应按风险安排和并行化独立检查
- 最快反馈不意味着所有昂贵检查每次运行，也不意味着可跳过必要证据

## 4. 验证与反例

- 失败候选无法无痕进入下游
- 版本、环境、跳过项和执行结果可关联
- 回归与待开发功能状态不混淆

反例：流水线显示绿色仅因为失败测试被默认跳过，报告却称完整回归通过。
