## 1. 先明确这次需要决定什么

本方法用于业务规则在多个入口传播、对象与关系数据的组织方式难以取舍，或编辑工作跨越多个请求并出现状态和并发责任不清的任务。先取得实际操作、规则变化、读写数据、失败结果、现有组件和版本信息，再选择需要阅读的部分。书籍中的模式不能证明当前项目已有缺陷。

只有独立目录编辑时，从第 2 节的简单条件开始即可；排查重复对象读第 4 节；处理草稿或多人修改读第 7–9 节。不要求小修改同时比较所有模式。跨系统含义冲突另用[上下文方法](context-meaning-model-evolution.md)，事务不变量的推导另用[聚合与事务方法](invariants-aggregates-transactions.md)。

### 1.1 原创题设与固定规则

下述图形卡包场景完全虚构。社团先维护图形目录，后来需要编辑卡包并发布不可变的印制说明；本例不执行印刷或外部发送。发布时必须满足当前启用的规则，之后目录改变不改写历史印制说明。实际操作权限仍需在工程任务中核实。

起始 **P0** 只有独立目录的名称和可用状态编辑，没有卡包发布需求。**P1** 增加发布：每行数量为正整数，总数恰为 12；所用图形当前可用且色组与卡包相同；选定卡背就绪。成功后保存图形版本、卡背版本、各数量、卡包版本和规则版本。**P2** 只追加一条：每种图形在整包中的累计数量不得超过 8。多行引用同一图形要合并计数。

| 初始事实 | 值 |
|---|---|
| 卡包 K1 | 版本 7，色组 `blue`，明细 17 引用 C1 共 6 张，明细 18 引用 C2 共 6 张 |
| 图形 C1 | 圆环，版本 4，`blue`，可用 |
| 图形 C2 | 方格，版本 5，`blue`，可用 |
| 图形 C3 | 三角，版本 2，`green`，可用 |
| 卡背 B1 | 版本 3，状态 `ready` |

因此，C1×6 与 C2×6 满足 P1、P2；C1×8 与 C2×4 也满足。C1×9 与 C2×3 合计 12，却只满足 P1。将 C1 拆成 5 张和 4 张，再加入 C2×3，仍违反 P2。C1×6 与 C2×5 总数为 11；C1×6 与 C3×6 虽合计 12，色组却不一致。这些预期由题设规则独立推导，不来自待检查的实现。

P1 已有“预览后发布”和“复制后发布”两条路径。后续比较让两条路径面对相同的 P2 变化。文字卡、单色组活动卡包和编辑资格等分支会在相应位置另行给出，不累加到初始规则。

## 2. 在同一变化中比较三种组织方式

### 2.1 先让简单方案成立

P0 只编辑独立目录时，一个清晰的操作过程可以读取条目、检查权限和输入、保存变化并返回结果。已有数据组件足以承担访问，就沿用它。此时增加卡包对象、通用规则框架或额外服务层，没有来自题设的收益依据。

到 P1，再把“编辑一个字段”与“形成满足整包条件的说明”分开。两者需要不同输入和结果，但这种区别仍不能独自决定必须建立对象模型。先画出实际步骤，找出哪些规则被哪些入口使用。来源 L01–L04。

### 2.2 事务脚本：按操作组织，允许共享普通函数

Transaction Script 是围绕一项业务操作组织的过程。它可以调用普通函数、数据访问组件和事务设施；“脚本”不意味着单个巨型函数，也不保证整项业务只有一个数据库事务。

在 P1 中，两条路径可以这样组织：

- 预览后发布先解析用户变化、读取所需目录，校验候选后返回预览。
- 最终提交取得用户确认的候选与依据，在受保护的提交范围重查，再保存说明。
- 复制后发布先读取旧包、形成独立候选，再读取当前目录并校验，最后进入相同的提交步骤。

`校验候选(明细, 当前目录, 卡背, 规则版本)` 可以是普通函数，返回明确的不满足项。P2 在这个函数内按图形标识累计数量，再检查是否超过 8。两条路径复用规则含义，而各自承担输入转换；最终提交仍要按第 8 节重新保护依据。复制旧包不能复制它曾经通过的结论。

按行检查 `quantity <= 8` 的初稿会放过 5+4 的拆行反例。改成按图形累计后，错误才得到纠正；增加一个服务类名称没有作用。过程组织没有阻止这次修复，也不需要为了比较而故意复制全部校验代码。

代价会在别处出现：如果多个操作都重复解释卡包状态、变更明细和协调相同关系，维护者容易漏掉某个入口。先看共用函数与明确输入是否已经解决问题；只有重复关系和变化传播仍然困难时，再比较更丰富的对象组织。来源 L01、L04；本例结构为工程展开。

### 2.3 表模块：围绕记录集表达集合工作

Table Module 把一张表或视图的业务处理集中在一个模块中，操作记录集中的多行。它不是为每行创建一个带行为的对象。卡包模块可以按 `kit_id` 取得主记录，明细模块按同一编号筛选行，并与图形记录集连接。

P1 的 `检查卡包(kit_id, 卡包集, 明细集, 目录集, 卡背集)` 计算该包总数与关联条件。P2 增加对所选明细按 `(kit_id, card_id)` 分组的累计检查。复制路径先把选中明细复制到新候选记录集，再调用相同模块；预览路径以编辑后的候选记录集调用它。最终提交把相同含义应用于提交范围内的依据。

这种安排适合既有记录集、数据绑定和批量处理组件已经成熟的情况：分组与连接直观，不必为每个明细构造对象。代价是业务身份多通过键和行选择表达，调用者传错记录集、遗漏筛选或混入另一卡包的明细，可能使总数错误。需要明确记录集代表数据库快照还是编辑副本，以及模块能修改哪些行。

若数据库完成分组，必须确认 SQL 与内存预览对于重复行、空集合、空值和整数数量的含义相同；同名函数不能证明两种实现等价。P2 上限按图形累计，不能误用“每个明细行一个处理对象”来冒充表模块。来源 L03、L05。

### 2.4 业务对象模型：让行为跟随其所约束的状态

Domain Model 用相互关联的业务对象表达状态和行为。在本题中，`卡包`可以维护明细，`卡包明细`表达图形引用、数量和顺序；共享的`图形设计`属于目录，不能因为被引用就由卡包取得修改权。

P1 可由 `卡包.评估发布(目录依据, 卡背依据, 规则版本)` 表达整包条件。P2 在此计算按图形归并的数量，或把确有变化需要的数量政策作为明确参数。两条路径都先形成卡包候选，再调用该行为。对象内部不必自行查数据库：应用协调取得所需事实，映射层负责保存，提交范围按第 8 节保护事实。

业务行为可以阻止不合要求的正式发布，但草稿允许暂时不完整。若把“总数必须为 12”硬塞进每次增删明细，会导致用户无法先删后加；应把草稿可编辑状态和可发布条件分开。对象方法有意义，是因为它表达了状态变化的条件，而不是因为类名对应书中的模式。

这个方案使规则和对象关系容易一起演进，但必须承担构造完整对象、维护引用、处理草稿状态、映射到关系数据以及加载生命周期的成本。如果 P2 仍由一个简单纯函数清楚表达，增加对象体系未必划算。来源 L02、L05、L07。

### 2.5 依据变化成本作决定，并保持可迁移

| 本题的证据 | 当前可取的选择 | 什么变化会使它值得重审 |
|---|---|---|
| P0 独立目录，规则稳定 | 简单过程与已有数据访问 | 出现跨对象约束、多个入口反复解释同一状态 |
| P1、P2 仍能用小函数共享规则，关系不复杂 | 保留事务脚本可以成立 | 脚本不断复制关联维护，规则遗漏在多个入口反复出现 |
| 团队已有可靠记录集组件，主要工作是批量筛选和分组 | 表模块可以降低对象构造成本 | 行键和筛选规则掩盖了重要业务状态与行为变化 |
| 卡包关系和状态变化不断增加，集中行为能减少理解与修改范围 | 比较业务对象模型及映射投入 | 映射和框架成本超过规则收益，或实际工作恢复为简单数据维护 |

P2 本身没有给出三者中唯一正确的答案。可先保留共享校验的过程实现，并记录后续变化是否真的难以控制；已有记录集方案也可以继续使用。若证据支持迁移，先把业务输入、规则结果和提交责任明确，沿一个操作替换组织方式，保留反例与旧入口的行为保护，再扩大范围。不要按函数数量、代码行数或书中定性曲线设置自动迁移阈值。具体行为保护复用[重构方法](refactoring-legacy-safety.md)。来源 L04、L17、L23、L26。

## 3. 为业务工作选择数据访问边界

### 3.1 服务层承担什么，取决于需要协调什么

Service Layer 是一组应用操作边界，用于组织用例及其协调。它可以是进程内函数或对象，不等于远程服务，也不要求把所有业务规则放进服务类。

P0 如果现有操作入口已经清楚地检查权限、调用数据访问并处理事务，额外加一层只转发同样参数，收益有限。P1 有两条发布路径时，可以将共同的“受保护地提交候选”作为薄应用边界：核对当前操作者、组织读取与事务、调用所选业务组织方式、保存结果。规则仍在共享校验函数、表模块或卡包行为中。

如果发布随后真的需要协调多个业务步骤，再让边界表达这些顺序和失败结果；不要因为书中服务层示例有事务或消息，就推断外部发送也包含在同一个数据库事务里。本题仅保存印制说明，没有增加通知或印刷职责。远程接口是否必要另由[架构方法](architecture-drivers-tradeoffs.md)决定。来源 L06–L09。

### 3.2 业务组织与数据访问是相关但不同的选择

| 数据访问方式 | 实际职责 | 放到本题时的判断 |
|---|---|---|
| Row Data Gateway | 一个对象封装一行的数据库访问 | 简单按行操作可复用；不要把整包规则塞到任意一行网关中 |
| Table Data Gateway | 一个入口封装整张表或视图的访问 | 适合返回记录集给表模块，也可供过程调用；业务校验与SQL封装仍可分开 |
| Active Record | 对象表示一行，并承担自身保存及部分行为 | 目录结构和规则简单时可减少层次；整包规则、复杂关系和独立模型演进会增加负担 |
| Data Mapper | 将业务对象与存储结构之间的转换另行组织 | 业务对象和数据库需要各自变化时有价值；增加映射、身份及加载维护成本 |

这些名称描述职责，不能按项目采用哪种语言直接选定。一个项目也可能让独立目录保持简单访问，而让复杂卡包使用映射器。混用需要清楚的工作范围与交互，不意味着每张表都能随意采用不同事务策略。来源 L10–L17。

先核对已用 ORM 或数据组件到底提供什么：同一工作内的对象身份、变化跟踪、保存时机、查询与未写入变化的关系、事务参与方式、失败后的复用限制。缺少产品和版本信息时，给出这些核查项；不能凭“使用 ORM”宣布责任已经落实，也不要先手写一套竞争机制。

## 4. 安排身份、变化追踪和写入责任

### 4.1 持久身份、对象引用和业务版本分别说明什么

在一次工作中，按编号查询 C1 和从明细导航到 C1，应识别为同一持久对象。Identity Map 保存该范围中已加载的身份与对象对应关系，避免出现两个可修改副本。它并不让 C1 在别的会话中停止变化，也不保证当前对象一直最新。来源 W16–W18。

映射键必须适合实际范围。明细编号 17 与另一张表的图形编号 17 不代表同一对象；可以由类型对应的映射分开管理，或在共同映射中包含必要的类型与存储范围。继承结构跨具体表查找、跨数据库导入时，单表主键也未必足以区分身份。不要因为某表的编号唯一就建立只按整数索引的全局对象表。来源 W17、M01–M02。

创建 K2 时先取得编号，只说明编号已分配。若编号在独立事务中保留而业务保存失败，编号可以空缺，K2也可能从未成为正式记录。不要用“编号非空”代替新建、已保存或提交成功的状态；分配策略、数据库返回键的时机和组合键的所有者信息需要分别确认。来源 M03–M04。

### 4.2 工作单元记录变化，不替数据库完成事务

Unit of Work 是一次工作范围内的变化记录及保存协调机制。它可收集新建、修改和删除对象，有时也记录影响决定的读取依据。它是否开启或加入数据库事务，需要看实际组件；仅存在一个叫 `commit` 的方法不能证明数据库已经提交。来源 W12、W14–W15。

| 变化跟踪安排 | 本题怎样使用 | 容易遗漏或付出的代价 |
|---|---|---|
| 调用者显式注册 | 编辑数量后登记对应明细或卡包变化 | 某个编辑入口忘记登记会丢失修改 |
| 对象变化时通知 | 数量修改方法通知当前工作范围 | 旁路字段赋值、集合直接修改和多个工作范围需要检查 |
| 与初始副本比较 | 保存读取时的状态，提交时比较明细和卡包 | 复制、比较及关联变化判断有成本；副本必须代表正确的初始状态 |

明细删除、共享图形引用变化和新增明细都要进入对应保存安排。若所有者负责完整保存依赖明细，就要让依赖变化使所有者可见；不能一边由所有者整组替换，一边由另一工作单元独立删除同一明细。原书警告依赖对象映射与工作单元可能漏掉删除等工作，应核查责任，而不是宣称现代 ORM 不能支持这两者。来源 W13、M10–M11。

### 4.3 写入顺序服从实际约束

新卡包、明细及引用关系应按外键和身份可用条件安排；删除时也要考虑剩余引用、级联规则和必要约束。示例里“先插入、再删除、后更新”的顺序不是通用排序算法。批量发送只减少往返，并不自动使多次写入原子化。来源 W14、L20。

把本次工作的责任写清：业务行为决定允许什么；映射将对象或记录集转换为存储操作；变化跟踪决定哪些操作需要发出；数据库事务保护约定的写入集合；并发方案保护它依赖的事实；连接和结果集由实际取得它们的范围释放。一个机制的名称不能替代其他责任。

## 5. 按所有权与查询需要选择映射

### 5.1 移除明细、解除关系和删除共享对象不能混用

K1 的明细 17、18 有数量和顺序，属于 K1。移除明细 17，只删除这条草稿明细；C1 是其他卡包也能引用的共享图形，仍要存在。这种关系有自身数据，不能简化成没有数量的纯关联。

如果只是解除可选引用，可以清除引用；若该引用是必需的，就要拒绝这个中间操作或改用允许不完整的草稿表示。将明细转移到 K2 则是另一项业务动作：目标包规则与转移权限尚未给定，不能按一次外键更新自动批准。整组删除再插入只有在依赖对象没有外部引用、身份和历史需求也允许时才可比较。来源 M05–M08、M10。

单向对象集合不一定直接携带修改数据库外键所需的信息。可以增加反向引用并维护两边一致，重新查询原集合取得差异，或保存初始副本比较；各自增加对象维护、数据库读取或内存成本。哪一种也不消除并发竞争，写入时仍需第 8 节的保护。来源 M07。

### 5.2 小值、依赖明细与历史快照有不同存储含义

卡包色组是随包保存的小值，不因存在一个 `Palette` 类型就必须有独立表。需要独立查询、外部引用或维护权时，再比较其他结构。卡包明细由包负责生命周期，但共享图形不因此成为可随包删除的依赖对象。来源 M10–M12。

已发布印制说明是题设规定的历史快照，可以保存当时名称、图形版本和数量；这与把当前图形复制到每份草稿、又期待它们自动同步，是两件事。需要按明细查询历史说明时，普通表结构可能更便于查询；主要整体取得时，可以比较序列化存储。序列化后要有可解释的格式版本和旧数据读取安排，不能假设类改变后旧对象图自然可读。来源 M13、工程适配 A10；演进复用[数据迁移方法](mixed-version-data-migration.md)。

### 5.3 出现文字卡时，先判断是否真的需要继承

独立分支新增文字卡：它有短语，图形卡有形状标识，两者共享标识、名称和可用状态。若行为差别很小，明确类型字段及对应数据已足够；不要先选继承，再制造一套映射需求。

若业务行为确实需要多态，再比较下表。来源 L22、M14–M17。

| 安排 | 读取与引用 | 变化成本 |
|---|---|---|
| 单表继承 | 一张表包含类型字段和各类属性，抽象类型查询直接 | 不适用列和约束表达需要处理；用程序类名作类型值会耦合类名变化 |
| 类表继承 | 基类及各层表的行共同表示对象，可能需要联接或多次查询 | 字段移到另一层涉及表变化；插入、删除要维护整个对象的相关行 |
| 具体表继承 | 各具体类型表包含继承字段，已知类型时读取较直接 | 公共字段重复；抽象查询、跨表身份和引用约束更复杂 |

具体类不一定只出现在继承树叶子。不能用“每表有主键”解决跨具体表身份，也不能因根表不存在就直接去掉引用约束。若共有映射代码确实重复，可以分开共有字段处理与具体类型选择；这不要求自己重新实现 ORM。性能、表宽和联接代价要依据当前查询与测量，不使用书中的联接数量限制。

既有目录表暂不能修改时，先列出不能改变的键、字段和引用，再比较局部映射、查询转换及分步迁移。无法改表会影响选择，但不是重建数据库或放弃业务规则的理由。来源 L23、M01、M08。

## 6. 让查询和加载的含义可见

### 6.1 同一个对象，不等于同一时刻的查询结果

数据库里 K1 的 C2 数量仍为 6，当前工作副本已改为 5、尚未保存。此时查询“数量为 6 的明细”，必须先说明是在问数据库快照，还是预览当前编辑结果。

若数据库按 6 选中了该行，再从身份映射返回已改为 5 的对象，查询条件与返回内容就来自不同状态。反过来，数据库没选中的行也可能因内存修改而满足条件。仅复用对象身份不能修复成员集合。来源 L18。

当前草稿预览可以在完整的当前候选上计算；数据库查询则标明所观察版本。若选择先把变化发送到数据库再查询，应确认发送行为是否只是事务内写入、是否触发约束，以及失败和取消怎样处理；不能为了刷新预览就提前正式发布。已有 ORM 的自动发送策略需要按版本核实。

### 6.2 加载计划同时影响完整性和成本

逐行取得图形容易增加往返；按所需图形标识去重后批量取得，或一次联接，可以减少部分访问。但结果必须仍包含没有明细的草稿，重复引用 C1 的多条明细也不能被错误合成一条数量记录。多行组成同一对象时，先明确身份、明细顺序和结果完整性，再比较成本。来源 L19、M09、工程适配 A09。

本题输入很小，不足以证明哪种查询更快。真正选择需要查看返回行数、读取字段、往返延时、缓存和数据库计划；一次大查询可能取得大量重复数据，按需查询也可能只用到少量关联。不要固定要求“永远延迟”或“全部一次取回”。

延迟初始化、代理、Value Holder 和 Ghost 都在安排数据何时进入对象；它们改变依赖、对象引用或加载状态。选择时检查调用方是否需要具体类型、代理与实体能否混用，以及加载时连接是否仍可用。业务结果允许空值时，用空值表示未加载会混淆含义；明确区分未加载、已加载为空、加载成功和加载失败。来源 W19–W23、L25。

加载 C1 后，加载 C2 失败，已经注册到身份映射的部分内容不能让发布继续。保存用户输入，停止依赖完整目录的判断；优先丢弃这个工作范围并重新取得必要对象。若组件提供恢复机制，需要证明对象状态及失败清理符合其约定，不能通过再次调用同一个属性就假定恢复完成。工程适配 A04、A08。

### 6.3 查询抽象应减少当前重复，而不是预建通用语言

题设只有按卡包编号、按色组及按可用状态三种固定查询。可以先用明确查找方法隐藏 SQL 与字段对应。查询条件确实需要组合且多个入口重复时，再比较有限查询对象。Repository 提供类似集合的业务对象查询边界，适合集中重复查询或数据源策略；接口像集合不代表 `all()` 的代价像本地数组。来源 L24、M20–M21。

元数据映射把字段与表列对应保存为数据，可驱动生成代码或反射。它减少重复，也增加映射配置、异常处理和调试工作。少数特殊情况可以隔离处理，不必无限扩展描述能力。字段重命名要同时检查外部配置与生成规则；重新生成代码不应覆盖未经管理的手工修改。反射性能、构建安排和代码是否纳入版本管理按实际工程决定。来源 M18–M19。

原书的字符串拼接查询只用于理解说明，不是本方法的实现模板。真正生成查询时核实驱动参数处理及动态标识符限制。用内存集合替换数据库，可以检查部分业务规则，但不能由此证明数据库的空值、排序、事务和并发行为。具体替身检查复用[测试层次方法](test-risk-oracles-layers.md)。工程适配 A11。

## 7. 保存跨请求的草稿

### 7.1 请求、草稿和正式记录分别识别

一次请求是一次交互处理；草稿 D1 是多次交互中持续编辑的数据；一次业务工作有开始、继续、取消和确认；数据库事务只保护其中约定的一段存储操作。将 D1 保存到数据库可以让它跨请求恢复，但它仍不是正式印制说明。来源 W01、W07–W11。

D1 保存 K1 版本 7、C1 版本 4、C2 版本 5、B1 版本 3及编辑变化。中间数量可以不满 12。正式查询要明确只读取已发布说明或正式记录；不能把所有已提交数据库行都计入正式卡包。使用草稿标记时，查询和视图都要遵守其含义；使用单独草稿表时，复制、恢复及升级都增加工作。来源 M36–M37。

### 7.2 在相同继续工作要求下比较存放位置

| 存放位置 | D1 怎样继续 | 需要承担的条件和成本 |
|---|---|---|
| 客户端携带状态 | 每次带回候选与依据版本 | 状态大小和传输成本；返回值不能受信任，关闭或丢失客户端可能丢草稿；权限与新鲜性另查 |
| 服务端对象或序列化状态 | 通过独立草稿标识找到状态 | 进程内保存最简单，但换节点或重启可能丢失；共享保存增加访问和恢复安排，格式要跨升级可读 |
| 数据库按字段保存草稿 | 每次读取和更新草稿行 | 可以使用查询与存储机制，但草稿隔离、并发修改、取消、清理及模式演进都需设计 |

选择取决于实际草稿大小、允许丢失的程度、需要继续工作的时长及现有宿主支持，不能仅凭“无状态”认定性能更好。将序列化内容放在数据库里，在本方法中仍属于服务端序列化状态；是否变成按字段可查询的草稿，是另一项取舍。来源 M34–M37。

同一登录会话可能有两个窗口分别处理 D1 和 D2。草稿与工作标识要区分，不能只用用户号或会话号互相覆盖。客户端提供了某个草稿编号，也不能证明当前用户有权读写；输入、权限、会话和版本核查要使用实际宿主机制。这里没有生成会话令牌或给出当前浏览器安全配置。工程适配 A06、A15–A16。

### 7.3 取消、清理和升级不能等到最后再考虑

若取消意味着正式记录不变，就把未确认变化留在草稿中，取消只结束该工作并按保留规则清理草稿。若产品明确要求每次请求就正式保存，取消只能有另行定义的后续动作；实现者不能为了方便把前一种要求改成后一种。

清理任务读到 D1 过期后，编辑请求可能同时继续它。清理不能稍后无条件删除：可以在同一草稿控制记录上检查所观察的版本与状态，再作删除或结束工作；继续操作也参与该控制。若清理先完成，继续操作应得到草稿已结束；若继续先更新版本或状态，旧清理条件应失败。数据删除与资格结束不能留下仍可写入的旧工作。这里要求实际存储提供对应原子条件，具体实现待核实。

升级需要说明旧草稿格式还能否读取、哪些字段含义改变、何时拒绝继续及怎样保留可恢复的输入。共享存储不自动完成这些工作，固定超时天数也不是书籍能代项目决定的条件。来源 M35–M37；格式演进与恢复复用[迁移方法](mixed-version-data-migration.md)，清理与保留复用[资源保留方法](resource-retention-cleanup-recovery.md)。

## 8. 把并发检查接到实际提交

### 8.1 先确定冲突究竟会损害什么

W1、W2 都从 K1 版本 7 开始。W1提交版本8后，W2拿版本7提交，应检测冲突；直接覆盖会丢掉 W1 的变化。检查在预览时通过，也不能保证稍后的提交通过。来源 M22、M24。

另一个时间线中，K1仍为版本7，但维护者把 C2 从 `blue`、版本5改为`green`、版本6。W1只比较 K1版本会错误放行。需要保护的既有待写卡包，也有参与发布判断的图形、卡背和当前规则依据。来源 M23。

并非每次任何字段变化都值得拒绝用户工作。整条版本变化可以作为保守冲突条件，但会使不影响决定的变化也触发重新确认；更细的条件应说明哪些字段影响规则和印制快照。不能在没有业务依据时自动忽略版本变化。本题发布记录采用确切图形版本，默认保留该差别并重新评估。

### 8.2 在明确存储前提下给出一条可检查的提交路径

以下是**原创的逻辑协议**，不是某种数据库或 ORM 的可执行代码。它假设全部相关数据位于同一事务资源；存储能在事务内取得指定控制记录的排他保护、读取当前已提交内容，并将保护保持到事务结束；事务全部写入共同提交或明确回滚。所有相关写入路径都遵守同一保护安排。这些能力必须依据实际产品核实，不能仅凭隔离级别名称推断。

可以将一个不可变候选输入送给应用边界，其中含 K1、预览时各版本、明细数量、规则版本及本次操作标识。按固定顺序取得所需控制记录，避免不同操作用相反顺序等待。顺序应涵盖该协议实际使用的记录类别与键，不只对某个函数内部排序。

1. 核对当前操作者与操作权限；在提交范围内核实会变化且影响本次授权或规则的依据。
2. 取得 K1及所引用图形、卡背和规则控制记录的保护，再读取它们当前的状态。缺少记录时停止相应判断，不把缺失当作可用。
3. 比较候选依据与当前版本。发现变化时返回受影响事实，结束这个提交尝试；用户草稿与输入另存，不因冲突丢失。
4. 根据当前受保护数据计算 P2：数量为正整数，总数12，按图形累计不超8，色组和可用状态满足，卡背就绪。不能直接信任客户端的“预览通过”。
5. 组织明细和卡包写入，保存不可变的印制说明与所用版本，并改变 K1版本。若采用操作结果登记，它必须与这些写入一起提交，且操作标识和输入绑定。
6. 提交成功得到明确结果后再报告成功；失败和结果未知分别按第9节处理。事务结束后释放数据库资源，后续请求重新建立相应工作范围。

这里用短数据库事务保护提交阶段，用户思考时间不占用这些数据库保护。拿到旧版本后进行普通 `SELECT` 比较，再释放保护去写，并不满足前提；把检查和写入分别放进两个事务也不满足。

实际组件若用带版本条件的更新，也可以实现相应局部检查，但要确认读取依据在检查后到写入完成之间受到保护，不能只对 K1加条件。原书的版本增量说明、工作单元机制及读取依据分析支持职责区分；本条控制记录方案是工程适配。来源 W05、W07、M22–M23。

### 8.3 “没有其他记录”需要保护集合条件

独立分支新增规则：同一色组同时只能有一个活动卡包。开始时没有，W1准备发布K1、W2准备发布K2。即使两者各自版本都正确，分别提交仍可能形成两个活动包；检查已读取记录的版本不能代表“没有别的记录”。

一个可比较的单存储方案是为每个已配置色组设置唯一的活动控制记录，字段为当前活动包标识或空值。所有发布、结束活动和色组变更都参与同一保护：在提交事务中取得色组控制记录，空值时才能改成目标包，并与卡包和说明共同提交。另一个提交取得保护后就会看到已占用。结束K1时还要确认当前占用者仍是K1，不能清掉后来K2的占用。

控制记录不存在时不能当作自由空位；需要经唯一性约束安全创建并取得保护，或先拒绝未知色组。也可比较数据库能直接表达该业务条件的唯一约束，但要核实它覆盖何种状态及并发情况。若数据跨多个不能共同提交的资源，这条方案的前提不成立，需要另行设计协调协议，不能继续沿用“事务会保护”的结论。来源 M23；共同控制方案为工程适配，更多不变量推导见[事务方法](invariants-aggregates-transactions.md)。

### 8.4 选择乐观、悲观或长事务时计入用户投入

乐观方式允许并发编辑，到提交时检测变化；冲突少时通常更少阻塞，但长时间编辑后失败可能昂贵。悲观离线锁在业务工作开始时限制冲突操作，仍需管理锁的身份、所有者、释放、放弃和共同可见性。它是应用保存的跨请求资格，不是把数据库内部锁保持整个会话。来源 M25–M29。

本题若经常有多人长时间编辑同一包，可以在开始编辑时取得独立工作资格，尽早告诉不能进入者原因。资格属于W1这次工作，不能仅以登录用户或会话为所有者，否则两个窗口可能被当成同一持有者。先取得资格再读取依据，或取得之后重新核对依据；先前预览不会因后来拿到资格而自动变新。

短小操作可以在一个数据库事务内完成时，先比较现成事务能力，无需增加应用锁表。长事务有时使实现更简单，但会占用连接和锁，影响等待、恢复及并发；不能把用户编辑全过程包进事务而不测量。比较实际冲突频率、重做成本、锁等待和恢复责任，不能把“冲突很少”当作正确性保证。

### 8.5 过期、撤销和迟到工作必须在写入处相遇

W1持有编辑资格E7后停顿；E7被撤销，W2取得E8并完成修改；随后W1恢复。如果它凭缓存说“我曾拿到锁”，仍可能覆盖新结果。超时清理只处理保存的资格，不会使旧线程或旧请求自动停止。

可比较的安排是在K1的共同控制记录中保存当前工作标识与不可复用的资格代号。每次受该资格约束的修改，在同一个事务中取得该记录的保护，核对当前工作与代号，再执行业务修改；撤销、授予新资格及释放也使用同一记录和保护。释放E7要匹配E7，不能按K1编号无条件删除E8。

因此，E8已生效后W1带E7取得保护，会看到不匹配并被拒绝；如果W1先进入受保护提交，撤销必须等这个提交结束，再改变资格。这里承诺的是**撤销生效后的旧资格不能再完成新的受保护修改**，没有承诺一个已开始的事务在某个墙钟时刻自动终止。若业务需要严格时间界限，还需可信时间、检查时机和提交边界的额外设计。

资格核查必须一直保护到实际写入完成，不能查完控制表就放开。所有普通保存、批量入口、目录或后台相关写入、旧版本程序都需要遵守对应保护；数据导入和运维旁路同样要核实。只装饰一个查询方法或加一个内存单例，不证明这些路径参与了。跨节点需共同协调的状态，本机内存表不能直接承担。来源 M26–M29、M33；资格代号和写入处保护属于工程适配A13–A14。

### 8.6 总量规则为何可能需要共同版本

两个人分别修改K1的两条明细，只检查各明细版本，可能各自基于旧数量作出“总数12”的判断，然后合在一起不再是12。对整包规则，可以让影响规则的明细变化共同受K1版本或控制记录保护，并在其中检查整个候选。新增、删除和改变引用也须参与，不能只有数量更新参与。

共享的是同一个K1控制点，不是让每条明细各自存一个数值相同的版本。代价是两个原本可独立的改动也可能冲突，保护范围扩大；收益是整包条件与变化的共同边界更明确。需要更高并发时，先说明哪些变化可以独立，再设计更细保护，而不是只拆版本字段。来源 M30–M32。

将必经的版本比较、写入资格检查和释放责任集中到公共代码，可以减少漏做。但为了编辑而提前取得资格仍可能是显式业务动作；等提交时才悄悄获取，失去尽早避免用户白做工作的目的。公共机制需把等待、拒绝和失败结果告诉调用者。来源 M33。

## 9. 在失败后确定能否继续

### 9.1 确定回滚时，数据库与内存分别处理

新明细插入成功后另一更新失败，整个事务确认回滚。正式记录仍是事务前内容，但内存中的新编号、已保存标记、共享版本增量或已加载集合未必自动退回。不能因为已捕获异常就重新使用这个工作单元。

保留用户的输入与目标，结束失败的工作范围，释放其资源，再按实际组件规定重新加载和构造候选。重新取得的是当前事实，可能与第一次不同，需重做受影响的规则判断。若组件保证某些状态可恢复，按该版本的具体行为验证后再复用，不能自行补几个标志位就宣布恢复。来源 W15、工程适配A07。

### 9.2 结果未知时，不把再试一次当作修复

提交后连接断开，调用者不知道是否成功。此时“没有成功响应”不等于事务回滚。盲目创建另一份说明，可能重复发布。

如果设计中已将稳定操作标识、对应输入和最终结果与发布记录共同保存，先按同一个标识核对结果；同标识却不同输入必须另行处理，不能返回另一项工作的结果。如果没有这种记录，也没有可证明唯一结果的查询依据，就保持未知，停止依赖重复创建，并取得可确认的存储结果。不要临时编一个新编号后继续。

原子结果登记、重复请求及结果核对的完整方法分别见[原子效果与恢复](message-atomic-effect-recovery.md)和[重复与去重状态](message-idempotency-ordering.md)。这里复用它们的条件，不声称原书离线锁示例已经解决网络中断或跨系统外部效果。

### 9.3 解决冲突要保留意图，但不能自动接受旧依据

W2遭遇K1版本冲突时，保存它想改变的数量与旧依据，重新读取已提交版本8，比较是相同字段竞争、相互独立变化，还是业务规则已改变。能否合并由业务含义决定；文本能合并不表示数量和总包规则仍成立。即使保留两方数量改动，也必须重新评估总数和按图形上限。

目录C2已经变为green时，重新执行旧保存过程会违反当前发布要求；应显示具体变化，允许用户调整或取消，再以新依据确认。是否能不打扰用户地重新计算，取决于操作含义和已确认范围，不能把所有并发异常列为自动重试。

部分加载按第6节结束不完整工作；清理与继续竞争按第7节核对草稿状态。失败处理应返回清楚的分类：输入不满足、必要事实缺失、依据冲突、确定回滚、结果未知、工作已结束。名称可以遵守项目接口惯例，但这些含义不能混为一个可重试错误。

## 10. 形成决定与验证计划

对实际任务交付一个与范围相称的决定：当前操作及规则、组织方式与替代条件、读写和工作范围、状态保存选择、提交所需保护、失败结果，以及尚缺的产品版本证据。小型P0任务无需输出整套方案；重要持久化改造需要能让下一位参与者复查上述依据。

| 需要检查的内容 | 本题可区分正确与错误的材料 | 证据的实际范围 |
|---|---|---|
| 规则与两条入口 | 6+6、8+4、9+3、拆行5+4+3、总数11、错误色组 | 检查规则含义与路径是否一致；不能由同一校验函数自证预期 |
| 映射与生命周期 | 删除明细后共享C1仍存在；相同整数不合并对象；编号已分配但保存失败 | 需要实际存储和组件支持，内存例子只证明局部行为 |
| 查询与加载 | 未保存数量5与数据库数量6、无明细草稿、重复图形、第二项加载失败 | 检查观察状态和完整性，再测量实际成本 |
| 并发责任 | 两编辑覆盖、只读目录变化、两个包同时满足不存在条件、E7在E8之后恢复 | 检查真正写入处的保护及所有写入路径，不只测试顺序成功 |
| 恢复与清理 | 已确认回滚、提交结果未知、取消、过期继续竞争及旧草稿格式 | 每种失败分别取得证据，不能以一条重试成功概括 |

这些材料规定应验证什么，不表示已经运行它们。实际任务按用户授权、项目阶段和可用环境取得所需证据；验证计划要注明已执行范围与尚缺结果。测试预期、替身与异步观察分别复用[测试层次方法](test-risk-oracles-layers.md)及[夹具与异步观察方法](fixtures-doubles-async-observation.md)。

无法确认数据库保护范围、关键写入入口或当前业务规则时，停止依赖该保证的实施或结论，保留可继续的局部工作。方案更新后同步调用入口、映射、查询、迁移与恢复安排；来源、版本和实际结果分开记录，不能用文档存在替代工程验证。
