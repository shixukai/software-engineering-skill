## 1. 何时使用

当业务规则涉及多个对象、需要决定哪些变化必须一起成功，或“每次请求都检查了条件”却仍可能产生非法状态时，使用本方法。目标是形成可以解释的边界与提交协议：**什么必须成立，谁负责维护，哪些并发写入会破坏它，采用的机制为何挡得住。**

简单的单行增删改，如果已有约束足以表达业务规则，不必引入完整领域模型、仓储接口和工厂类。跨服务流程也不能只凭“这是一个聚合”就获得原子提交。缺少业务规则、允许的中间状态或存储能力时，先保留候选分支，不能替业务方假定“最终一致即可”。

下文是 DDD、PoEAA、DDIA 的**多源综合方法**。带容量预约的所有需求、对象、数字和伪代码均为原创假设，用来推演逻辑；它们不是书中现成算法，也不是特定数据库的可运行实现。来源对应关系见第 9 节。

## 2. 把业务要求变成可判断的不变量

### 2.1 先写合法状态与成立时刻

“保持一致”“不能超额”还不足以指导设计。把一句要求展开为：作用域、状态、计量单位、条件、成立时刻。例如本例假定：

> 一个容量桶代表某一固定资源和固定批次。每个已接受预约消耗正整数个单位；取消后释放。每次成功提交后，有效预约总量不能超过该桶的容量。客户端不能把待处理请求视为已接受预约。

这里的批次互不重叠；任意重叠时间窗的预约不在假设内。桶的容量允许修改，但不允许降到已占用量以下。通知允许晚到，不影响预约是否已接受。以上都是示例明确给定的规则，实际任务需要取得相应事实。

令 `active(P)` 表示属于桶 P 且状态为 active 的预约，`units(r)` 为预约单位数。可以得到：

| 标识 | 要保持的条件 | 成立时刻及含义 |
|---|---|---|
| I1 | 对每个预约，`units > 0`；桶容量为非负整数 | 创建及每次修改后；决定校验与存储约束 |
| I2 | `used(P) = sum(units(r) for r in active(P))` | 每次提交后；used 是用于决策的权威汇总，不能异步漂移 |
| I3 | `0 <= used(P) <= capacity(P)` | 每次提交后；拒绝先超额再补偿的成功承诺 |
| I4 | 同一请求标识和相同参数重试，不重复接受或重复释放 | 成功结果查询与重复命令处理时；结果未知需要此契约 |

把“提交后必须成立”与“允许延迟收敛”分开。查询投影暂时落后可以接受，不表示准入判断可以读取同样陈旧的数据。业务明确允许排队时，可以引入 pending 状态；它不会自动获得已接受状态的保证。

### 2.2 列命令，反向找所有会改变前提的入口

不要只分析主接口。按每条不变量反问：谁能改变其中的字段或集合成员？这一步决定保护范围。

| 命令 | 读取的决定性事实 | 允许条件 | 必须一起改变的事实 |
|---|---|---|---|
| 接受预约 | capacity、used、请求是否已完成 | 单位数合法且 `used + units <= capacity` | 新增 active 预约、增加 used、保存请求结果 |
| 取消预约 | 归属桶、预约状态和数量 | active 才释放；已取消返回既有状态 | 状态变 cancelled、减少 used、保存取消结果 |
| 下调容量 | 当前 used | `new_capacity >= used` | 修改 capacity；参与相同并发保护 |
| 修改数量或转桶 | 原预约、原桶与目标桶条件 | 本例暂不支持，不能从普通预约接口顺便实现 | 如业务需要，重新确定多边界原子性或中间状态 |
| 批量导入、超时释放、管理修复 | 所触及的不变量字段 | 与正常命令承担相同责任 | 禁止绕过既有保护协议直接改行 |

前两行是完整推演的核心；后两行展示如何识别范围扩张和旁路。发现尚无协议的写路径，应把相应能力标为未实现，而非默认它不会发生。

## 3. 从身份与生命周期选择边界

### 3.1 先回答什么是同一个对象

DDD 的 Entity（实体）围绕持续身份；Value Object（值对象）围绕属性含义。判断方法是：属性相同的两个对象是否仍需分别跟踪？属性改变后是否还是原来那个对象？数据库有主键不等于领域上需要独立实体。[来源 A、B]

本例两份同量预约即使客户、桶、数量相同，也可能分别取消，因此有预约身份。数量只表达一个正整数值，不需要独立生命周期。容量桶的容量改变后仍是同一桶。预约有身份，**并不因此必然成为聚合根**；还需要看外部访问、生命周期和同步不变量。

### 3.2 比较候选，解释取舍

| 候选边界 | 为什么看起来合理 | 本例中的决定性问题 | 结论 |
|---|---|---|---|
| 每份预约一个根，分别提交 | 单份预约可以独立查询和取消；写入分散 | I3 依赖全桶总量，预约各自正确不能维持总量 | 单靠这个边界不够；必须另外设计共同容量分配协议 |
| 每个固定桶一个根，拥有有效分配记录 | used、capacity 和分配变化构成同步一致性边界 | 热门桶会产生竞争；无界历史不能每次全部装入内存 | 作为本例候选，接受按桶协调的成本；历史用独立只读投影 |
| 全部桶和预约一个根 | 容易描述“所有数据一起正确” | 没有跨桶同步不变量，却把无关命令耦合到同一竞争点 | 本例无依据采用 |

选择第二种，是因为本例的强约束以桶为单位。不是因为“聚合越小越好”，也不是因为这些数据刚好在同一张表。把最小必要协调范围和足以执行规则的状态放在一起，同时检查生命周期与竞争代价。[来源 A、B；表格为工程综合]

若业务要求预约具有独立的长生命周期、跨桶变化或跨服务处理，可以重新建模：容量桶维护具有稳定身份的分配凭据，预约流程引用该凭据；由未确认到确认的状态转移必须有明确协议。没有获得业务允许的中间状态和失败处置前，不能直接拆开原子承诺。此处提示重新设计的条件，不提供未经推导的分布式方案。

### 3.3 边界要落实到访问与职责

对外暴露 `reserve`、`cancel`、`change_capacity` 等根操作；外部持久引用通过桶身份定位。预约编号可以作为值传递和查询条件，但可变的内部预约对象不能被外部长期持有后自行修改。只读查询可以返回快照或投影；从投影发出的命令仍回到权威边界检查。[来源 A、B；查询投影是工程适配]

逻辑上一个聚合可以存于多张表。持久化可以按需加载，但本次命令依赖的事实必须完整且一致，不能因为“懒加载”漏掉约束。这个边界也不要求把数据库事务长期保持到用户完成界面操作。事务生命周期在第 6、7 节确定。

## 4. 找到单次正确却并发失败的位置

### 4.1 展开谓词、决定与写入

设某桶容量为 1，初始没有预约。A、B 各申请 1 个单位。朴素实现是“查有效预约总量，小于容量就插入预约”。单次执行都正确，但两次执行可以发生下面的交错：

| 时刻 | A | B | 已提交状态 |
|---|---|---|---|
| 1 | 查询 `SUM(active.units)=0` | — | 无预约 |
| 2 | — | 查询 `SUM(active.units)=0` | 无预约 |
| 3 | 判断 `0+1<=1`，准备写预约 a | 判断 `0+1<=1`，准备写预约 b | 无预约 |
| 4 | 插入 a 并提交 | — | 总量 1 |
| 5 | — | 插入 b 并提交 | 总量 2，I3 违反 |

决定性信息是：**两个写集合虽然是不同预约行，却都改变了对方依据的总量谓词。** 给 a、b 各加一个版本号，或只保证各自 INSERT 原子，不会让它们竞争同一个事实。这是写偏斜（write skew），不是“后写把同一行前写覆盖掉”的丢失更新。[来源 D]

把同样的推导用于实际规则：先圈出查询条件和参与求值的字段，再写业务分支，最后列出会改变这些条件的新增、更新和删除。只审查最后 UPDATE 的表，会遗漏读依赖。

### 4.2 空结果也是重要的业务事实

上述初始查询为空。若机制只锁住已经返回的行，就没有对象可锁；锁住两份尚未创建的预约也没有意义。需要保护的是“这个桶还有容量”这一事实，或能代表这组冲突的共同对象。

这不等于断言某条 SQL 在所有数据库都“不加锁”：谓词锁、范围锁、间隙保护可能覆盖未来插入，实际语义取决于数据库、索引、隔离配置与访问方式。必须说明采用的是哪种保证。[来源 D]

## 5. 选择能覆盖冲突的机制

按不变量的形状和实际存储能力选机制，不把下表当作一律从上往下尝试的流程。先问：每种会破坏规则的提交组合，会在哪一步被拒绝、等待或整笔中止？

| 机制 | 能保护什么，需满足什么 | 失效条件与代价 |
|---|---|---|
| 存储约束 | 能被真实约束完整表达的条件，例如业务唯一键 | 唯一的预约 ID 不能表达“所有预约数量之和不超限”；约束报错需要转为相应业务结果 |
| 条件化原子更新 | 用同一权威行中的 used、capacity 判断并增加用量 | 比较必须作用于当前状态；分配记录仍需与计数原子提交，所有释放、调容量路径也维护它 |
| 先锁共同控制行 | 在读取决定性事实前锁定桶，锁后读取有效状态、判断与写入，直到提交才释放 | 所有相关写路径遵守协议；锁定之前的旧判断不能继续用。热点等待、多锁顺序与死锁需处理 |
| 同根版本 CAS | 从一致状态取得事实和版本，提交时原子比较当前版本；版本变化与所有相关业务写入同一事务提交 | 子行各自版本、分开提交、漏掉旁路、旧总量配新版本都不成立；高竞争会造成重试负担 |
| 真正可串行化的事务 | 把决定所依赖的读和写放进正确实现、正确使用的串行化保护中，处理被中止事务 | 不能用“快照隔离”名称替代；事务外旧读、异步副本和外部效果不自动受保护；需评估等待或重试成本 |

可串行化有不同实现。严格两阶段锁（2PL）通过锁协调冲突；要涵盖幻读，需要谓词保护或安全的范围近似，不能只列已存在的行。可串行化快照隔离（SSI）执行快照读并跟踪危险的读写依赖，必要时中止事务；普通快照隔离没有同样保证。这里的 2PL 不是分布式提交中的 2PC。[来源 D]

为了制造共同锁点而引入控制行，是 DDIA 所讨论的“物化冲突”思路：必须证明所有逻辑冲突都映射到了该点，不能漏掉重叠范围或边界条件。作者提醒这种映射容易出错，不应无条件作为默认方案。本例容量桶本身已有业务意义；是否采用根版本或锁，仍需依存储能力和竞争情况判断。

本例采用“同根版本 CAS + 同一原子事务”继续推演，以展示保护链。选择它不表示它优于已经能正确实现规则的条件更新或串行化事务。上线实现前仍须核实实际平台保证。

## 6. 把候选方案推导成提交协议

### 6.1 明确存储前提，再写伪代码

假定根保存 `pool_id, capacity, used, version`，内部预约保存 `reservation_id, pool_id, units, status`。本例另有按业务请求作用域唯一的结果记录。先成立 I2，随后每条写路径同时维护 I2、I3。

下面的 `read_coherent_command_view` 和 `compare_current_and_set` 是**协议所要求的语义**，不是任何 ORM/API 已具有该保证的声明。请求结果的存在性与根的 capacity、used、version 必须来自同一一致观察：

```text
reserve(pool_id, request_id, units):
  在调用者允许的截止时间和有限重试次数内:
    开始一个新的数据库事务
    s, prior = read_coherent_command_view(pool_id, request_id)
    如果 prior 为该 request_id 的成功结果:
      参数相同则结束只读事务并返回既有结果；参数不同则拒绝键复用
    校验 units 是正整数；若 s.used + units > s.capacity，结束事务并业务拒绝
    准备一个属于该桶的 active 预约
    changed = compare_current_and_set(
        root.version == s.version,
        root.used = s.used + units,
        root.version = s.version + 1)
    若 changed 不为 1：回滚整个事务，丢弃 s，进入有限重试
    写入预约，并在同一事务内保存唯一 request_id、参数和成功结果
    提交整个事务
    返回成功结果
  到达截止时间或重试预算：返回可辨识的暂时冲突结果
```

同请求并发执行还可能在唯一结果记录上发生冲突；不能忽略异常后继续提交其他写入。应整笔回滚，再查询已提交结果并核对参数。若结果尚不可见或提交结果不明，进入下节的结果确认路径。预约成功的依据是事务提交，不是 CAS 返回 1。

幂等查询也不能与容量判断拼接：B 先查不到请求结果，A 随后提交并耗尽容量，B 若再读取新的 used，就会把 A 已成功的同一请求误报为容量不足。共同一致观察使 B 要么同时看见 A 的结果与新根，要么同时看见旧结果状态与旧根；后一种情况经 CAS 冲突后重读，返回已有成功结果。只有一个“事务”名称而每条查询各取新快照，并不足以兑现这个要求。

### 6.2 逐步说明为什么有效

仍从 `(capacity=1, used=0, version=0)` 开始，A、B 都读取版本 0。A 的事务比较版本 0，写入 used=1、version=1、预约 a 和结果，一起提交。B 随后尝试以版本 0 提交时必须失败，或者由存储系统中止整个事务；B 的预约不能留下。B 开新事务读到 used=1，再执行 `1+1<=1` 的业务判断，得到拒绝。

如果 B 在 A 提交前取得该根的原子更新权，结果对称。关键保证是：**从同一版本出发的竞争变更最多一个成功提交；失败者不留下部分效果。** 这是所需存储语义，应由当前平台文档和对应实现检查确认。

以合法状态为起点，每次成功接受使 used 和有效预约之和同步增加；准入条件限制增量，故保持 I2、I3。取消只对 active→cancelled 做一次同步减量；容量修改先比较 used；其余会改变这些事实的命令也必须受同根协议约束。遗漏其中任何路径，这个论证都不成立。

### 6.3 用反例检查是否偷换了前提

| 看似实现了协议 | 为什么仍会失败 | 需要修正什么 |
|---|---|---|
| 先读取预约总量 0，其他事务提交后再读到根版本 1，组合两者提交 | CAS 可能接受版本 1，但业务判断来自旧状态 | 读取事实与版本必须构成一致观察；本例直接读取同一根的权威 used、capacity、version |
| 版本自增先提交，随后另一个事务插预约 | 第二步失败会产生部分成功，或出现未受保护写入 | 根变化、预约、成功结果要一同提交或回滚 |
| 只在新增预约时推进根版本 | 取消、恢复、改量或下调容量仍可能使判断过期 | 全部影响不变量的入口参与协议；不支持的命令明确拒绝 |
| CAS 的条件检查仍读取旧快照 | 条件通过不能证明当前版本未改变 | 核实真实原子比较语义；没有证据就保留未验证结论 |
| 冲突后仅重发 INSERT 或沿用旧 s | 重试仍基于已经失效的可用容量 | 开新事务，重新读取并重新执行业务决定 |
| 请求结果查询读旧状态，根查询却读新状态 | 同一成功请求可能被误报为容量不足 | 请求结果存在性与根也要处于同一一致观察，不能只保证根的三个字段一致 |

版本在其竞争保护期内不能任意重置或重复使用，否则可能把变化后的状态误当原版本。多写入副本各自接受本地 CAS 也不等于存在一个共同权威比较点；该方案不自动推广到多主异步合并。[来源 D；协议证明与版本管理要求为工程适配]

### 6.4 给失败分配不同语义

| 观察到的结果 | 应做什么 |
|---|---|
| 确认事务已中止的暂时并发冲突 | 在预算内退避，重做整个命令；只有重新读取后业务条件确实不满足，才返回业务拒绝；预算耗尽仍返回暂时冲突 |
| 容量不足、非法数量等业务拒绝 | 返回业务结果；不得把永久条件错误无限重试 |
| 提交响应丢失，无法确定是否成功 | 用稳定请求 ID 查询权威结果；暂不可判定则保留“处理中/结果未知”，不能宣布失败或换 ID 重发 |
| 数据库提交成功，但通知失败 | 预约仍然成功；按通知交付协议补发与去重，不回滚事实来伪装未接受 |

可重试事务内不能直接执行无法回滚的邮件、扣费或外部调用。仅“提交后再发消息”仍有提交后进程崩溃的漏发窗口。若要求可靠交付，应另行设计持久发送意图与重复处理协议，参见[数据库变更与消息原子衔接](../rules/se-integration-atomic-effect.md)和[重复投递与幂等](../rules/se-integration-idempotency.md)；本篇不把这些问题视为已经解决。[来源 D]

## 7. 补齐生命周期与持久化职责

### 7.1 不只检查新增路径

| 生命周期阶段 | 本例必须落实的协议 | 错误信号 |
|---|---|---|
| 创建 | 创建合法桶：容量非负、used=0、身份唯一；首次预约通过根命令形成完整有效变化 | 调用者逐字段拼装可变对象并把半成品公开 |
| 重建 | 保持原身份与版本；恢复本次判断所需的状态，不重放“新建预约”的外部效果；发现结构或汇总不一致时进入显式修复路径 | 用初始化默认值覆盖旧版本，或静默把非法历史状态修成“看起来合法” |
| 查询 | 需要改变状态时取得权威根；只读展示可使用带时间/版本含义的投影 | 先用缓存判断有容量，然后把结果当成写入授权 |
| 取消 | 读取归属、状态、数量；只允许 active→cancelled 释放一次；同事务减 used、推进根版本、保存取消结果 | 对“取消请求次数”做减法，重复取消使 used 为负 |
| 到期或容量变更 | 若增加到期功能，先明确有效时间与状态语义，再用同样的状态转移和根保护；下调不得越过当前 used | 后台定时器、批量任务或管理 SQL 绕过协议 |
| 删除与归档 | 先决定业务上是终止、归档还是物理删除；根删除不能留下仍可变的内部对象；本例有有效预约时拒绝删除 | 单删根造成孤立预约，或删除去重结果后让迟到重试再次生效 |

DDD 的工厂负责复杂创建的装配与有效性；简单构造函数足够时就使用它。仓储负责需要直接访问的根的查找和存取，避免客户绕开边界操纵内部对象。重建、历史数据异常处置和去重保留期是这里补充的工程设计义务，不能把 2015 年简短定义当成所有细节的原文依据。[来源 A、B]

历史预约和成功结果需要明确保留期、迟到重试策略和归档查询方式；本例未指定无限保留或具体时长。有效分配记录属于一致性边界，历史展示可分离。分离存储并不意味着删掉取消所需身份或提前遗忘重复请求。

### 7.2 不同的责任不要相互替代

| 概念 | 回答的问题 | 本例职责 |
|---|---|---|
| Aggregate / Root | 哪些规则需要同步成立，谁承担改变责任？ | 桶接受或拒绝分配，维护状态转移和 I2、I3 |
| Repository | 领域对象如何被找到、保存，而不泄漏存储访问细节？ | 按桶身份取回根，协调所需对象的重建与持久化接口 |
| Unit of Work | 本次工作改了什么，如何组织提交？ | 跟踪新增预约、脏根、状态变化和结果记录，协调并发检查与数据库写入 |
| Identity Map | 同一工作上下文中，持久身份相同是否对应同一个可变对象？ | 同一桶在本工作上下文内被多次加载时返回同一实例，避免互不知情的副本覆盖 |
| 数据库事务与并发机制 | 提交是否全成或全败，竞争者如何受保护？ | 执行已核实的原子提交和根版本比较，失败后丢弃旧上下文 |

Unit of Work 并不自行推断业务不变量。需要核对现有 ORM 的变更跟踪、flush、事务范围和并发令牌语义，而不是再实现一套同名机制。[来源 C]

选择变更跟踪方式时，PoEAA 的具体取舍是：调用者注册容易漏掉变更；由对象方法注册必须覆盖每处修改；读取时留快照、提交时比较可以降低注册负担，但增加复制和比较成本。选择已存在且能满足要求的机制，并检查子对象变化是否真的进入本次提交。

Identity Map 的查找顺序是先查映射，有则返回；没有才加载并登记。键要在映射范围内稳定唯一，例如映射类型范围与持久 ID 的组合；同一实体经父类或子类加载时，仍须归入同一身份，不能按请求类型生成两份可变实例。它解决同一会话的对象身份一致性，**不解决会话外并发**，也不把缓存内容变成最新数据。冲突重试应开启干净的工作上下文，避免旧脏对象再次被 flush。不要把跨请求共享可变对象映射当成普通性能优化。[来源 C；重试上下文要求为工程适配]

## 8. 检查方案并知道何时停下

### 8.1 检查可改变结论的反例

检查深度依任务和风险裁剪；不要求每次都建立测试框架。设计咨询可以先静态推演，实施任务则按已有授权验证实际机制，并分别报告两种证据。

| 检查问题 | 本例应观察到什么 | 能说明与不能说明什么 |
|---|---|---|
| 两请求读到最后一个单位，再各写不同预约 | 朴素版本可以超额；保护版最多一个接受，另一个重新判断 | 暴露读依赖；单线程成功不能替代这个检查 |
| 查询为空，或只对子行分别加版本 | 仍需共同保护点或正确谓词保护 | 防止把行锁/子行版本的局部保证外推 |
| CAS 与预约写入之间发生失败 | 根、预约、结果全部回滚；没有半成功 | 需要真实存储的原子性证据，离散推演不能证明 |
| 预约与取消、下调容量并发 | 每个成功序列均维持 I2、I3，竞争失败重新判断 | 需要涵盖相关写路径，不仅新增预约 |
| 同请求重复、取消重复、提交响应未知 | 返回同一成功结果或明确未决；不重复增减 | 去重与结果确认协议的证据需单独核实 |
| 单行 CRUD 或已有完整存储约束足够 | 接受简单方案，不强迫引入整套对象层 | 检查方法是否被滥用 |

本例还有一个有限的机械推演：两个事务各有“读、提交”两步，保持各自先读后提交，共 6 种顺序。朴素方案有 4 种超额；理想原子 CAS 模型的 6 种都保持容量约束。这个枚举只检查该离散模型的推理，不覆盖取消、结果去重、宕机、数据库隔离实现或模型使用 Skill 的行为。

### 8.2 输出足以评审的决定

按任务需要把下列信息放进回答、设计或代码说明；不强制另建文档：

1. 用业务词语和可判断表达式说明不变量与成立时刻，注明确认事实和假设。
2. 给出候选边界及选择理由，指出哪些身份、生命周期或竞争条件会改变选择。
3. 用一个最小交错展示风险；若不存在实质风险，也说明已有机制为何足够。
4. 给出完整读、判、写、提交、失败协议，以及所有必须参与的写入口。
5. 分别列出已证明的逻辑、已检查的实现和仍未知的平台行为，不借模型打分填补证据。

若无法指出共同权威状态、不能证明条件比较和业务写入原子提交，或关键写路径尚不受保护，应明确“候选方案尚不能作为完整实现”。若业务规则和现有机制已足够，不因阅读了本篇继续拆服务、增加模式或调整数据库隔离级别。
