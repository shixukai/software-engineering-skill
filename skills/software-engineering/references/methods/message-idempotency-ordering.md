## 1. 先说明重复时必须保持什么

需要判断重复或乱序请求能否再次处理，选择业务操作身份、并发保护或历史清理条件时，采用本方法。**幂等**描述相同操作重复执行后的效果与执行一次相同。**去重记录**保存用于识别已处理操作的证据；记录存在不自动证明业务完成，删除记录也不证明旧请求已经消失。

先写清所要求的效果与返回结果，再比较足够的小方案：

| 业务需要与已知条件 | 先比较的方案 | 仍需检查 |
| --- | --- | --- |
| 重复不会产生新的业务效果，例如只读查询 | 直接读取 | 查询结果是否允许随时间变化；不能借查询安全证明原写操作安全 |
| 设置同一确定值，而且不存在会被旧设置覆盖的后续变化 | 重复设置 | 与其他操作穿插后的结果；旧值是否可能覆盖新值 |
| 业务记录自身已经保存操作身份、原输入和稳定结果，并有相应唯一保护 | 复用该记录 | 同一对象能否有后续新操作、拒绝结果和删除后证据如何处理 |
| 需要区分多次意图、保存拒绝或复用历史结果 | 明确的操作决定记录 | 业务效果与决定怎样共同保存、竞争怎样处理、历史保留多久 |

不要先选一张去重表，再把所有业务改成适合这张表的样子。操作可交换只说明交换顺序可能不改变结果，不说明重复也无影响；两个计数增量即使可交换，同一增量重复两次仍会多加一次。消息确认和业务效果的区别参见[消息交付、确认与异常处置方法](message-delivery-acknowledgment.md)。

## 2. 定义操作身份、输入与存储前提

### 2.1 同一处理单场景中的不同身份

以下是**原创静态推演**，没有执行示例、Skill 或真实案例。沿用文档处理单场景：接入程序 S 请求处理服务为文档 D1 创建结构检查处理单，实际文档检查不在本例内。请求为 `Create(A,K1,D1,structure)`；A 是 S 的稳定命名范围，K1 表示这一次业务意图。需求是：**同一完整操作身份 `(A,K1)` 永久最多创建一张处理单，且文档和检查种类与该请求一致。**

S 在发送前持久保存身份与规范业务输入，获准接入路径保持这些字段。正常分支以这项输入来源条件为前提；真实系统没有对应证据时，不能默认成立。首次收到的内容有冲突时，按第 4 节处理，不能用数据库赢家认证原始意图。

| 标识 | 谁产生、何时保持 | 不能替代什么 |
| --- | --- | --- |
| A 与 K | 接入约定分配 A；S 为新意图生成 K，并在重发时同时保持 A、K | 换连接、换消息信封或换处理者不能产生新的业务意图；不能靠换 A 绕过旧 K |
| document_ref、work_id | 文档目录及处理服务标识业务对象 | 同一文档可有两次不同检查，同一处理单可有多次修改，不能把所有操作都去掉 |
| M | 消息信封标识；重新包装信封可以改变 | M1 与 M9 都可能承载同一 A/K1；只比较 M 会漏掉这种业务重复 |
| 发送、交付尝试标识 | 每次尝试分别记录 | 用于关联观察，不能证明效果唯一或旧工作已停止 |

例如，对 D1 发起另一轮结构检查是新意图，应有新的 K；相同输入不意味着必须是旧请求。相反，把 K1 重新包装为 M9 仍是原操作。处理者不能在遇到超时时自行生成新 K 再创建。

### 2.2 输入与结果要一起定义

本题消息格式为版本 1，身份和对象标识是非空字符串，Create 只支持 `check_kind=structure`。比较输入时保留 `operation、document_ref、check_kind`；不把 M、尝试编号或接收时间混进业务输入。不擅自对稳定文档标识折叠大小写，也不因 JSON 字段排列不同就认定业务不同。改变规范化方式或格式版本前，须明确旧请求如何继续比较。

创建决定保存 A、K、规范输入、`decision_id、outcome`；created 还保存 work_id，rejected 保存 archived 或 not_found 理由。相同操作重复时返回这些稳定业务字段，不要求响应时间、连接标识等传输信息逐字相同。摘要值可以加速比较，但必须说明计算对象及碰撞处理；不能用“摘要相同”替代完整的身份与输入要求。

本题选择在同一权威数据库 DB 保存两类内容：

- `Decisions`：以 `(A,K)` 为唯一键，保存规范输入和完整终态决定。
- `Work`：保存处理单及来源操作身份、文档、检查种类和后续业务状态。

这是一种有条件的候选。Create 同时包含成功和没有 Work 的业务拒绝，后续修改也有独立结果，所以决定记录有用途；若实际业务记录已能完整承担这些职责，应优先比较复用它，而非重复建表。

### 2.3 把存储保证拆开核实

本题新增以下**原创存储条件**，它们不是上一方法已有的能力，也不是任何数据库名称自动带来的保证：

1. DB 对所有写路径执行 Decisions 的唯一性。竞争同一键时，最多一个完整事务可以提交该键；失败者退出失败事务，再读取可见的已提交事实。
2. 决定终态及对应 Work 效果在同一本地事务内共同生效或共同不生效。未提交占位不对外充当完成决定，不单独持久发布一个“已处理”标记。
3. 明确成功响应在持久提交后发出，已提交内容能经进程重启保留；提交响应仍可能丢失。本保证不包含磁盘损毁或恢复旧快照。
4. Q 保存消息，E 保存异常处置，它们与 DB 分别提交。网络调用、外发消息、邮件及其他存储不因位于一段代码里就加入 DB 事务。

原子性处理一笔事务中多次写入的失败；唯一性及后文的受保护条件更新处理不同执行者竞争。只说“使用事务”没有回答第二个问题。实际产品的约束范围、隔离、冲突后的事务状态、读可见性及持久配置都要另取证。局部状态保护参见[业务不变量、聚合与事务方法](invariants-aggregates-transactions.md)。

## 3. 从首次处理推到重复结果

初始时 Decisions 和 Work 均为空，D1 可处理。P1、P2 是可以并发处理消息的程序；各方只能依据自己取得的证据判断。

| 步骤 | 动作与持久状态 | 接下来可以判断什么 |
| --- | --- | --- |
| 1 | P1 读取并检查 K1 的格式和规范输入，开始 DB 事务并竞争 `(A,K1)` | 取得处理机会不等于业务完成，Q 仍保留消息责任 |
| 2 | K1 没有已提交决定；P1 核对 D1，在同一事务中准备 W1、created 决定及规范输入 | 这些尚未提交的内容不能用于对外宣布成功 |
| 3 | DB 把 W1 与完整决定共同持久提交，P1 收到并核对成功结果 | P1 有创建完成的证据，可以返回 decision_id 与 work_id；Q 是否收到处理确认是另一事实 |
| 4 | M9 再次携带相同 A/K1/D1/structure 到达 P2 | P2 读取 K1 已提交决定，逐字段比较输入 |
| 5 | 输入相同，P2 返回原 decision_id、created、W1 及对应字段 | 此次无需再创建；判断依据是完整已提交决定及持续有效的写保护，不是“以前大概做过” |

本题 D2 已归档时，服务在同一资源保存 Kd 的 rejected 与 archived 理由，不创建 Work。以后 D2 恢复可处理，Kd 的重复仍返回原拒绝；若业务方要发起新请求，须明确形成新的 K。这是本题的业务决定政策，不是所有接口都应永久缓存所有错误。

DB 暂时不可用、缺少前序或提交结果未知，均没有形成这样的业务终态。不要把临时基础设施失败保存为永久业务拒绝，也不要以一条进行中记录冒充可复用结果。若实际方案单独持久保存进行中状态，还要定义负责人、旧工作是否仍可提交以及如何恢复；本题没有借一个租约或超时补出这套能力。

同 K 已绑定 D1 后又收到 D9，不属于相同请求重试。P2 保留原决定及两组必要字段，向 S 维护者和业务请求负责人报告输入冲突；不把 D1 的成功用于回答 D9，也不覆盖旧决定或重新创建。请求方须判断是否误用了 K，处理者没有自行改键重做的权限。

## 4. 展开两个处理者的竞争

### 4.1 先查后写为什么不够

先考虑没有上述共同保护的错误方案：P1 查 K1 不存在；P2 也查不存在；P1 创建 W1；P2 创建 W2；两者最后才写去重标记。检查发生时都没有记录，与最终出现两张处理单并不矛盾。后来只保住一个标记，也无法撤销先前已经提交的重复效果。

按本题候选，P1 与 P2 必须先在 DB 的同一键范围内竞争，而且决定与业务效果共同提交：

| 竞争结果 | 另一处理者能做什么 | 不能据此推出什么 |
| --- | --- | --- |
| P1 明确提交 K1 决定和 W1；P2 得到唯一冲突 | P2 退出失败事务，以能看见已提交结果的读取取得 K1，比较输入后复用或报告冲突 | 唯一冲突本身没有提供完整结果，也没有证明输入一致 |
| P1 的事务被确证原子中止且不会继续提交 | P1 未提交的占位与 Work 均不生效；P2 可以在同一保护下取得键并处理 | 本地取消等待不等于取得了这种中止证据 |
| P2 只收到超时，或冲突后查询又失败 | 保留未知；后续尝试仍经过相同唯一保护和共同事务 | 不知道赢家是谁，不等于没有赢家；不能绕过保护另建 Work |

不能用单进程锁覆盖其他消费者、其他实例或直接接口。也不能用租约到期推导旧执行者已停止：如果旧执行者仍可写业务，租约字段本身没有提供保护。当前平台不能满足题设条件时，应重新选择候选或停止宣称该保证。

### 4.2 第一次绑定也可能收到冲突输入

让 Kx 起初没有记录，P1 收到 A/Kx/D1，P2 收到 A/Kx/D9。DB 仍最多允许一份绑定与对应业务结果提交；例如 P1 提交后，P2 退出失败事务，读取 D1 输入并与 D9 比较，必须转入冲突分支。

这里有三件不同的事：最多一个本地效果、后续输入与已保存绑定一致、已保存绑定与 S 的原始意图一致。前两件可以由当前存储证据分别判断，第三件不能由“先到达”或“先提交”证明。

若无法取得原请求证据，处理者保留已发生的效果、决定标识和两份输入，停止自动产生新效果。S 维护者与业务请求负责人取得 S 持久保存的原始请求后，才能判断哪份输入有误；已有记录不得为消除冲突而覆盖。错误效果已经发生时，修复属于另外的业务决定与恢复安排。本方法没有在缺证分支继续承诺“输入必然正确”。

## 5. 把失败位置对应到持久事实

| 候选顺序或失败位置 | 可能留下的事实 | 结论与下一步 |
| --- | --- | --- |
| 先单独保存已处理，再执行业务；标记之后崩溃 | 标记存在，处理单不存在 | 后续跳过会漏做，不能采用这个顺序证明完成 |
| 先单独提交业务，再保存标记；两步之间崩溃 | 处理单存在，去重证据不存在 | 后续当作首次请求会重做，业务效果与证据应共同保存 |
| 在本题同一 DB 事务提交前确证中止 | 本次决定和业务写入均未生效 | 可以重新竞争；保证只涉及这笔事务实际包含的写入 |
| DB 共同提交完成且响应已收到 | 决定与 Work 都存在 | 按保存结果返回；消息确认仍需单独处理 |
| 提交响应丢失 | 可能提交，也可能未提交；处理者无法仅凭超时区分 | 查询到匹配的完整决定可复用；查询为空不能排除仍在提交 |
| DB 已提交，P 未确认 Q 或确认丢失 | 业务结果存在，Q 仍可能重投 | 重投再次读取受保护的决定，不再次创建；不由此宣称 DB/Q 已原子完成 |

提交未知时，重新尝试与盲目重做有具体区别：本题中，新的尝试仍必须竞争相同 `(A,K)`，并把全部本地效果纳入同一事务。旧事务若先提交，新尝试只能转为比较既有决定；旧事务若明确中止，新尝试才可能成为处理者。查询失败或冲突状态暂不能解决时继续保持未知，不强行输出无效果失败。

这项有限结论依赖历史记录没有被清掉、所有写路径使用同一保护、没有事务外副作用。撤掉任一条件，就不能直接沿用。它也没有证明 Q 的最终交付、E 的原子转交或外部动作的恢复已经完成。

## 6. 单独处理乱序与缺少前序

### 6.1 同一处理单的两个不同操作

W1 建立后，优先级为 normal，`last_seq=0`。S 已持久批准两次不同操作：K2 对应 `seq=1、priority=urgent`，K3 对应 `seq=2、priority=normal`。本分支业务要求逐项保存批准变更的本地历史，包括操作身份、顺序号、改变前值和改变后值；这两条历史分别应为 normal→urgent、urgent→normal。没有外部动作参与。

顺序号由有权批准这些修改的 S 针对同一 work_id 连续分配并持久保存；它不是消费者的接收顺序，也不是任意消息编号或墙上时钟。`SetPriority` 的输入包含 operation、work_id、priority 和 business_seq；priority 只允许 normal/urgent，business_seq 是从 1 开始的正整数。

如果 K3 先设置 normal，K2 后设置 urgent，最后值及历史都错误。K2 自己连续设置 urgent 两次可能看似无害，但在 K3 之后重做 K2 就会把新值改回旧值。去掉重复与执行不同操作的正确先后，是两个问题。

### 6.2 从缺项推到条件更新

本分支增加 DB 的明确条件：比较 `Work.last_seq` 与写入新状态是同一受保护动作；同一前置状态至多被一个竞争者成功推进。Work 变化、`ChangeHistory` 和 Decisions 终态共同提交。ChangeHistory 保存 work_id、seq、操作身份及 before/after；所有优先级写路径遵守同一检查。

| 到达与观察 | 动作 | 完成后持久结果 |
| --- | --- | --- |
| K3 先到，见 last_seq=0，seq1 缺失 | 不跳到 2，不记录成功；先确认本次 DB 事务中止并释放未提交占位与锁，再由既有消息保存责任等待缺项 | 没有 K3 成功决定，Q 仍保留待处理责任；复核期限不是自动删除时间 |
| K2 到达，能在事务内满足 last_seq=0 | 竞争 K2，受保护地改为 urgent/1，写 seq1 的 normal→urgent 历史及 K2 决定，共同提交 | 三类状态一致；成功响应描述这次修改 |
| K3 再取得处理机会，满足 last_seq=1 | 受保护地改为 normal/2，写 seq2 的 urgent→normal 历史及 K3 决定，共同提交 | 两次批准变化均有对应记录 |
| K2 迟到重复 | 读取 K2 决定、比较输入并返回原结果，不再写 Work | 当前仍为 normal/2；K2 历史仍为 normal→urgent |

SetPriority 的稳定响应为 A、K、规范输入、decision_id、`outcome=applied、work_id、approved_seq、before_priority、after_priority`。因此最后一行返回 K2 的 after=urgent，明确表示历史决定，不表示当前优先级仍为 urgent。需要当前值时，另作一次观察并说明观察时间与范围，不能用它替代 K2 的原结果。

条件更新必须确实改变一个符合前置状态的目标，才能提交成功决定和历史。未匹配、冲突或其他事务失败时，整笔中止，不能留下成功决定、占位或一半历史；中止响应未知仍按未知处理。等待前序不能占住阻止前序更新的事务资源。

再让不同 K 的 K2 与 Kx 都声称修改 W1 的 seq1。它们各自的 Decisions 唯一键不会互相冲突，所以真正防止双成功的是 Work 条件更新。若 K2 提交后，Kx 的条件更新不再匹配，Kx 整笔中止，再读已提交事实；见 last_seq=1 但找不到自己的决定，不能报告“Kx 已完成”，应由 S 和业务负责人核对批准冲突。

同理，`seq≤last_seq` 不总等于“本操作已完成”。已有匹配决定时可复用；没有本操作决定时，要区分同序号被另一操作占用、历史丢失和其他异常。不能把所有较小编号都静默删除并报告成功。没有权威顺序来源或存储条件写能力时，这套推导尚不成立。

### 6.3 哪些条件允许更简单的方案

严格等待保留逐项历史，却会让缺失的 seq1 阻塞后继；前序永远不来时，不能同时承诺所有后继继续完成。负责人应核对批准记录及待处理请求，决定如何解决缺项，不能由消费者编造一个前序。

若业务明确**只关心当前完整优先级**，不要求每次中间变化都执行，也不要求返回每次实际 before/after，则可以比较较小方案：S 提供同一对象的权威版本，消息携带完整 priority，DB 以条件更新阻止版本回退。seq2 先到可以保存 normal/2；seq1 后到只返回事先约定的过时未应用，不得声称 seq1 已执行。

这改变了逐项历史义务，所以不能直接替代上一分支。它也只处理状态版本问题：同 K 异输入怎样报告、过时结果是否保存、重复时返回什么仍要另定。消息只含部分字段、需要处理删除或存在跨对象前提时，较新编号未必包含旧操作的全部业务后果，不能照抄“保留最大版本”。

## 7. 推导历史保留与清理条件

### 7.1 删除信息会改变可证明的保证

继续使用 K1 与 W1，比较四种状态：

1. **K1 决定仍在。** 旧 M1 或新包装 M9 到达，服务取得原输入与 W1 结果，沿第 3 节复用。
2. **K1 决定已删除，接收者没有其他受保护证据。** 即使 W1 仍在，只查 Decisions 的处理者也会把 K1 当新请求，再建 W2。查不到记录不是从未执行的证明。
3. **删除后把 K1 重新分配给 D9。** 迟到 D1 与新 D9 共享身份，系统失去区分原意图的依据。禁止新分配复用 K 是必要政策，但它本身也挡不住第二步已经存在的旧副本。
4. **旧请求从另一条路径回来。** Q 已删除某份消息，S 的离线记录、E 的异常再处理或其他获准重放仍可能再次带来 K1；当前队列空不能替代这些路径的证据。

本题没有可信的最晚重放时点，因此有限 TTL 不能满足永久最多一次。主方案保留识别 K、比较输入和复用决定所需的证据；不能悄悄把要求改成“保留期内最多一次”。

业务记录自身若可靠保存 origin、原输入和稳定结果，且唯一性覆盖所有写路径，可以承担部分证据。这样可以减少重复存储，但仍须处理没有 Work 的拒绝、处理单删除，以及可变字段不再代表原输入的情况。压缩为最小历史记录也有条件：“见过 K”或许足以拒绝旧请求，却未必足以比较输入、返回原结果。记录换个名字不会消除这些义务和存储成本。

### 7.2 有期限的候选必须回答什么

只有实际系统已具备可证明的旧请求拒收边界，或能覆盖所有允许路径的重放期限，才有理由继续设计有限保留。至少列清：

| 需要界定的对象 | 必须取得的事实 |
| --- | --- |
| 保留从何时计起 | 从原意图建立、最后允许发送还是终态提交计起；各时间由谁记录，为什么覆盖较晚到达的副本 |
| 允许旧操作再次进入的路径 | S 重试与离线发送、Q 重投与归档、E 再处理，以及实际允许的恢复或人工入口；分别有何上界或拒收条件 |
| 接收时怎样识别已过边界 | 旧请求不会在证据删除后重新被解释为首次请求；不能仅由发送者承诺不再新发作保证 |
| 清理与在途提交怎样协调 | 清理时旧处理者是否还可提交，拒收条件能否在与业务写入相同的保护范围内生效 |
| 恢复后边界是否仍有效 | 旧快照、旧消费位置或历史恢复是否会重新放行已经执行的请求 |

清理线程给删除动作加锁，不足以保证另一处理者不会在其后提交旧效果。必须证明旧尝试不能再提交，或让接收拒收条件与业务写入受到一致保护。本题没有这些额外事实，所以没有可用的清理天数或公式；结论应停在保留必要证据或方案不足，而不是凑一个宽限期。

长期保留也不是无限免费。令可保存决定的预算为 C；这是待工程评估的容量，不是通用推荐值。预算不足时，由业务和存储负责人增加可证明的保存能力，或明确重新评估业务条件。在保护证据不足时停止新效果写入，不能先删历史再继续原承诺。完整队列积压、恢复吞吐与容量计算仍需单独设计。

## 8. 明确停止动作与剩余责任

| 原因 | 谁停止什么，保留什么 | 继续需要的证据 |
| --- | --- | --- |
| DB 提交结果未知或无法读决定 | P 保留 A/K、输入、提交尝试和最后观察；不绕过唯一保护新建业务记录 | 可见的完整决定，或在同一保护下取得明确竞争结果；查询空不够 |
| 同键输入冲突或原意图缺证 | P 不覆盖、不换键、不自动产生新效果；S 维护者和业务负责人保留并比较原请求及已发生结果 | 原输入来源及业务处理决定；先提交不证明原意图正确 |
| 顺序缺项或同序号冲突 | P 退出已确证中止的事务后等待或保留异常；Q 原责任保持，S 及业务负责人核对批准记录 | 前序已提交的事实，或另经业务决定的处理安排；不伪造前序 |
| 无法保存所需历史 | 接入方停止新增受理承诺；P 停止需要新增证据而无法保证保存的效果写入。仍可安全读取既有决定 | 足够容量或经证明不丢失保护证据的方案；停收不撤销 Q 已承接的请求 |
| 旧快照丢失已提交决定 | DB 恢复负责人暂停依赖缺失历史的全部效果写路径，包括普通交付、自动重试、人工重播和直接接口；保留 Q/E 责任及在途未知 | 业务状态、历史证据与所有写路径重新一致的证明，或可证拒收受影响旧请求的边界；具体恢复另行完成 |
| 发现不能共同提交的外部效果 | P 不启动或重试未经保护的外部动作；已调用但结果未知则记录未知、原请求和当前责任，不以 DB 成功替代外部成功 | 外部结果与重做依据，以及后续可靠发送、对账或补偿方案和相应授权 |

停止指令不是已经停止的证据，也不终止所有在途事务。Q 已保存并受理的消息仍须由 Q 保留；P 不能因为无法继续就提前确认完成。E 只有在确实保存必要信息、授权负责人实际接手后才承接异常责任，沿用前篇的条件。暂停处理与保留请求是两件都要做到的事。

本题的持久保证只覆盖进程重启。恢复到缺少去重证据的旧快照，已经撤去了永久唯一性的必要前提，不能仅关闭一个叫“重放”的入口便恢复原保证。跨资源发送、外部效果未知及完整恢复方法是后续工作，不能由本篇的本地事务推导代替。

## 9. 形成可审查的设计说明

按当前风险交付一份足够小的说明，至少让读者回答以下问题：

1. 重复时必须保持哪些业务状态和返回字段，哪些后续操作与原请求不同？是否存在更简单且仍满足要求的方案？
2. 操作身份由谁生成，重发保留哪些字段，规范输入如何比较，同键异输入及原意图缺证分别由谁处理？
3. 哪个权威资源保护竞争，哪些决定、业务状态和历史共同提交，冲突者和未知提交怎样取得下一项事实？
4. 不同操作需要怎样的业务顺序，谁有权赋序，缺项和条件更新失败怎样退出，是否确实需要每个中间效果？
5. 哪些路径可能带回旧请求，保留从何时计算，清理、在途工作、容量和恢复怎样影响保证？
6. 哪些动作已获证据支持，哪些仅是题设，哪些缺失事实要求停止并保留责任？

评审时优先寻找能改变结论的反例：同键不同输入、两个处理者同时查空、业务成功后决定未保存、旧赋值晚于新赋值、清理后旧消息再来、恢复后证据缺失。用具体状态与可见证据说明反例是否被方案排除，不凭使用了某个产品名或模式名判断。静态推演与平台行为核验分别登记；本篇没有工程执行结果。
