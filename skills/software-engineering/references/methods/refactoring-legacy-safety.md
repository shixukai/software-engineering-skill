## 1. 先确定此次改变什么

当已有实现需要修改，但测试不足、环境难以控制，或者结构调整容易连带改变行为时，使用本方法。目标是让本次修改获得适当保护，并以可解释的小步完成；不以清理全部旧代码为目标。

先写清当前变化为何困难：要改哪个判断，它影响哪些客户与外部效果，哪一种局部调整能降低风险。若已有入口可控、逻辑纯且变化很小，直接修改并补对应检查可能足够。不要因为函数长、代码旧或没有理想架构，就默认重写。[来源 A、B]

区分两种意图：**重构保持约定的行为，功能或缺陷修复有意改变行为。** 两者可以在同一任务交替，但每一步的期望依据必须清楚。“两顶帽子”不要求每一步提交，也不禁止补遗漏测试或迁移内部接口；不能同时改变实现与期望，让意外差异悄悄消失。[来源 A]

需要重新决定模块职责时，参见[模块与契约方法](module-responsibilities-contracts.md)；本篇解决的是已有代码如何到达可安全修改的状态。数据库迁移、分布式交付与大规模系统替换另需相应协议，不由抽函数自动获得保证。

## 2. 用有限场景定义保护范围

### 2.1 给定旧流程与变化请求

下文“阅页提醒器”是完全原创的虚构场景。伪代码、数据和结果均用于静态推演，没有执行旧程序、通知发送或真实案例。具体工程中，读源码得到的预期、隔离运行的观察和已经认可的契约必须分别记录。

旧入口接收有效读者标识，建立两个外部依赖，取一次UTC日，读取借阅列表，发一份摘要后记录提醒日期。题设约定输入是有限的合法记录列表，每条含标识及整数到期日；日期转换、时区转换和非法记录处理不在本例算法内。原流程如下：

```text
remind(reader):
    repo = new LoanStore()
    mail = new MailGateway()
    today = utcDay()
    loans = repo.openLoans(reader)
    lines = []
    count = 0
    for loan in loans:
        if loan.dueDay - today <= 2:
            lines.append(loan.id + ":" + loan.dueDay)
            count = count + 1
    if count == 0: return 0
    mail.send(reader, join(lines, "\n"))
    repo.markReminded(reader, today)
    return count
```

本例的读取和构造都可能失败；错误向调用者传播，后续语句不再执行。`send` 返回只按既有网关契约解释，不宣称邮件已被最终收件人收到。记录失败可能发生在发送已经产生效果之后；旧返回类型没有表达全部恢复状态，不能因此推断可安全重试。

本次新需求是允许调用方显式选择提前提醒天数，省略时仍为2；允许范围为整数0至30。过期记录继续入选，输入顺序和重复记录继续保留。新参数非法时必须在创建外部依赖前拒绝。这些是**本例给定的需求**，不是从历史输出推导出的业务真理；新参数的校验和新阈值属于功能变化。

### 2.2 把“现状”与“应该”分开

| 信息类别 | 本例如何处理 | 不应作出的推断 |
|---|---|---|
| 已给定保护契约 | 默认阈值2、包含过期、输入顺序与重复、一次摘要发送、先发送再记录、无匹配则不发送不记录 | 不把去重、排序或排除过期夹入结构调整 |
| 代码阅读所得预期 | 顺序为构造库、构造网关、读日、读借阅；失败后不继续下一步 | 未实际观察时不能称“现有回归基线已通过” |
| 可疑或不充分的旧语义 | 发送后记录失败时调用者只看到异常，可能误重试 | 刻画这个现象不等于认可其恢复政策；本次不偷偷改成成功或未发送 |
| 新需求 | 显式阈值、默认兼容、0与30边界、非法值早拒绝 | 不能用旧输出作为新阈值的唯一期望 |
| 决定性未知 | 真实依赖的初始化、失败和确认语义，以及外部客户依赖 | 用替身通过不能补出未知的平台保证 |

特征测试（characterization test，也称刻画测试）记录代码**实际做了什么**，不是证明它**应当如此**。对现状先分类为需要保留、已有依据要改变、或尚待确认；域外偶然行为不必永久冻结，但调整保护域需要依据，不能因为某个测试失败就删除它。[来源 A、B]

## 3. 从修改点选择观察点

阈值判断先影响入选行，继而影响摘要、发送次数、记录动作及返回计数。只测新判断函数，会漏掉旧入口仍发送原列表的错误。选择能感知这个传播链的最小可控范围，再为真实依赖保留必要的边界检查；不必从每次全系统运行开始。[来源 B、C；本例传播链为工程综合]

| 要防止的错误 | 本例观察点与可区分输入 | 为何不能只看最后返回值 |
|---|---|---|
| `<=` 被改成 `<` | 到期日正好为 `today + 2`，检查摘要包含该行 | 非边界输入也可能返回相同计数 |
| 新函数算对但没有接入 | 从保留的 `remind` 入口追踪被发送内容与返回值 | 单独调用helper无法证明产品入口用了它 |
| 发送失败却先写了提醒日期 | 发送替身记录尝试并失败，观察记录调用是否发生 | 两种实现都可能抛异常，持久状态却不同 |
| 重复发送或重复读时钟 | 感知替身记录有关调用的次序、实参与次数 | 相同摘要不排除发了两份或读取了不同日期 |

使用固定日、明确借阅序列、可记录调用且能按阶段失败的依赖。控制了这些输入，只能说明此范围内的逻辑和接线；网关到底何时生效、数据库是否提交成功，仍需实际边界证据。[来源 C]

不是每个内部调用都要写入断言。只保护与契约或本次风险有关的内容；无关对象名称、分配身份或helper调用次数会使测试绑死实现。反过来，也不能为让快照稳定而无条件排序、去重或删除时间字段——若它们参与行为，归一化就会掩盖回归。[来源 C及工程适配]

## 4. 取得第一个可控的测试接缝

### 4.1 先找已有边界，再决定首个编辑

先检查现有更高层入口、依赖替换配置或对象参数能否在隔离环境感知目标行为，同时阻止外部效果。有可用接缝就利用它；不要先修改设计再寻找理由。找不到时，接受“需要先做一点没有充分测试保护的解依赖”的事实，限制这一步的范围，而不是声称风险已被未来测试消除。[来源 A、B]

接缝是可以替换行为的位置，激活点（enabling point）决定采用哪一种行为。只有一个接口或虚方法还不够：如果被测方法内部仍创建固定实现，测试可能没有选择机会。还须检查导入、全局初始化、构造和后台线程的效果是否发生在激活点之前。[来源 B；前置效果检查为工程展开]

本例选择参数化一个内部入口，保留外部 `remind(reader)`。测试在调用内部入口时传入库替身、发送替身和日期函数，这就是激活点；生产入口继续传真实依赖。传入普通函数或对象即可，不需要依赖注入框架。

```text
remind(reader):
    repo = new LoanStore()
    mail = new MailGateway()
    return runReminder(reader, repo, mail, utcDay)

runReminder(reader, repo, mail, readDay):
    today = readDay()
    loans = repo.openLoans(reader)
    # 从原来的 lines = [] 起复制剩余主体，不同时清理或改阈值。
```

`utcDay` 在此传的是函数，尚未调用。原来先创建两个依赖再读日的顺序保留；不能把它写成调用结果后又在内部读一次。内部入口不能重新构造真实对象或用同名局部覆盖传入依赖。若目标语言的参数求值、绑定或生命周期不同，按实际语义核实，不把伪代码当通用语言保证。

### 4.2 诚实完成首次保护

首个编辑只为接入依赖：逐项核对原签名、参数位置、返回与异常传播、构造/读日/读取顺序、名称绑定及资源责任。运行可用的语法、编译和已有保护；它们检查不到的行为仍要保留为盲区。不要同时重命名所有字段、转换日期单位或更换错误政策。[来源 B]

接着在隔离替身上观察实际结果，建立刻画检查，并确认目标分支确实执行、错误能被断言区分。若安全可用的旧入口基线存在，可与它比较；若没有，首次编辑后的刻画不能倒过来证明编辑前后等价。此时依据源码逐行对照与已有外层证据说明残余风险；关键风险仍不可接受时，缩小编辑、寻找其他隔离点或先取得必要条件。

保留的生产入口还要检查它确实转发到新内部入口，并仍装配真实依赖；内部替身检查无法独自覆盖这条接线。若构造本身无法安全运行，先保留静态接线证据及未验证说明，不通过触发真实发送“补齐测试”。发布前的相关环境核验须在具体任务授权下完成。

## 5. 追踪数据流并小步提取

### 5.1 选择一个能解释清楚的片段

取得适当保护后，先提取从 `lines = []` 到筛选循环结束的部分。不是看到循环就抽函数，而是因为它完整回答“在给定日，哪些借阅行应进入摘要”。提炼前把变量和效果分成四类。[来源 A：6.1]

| 数据或控制 | 原位置的用途 | 此次提取如何保持 |
|---|---|---|
| `loans`、`today` | 循环只读的外部局部值 | 原位置读取后显式传入；不在helper重新读库或时钟 |
| `lines`、`count` | 在片段内创建和修改，片段后继续使用 | 声明一起移入，通过返回值由调用方接回 |
| 借阅记录与集合 | 只读标识和到期日，不修改原集合 | 保留顺序及重复；不原地排序、删除或增加共享别名 |
| 异常与外部效果 | 计算失败会阻止发送；发送和记录在片段外 | 不吞异常、不提前发送，不将记录移入helper |

复制片段为 `collectDue`，先处理作用域和返回值，再将原片段替换成调用。以下是有意保留冗余计数器的中间状态：

```text
collectDue(loans, today):
    lines = []
    count = 0
    for loan in loans:
        if loan.dueDay - today <= 2:
            lines.append(loan.id + ":" + loan.dueDay)
            count = count + 1
    return (lines, count)

runReminder(reader, repo, mail, readDay):
    today = readDay()
    loans = repo.openLoans(reader)
    (lines, count) = collectDue(loans, today)
    if count == 0: return 0
    mail.send(reader, join(lines, "\n"))
    repo.markReminded(reader, today)
    return count
```

先核对日期边界、顺序、重复、无匹配及错误后的调用轨迹。不要在同一步把阈值变成新参数、把列表去重，或为“更函数式”改写整个循环。多个写出值可以先返回记录或元组；也可以缩小提取片段。选择由当前数据流决定，不要求一律返回一个标量。

一个能编译却错误的提取是：把 `count` 作为普通值参数传入helper，在内部增加它，却没有返回并接回。调用方仍见0，可能不发送任何摘要。另一种错误是helper已返回新行列表，原入口却继续发送旧列表。需要验证的是值回到哪里、谁真正使用它，而非只验证helper产生了正确列表。[来源 A、B]

若实际片段含 `return`、`break`、`continue` 或资源清理，先检查控制作用域；把原方法的提前返回搬到helper后，可能只结束helper而继续后续发送。不要用无条件“提取成功”推断控制等价。本例没有循环内提前退出，因此不需要额外退出协议；有这种情况时，可缩小片段或明确返回退出决定，再核对调用方执行它。

### 5.2 再决定是否分离计算与外部操作

本例循环每追加一行才增加一次计数，没有其他计数更新。可在下一小步把计数改为结果行数，并重新检查原来的边界和失败路径。随后将行、正文和计数组织成一个明确的准备结果，让用例使用这一个结果执行发送与记录。每一步都有独立理由，不必一次改完。

| 中间状态 | 唯一主要改变 | 必须继续成立的证据 |
|---|---|---|
| S1 依赖可传入 | 将环境依赖暴露在激活点，主体暂不整理 | 构造/读日/读取顺序、产品入口接线及首次编辑盲区 |
| S2 提取筛选 | 只读输入显式传入，局部写出由返回值接回 | 同一输入的行序、重复、计数；旧入口消费返回结果 |
| S3 准备结果 | 以已取得的同一批数据生成摘要计划，外部操作仍在用例 | 读库与读日各一次；空计划不发送；成功发送后才记录 |
| S4 新阈值 | 改变经确认的选择条件并增加新输入校验 | 默认2兼容；新阈值的独立期待与调用接入 |

拆分阶段不是把任何交错过程都改成“先算完、后全部写”。**本例原来就是先完整筛选，再发送一次，因此保留这个边界有依据。** 若旧程序逐行发送，第二行计算失败时第一行可能已经发送；改为先准备全部计划会改变失败后的状态。应另行决定是否要这个新保证，不能把它当成纯重构。[来源 A：6.11及工程适配]

查询与修改分离也不意味着让调用者分别运行两遍。不要先调用“获取摘要”，再让“发送摘要”重新读时钟和借阅列表；两次读取可能不同，查询也可能昂贵或有隐藏效果。本例在一次用例内取得数据、计算一次并使用同一计划，保留原入口返回计数的完成时点。原子“取出并移除”之类操作若拆成查询和删除会产生竞争窗口，应保留复合契约或先设计相应保护。[来源 A：11.1；并发及重复读取条件为工程适配]

## 6. 再引入有意改变的行为

### 6.1 给新阈值独立的期待

在默认阈值2的中间状态获得相应保护后，再使 `collectDue` 接收已校验的 `leadDays`，将唯一条件改为 `loan.dueDay - today <= leadDays`。保留旧 `remind(reader)`，让它以固定2调用新入口；新入口先校验显式阈值，再按原顺序建立依赖并调用用例。旧签名存在不代表兼容已证明，默认值、异常及返回语义仍需核对。[来源 A、B]

省略参数只通过旧入口取得默认2；显式0是合法值，不等于缺失。布尔值、空值、字符串、小数及范围外整数不属于本例新阈值域；不要用 `leadDays or 2` 一类真值替代默认规则。目标语言若把布尔视为整数子类，应用校验仍须表达本例的实际输入域。

以下日编号只用于算术，不表示真实日期：`today = 100`，输入顺序为 `L1:99`、`L2:103`、`L3:102`、`L3:102`、`L4:100`。本表给出预期，未运行测试。

| 请求 | 应产生的摘要行及返回计数 | 依据与能发现的问题 |
|---|---|---|
| 旧入口／默认2 | `L1:99`、`L3:102`、`L3:102`、`L4:100`；4 | 旧保护域；可发现错用 `<`、排除过期、去重或改变顺序 |
| 新入口，阈值4 | 原输入5行全部保留；5 | 新要求；只测新helper不够，旧/新公开入口的实际调用也要核对 |
| 新入口，阈值0 | `L1:99`、`L4:100`；2 | 0是有意义的选择；可发现被错误替换为默认2 |
| 阈值30与31 | 30合法；31在构造依赖前失败 | 输入域依据，不能靠当前数据恰好无差异证明31有效 |
| 无记录或没有入选行 | 0，无发送与记录调用 | 保留空结果语义，不把读取失败转换为这个正常结果 |

新增功能的验收可以暂时失败，但既有受保护行为的失败仍是回归信号。先确认新检查因缺少目标能力而失败，不是因夹具、构造或权限错误失败；不把一切红色都标为“功能还没做完”。需求改变时只调整有依据受影响的期待。[来源 A、C]

### 6.2 保留失败链，避免错误的“恢复”

| 失败位置 | 本例应保持的流程结果 | 不能附加的保证 |
|---|---|---|
| 构造、读日或读借阅失败 | 后续步骤不执行；保留错误及相关阶段 | 读取失败不是空列表，构造失败也不代表此前未有初始化效果 |
| 准备摘要失败 | 不调用发送和记录 | 不能用空摘要吞掉内部问题 |
| 发送报错 | 不调用记录；错误仍向上传播 | 发送报错可能是明确拒绝，也可能已生效但确认丢失；异常本身不能证明未发送 |
| 发送返回后记录失败 | 调用者得到错误，但发送可能已经生效 | 不能直接重试整个入口，也不能因代码回退就声称邮件撤回 |
| 全部成功 | 返回计划行数，发送和记录按约定完成 | 不自动具备去重、最终投递或跨系统事务保证 |

如果任务还要求可靠恢复，应单独定义状态、操作身份和查询/重试政策，再选择实现；那已经超出本次保行为整理。关于未知结果与资源责任，可按需要读取[模块与契约方法](module-responsibilities-contracts.md#5-把失败状态和资源责任写进契约)。

## 7. 用反例检查保护是否有效

设计保护时，不止列出“正常、异常、边界”三个名称。为重要风险找一个错误版本，并说明现有观察怎样区分它。在获准的隔离环境中，可以用安全、可逆的已知错误核查保护是否真的生效，然后恢复；本篇只给静态反例，未执行变异或行为测试。[来源 A、B]

| 错误版本或变体 | 应由什么暴露它 | 若仍无法区分，意味着什么 |
|---|---|---|
| 原入口忽略 `collectDue` 返回值 | 通过公开入口观察到期边界行和发送实参 | 只有helper保护，接线尚未受保护 |
| 筛选改成排除过期或去重 | 本例 `L1:99` 与两行 `L3:102` | 成功计数、行内容或输入选择太弱；不能排序去重后比较 |
| 将读钟从循环内移到循环外 | 对真正逐条采样的另一实现，给两次跨过边界的时刻 | 本例原来读一次，不足以证明其他采样策略可合并；先明确目标实现语义 |
| 发送失败前已调用记录 | 感知相关事件顺序，令发送在尝试时失败 | 只断言“抛异常”漏掉状态变化 |
| 测试传入替身，但入口覆盖成真实依赖 | 核对实际绑定、构造入口与测试替身收到的调用 | 参数存在但激活点无效；不要继续运行有外部效果的路径 |
| 新旧入口都真实发送一次，再比较返回4 | 发送轨迹出现两个效果，即使返回和正文相同 | 比较过程自身改变了系统，不能用作安全的等价检查 |

比较新旧逻辑，应从同一明确输入和可控制的依赖开始，对需要保护的结果和效果轨迹分别判断。只有无外部效果且语义允许的计算才能自由重复；不要把旧程序再次读出的动态状态拿来与另一时刻的新程序比较，然后把差异全部归为重构问题。

刻画检查可能帮助发现遗漏，不能通过无审阅重录快照来消除失败。失败时先确认是保护义务被破坏、夹具脆弱，还是已认可的新行为；解释不清就回到最近可解释的小步。不要以模型判断、覆盖率、测试数量或编译通过代替这项分析。[来源 A、B、C]

## 8. 选择改动规模并停止

### 8.1 小改动、新生方法与包装的取舍

Feathers 的新生方法（Sprout Method）把新增行为放入独立可测部分，再由旧路径调用；新生类可承载相对独立的新增责任；也可以在旧类难以构造或编译时，先将连续的新行为放入可测试的新类，即使最终职责边界尚未确定。这能先保护新逻辑，但旧主体和调用点仍可能缺少保护，甚至暂时留下职责分散的代价。不要把这种局部策略说成旧系统已重构完成。[来源 B]

| 选择 | 本例何时采用 | 必须承担的代价与检查 |
|---|---|---|
| 直接局部修改 | 判断很小、现有入口已可控且相关保护足够 | 只改必要条件，继续检查边界和外部轨迹，不为一条规则建框架 |
| 新生函数或类 | 新规则可由明确输入计算，旧主体暂时难以全面保护 | 新函数独立验证后，旧入口必须在发送前调用并使用结果；新类需有独立职责或具体的构造/编译隔离收益，后者保留临时结构的代价 |
| 包装已有操作 | 新行为确实发生在旧操作之前或之后，边界语义清楚 | 先后次序、失败传播和成功定义须保留；旧发送后包装动作失败不等于旧发送撤销 |
| 继续提取与整理 | 重复或依赖已实际妨碍这次变化，已有反馈能支持下一步 | 每个小步有独立目的；不能把短期接缝演变成无限包装链 |
| 重写或通用规则引擎 | 只有恢复行为、迁移客户和长期成本有充分依据时另行比较 | 本例一个阈值不足以支持；代码少不等于兼容和迁移成本小 |

共享可变状态、逐条外部操作或前后步骤的原子关系，使新逻辑难以独立时，不要硬套新生方法。可以先把真正需要的输入与输出澄清，或选择更小修改；若必须改变相关行为，转为明确的功能或协议设计。[来源 A、B及工程适配]

### 8.2 交付、停止与回退

交付应说明：此次意图与保护域、关键中间步骤、哪些入口和效果实际得到检查、仍未覆盖的风险、新功能的独立期待，以及需要保留的旧入口或临时接缝。可以写在当前变更说明与已有检查记录中，不强制新增一套文档。

当前变化已满足、关键连接有适当证据且残余风险清楚时，停止无关整理。临时结构若本次已不需要就清理；如果仍用于隔离难测部分，保留具体用途与退出条件。不要为了“整洁”在交付前突然删除唯一可用接缝。

出现无法隔离的外部效果、不能确认的保护域，或首个编辑风险已超出可接受范围时，停止依赖该证据的步骤；继续独立可做的局部分析，指出下一项最小补证或更窄方案。也不必等全库都有完善测试，才允许处理一个已能控制的局部变化。

检查失败时，恢复最近可解释的本次小步，保留用户的其他工作和既有暂存状态；不得用整体重置替代局部回退。代码回退只改变后续执行，不能撤销已经发送的通知或写入的外部状态。旧实现如果不接受新输入或无法维持已经对外承诺的行为，也不能直接切回。[来源 A及工程适配]
