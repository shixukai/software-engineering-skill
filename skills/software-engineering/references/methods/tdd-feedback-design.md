## 1. 适用任务与必要前提

在已有授权内实现可观察行为，需要决定下一项检查、一次改动多大，或检查困难是否提示结构问题时，采用本方法。测试驱动开发（TDD）用自动检查引导当前行为的实现和结构调整；它不能替代需求判断，也不自动产生合适的系统架构。

先明确当前目标、有效的行为依据、允许修改的范围、已有检查与实际运行条件。将未知分为三类：**需要什么结果、怎样观察结果、怎样实现结果**。预期尚有争议，先处理会改变结果的需求问题；检查不能运行，先建立必要的调用与观察；实现尚不确定，才用下一例帮助选择步骤。独立预期和检查范围沿用[风险、独立预期与验证层次方法](test-risk-oracles-layers.md)，不用待测函数生成预期。

以下情况可以采用较轻的做法：无行为影响的文字修改按影响范围检查；只为了解 API 或算法的探索，先记录待核实假设和结论，不把探索代码直接当作功能；熟悉且关系明确的局部实现直接完成并验证；旧代码缺少保护时先采用[行为保护与渐进重构方法](refactoring-legacy-safety.md)建立必要观察。未采用完整 TDD 顺序，仍须完成当前任务需要的验证。

GUI、数据库或分布式系统的类别本身不能决定是否采用 TDD。应看当前行为能否被触发、观察和可靠复现，以及准备与运行成本是否合适。不要为了缩短反馈而替换掉本次必须证明的真实连接；需要更多准备时，将其作为独立工作，不假称已经经历有效反馈。

## 2. 选择能澄清当前问题的下一例

从当前目标维护一份简短的待做列表：尚未支持的行为、边界、已知风险及必要结构整理。新想法先判断是否属于当前目标；列表可调整，不能把已知必要行为移走后称目标完成。已有项目记录足够时不另建表单。

选择下一例时，比较它将排除什么错误，以及需要同时解决哪些未知。重复已经区分过的输入可能没有新信息；很大的输入可能同时涉及多组状态，使失败难以定位；简单而有区别的一例则能使下一步明确。选择依据是当前信息和实现把握，不是固定按输入大小、测试层次或最高风险排序。严重风险可以改变顺序，但须说明它与当前改动的关系。

分别控制两种步幅：**本例新增多少行为**，以及**一次结构修改涉及多少地方**。如果一次失败同时可能来自新接口、运行支持和业务实现，先分开这些变化。若实现已经清楚，就不必逐字拆成很多步。运行等待很长时，调查准备、编译、真实协作和重复执行分别花在哪里；采用更有针对性的检查仍须覆盖目标风险，不规定统一的分钟数、行数或用例数量。

Beck 的启动测试可以先用几乎不做工作的操作澄清调用；GOOS 第 5 章则偏好最简单的成功情形，担心只做退化或失败情形得不到真正行为的反馈。这是选择重点的差异。若未知是调用如何接入，空输入可以有价值；若调用已经清楚，下一例应说明当前最需要弄清的成功行为，不能因为空输入最短就一直停在准备阶段。第 5 节从空输入开始，限定在开发者尚不熟悉接入的假设下。

## 3. 先确认失败在说明什么

本方法中“红”指当前检查确实运行并观察到需要处理的失败，“绿”指在声明版本与条件下实际执行的检查通过。写下检查或静态推演出预期结果，都不等于实际红或绿。第一次尚缺接口或类型可以是有用的准备反馈，但还不是目标行为受到检验的证据。

| 当前现象 | 它能说明什么 | 下一步 |
| --- | --- | --- |
| 用例未被发现，或没有执行到断言 | 检查没有提供目标行为证据 | 核对发现规则、入口与实际执行记录 |
| 名称、导入、类型或检查接入错误 | 当前检查尚不能观察目标行为 | 修正必要接口或检查接入；不要为消除设施错误随意改业务逻辑 |
| 环境或依赖故障 | 在该条件下无法取得所需观察 | 分清环境、准备和产品错误；保留受阻或不确定 |
| 实际输出与独立预期不同 | 若输入、对象和调用已核实，可定位这项行为差别 | 记录输入、预期、实际结果与失败位置，再修改对应实现 |
| 新例和相关既有检查均通过 | 本次执行在所声明条件和观察范围内符合预期 | 检查是否留下临时实现、结构问题与未覆盖行为 |

若计划的失败没有出现，先查行为是否已支持、输入是否有区别、断言是否观察正确对象；不要人为破坏生产实现来制造一次红灯。外层尚未实现的功能检查可以保持未完成，已有功能回归失败仍须单独调查，不能混成“现在本来就是红的”。

## 4. 按实现把握切换策略

| 策略 | 适用条件与动作 | 必须保留的限制 |
| --- | --- | --- |
| 伪实现（Fake It） | 调用、检查或计算关系尚不熟悉时，暂用常量或特例取得一项明确反馈，再替换为输入之间的关系 | 标明还不支持的行为，继续去掉临时结果；当前例通过不等于功能完成 |
| 显明实现（Obvious Implementation） | 实现关系清楚、改动范围可控时，直接写出所需实现并验证 | 知道怎样写不等于已经通过；意外失败反复出现或难以定位时缩小变化 |
| 三角法（Triangulation） | 不能确定正确概括时，选择另一项会使错误概括失败的输入，迫使实现体现有区别的关系 | 不是任意第二组数据；两例也不是充分证明。概括已清楚时，无需强制再写常量或额外特例 |

三者可以切换。不要把“常量、两个例子、一般化”规定为每项工作的固定顺序；也不要持续增加按样例返回的分支而推迟解释真实关系。缩步的理由是当前未知和失败定位困难，随后应重新判断是否仍需小步。

## 5. 原创推演：相邻标签归并

以下是事先限定题设的原创静态推演，**没有执行示例程序或 Skill**。文中的失败和保持结果均为按伪代码推导的预测；实际实施仍须取得第 3 节所述运行证据。

### 5.1 题设与独立预期

输入是只含 `A`、`B`、`C` 的有限列表。相等按原值判断，不作大小写或其他标准化。输出按原顺序列出 `(标签, 正整数次数)`；只归并相邻相同标签，相隔的同标签仍是不同组。空输入返回空列表，不修改输入。没有时间、网络、存储或其他外部状态；范围外输入的处理尚未约定，不为示范增加错误处理政策。

预期由题设直接数出。例如 `[A,A,B,B,A]` 中前两个 A 相邻，接着是两个 B，末尾 A 与第一组隔开，因此预期为 `[(A,2),(B,2),(A,1)]`。只检查次数总和为 5 不够：错误结果 `[(A,3),(B,2)]` 也满足总和，却丢掉顺序和分组。输出分组是否符合预期、输入列表是否保持不变，需要分别检查。

### 5.2 从最小调用到有区别的下一例

假设开发者不熟悉这个操作如何接入检查，先选择 `[] → []`，临时实现 P0 为 `return []`。它仅帮助建立调用和空输入观察；下一项 `[A] → [(A,1)]` 会得到空结果，因而区分“永远为空”的错误。若当前只想确认非空结果的表达，可以得到 P1：

```text
P1(xs):
    if xs is empty: return []
    return [(A, 1)]
```

P1 保留空输入，但只解释了一个非空例子。此时比较三个候选，而不是预先固定测试顺序：

| 候选 | P1 的预测与题设预期 | 对当前未知的价值 |
| --- | --- | --- |
| 再写一次 `[A]` | 都为 `[(A,1)]` | 没有区别固定标签与输入标签，暂不增加 |
| `[B]` | P1 为 `[(A,1)]`，预期 `[(B,1)]` | 单独说明输出标签必须来自输入；选择这一例 |
| `[A,A,B,A]` | P1 只有一项；预期 `[(A,2),(B,1),(A,1)]` | 同时涉及次数、组边界及分隔后同标签；这些关系尚不熟悉时先记入待做列表 |

选择 B 是因为本轮未知是标签来源；如果已经清楚完整归并算法，就应直接实现，不必故意走完以下所有临时状态。

### 5.3 连续推进，并保留已成立的要求

| 状态与选中输入 | 当前实现为何不足 | 本轮合理变化及仍成立的旧要求 |
| --- | --- | --- |
| P1；`[B]` 预期 `[(B,1)]` | 固定 A 会返回错误标签 | P2：空时返回 `[]`，否则 `[(xs[0],1)]`。空输入与 A 单项仍符合；B 排除固定标签，这是一次有区别的三角法选择 |
| P2；`[A,A]` 预期 `[(A,2)]` | 次数固定为 1 | P3：空时返回 `[]`，否则 `[(xs[0],length(xs))]`。先前空输入和单项仍符合；它只解释一个连续组，不声称任意非空列表都是一组 |
| P3；`[A,B]` 预期 `[(A,1),(B,1)]` | 把全列表概括成一组，会得 `[(A,2)]` | 不再追加 A/B 特例；按相邻关系直接实现 P4。新输入排除错误的一组概括，旧例仍由同一关系解释 |

P3 是受限的中间状态，不能进入交付。开发者若从一开始就知道完整归并算法并能迅速实现，这个临时状态没有必要；表格用于说明未知如何缩小，而非要求故意编写已知错误。到 `[A,B]` 时，相邻比较与累积已明确，显明实现优于继续积累特例。下面是 P4，仍保留一个随后可审查的单项分支：

```text
P4(xs):
    if length(xs) == 1: return [(xs[0], 1)]
    groups = new empty list
    for label in xs, in input order:
        if groups is empty or groups.last.label != label:
            append (label, 1) to groups
        else:
            replace groups.last with (label, groups.last.count + 1)
    return groups
```

这里只写入新建的 `groups`，不写 `xs`。空输入不进入循环；单项保持原值；AA 累加当前组；AB 创建第二组。因此旧要求不因选择新例而消失。检查实际实现时还要核对对象别名和具体数据结构，不能把伪代码的所有权假设自动转成语言实现事实。

### 5.4 用剩余区别输入检查概括，而不是追求例子数量

继续由题设选择 `[A,B,A] → [(A,1),(B,1),(A,1)]`。P4 只与最后一组比较，预测会新建末尾 A 组。若有人提出“按标签放进字典再计数”的更短实现，它会把两个 A 合并为一组；这个候选在空输入、单项、AA、AB 上都可能正确，却不能满足本例。已能从题设识别的错误应直接拒绝，无需为了形式先引入错误再等待失败。

`[A,A,B,B,A]` 进一步检查切换组后次数是否从 1 开始；例如新组错误继承前组次数会在此暴露。`[C,C,A] → [(C,2),(A,1)]` 检查允许的第三种标签，防止实现只枚举 A/B；这是既有题设内的补例，没有扩展输入政策。

对输入保持不变，检查方在调用前保存独立值副本，调用后比较原列表的顺序和值；仅令 `before = xs` 指向同一可变对象不能提供这个证据。本例的标签是给定值，独立复制列表即可表达题设；其他可变元素是否需复制属于实际接口另需说明的条件。

有限例子之外，再检查循环关系：每处理一个输入前缀，`groups` 应恰好表示该前缀的连续分组。首项建立一组；后继相同项只增加末组次数，不同项追加一组；没有语句重排、删除或写入输入。这解释了为什么同一结构适用于其他长度和 A/B/C 组合，但不是实际程序已运行或所有实现错误已排除的结论。类型、资源和运行限制在具体实现中核实，不凭空规定最大长度或异常政策。

### 5.5 绿色阶段只整理当前结构

若 P4 及相关检查实际通过，可以审查单项分支：循环自身会对唯一项建立 `(label,1)`，专门分支没有独立行为作用，还迫使维护者检查两个构造结果的位置。P5 只删除这一个分支，保持公开输入输出。空输入、A/B 单项、连续重复和多组例子保护相应要求；再确认输入保持不变。这个变化有明确理由，不需要创建策略类、依赖注入框架或通用分组组件。

如果结构本来已经清楚，就没有必须完成的重构动作。删除或合并检查也单独判断：单项 A/B 虽经过同一分支，仍能说明输出来自输入；AA 与 ABA 说明不同的归并条件。不能只因路径重叠就删除。只有错误发现作用与行为说明都被其他检查保留时，才结合维护成本考虑合并。

假设另一项“整理”把 P5 换成全局字典计数，ABA 的顺序分组要求被破坏。应暂停后续功能变化，保留本次结构差异与失败输入，只缩小或恢复自己刚做的这项修改，再复查既有行为；不回退整个工作区，不覆盖其他独立修改，也不弱化序列断言来保绿。若有人实际要求改为全局计数，那是需求变化，须先确认新要求及受影响预期，不伪装成保持行为的重构。

## 6. 用反馈判断结构是否需要调整

难写、缓慢或容易失效的检查是调查线索，可能来自检查表达，也可能来自生产代码。先说清具体困难，再比较原因：预期不明确，回到行为依据；准备代码重复且与本次行为无关，先整理检查自身；为了观察简单结果不得不经过无关外部操作，调查职责或依赖；必要的真实协作运行较慢，则先判断准备与观察是否能改善，不直接全部换成替身。

检查提示的设计假设仍需当前代码证据支持。例如依赖逐个增加后，应看哪些依赖总是共同使用、是否具有相同生命期，以及能否为它们的共同职责给出有意义的名称；单纯把参数藏进容器不会自动改善设计。新组件还会增加创建与维护责任。本篇纯函数没有这类依赖，不能为了展示书中方法给它增加类层次。

如果写下一项失败检查时就发现结构妨碍表达，可以**先作准备性重构**：确认已有行为与检查基线，明确只改变哪项结构，完成并复查后再添加新行为。无须等新例先通过才允许重构；但已有回归原因未明时，不应同时大改结构。首次缺少行为保护的旧代码仍须先处理观察与修改风险。

### 6.1 测试反馈与抽象设计的分歧

抽象把一项完整职责交给某个函数或组件，使调用方只需理解完成任务所必要的输入、结果和使用条件。这里要判断的是：当前需要的职责是否完整，调用方是否还得自己拼接本应由内部完成的步骤。它不要求增加类，也不由方法数量决定。

Ousterhout 在《A Philosophy of Software Design》§19.2–19.4 赞成增量开发和支持重构的测试，但明确批评 TDD 容易让注意力停在下一项功能通过。他主张在确实需要一个抽象时，集中设计其相互配合的核心功能，而不是随每个测试逐块拼成抽象。Beck 与 GOOS 则把重构和设计反馈放进测试驱动过程，GOOS 还明确允许在下一项测试难写时先改结构。两种设计安排的主张存在分歧；已有重构步骤不能自动证明 Ousterhout 的担心已消失，他对 TDD 的批评也不能改写成 TDD 没有设计活动的事实判断。

本方法据此增加一个有条件的判断：当下一例已经能清楚表达，却仍不清楚完整职责应由谁承担，或者调用方必须重复拼接内部步骤时，单独比较抽象边界。若困难只是当前计算关系不清楚，仍可用第 4 节的策略推进；若当前职责和结构已经清楚，保留现状即可。以下步骤是本方法的工程适配，不是三书共同认可的统一流程。

### 6.2 在当前需要内审视完整职责

1. **写出当前必须共同成立的行为。** 从已确认要求列出输入、完整结果、必须保持的关系和不可省略的失败条件。不要只描述下一项断言；也不要把尚未确认的需求放进核心职责。要求本身有分歧，先停下依赖该分歧的设计判断。
2. **检查调用方必须知道什么。** 沿一次完整使用过程，指出调用方要安排哪些顺序、保存哪些中间状态、重复哪些判断。判断这些知识是否确由调用方负责，还是内部扫描或计算的细节外露。检查实际代码或固定题设，不能只因测试写起来长就判定生产结构有错。
3. **比较能完成同一职责的边界。** 至少把现有方案和一个有具体理由的替代方案放在相同条件下，说明谁承担上述判断和状态。测试用于检查约定行为是否保持；结构选择还须解释调用负担、变化影响与新增维护责任。必要的输入限制和失败责任即使让接口说明变长，也要保留。
4. **把决定带回下一步。** 需要新行为，先固定可观察预期；只调整结构，按已有保护分步修改并复查。若较完整的设计仍需要未知的使用方式才能选择，记录这个未知，先完成不依赖它的工作。当前完整职责已有清楚归属、关键使用条件可说明时即可停止比较，不为猜测的未来用途提前增加功能。

§19.2 允许等某个功能确实需要抽象时再开始设计；§19.4 所说较完整的核心功能，也不能解释为一次实现所有未来变化。抽象审视本身有时间与返工成本。对本篇的小函数，下面的一次责任比较已经足以说明当前选择，不需要独立设计项目。

### 6.3 原创静态比较：结果相同，调用责任不同

仍用第 5.1 节的题设：每次传入完整有限列表，得到完整相邻分组，不修改输入，没有外部状态。假设两个候选都使用 P5 的相邻比较关系，区别只在调用方式：

| 候选 | 调用方需要承担的工作 | 静态判断 |
| --- | --- | --- |
| 一次调用 `groupRuns(xs)` | 提供列表，取得完整结果；函数内部建立并结束本次扫描状态 | 当前输入和结果已完整表达这项职责；相邻比较与累积细节留在函数内部 |
| 逐步调用 `appendLabel`，最后 `finish` | 每次归并先建独立可变状态，按顺序送入各标签，并在全部送入后取结果 | 正确使用时可以得到同样结果，但调用方多承担了状态归属与结束顺序；当前题设没有要求公开这些中间步骤 |

对 `[A,A,B,B,A]`，两者在上述正确使用假设下都预测得到 `[(A,2),(B,2),(A,1)]`。这一个观察即使实际通过，也无法替读者决定应该把哪些步骤放在接口外面。当前应保留一次调用的纯函数：它覆盖本次完整归并职责，调用方不用维护逐步调用协议。这里比较的是责任安排，不是函数比其他形式更快、更可靠的实验结论；第二方案仅用于静态比较，没有实现。

反过来，若后来确认输入必须分批到达，或调用方必须在结束前取得中间结果，“每次给出完整列表”的前提就变了。此时要先明确分批输入、结果时机、状态归属和结束条件，再重新选择接口。现在加入流式协议、持久状态或策略类既不能帮助区分第 5 节的错误概括，也没有当前行为依据。把这些设想记为尚未确认即可。

### 6.4 修缺陷时保留先取得失败证据的例外

Ousterhout 在 §19.4 明确支持修缺陷前先写能触发该缺陷的失败测试，再修复并确认它通过。理由是：先改实现再补检查，检查可能从未触发原问题。这项赞同不消除他对一般 TDD 设计安排的批评。

例如在实际实施中，若已知某实现把相隔的同标签全局累计，而当前约定仍是相邻归并，就先选择 `[A,B,A]`。从题设可独立得出三组 `[(A,1),(B,1),(A,1)]`；全局累计只能给出两组。`[A,A]` 对两种关系都得到一组，不能单独证明检查抓住了这个缺陷。取得目标差异的实际失败后，再修复并复查该例、相关回归及输入保持不变。

若检查未被发现、导入出错或没有观察到这项差异，回到第 3 节修正观察；不能把设施失败当作缺陷已经复现。若环境仍受阻，就留下修复前行为证据缺失的事实；若新例已通过，先调查原问题是否在当前对象和条件下存在，不故意破坏实现补一轮红绿。这里仅推导应当观察到的区别，没有执行检查或修复。

## 7. 结束条件与交付记录

分别判断三个范围。当前例子是否通过，以它的实际调用、输入、预期与结果为据；当前功能是否完成，还要核对全部已确认必要行为与相关回归；更大功能、发布或项目目标按各自要求判断。现有检查全绿、待做列表为空、代码较短或个人有信心，都不能单独替代后两个判断。

对本例，结束前至少核对空输入、三种允许标签、重复次数、组边界、分隔后相同标签、输出顺序和输入保持不变；确认常量标签、固定次数等临时实现已消除，必要的结构整理已处理。范围外输入仍未约定，就明确适用范围，不偷偷采用忽略、转换或抛异常的政策。上文只有静态证据，不能填写“函数已验证完成”。

在已有任务记录中留下：本轮目标与预期依据、下一例为何有区别、采用策略及改变原因、相关检查的实际结果、临时实现与未决项如何处理。若发生需求冲突，保留冲突并只暂停依赖它的工作；若仅环境不可用，分别记录已完成的实现与尚未取得的验证证据。任务授权包含实施时继续完成所需工作，评审任务则交付判断与依据。

本轮若比较过抽象边界，再留下当前完整职责、调用方原先和现在分别承担的步骤、选择依据及重新讨论所需的新事实。一次检查通过的记录不能替代这些设计理由；有具体理由保留原结构也是结果。
