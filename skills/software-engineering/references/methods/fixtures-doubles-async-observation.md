## 1. 从要证明的行为选择检查

需要建立测试状态、替换难以控制的依赖，或等待后台工作的可观察结果时，采用本方法。**夹具**指为本项检查准备的对象、数据、连接和其他资源；**测试替身**指在声明的范围内代替实际依赖的组件；**异步观察**指调用返回后，继续收集与本次工作有关的结果。三者分别解决前提、依赖控制和观察时点的问题，不能互相代替。

先写清本项输入、独立预期、实际经过的组件和观察位置，再选择设施。预期依据及验证范围参见[风险、独立预期与验证层次方法](test-risk-oracles-layers.md)；实现过程中选择下一例参见[反馈步幅与测试驱动设计方法](tdd-feedback-design.md)。沿用当前任务授权，不因检查困难自动改造产品接口、加入取消能力或操作共享环境。

| 当前问题 | 足够的起点 | 尚不能据此说明的事 |
| --- | --- | --- |
| 纯计算是否满足输入与结果关系 | 每项新建必要对象，直接观察结果与输入是否改变 | 持久化、真实依赖及后台调度 |
| 调用方是否正确组织对外请求 | 保留调用方真实逻辑，使用能控制所需条件的最小替身 | 被替换组件的实际行为 |
| 写入、查询、格式或提交是否相容 | 经过相关真实适配器与依赖，明确事务和读取位置 | 未经过的应用配置及完整部署 |
| 后台完成及通知是否可见 | 关联本次动作，建立有效监听或持久结果观察 | 任意消息保证、无副作用或可安全重试 |

若无法观察所需行为，先登记具体缺少的接入与受阻原因；不要把更长的等待或更宽松的断言当作补证据。只需要局部状态的检查，不必加载下文全部持久及异步安排。

## 2. 原创题设与证据边界

以下用一个明确题设的虚构场景贯通三条因果轨迹，**只作静态推演，没有运行示例或 Skill**。预期、可能失败和修正后的结果都是依据题设作出的预测，不是执行日志。

“异步标签批次报告”使用前篇相邻标签计算作为纯计算部分，另加新的异步调用方。纯函数条件不变：有限列表只含 `A/B/C`，按原值判断相等，仅合并相邻相同标签，保持组的输入顺序，空列表得到空列表，不修改输入。范围外输入政策未定。前篇纯函数仍无外部状态，本篇新增外层不改变它的题设。

每项检查先保留一个独占命名范围 `N`，只提交一个全新任务 `J=(N,1)`，不复用 J、不重试。独占意味着已确认不与仍有资源或仍在工作的检查冲突，并记录资源归属；生成一个随机字符串本身不是所有权证据。旧检查与并行检查使用不同范围。调用方在观察期间也不修改输入列表。

提交得到的受理回执只表示请求已接收。正常实现计算后，经工作方的独立事务提交报告，再调用通知接口发送 `done(J)`。报告包含 J 和完整有序的分组列表，提交后保持不变直到本项清理。保存、提交、发送调用和监听收到通知不构成一个原子操作，也没有恰好一次或全局顺序约定。

本虚构检查接入具有三种能力：读取自己范围的已提交报告；确认本次监听已经生效并记录之后收到的事件；接收与 J 关联、带有发生阶段的后台错误。直接读取是检查接入，不是要求产品新增查询接口。通知短暂且不可重放，不保证传输不丢；没有“处理中”查询，也没有自动取消或排空保证。观察接入自身失败必须另报，错误通道也不能保证捕获一切故障。

准备连接 P、工作连接 W、观察连接 O 在此题设中明确不同，W 的事务不参加 P 的事务。读取须从符合已确认可见性条件的新观察中取得已提交值，并绕过进程内对象缓存。这里没有指定数据库产品、隔离级别或驱动；实际条件未核实，就不能把题设当作该技术的保证。

主输入 `[A,A,B,A]` 的预期直接数出为 `[(A,2),(B,1),(A,1)]`。同时检查输入未改变。空输入的预期是 **J 对应的已提交空报告**；“没有找到报告”不等于“报告内容为空”。后续各轨迹保留这些条件。

## 3. 从旧结果污染追到资源责任

### 3.1 旧成功如何使下一项误判

先考虑一份有缺陷的检查：检查甲将主输入报告留在共享表；检查乙只准备输入、忘了提交，却查询“有没有内容等于预期的报告”。它读到甲的旧报告便通过。即使乙生成了新 J，只要查询仍不带 J，错误仍存在。单独运行乙可能找不到报告，甲后运行乙则可能通过，差别来自准备与观察范围。

修正时，把准备、触发和观察连起来：先确认 N 的归属及 J 尚无报告；记录提交的 J 与输入，取得对应受理证据；只读取 J 的已提交报告，并逐组比较标签、次数和顺序。若调用根本未发生，初始无报告就不能满足成功条件。旧 J 和并行 J 即使内容相同也不得满足本项。

这还没有证明所有并行问题已经解决。写入、查找、计数、清理以及唯一性约束中的所有共享可变资源，都须符合本项范围。如果主记录带 N，而全局唯一名称或相关表仍共用固定值，两个检查仍可能碰撞；需要改用可独立命名的关联数据，或选择真正独占的数据库等资源。不能用全表清空来修复共享环境中的污染。

| 准备方式 | 可预测的隔离条件 | 仍需核实的事情 |
| --- | --- | --- |
| 单独运行 | 初始 J 不存在，必要只读数据已就绪 | 不是靠上一项建立对象 |
| 改变顺序 | 每项只依赖自己的可变状态及固定只读参考 | 共享构造器、缓存和全局配置没有保留前项变化 |
| 重复运行 | 本例每轮使用全新 N/J；已停止且清理确认的底层物理资源才可重新分配 | 不复用旧的逻辑 N/J，仍须检查底层资源残留 |
| 并行准备 | 资源所有权、读写与清理范围均不相交 | 数据库全局约束、共享队列及固定资源名是否仍会碰撞 |

这是检查设计的条件分析，没有声称已经按这些顺序执行。帮助函数可以隐藏连接准备等重复操作，但 J、主输入和独立预期应留在检查中。这个小场景不需要通用数据构造框架；复杂对象才考虑构造器，且每项新建或可靠复制，不能让前项设置沿用到后项。

### 3.2 准备中途失败仍有资源责任

在创建资源前建立本项记录：已获准范围、计划资源身份、创建是否确认、所有权依据及清理状态。假设 N 已保留，监听也已安装，随后准备持久连接失败。检查正文尚未开始，但前两项资源已经存在；清理只挂在正文末尾就会漏掉它们。

因此，准备与检查共用一份从最早资源取得时就可访问的记录，每取得一个资源就更新。创建调用超时、结果不明时，保留计划身份和所有权范围，按这些已知信息查明是否创建，不直接重复创建或删除相同名字的他人资源。尚不能证明所有权的对象不得删除，须保留为待核实残留。共享只读参考数据可保留，但要确认它确实不被本项修改，也不由本项清理。

若释放监听失败，仍尝试清理其他互不依赖且有权清理的资源；若一项失败会使后续删除不安全，记录依赖并停止该部分。原始准备或断言失败与清理失败分别保留。框架提供 teardown 或 finally 不等于它一定运行，也不等于进程崩溃后没有残留；下次分配资源前仍须检查范围是否可复用。

### 3.3 外层回滚为何可能没有清理后台写入

假设 P 为检查打开事务，W 在独立事务保存并提交 J 的报告，之后 P 回滚。P 回滚的范围不包含 W 已提交的写入，报告仍可能存在。下一项若重新使用相同 J，污染就重新出现。造成这个反例的是 **独立已提交事务**；不能仅凭“另一连接”推断事务一定独立，也不能由“另一事务”断言一定换了物理连接。

| 选择 | 成立条件与代价 | 对本题设的判断 |
| --- | --- | --- |
| 同一未提交事务内检查后回滚 | 准备、被测动作和观察都确实参加该事务，目标不依赖真实提交效应；需核实框架及数据库行为 | 不能包住已定义的独立 W 提交，也不足以证明提交约束或其他事务可见性 |
| 独立命名数据，真实提交后按归属清理 | 所有相关读写都能限定到 N；需要可靠的停止和残留管理 | 条件成立时保留真实提交路径，成本较小；共享全局约束可能使它不足 |
| 独占数据库或等价独占持久资源 | 需准备、迁移、连接切换和销毁权限与成本 | 可隔开不同运行；同一运行内的多项检查仍要隔离，销毁前也要处理工作生命周期 |

本例先选择满足条件的独立命名数据；若实际数据库无法按 N 隔离相关状态，再比较独占资源。观察报告时经过已提交数据的读取路径，不能只从工作方缓存取回刚写入的对象。写入和读取若共用同一个错误映射，往返相等也可能掩盖错误，因此预期有序组由题设独立给出，必要时通过独立数据访问核对存储表示。是否清空缓存、何种事务能看到提交及 DDL 是否可回滚，按具体技术核实，不在这里设通用答案。

## 4. 选择能回答当前问题的替身

### 4.1 先界定保留的逻辑，再选替换位置

现在只判断调用方是否将 J 与正确报告交给存储，并在存储提交成功后发出对应通知。保留实际调用方及相邻标签计算；用一个最小的存储替身控制提交结果，用一个记录器观察通知调用。它们不证明真实持久化或传输。

| 需要控制或观察的事 | 可用的替身作用 | 不应附加的行为 |
| --- | --- | --- |
| 提供提交成功或明确失败的间接输入 | 存根返回题设给定结果，失败分支给定错误 | 永远成功后宣称失败处理得到检查 |
| 在一组局部操作间保存简化状态 | 内存实现保存 J 与有序列表，供局部读取 | 将内存相等当作真实约束、事务或缓存行为 |
| 观察间接输出 | 记录器保存存储参数与通知参数；必要时使用带明确预期的 mock | 规定所有内部方法的调用顺序和次数 |

本项无需读取内存数据库，使用记录参数并能给出成功或失败结果的存储替身已经足够。成功分支检查交出的 J 和完整分组；失败分支检查错误被传回规定观察位置；要断言该分支没有发出成功通知，还须取得该局部调用路径及其可能委托的通知工作已结束的可靠证据，再核对完整调用记录。尚无这种结束证据时，只能记录“目前未观察到通知”，不能以空记录器证明以后不会发送。该局部结束也不代表整个异步任务及其他写入都已结束。因题设要求提交后通知，需要观察这一个先后条件；没有依据要求调用方使用几个帮助函数、如何缓存局部值，或限定未约定的内部调用次数。

若把“构造报告”抽成一个私有帮助函数，外部结果和规定次序未变，检查应保持有效。若它因内部函数名变化而失败，先调查是否过度约束了实现。反之，移动通知到提交前会破坏本项规定的次序，应由这一条交互观察发现。静态分支预测不能替代实际执行证据，也不能把替身模拟的故障称为真实依赖已经发生的故障。

### 4.2 局部通过后，真实格式仍可能不相容

用同一主输入继续推演。内存替身接受 `J + [(A,2),(B,1),(A,1)]`，因此局部参数符合预期。应用仍要求按 J 保存报告头和全部分组行，每组行包含从 0 开始且表示组顺序的 `position`、`label`、`count`；报告头与分组行在 W 的同一事务一并提交，空列表保留报告头而没有分组行。现在给拟用的虚构关系存储依赖标记版本 V1、配置 C1。C1 的字段说明要求显式提供整数 position，同一 J 内不得重复；V1 的提交说明声称成功返回时，整份报告已经提交且能由满足可见性条件的新观察 O 读到。说明是需要核对的假设依据，还不是该实现确实兑现的证据。以下版本、配置和观察结果都属于原创静态题设，不对应任何真实产品。

需要区别的第一个问题是：省略 position 时，实现确实拒绝，还是自动补入某个值？第二个问题是：未指定顺序的读取按 position 排列，还是按写入先后等其他顺序返回？V1 的提交成功是否真有上述完成含义，也须保留为一项独立假设。应用的预期来自已经定义的有序组和提交要求，不从待检查适配器或其读取函数生成。以下分支比较同一 J 的准备状态，属于互斥的静态推演；实际分别检查时，每项仍须使用全新 N/J，不重复提交同一 J，也不靠重试消除差异。

先设计最小的字段学习检查：在已确认没有 J 报告的状态下，直接向计划使用的依赖版本与配置提交缺少 position 的一组行，保留依赖原始返回。若它以缺字段原因拒绝，就支持“这项输入要求显式位置”，反对“这项输入自动补齐”；若它接受，则与 C1 的字段说明不符，应查明配置或实现差别。仅有拒绝还不能证明没有副作用，需要按已确认的观察条件分别查看 J 的报告头和行。连接失败或无法取得可信观察只说明本项受阻；即使预期拒绝，也不能把任意错误都算作假设成立。这一项没有经过本应用适配器，也没有检查三组的完整顺序。

再用同一主输入的三组作区别顺序的学习设计。逻辑位置仍是 `(0,A,2)、(1,B,1)、(2,A,1)`，只将送入依赖的行次序设为 2、0、1；这样，按位置读取应得到原定三组，按写入先后读取则会先出现 `(A,1)`。不能按 label 排序或把两个 A 组合并，那会改变相邻分组的含义。为继续这条静态轨迹，设 V1 确实拒绝缺字段；完整位置行提交后，新观察 O 取得同一 J 的报告头及三个原始行，默认返回位置为 2、0、1。观察者核对原始 position、label、count，不使用待验证适配器的反向转换。这个结果否定了“这次默认读取已按位置排列”，却不能仅凭一份样本证明所有读取都遵守写入顺序，也没有证明所有提交和故障分支均正确。

这份差异可以导向一个有依据的适配，但先要确认能取得同一次提交的完整行集合，且位置含义与应用一致。条件成立时，适配器从应用已经排好的分组列表明确写入 0、1、2，读取时核对 J、报告头、字段和位置的唯一连续性，再按 position 还原三组顺序。本项检查另按独立预期核对确有三个组；位置连续本身不能排除末尾行缺失，完整行集合仍需上述依赖保证和相应证据。原先故意遗漏 position 的错误适配器会在上述拒绝条件下暴露；只补写字段还不够，还要经过本适配器与实际依赖，独立查看实际保存的三个位置，并核对应用读回的完整顺序。否则写入与读取同时丢掉顺序，往返相等仍可能掩盖错误。空输入也须按题设保留已提交报告头，不能因零行而译成无报告。这里说明待取得的证据及预测结果，没有执行这段适配。

同样的乱序观察也可能使适配方案停止：如果依赖无法提供完整的同次提交行集合，或者位置缺失后已无法辨认两个 A 组原来的先后，排序和类型转换都不能补回这些事实。此时不能为了让比较通过而改用无序集合，或悄悄把缺字段补成 0。要保持原有有序、完整报告承诺，就补齐缺少的能力或停止使用该依赖；若业务愿意接受更弱的结果，则先重谈明确的输出与完成要求，必要时版本化接口并协调消费者。模块方法中的[接口约定与行为替换](module-responsibilities-contracts.md#72-签名相同不等于可以替换)给出同一原则，包装本身不能证明含义相等。

学习检查只核对依赖假设，适配器检查才经过本应用的转换。即使后者有证据，还须按当前目标确认实际构建的应用确实选择了该适配器、V1/C1 及独立工作事务 W，再从符合条件的新观察 O 核对 J 的提交结果；单独构造正确适配器不能排除应用连接到别的实现。若为快速回归保留 fake，它也应有维护相关行为的自身检查；**若采用**同一组公开接口检查分别对照实际实现与 fake，须明确两者模拟的是哪一个边界、共享哪些输入，以及预期从何而来。两侧共同接受同一个错误预期，或都忽略 position，并不会增加顺序证据。这种对照是一种办法，不是每项任务都必须加跑的第四个步骤。

沿同一轨迹再设一次虚构升级：V2 保留字段形状、position 含义及 C1 的字段限制，却把同名提交调用的成功返回改为“已受理，稍后提交”。这是本次题设唯一新增的依赖差异。于是，在调用刚成功返回时，O 尚未找到 J 的报告，后来才读到完整报告，是 V2 允许的时序；按 V1 的完成说明，这个时点本应已有已提交结果。观察必须仍满足已确认的可见性条件，否则“没读到”还可能是观察接入问题。即使某次 V2 返回时报告恰好已出现，也不能据此恢复“每次返回均已提交”的旧保证。

这次升级首先使“依赖成功返回即已提交”这一假设及依赖它的旧通过结果失去对 V2 的证明力。fake 的处置取决于它代替谁：模拟 V2 原始依赖的 fake 应表达受理与实际提交的区别，不能仍在成功返回时立刻伪造已提交报告；模拟应用的“提交已完成”接口的替身，则仍须按应用原约定控制成功与失败，不能跟着 V2 悄悄削弱含义。前一种需要按新依赖假设维护，后一种的局部通过依然不能证明 V2 适配已经完成。

适配器只有取得能关联到本次 J、明确证明实际提交的可靠完成证据，才可继续兑现应用原来的成功含义；还须以明确的 V2 完成约定及独立核对的完成含义为依据，核对该证据的来源、失败路径和所用配置。单次读到了值，或事件里带有 done 字样，只支持各自观察到的事实；不能单凭它们推出提交、持久保存或故障后的保留保证。既有检查接入 O 不是默认提供给产品的查询能力，不能直接把它移入适配器来填补缺口，也不能用固定延时或刚写入的本机对象冒充完成证据。若已有、获准使用的依赖能力能够提供所需确认，可在确认后返回应用原有成功结果，并补查这条实际连接；若没有，就不能宣布适配可靠。应暂停按旧含义使用 V2，或重谈一个明确区分“已受理”与“已提交”的新接口。选择后者会影响消费者的状态处理和成功通知时点，需协调其变更；签名未变不是消费者无需变化的理由。

因此，保留旧应用承诺的消费者仍只能在提交已证实后发送 `done(J)`，不能把 V2 的受理回执当完成。若确认尚缺，它应保留未确定的结果并按已有错误、等待和资源责任处置；不能直接当作没有副作用，也不能自动重试或删除仍可能被写入的数据。下文的有界观察和可靠停止后清理仍适用，升级没有产生新的取消、排空或重放保证。

旧证据也要逐项判断。题设没有改变相邻归并、主输入的三个预期组及应用的 position 约定，对这些不变要求的独立预期和合适的局部证据可以继续使用。V1 的字段、持久和装配检查保留为 V1/C1 的历史结果，不能自动认证 V2；其中的区别输入和独立预期可复用为新版本的检查设计，涉及“返回即提交”的假设和相应 fake 必须调整。已有且仍适用的证据可以复用，只补当前变化和目标留下的缺口，不要求每次重做学习、适配、装配与 fake 对照。

把这套设计用于实际任务时，本地第三方库和受控实例须核对实际版本、配置及连接；第三方测试服务还须确认可用范围、权限、费用、数据、副作用和清理条件；收费或生产服务的快速自动回归可以在相应边界隔离。隔离后尚缺的真实行为事实仍是待定，不由书籍授权直连、付费或录制。没有获准环境或可靠观察，就记录缺少什么，不能把放宽 fake 当作补证据。若目标只是纯计算，本节的持久路径无需加入；若目标包含保存，则取得该目标尚缺的真实持久及应用连接证据。

“报告内容符合预期”“应用调用通知接口”“检查方收到通知”也要分开。存储参数记录只能证明本次调用给了什么；实际持久读取才能支持已保存内容；通知记录器只能证明应用发出了怎样的调用；经过实际接收路径的匹配记录才支持检查方收到本次通知。要证明三项，就分别取得三项所需观察，不能拿一个 done 事件替代正确报告。

## 5. 从监听竞态建立异步观察

### 5.1 先触发再监听会失去什么

假设报告保存很快：检查提交 J，工作方提交报告并发送 done，检查随后才安装监听。题设通知不可重放，事件没有进入本项记录器。随后等待空历史，不论等多久都不能恢复这个已经错过的事件；报告可能已经正确，通知接收的检查仍没有证据。

修正为先建立本项监听并取得 **监听已生效** 的明确确认，再提交 J。订阅函数返回只是调用返回，除非接口明确保证生效，否则不足以满足此前提。安装失败或一直未确认时，将接入记为受阻，不开始声称能完整观察该次通知的检查。事件记录器须从生效后就保存收到的事件，等待开始时先查已有记录，避免事件已被接收但早于等待而再次漏掉。

这只消除了上述安装与等待竞态，没有证明传输不丢。若报告读取正确而通知历史为空，报告目标可以取得自己的证据，通知接收目标仍未得到证明。若实际系统没有生效信号，可在已授权范围内选择有依据的重放起点或持久状态观察；两者都不存在时记录接入缺口，不能偷偷新增产品查询、重放或订阅保证。

### 5.2 轮询为什么可能看不到中间变化

另一份错误检查轮询一个临时“刚收到通知”标记：第一次采样时为否，两次采样之间标记变为是，又被下一个事件覆盖，第二次采样仍为否。提高采样频率不能保证看到任意短暂变化，也会增加负载。

本题设中，要判断报告完成，可以读取 J 对应且保留到清理时的已提交报告；要判断收到通知，则检查已生效监听的 J 事件历史。不能要求一个短暂状态替两项目标作证。两次后续操作之间需要稳定观察时，先取得当前目标所需结果再触发下一动作，避免自己覆盖待观察的变化。

同样，当前没有通知不表示某个动作永远不会发出通知。若用后续标记证明前一动作“无效果”，必须已有标记不会超越前一动作完成的保证，且它不改变待判断结果；仅发送顺序相同不够。本题设没有这种完成顺序保证，因此不使用该证明方式，也不因此加入新操作或消息协议。

### 5.3 成功、失败和未知各自如何结束等待

开始前确定本项究竟判断报告、通知，还是两者；确定固定截止点 D、总预算 B 与采样间隔 I。预算根据实际环境已知延迟、反馈成本及观察负载选择；本静态推演没有测量值，不编造毫秒阈值。使用单调计时控制等待，各次观察和阻塞调用都受剩余预算限制，不能每轮重新得到完整 B。通知准备阶段也应有自己的明确上限，不允许在正式等待前无限阻塞。

| 当前证据 | 可以作出的判断 | 等待与后续处理 |
| --- | --- | --- |
| 没有提交记录，或只有其他 J 的结果 | 本项没有成立的触发或完成证据 | 纠正检查；不得接受旧成功 |
| 只有本次受理回执 | 请求已接收，是否处理未知 | 在预算内继续观察；不制造“处理中”事实 |
| 读到本次已提交报告且完整内容符合预期 | 报告目标取得证据 | 若本项目标还含通知，继续等待对应接收证据 |
| 收到本次 done，但尚未读到报告 | 接收目标有相关证据，报告目标仍缺失 | 核对可见性和观察接入，在剩余预算内继续取得报告证据 |
| 已可靠读到本次已提交且不再变化的报告，内容不符 | 报告目标已有确定的不符证据 | 结束成功等待，保留差异并处理工作生命周期；不再等待到超时后改称未知 |
| 对 J 的确证错误指出保存失败或通知发送失败 | 相应阶段已有失败证据；其他阶段按已有观察说明 | 结束该目标的成功等待，保留错误及已有报告，转入生命周期处置 |
| 读取、监听或错误通道自身失败 | 检查受阻，不能据此认定业务失败 | 保存接入错误与最后可信观察，停止无意义轮询 |
| 到 D 仍缺所需证据 | 期限内未证实该目标，业务结果可能未知 | 停止本次等待，不能推出无副作用或允许重试 |

成功条件满足即结束该项目标的等待；后台错误一旦确证并关联到 J，及时传回检查方，不吞掉后只剩超时。每次记录本次 J、最后可信样本、观察时间、已知阶段和错误，避免只显示“等待失败”。如果保存已经提交而通知失败，应分别保留“报告已有证据、通知发送失败”；若提交响应丢失，只能记提交结果未知，除非另有可核实证据。

本例没有业务时钟。若另一项检查要验证定时触发，控制业务时间、推进调度器和控制等待期限是三件事：推进虚构时间不自动运行真实后台工作，直接触发处理函数也不证明真实调度路径。根据当前目标选择，留下未经过的真实触发证据，不为本例添加定时任务。

## 6. 将等待结果与清理结果分开

延续超时分支：检查在 D 停止等待并立刻删除 N 的数据；W 此时仍在计算，随后提交 J 的报告，数据又出现。finally 已执行也没有防住迟到写入。更早发一个取消请求同样不够，取消被受理并不是工作已终止的证据。

清理前，必须确认本项可能写入的准备及后台工作已经终止，且没有本项仍在排队或委托中的后续写入。可采用当前系统已有且含义可靠的结束确认、等待受控工作退出或排空机制；具体机制要覆盖相应工作，不能以某个线程退出推断其他进程也停止。本题设没有自动保证，因此不能凭空写一个“取消并等待”步骤后宣布安全。

无法确认时，隔离 N，保留它的所有权、J、已知工作状态及残留记录，禁止后续检查复用；若现有设施不能隔离共享资源，就阻止依赖该资源的后续检查，继续不依赖它的工作。隔离只防止把本项残留误当新结果，不等于消灭后台负载或解除资源责任；仍须在授权范围内查明工作停止并完成清理。

取得可靠停止证据后，按真实依赖关系释放本项资源，并核对已拥有的数据与监听是否移除。已提交报告、通知发送任务和检查方停止等待可以处在不同状态。报告成功并不保证通知工作停止；关闭监听也不代表发送方不再工作。清理失败时保留原始失败和新增错误，不擦掉诊断依据，也不把资源分配给下一项。

原书分别讨论开始前建立已知状态、保留诊断数据和结束后的释放。实际选择要兼顾隔离与诊断：在独占范围内可保留失败现场，但标明归属与不可复用；重新使用前先确认工作停止并处理残留。不得把书中的开始前清表建议推广为删除共享环境中所有数据。

## 7. 结束条件与交付内容

结束本次工程任务时，给出范围足够小的一份记录，分别说明：

- **行为判断**：本次对象、输入与独立预期，实际经过的组件，取得的报告、发送或接收证据，以及结论成立的范围。
- **检查状态**：实际执行、静态推演、环境受阻和结果未知分别标明；保留关键输入、最后可信观察及错误，不把环境故障直接列为产品缺陷。
- **资源状态**：本项拥有的资源、工作终止证据、清理结果及不能复用的残留；产品结果成功也不能省略这一项。
- **仍需证据**：被替换的真实依赖、未经过的应用配置、调度和传输路径，以及当前任务需要但尚未取得的观察。

实际完成条件包括预期观察成立、必要真实连接得到适当检查、等待有明确终止、异常与资源责任有明确处置。不能只凭“全绿”判断，也不要为满足这份记录建立庞大通用测试框架。即使文档静态审查通过，也只表示这套指导在声明范围内可复查；它不等于本 Skill 的行为评估或真实工程效果已经通过。
