## 1. 何时使用

已经知道某个行为应当怎样发生，但还不清楚应检查哪些输入、运行哪些组件，或者现有检查全部通过却不足以支持目标结论时，使用本方法。**验证层次在这里指一项检查实际包含的实现和连接范围**；标签相同的两项检查，可能提供完全不同的证据。

先取得当前任务、有效要求及版本、改动位置、相关依赖和已有检查。未知实现写为待核实，不从书籍推断当前项目必有某个缺陷。预期仍有歧义时，先用[需求澄清方法](requirements-language-behavior.md)处理会改变判断的事项；要求或版本发生变化时，结合[验收依据与变更影响方法](acceptance-evidence-change-impact.md)判断旧预期与旧结果能否继续使用。

本方法帮助选择检查并说明证据范围。是否执行、修改系统或发布，沿用当前任务授权；分析检查方案不产生新的操作授权。纯文字修改若不改变含义、操作或外部引用，核对文字和必要链接即可，不必展开全部步骤。

## 2. 从具体失败选择检查责任

### 2.1 写清可能错在哪里

先从本次变化提出可核实的失败假设：**在什么条件下，哪段判断、转换或连接可能产生什么错误，影响谁的什么结果**。例如“截止比较把等于也算允许”与“应用未使用实际存储适配器”是不同假设；“存在测试风险”没有指出检查对象。

按需要结合以下事实决定先检查什么：

- **后果：** 错误影响的数据、参与者和业务承诺，能否察觉及恢复；严重后果不能仅因难以准备环境而忽略。
- **变化与传播：** 改动是否经过这段逻辑或连接，是否有多个调用者、版本或环境；一段代码未修改也可能收到改变后的输入。
- **已有证据与未知：** 现有检查实际运行到哪里，其输入是否能区别该错误；没有证据不等于错误已经存在，也不等于风险很低。
- **获得证据的代价：** 数据和环境准备、反馈等待、失败定位及后续维护。先采用能看到目标错误的较小范围，再为关键连接补证据。

没有发生频次和后果估算依据时，用具体比较说明优先级，不编造概率、分数或固定检查比例。保留尚未处理的关键假设及原因；清单只记录已经识别的问题，条目为空不能证明没有遗漏。

### 2.2 将假设变成检查责任

为重要假设回答五个问题：什么输入使正确与错误行为不同；正确结果依据什么；必须运行到哪个位置；在哪里观察差别；即使通过还排除不了什么。已有检查能回答这些问题时，先复用其定义；不要只因层次名称不同再抄一份相同断言。

同一业务事实在不同范围出现可以有价值：局部检查证明截止比较，入口到存储的检查证明规则、连接和状态保存能协作。两者虽然都涉及取消，却承担不同责任。若两项检查包含相同实现、相同故障位置和相同观察，只增加运行与维护成本，应考虑合并；判断重复不能只比较用例名称或输入。

## 3. 分开建立预期与观察方式

先回答“正确结果是什么”，再回答“怎样知道实际发生了它”。预期应能回查到已确认要求、有效外部约定或明确标注的虚构题设；由简明推导、经核对的参考数据或独立参考模型得到，说明假设和局限。直接调用待检查函数生成预期，或复制实现中的复杂算法，可能让同一个错误同时出现在结果两侧。

可读的表达式不自动成为独立预期，硬编码常量也不自动正确。让读者能复查输入与结果的关系，并挑一个具体错误推演差别。例如要求 `t < D`，取 `t = D`：正确比较为假，错误的 `t <= D` 为真；只取远早于截止的时刻，两者都为真，无法排除这个错误。这个输入只能区别相应比较，不能证明受理时间来源、活动版本或保存动作正确。

行覆盖率记录统计范围内哪些代码行在检查中被执行；解释数字时，须同时说明覆盖类型、分母和包含的检查。它可以提示尚未执行的代码，却不能证明已执行行的结果被有效断言。沿用上面的截止比较，即使 D 前输入执行了判断行，也仍不能区别 `<` 与 `<=`；检查选择还要回到要保护的行为、独立预期和区别输入。不要以任意覆盖率门槛替代这些证据，也不要因覆盖有局限而弃用它提供的空白线索。

同时列出允许变化、不得改变的状态以及可见结果。成功响应不能代替持久变化；拒绝响应不能证明没有副作用。使用关系或不变条件作为预期时，说明它遗漏的错误，例如总名额不变仍可能把名额记到错误申请。

**预期推导独立与检查之间独立是两个要求。** 前者防止结果与预期重复同一实现错误；后者要求一项检查不依赖另一项先执行，也不受其遗留可变状态干扰。它们分别需要依据核对和状态准备，不能用其中一个代替另一个。

## 4. 按实际包含范围选择检查

先圈出需要验证的行为和连接，再决定保留哪些实际组件、替换哪些依赖，以及观察什么。替身是为当前检查代替某个依赖的对象或服务；如果把需要证明的判断或连接也替换掉，就失去了对应证据。

| 常见称呼 | 实际要说明的范围 | 通过后仍可能缺少什么 |
| --- | --- | --- |
| 局部检查 | 一个函数、对象或小组协作中保留的实际逻辑；外部依赖是否被替换 | 请求转换、应用连接、实际存储及外部系统行为 |
| 接口约定检查 | 哪一方应接收、返回或拒绝什么；适用版本、格式和含义；本项实际运行哪一方或双方 | 只运行一方不能证明另一方符合约定；共享同一错误定义不能提供独立预期 |
| 集成检查 | 哪些实际组件经过哪条真实连接交互，使用什么版本和配置；其余部分是否被替换 | 未经过的应用装配、用户操作、其他环境或依赖 |
| 端到端检查 | 从哪个用户或系统入口到哪个可观察终点，经过哪些实际组件，环境与外部替换是什么 | 未包含的第三方、未选输入、并发、规模和其他部署环境 |

接口约定是检查目的，可以通过局部、集成或更大范围实现，**不是夹在它们之间的固定一层**。局部检查不要求每个函数各写一项；集成检查也可能用替身观察应用回调，只要需要证明的真实连接仍在其中。端到端检查须声明两端，不默认等于生产验证。

对不熟悉的外部组件，可以用小范围学习检查核对将要依赖的具体行为，记录所用版本和配置。随后再检查应用的实际适配与连接；一个外部 API 的检查通过不证明应用已使用它。替身的假设须与实际组件证据相符，文档或历史通过结果只支持各自适用范围。

## 5. 原创推演：同一次取消需要哪些证据

以下为原创静态推演，未执行程序或 Skill。它沿用前篇“青岚社区工作坊”，并明确新增用于比较检查范围的虚构结构；没有声称存在这样的实际系统。

### 5.1 固定业务条件与新增结构

沿用的条件：活动容量为 2；考察某人某场活动的一份有效申请，格式、身份与访问权已核实，不据此推导全系统唯一申请政策。收到申请不占名额，获位才占名额；取消参与与释放原占名额分别观察。`t` 始终是**系统受理取消事件时刻**，不是收到请求或客户端点击的时刻。

名单未交付且已获位时，V1 在 `t < S` 接受取消，V2 在 `t < D` 接受取消，其中 `D < S`；接受则取消参与并释放原占名额一次，截止起拒绝并保留参与与占位。V2 只用于采用新规则新建的活动，已有活动保留 V1。固定同一天、同一时区的 `S = 20:00`、`D = 19:50`，不涉及再次调整活动时间。

本篇选择 V2 的上述分支。名单已交付时的开始前政策（包括 `U-LIST` 及申请不在名单内的情况）、未获位申请的撤回、竞争选择、重复请求、结果查询与恢复方式以及“立即”的可测时限仍未决定。释放生效后名额即可供后续分配，不以调用者收到响应为条件；本例不推断竞争和重复取消规则。

**新增虚构结构：** 用户页面将活动与申请标识交给请求处理器；处理器调用取消服务；服务读取活动版本和状态，以受理时刻调用截止判断，再经存储适配器保存结果。示例的同步接口在完成这次处理后返回 `accepted` 或 `refused`；页面据此显示结果。只为说明观察范围，另设检查方能经独立连接读取同一存储记录，绕过应用内存缓存。这是检查接入题设，不是给用户补定结果查询功能。存储引擎、并发保证及异常恢复均未给定。

### 5.2 先建立能区分错误的输入

每项检查各自建立“V2、名单未交付、目标申请已获位且原占名额存在”的初始状态，不接续上一项的处理结果。预期只由上面的时间比较和状态规则推导。

| 受理时刻 | 独立推导的业务预期 | 用来区分的错误及观察限制 |
| --- | --- | --- |
| `19:49:59` | 接受；目标申请参与取消，其原占名额释放一次 | 可识别允许分支未保存、存错申请等；判断函数返回允许还不能证明保存发生 |
| `19:50:00` | 恰好 D，拒绝；参与和原占名额保持 | `t <= D` 会接受；需分别观察拒绝原因与状态，拒绝码本身不排除错误释放 |
| `19:59:59` | D 后，拒绝且保持状态 | 错把 V2 按 S 判断会接受；用独立建立的 V1 活动对照应接受，防止把全部活动改成 V2 |

“释放一次”指本次单次操作释放其原占名额，不检验重复请求是否幂等。数据记录中的状态与界面文字是不同观察，不能因一项符合预期就填上其他项通过。

### 5.3 同一行为的四种检查怎样分工

以下都是候选检查设计。它们采用相同业务预期，但刻意包含不同实现；表中的错误是人为设想的错误位置，不是执行发现。

| 候选检查及实际包含范围 | 替换或排除部分、观察方式 | 可区别的具体错误、盲区与代价 |
| --- | --- | --- |
| 局部：实际截止判断，显式提供 V2、D、t | 不运行请求处理器、服务或存储；直接看允许/拒绝结果 | `t = D` 区别 `<` 与 `<=`；反馈与定位集中。看不到时间取错、版本读错或状态保存 |
| 接口约定：实际请求处理器，用可记录调用的取消服务替身返回预先给定的 `refused` | 检查活动和申请标识传给谁、返回值与字段含义；按独立接口约定判定，排除服务内部和保存 | 可区别目标标识传错或把 `refused` 映射成 `accepted`。还须核对页面的实际解释；本项不证明真实服务在 D 会拒绝。替身随接口变化需维护 |
| 集成：应用实际入口、处理器、取消服务及存储适配器，由应用装配创建；操作实际存储 | 用户页面不运行；独立连接读目标申请与原占名额，核对初始与最终状态 | 能区别装配指向错误适配器、保存错误对象或遗漏状态更新。前提是观察同一存储实例、对象和操作完成点；环境和数据准备更多，不能证明页面接线正确 |
| 端到端：实际页面操作，经上述应用到存储，再观察页面结果及存储事实 | 本题入口为页面取消动作，终点为该次结果展示与相应状态；本题没有第三方参与，不能外推到其他系统 | 能区别按钮传错申请、页面把拒绝显示成成功等用户可见错误。运行面更大，失败需逐段定位；少量通过不能覆盖全部边界和版本 |

接口检查采用的虚构约定是：输入准确指向该活动与申请；服务结果 `refused` 必须被表达为拒绝，不能反转。若实际项目没有确认的字段或语义，先补足约定，不能让实现和替身一起猜出同一答案。本例也不要求为了接口检查造一套生产中不存在的网络服务。

### 5.4 替身通过而应用连接仍然错误

设取消服务的局部协作检查注入内存替身，`19:49:59` 时参与和占位在内存中都正确变化。另有适配器检查直接创建实际存储适配器，保存也正确。两组均可能通过，但若应用装配仍注入内存实现，真实入口返回 `accepted` 后持久记录仍为已获位，原占名额仍被占用。

缺失的是**应用实际创建的服务到实际存储的连接**。在两个已有检查中再增加截止输入，都不会运行到这条连接。应补表中的应用集成检查：从实际入口触发，核对它使用的存储实例，再经独立连接观察原记录。若“独立读”仍读服务内部同一内存对象，错误仍会被遮住。该集成检查足以涉及这个错误位置；是否还增加页面检查，取决于本次是否需要证明页面传参和显示，不能只因发现连接风险就强制扩大到所有用户操作。

这段推演并不保证未来一定能观察到故障。实际建立检查时还需明确提交完成点、读取可见性及缓存影响；这些事实不足时，保留接入受阻或结果不确定，不能把读不到变化直接归因业务判断错误。

### 5.5 两种改动，选择不同检查

**只改截止比较。** 已核实改动只在判断逻辑，调用关系、时间与版本输入来源、接口及存储连接未变，且已有检查定义覆盖这些连接时，优先补 D 前、恰好 D、D 后及 V1 保留条件的局部检查。复用现有集成与页面检查的定义，按受影响范围和项目既定要求取得当前版本结果；不必为三个边界各新增一条完整页面流程。未证明旧结果仍适用时，保留历史通过记录，但不能拿它给新构建填写通过。

**改应用装配或存储配置。** 即使截止逻辑没有变化，也优先检查实际应用连接到哪里，以及独立读能否看到正确对象的变化。已有局部边界检查不需因这次连接变化复制一遍。若配置同时改变页面使用的入口，则追加相应页面路径；如果只是内部存储选择，先取得应用集成证据。严重状态错误的后果和未经过的连接，使这项证据比更多相同局部断言更关键；此处没有发生概率或耗时测量。

两种选择都保留未覆盖项。选择较小范围是因为它能看到目标错误，不能因为方便准备就忽略必须证明的连接。

## 6. 检查本身怎样造成误判

### 6.1 上一项遗留状态遮住下一项动作

仍在虚构的允许取消分支：检查 A 留下目标申请“参与已取消、原占名额已释放”。检查 B 原本要验证从已获位到取消的变化，却复用 A 的记录，既未重建前提，也未核对初始状态；由于错误的检查接入，它没有发出取消动作，最后只读到已取消、已释放，于是可能给出通过。

这里先暴露的是检查的准备和触发缺口，不能据此判断产品正确或错误。B 应自行建立并核对目标申请的初始状态，确认该次动作确已触发，观察同一对象的结果。使用独立记录或受控重建状态可以减少干扰；共享只读数据并不必然有问题。还需按环境明确失败后的残留识别、并行资源归属与清理责任，不能无条件删除所有共享数据。本节只定位缺失责任，完整夹具与异常清理方法另行展开。

### 6.2 异步操作尚未执行，却读到了旧结果

另设一个**虚构异步观察变体**，不将它当作同步主例已经具备的能力：入口将一份新的取消请求放入待处理队列，工作进程尚未取出；存储中另一个申请早已有取消成功记录。检查若只看“存在成功记录”，或者把“已收到请求”当成完成，就可能在本次动作没有执行时通过。

至少需要把观察对应到本次操作和目标对象，区别已收到、完成及结果未知，并核对本次状态变化；只有存在相应证据时才区分正在处理，不为检查强制新增中间进度能力。操作关联和完成信号的具体实现尚未给定，不能凭空补一个结果查询接口。固定等待几秒不能替代完成事实，超时也不能证明没有副作用；重复提交和恢复政策未决时不推断可以安全重试。完整的监听、轮询、等待上限、错误传播和清理方案不由这段短例完成。

### 6.3 重跑和停用不能改写已经取得的结果

反复进入开发反馈的检查，除了写出和运行，还需要有人处理失败。慢、脆弱或不稳定的检查会增加等待与诊断成本，并削弱人们对结果的信任。选择检查时，应同时考虑能否及时取得可信结果以及持续维护的投入；并行或自动重跑消耗计算资源，不能代替不稳定原因的处理。

出现失败时，保留原始失败和相应版本、输入、环境与观察；同一版本的每次重跑另记条件和结果，不能只留下最后一次成功。先区分产品行为不符、检查本身错误和环境问题，尚不能归因时保留不确定性。不稳定也可能来自产品自身的竞争等缺陷；偶然通过不能证明修复，更不能抹去此前观察到的失败。

确实不能立即修复且已有批准例外时，暂时停用须保留原因、受影响范围、负责人及恢复判据，并继续跟踪。报告分别保存实际通过、已知失败和禁用状态：禁用项没有提供本次执行证据，已知失败仍是未解决问题，汇总为绿色不能改写它们。恢复检查应取得与修复对象、条件和判据相符的证据；严重产品问题不会因已有工单或暂时停用而解除阻断。

## 7. 交付与停止条件

在已有项目记录中留下最少但可复查的内容：失败假设及优先理由；依据与区别输入；实际包含的组件和连接、替换部分及观察；准备条件和未覆盖项。已有检查可复用时直接引用，不新建竞争性清单。

分别记录“预期已明确”“检查接入已准备”“已执行且可判断”与“未执行、受阻或不确定”。只有取得相应版本、条件和观察结果，才能登记该范围通过；方法文档、结构检查和评审通过均不能代替运行证据。

当其他人能按这些信息知道检查什么、为什么选这个范围、怎样区别目标错误，以及尚不能得出什么结论时，检查选择分析可以结束。若任务还包含实施或验证，则继续完成已授权工作；关键前提未知时，只停止依赖它的部分，继续能独立完成的工作。不要因为采用本方法就要求所有改动遍历四个名称。
