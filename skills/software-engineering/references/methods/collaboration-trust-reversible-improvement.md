## 1. 从工作问题确定观察范围

协作改进从具体工作受阻开始：什么成果没能按所需条件交付，在哪一步等待或反复切换，必要支持是否有人接手，投入和负担是否持续增加。先分清事实、可能解释和未知，再决定需要改变什么。不能根据书籍、等待、沉默、不同意见或不能加班给个人判断动机。来源 E1–E3、T1–T5；具体分析为适配 A1。

| 需要取得的输入 | 它影响的判断 |
|---|---|
| 成果、接收者和必要检查 | 工作是否真正完成，哪些条件不能为了加快而删去 |
| 请求、输入和预期版本、实际等待步骤 | 等待的是新决定、必要核查，还是已经明确范围内的重复确认 |
| 当前决定范围、人员能力和可用时间 | 有无合格且获授权的人，能够在所需时段处理 |
| 任务类型、普通问询和紧急支持 | 连续思考与及时协作分别需要怎样的安排 |
| 实际投入、返工、学习和交接 | 改善是否只是把成本转给其他人或以后 |
| 决定人、期限和可恢复安排 | 当前能提出什么、谁能批准、何时停止 |

单次责任不清，可能只需补充输入并确认接手；持续发生的支持冲突或审批等待，才需要展开有期限的改进。不要为了使用本方法给简单请求建立整套团队制度。涉及估计、人员窗口和预案时，结合[成果、依赖、估计与预案方法](work-dependencies-estimates-contingencies.md)。

测量应回答一个需要决定的问题。例如，“模板确认是否仍在等待一次已有范围内的重复决定”需要版本、授权与等待记录；“新版本交付后用户是否更容易取得正确结果”还需要交付事件和用户操作的分别观察。代码行数、提交数、速度点或忙碌程度都不能单独回答这两个问题。Accelerate 第2章也提醒读者，局部活动量可能诱导偏离共同结果的行为；速度点可以服务本团队容量计划，不能直接成为跨团队或个人优劣的尺度。来源 ACC-SRC-01。

内部预览任务按本题完成条件观察即可，不能为了凑齐指标把它改称生产部署。只有当前问题确实涉及软件交付过程，才使用第5.4–5.6节的补充判断；对简单协作请求不增加无用采集。

### 1.1 原创题设

下文“展签内部预览协作安排”完全虚构，只作静态推导。请求记录、支持日历、指标比较和学习分支是不同的对照，不能拼成同一次真实经历，也不表示它们在统计上独立。没有执行人员试验、软件或 Skill 行为，所有数值与授权均需在实际应用时重新核实。

目标是给八项虚构展签请求生成对应输入版本的内部预览。文本和模板须在已批准范围内；内容、顺序及显示结果要经独立检查，并交给内部接收者。新的内容要求须先获得内容负责角色的决定及独立预期。仅生成文件或发送回执不算完成，内部预览通过也不产生外部发布权限。

甲负责实现与模板选择，能够处理需要实现知识的紧急请求；乙负责独立检查，可在有空闲时备援。丙当前已具备普通支持受理、分类及升级所需能力，超出已知类别要请求帮助。丁负责题设内的范围和协作安排，新的内容要求仍由内容负责角色决定。下午培训不反过来证明丙上午已经具备其他能力。

现行安排 R0 允许制作未交付候选供检查；在内部接收者使用前，模板选择仍须丁确认。乙的独立检查一直保留。先依据这一实际安排观察问题，不能在提议生效前自行按新范围操作。

## 2. 用竞争解释辨认等待和信任问题

当成员承担结果责任，却连已批准范围内的不同做法也不能选择时，反复逐项替代判断可能削弱自主和反馈。这个机制值得检查；它不能单独证明负责人不信任某人，也不能证明所有审批有害。来源 T1–T2、T6。

### 2.1 同样是等待，原因可能不同

| 记录 | 可核实事实 | 目前能支持的判断 |
|---|---|---|
| Q1 | 文本 v4、模板 A/B 均已批准，只作内部预览；09:10 就绪，09:30 独立检查通过并向丁请求确认，11:30 得到答复 | 等待丁确认 120 分钟；还需核实该选择是否需要新决定，以及丁当时是否可用 |
| Q2 | 文本从 v4 改为未批准的 v5，新预期未明确；09:20 请求内容决定，10:50 得到决定 | 90 分钟包含必要内容决定，不能视为可删除的多余审批 |
| Q3 | 输入没有版本，预览无法对应独立预期 | 结果尚不能判断；增加自主权不能补出缺失输入 |

对这组事实至少保留四种解释，允许它们同时存在。适配 A1。

| 解释 | 能区分它的证据 | 证据成立后可考虑的有限响应 |
|---|---|---|
| 已明确的低风险工作仍逐项集中决定 | 批准范围、检查结果及请求路径表明该次不需要新增内容决定 | 由有权限的人明确有限自主范围，保留独立检查和升级 |
| 新要求需要决定或独立预期 | 版本变化及未决事项，如 Q2 | 找到内容负责角色并取得决定，不能用模板自主代替 |
| 决定范围清楚，但决定人不在或已被其他工作占用 | 请求到达、实际接手、人员日历及合格替代者 | 调整响应安排或提出备援需求，不先推断控制欲 |
| 输入、必要能力或分类不清 | 缺版本、检查无法判断、人员不会处理的具体类别，如 Q3 | 补输入、说明或有限学习，未知时停止相应推进 |

丁随后确认 Q1 类型不涉及新的内容决定，乙原有独立检查仍适用，并明确批准试行 R1。新证据支持对这个范围改变决定方式；Q2 和 Q3 则否定“所有等待都能取消”的提议。即使 Q1 的等待随后减少，也不能反推过去只有一个原因，更不能据此报告团队信任已经修复。

若发现 Q1 实际要向外部发布，或使用未批准模板，原判断立即失去前提，应按新事实重新取得决定。用同一名称包装成“预览”不能扩大原批准范围。

### 2.2 处理协作机制，不诊断个人

进一步检查责任与实际选择空间是否一致、问题能否及时暴露、不同意见能否进入工作判断，以及观察记录是否被用于追责。记录具体被否定的选择、缺失的输入、反复检查的实际用途和造成的等待；沉默既可能来自顾虑，也可能来自忙碌、信息不可见或尚无结论，不能替参与者解释心理。来源 T1–T4、L2、L4；适配 A1、A4。

应认真处理对新安排的质疑，例如“丙值守时还要参加培训”就是容量冲突的证据。把提问者当成不配合，会使这些信息更难出现。回应应说明哪些成果责任保持、哪些选择可以自行作出、出现未知怎样求助，而不是要求公开证明忠诚或承诺更多加班。

“信任受损”本身也应拆成可核的工作主张：成员是否能依赖已明确的决定范围，暴露未知是否仍能获得按已说明条件处理的反馈。它不是一个需要给个人打分的属性。先取当前工作所必需的规则、版本、结果和具体反馈，区分以下情形。表中是判断条件，不是 Q1–Q3 已发生的事实；没有证据时继续标为未知。适配 A1、A3–A4。

| 待核机制 | 哪些工作事实有助于区分 | 有限响应与停止推断的条件 |
|---|---|---|
| 声明的自主范围不能被依赖 | 已明确允许某种选择，却在结果满足原检查后，按事先未说明的偏好反复要求重做；核查是否其实发生了新风险、新输入或正式范围变化 | 由原决定负责人澄清并记录当前范围、必要检查及改变范围的方式；若确属新风险，按新决定处理，不能把合理变更称为不信任 |
| 问题反馈受到抑制 | 具体工作问题被提出后，得到的是贬低提问者而非处理事实；进一步核查问题是否因这种处理而延迟报告，以及信息不可见、繁忙或已有其他报告路径等解释 | 先回应未决工作问题，明确暴露未知和请求帮助的处理方式，由有权限负责人纠正规则与执行不一致；不能仅因没有人再提问就认定改进有效 |
| 能力或输入缺口使限制必要 | 尚未有能力处理某类输入，或结果无法与独立预期对应；与已批准且检查通过的选择分开 | 保留必要核查、指导和升级，在取得对应证据后再讨论缩小限制；要求立即完全放权并不能修复这个缺口 |

前两种事实若被证实，支持的是“当前安排使已说明的选择空间不可靠”或“当前反馈方式可能阻碍问题暴露”这样的有限结论。它们不能证明某人内心怎样想。应请受影响角色核对对具体工作问题的理解，允许不同解释，不要求公开私人经历或强迫表达信任。若证据只支持规则模糊，就处理规则；若已确认范围反复被否定，就处理范围与执行的不一致，不能再用一次普通答疑替代。

后续取证也应针对机制：在相同批准条件下，选择是否仍按事先说明的检查处理；已提出的未知是否得到具体回应，未决事项是否继续可见。完成更快、满意度数字或一段时间无人反对，都不足以单独证明这种变化，更不证明团队信任整体恢复。有限安排超过权限或造成新的负担时，按第6节停止并交由负责角色决定，不把“修复信任”当作无限干预的理由。

无实际用途的手续可以提出缩减，但信息记录、独立核查或依法授权的限制不能仅凭不方便就删除。共同工作需要可达的信息、交流机会和清楚的责任，不能由本方法直接推导统一办公地点、相似性招聘或保证团队形成的处方。这里提供工作安排的有限分析，不作心理、医疗或人事判断。

## 3. 将自主范围与必要检查一起明确

R1 的机制假设是：对输入和选择范围已明确的工作，减少重复决定可能降低等待，同时保留接收结果所需的质量依据。授权、能力、输入和检查必须一起成立。来源 T2、T6；适配 A3。

| R1 的要素 | 本题明确条件 |
|---|---|
| 谁可以决定什么 | 甲可为已批准文本 v4 在模板 A/B 中选择 |
| 输出范围 | 只供题设内部接收者使用 |
| 必须保留什么 | 乙独立核查内容、顺序和显示，结果绑定输入、模板与规则版本 |
| 哪些仍需决定 | 新内容由内容负责角色决定；新模板、外部发布、访问权限变化均不在本范围 |
| 期间与负责人 | 仅两天的 09:00–11:00 窗口，第二天 11:00 到期；丁决定是否保留 |
| 未知或失败 | 缺预期、输入不明、超范围或检查失败时，停止相应推进并请求负责角色处理 |

丁须明确批准范围、期间、成本、责任、停止与恢复安排。没有答复时，继续遵循 R0 和现行支持安排；沉默不是试行批准。提议允许甲选择模板，不等于允许甲替内容负责人决定新要求，也不等于允许跳过乙的检查。

每个结果应能对应实际适用的 R0 或 R1、输入和模板版本以及独立检查。v4 的通过结果不能证明 v5 也满足预期，规则到期后也不能仅因上次获准而继续。具体独立预期与变更复核可使用[验收依据与变更影响方法](acceptance-evidence-change-impact.md)。

这类范围澄清只能改变明确的工作安排。它不替代系统设计一致性、跨模块设计责任和最终设计决定权的判断，也不会增加代理的人事、资金或外部操作权限。

## 4. 保护持续工作时保留有效支持

需要持续思考的工作与即时支持有不同条件。安排连续工作时间时，应确认普通请求去向、紧急请求怎样找到合格人员，以及支持者本身的负担。不能靠压住求助或把所有共同工作称为干扰来提高“专注”数字。来源 E2–E3、T4；适配 A2。

### 4.1 先排除人员被重复使用

第一天甲、乙、丙各有 09:00–12:00 与 13:00–16:00 两个工作窗口，每人六小时，共十八人时。丁的决定工作单列，不是额外免费人员。改进只涉及 09:00–11:00 的支持安排，窗口外沿用已确认安排，其成本仍要另计。

甲、乙在 09:00–11:00 尽量不受普通问询打断，由丙受理和分类；紧急路径始终保留。初稿同时让丙 09:40–10:40 跟甲培训，丙因此有六十分钟被重复安排。没有已确认的合格备援，这个安排就不能实施。

将培训移至下午，并同时计入指导者与学习者后，得到如下第一天安排。区间到右端即释放，不把相接时刻算作重叠。

| 活动 | 时间 | 人员 | 合计占用 |
|---|---|---|---|
| 受理与分类 | 09:00–11:00 | 丙 | 两人时 |
| 培训 | 13:00–14:00 | 甲、丙 | 两人时 |
| 必要交接 | 15:30–16:00 | 乙、丙 | 一人时 |

合计五人时，不是只计算丙的三点五小时。甲余五小时，乙余五点五小时，丙余两点五小时，共十三人时。这只是扣除表内活动后可用于其他必要工作的上限，还要扣除窗口外支持和其他任务；不能直接称为十三小时编码产能，更不能换算成工期缩短。

学习、交接和导师占用属于改进成本。人数不变不代表上下文和能力不变；人员更换、输入变化或支持类别变化时，应重新检查可用能力。来源 L1；更完整的资源冲突处理见计划方法。

### 4.2 有效接手不能由自动回执替代

本题要求紧急请求到达后十分钟内，由具备相应能力的人明确接手；这是虚构的批准条件，不是通用响应标准。丙可以分类和升级，不代表丙能够解决所有实现问题。自动回执、转发与接手分别记录，接手也不等于解决。

一个成功分支中，请求于 09:45 到达，甲 09:50 接手并处理到 10:20。接手用时五分钟，甲额外占用半小时，前述可用上限相应从十三降到十二点五人时。甲的持续工作被必要支持中断，应如实计入，不能为了漂亮的专注记录隐藏它。

另一个失败分支中，09:45 到达，09:46 自动回执，合格人员到 10:03 才明确接手。真实接手历时十八分钟，比十分钟条件晚八分钟。回执只花一分钟，不足以认定响应达标；原到达时间也不能在转发后重置。

此时先恢复可用的合格接手路径，暂停依赖未经证实覆盖的保护安排，并查明迟到原因。迟到说明必要条件被突破，尚不能证明是某个人态度不好，或保护安排必然是唯一原因。若没有可用备援，应让有权限负责人处理资源和优先级，不能让求助者承受无人的时间段后仍报告安排正常。

## 5. 比较成果时检查组成和实际投入

观察需要事先明确单位、分母、完成条件与比较范围。计数容易得到，解释必须保留工作组成、人员和同时发生的变化。来源 E1、E3；以下比较为适配 A2，不是原书给出的统计方法。

### 5.1 总体比例上升，分组却没有改善

两个等长窗口起点各有八项原创请求，不混入旧积压或后来到达的请求。每个请求只计一次当前结果，多次尝试不增大完成数，返工另记；未完成项保留在分母。完成必须满足对应版本的内部预览通过必要检查并已交给内部接收者。

开始时按输入划分两类：S 已有齐备的批准文本和模板；C 需要新的内容决定、预期或较复杂检查。分类及初始版本固定，不能完成后把容易的请求重分组，也不能丢掉未完成或未知结果。

| 类别 | 前期完成／总数 | 后期完成／总数 | 可直接观察的变化 |
|---|---|---|---|
| S | 2／2，即 100% | 5／6，约 83.3% | 完成比例下降 |
| C | 3／6，即 50% | 1／2，即 50% | 完成比例相同 |
| 总体 | 5／8，即 62.5% | 6／8，即 75% | 上升 12.5 个百分点 |

后期 S 占得更多，总体因此可能更好看。S 下降而 C 不变，已经足以否定“总体上升证明安排有效”的推断；它仍不能证明安排造成损害。分组内复杂度、到达条件、人员和其他变化尚可能不同，样本也很少。应报告这些事实和限制，不从八项请求制造改善概率或统计置信度。

### 5.2 名义工时会藏掉投入

另一项成本对照沿用前期完成五项、后期六项的计数：前期实际投入十八小时，后期名义十八小时，但实际用了二十四小时。若只用名义分母，会从 `5/18` 得到后期 `6/18=1/3` 项每小时；采用实际分母，后期则是 `6/24=1/4`，还有六小时原先漏记的投入。

这只展示分母遗漏，不能用异质请求的“项数／工时”评价生产率或个人。额外投入也不因已经发生就获得批准。应查明它用于必要支持、学习、返工还是补偿其他缺口，并由负责角色处理，而不是把成本藏起来后许诺更高速度。

长期反复增加投入可能影响恢复、质量、知识延续和人员可用性。短期应急与长期常态应分开判断；不能直接采用原书固定工作小时数、补偿倍率或历史故事，也不能要求成员公开家庭细节来证明无法加班。来源 E1、T5、L1。

### 5.3 同时查看成果、质量、可达性和负担

| 观察面向 | 应保留的信息 | 会否定局部改善的情况 |
|---|---|---|
| 成果 | 对应版本、必要检查、接收状态、未完项 | 完成数增加但降低验收或积压复杂请求 |
| 质量 | 检查失败、返工、错误输入与结果未知 | 重做被计成多次成果，或跳过检查 |
| 支持 | 合格接手时间、覆盖缺口、求助绕行 | 自动回执达标但无人真正接手 |
| 投入与负担 | 支持、学习、指导、交接和额外投入 | 甲乙看似安静，但成本全部转给丙 |
| 工作反馈 | 受影响角色遇到的具体障碍、反例和未解问题 | 用沉默或没有投诉代替改善证据 |

只收集回答当前问题所需的工作信息。先说明请求类别、必要版本、状态和投入类别的用途，哪些处理或核查角色需要访问，在何时复查留存以及谁负责删除不再必要的细节。成果与决定依据可按需要保留，原始个体细节不能仅为方便无限保存。适配 A4。

只有三名工程角色时，按轮值时段汇总仍可能识别个人；“汇总”或“匿名”不能当作无法识别的保证。更广分享和其他用途需另外明确。无需采集键盘活动、私人聊天或生活安排，也不能将本为改善工作环境的观察改作个人排名或心理判断。当前例子全部由题设生成，没有采集真实人员资料。

### 5.4 先选要回答的问题，再定义交付指标

交付指标描述软件变化进入指定使用环境及发生问题后的过程。它需要团队先确定服务范围、事件身份与起止，再由相应记录的负责人保存证据；协作改进者用这些事实辨认等待、失败及恢复问题。它不能替代第5.1–5.3节的成果、质量、支持和投入，也不独自证明用户获得了价值。来源 ACC-SRC-01–02；具体记录安排为适配 A6。

Accelerate 2018年第一版第2章使用下列四项。这里保留书中对象，具体统计定义还须由当前任务明确；这些名称不构成当前官方标准或必须达到的目标。

| 书中指标 | 原书观察的对象 | 当前使用前必须补充的定义 |
|---|---|---|
| 交付前置时间 | 第2章从代码提交到代码成功在生产运行 | 哪个提交、哪个服务和环境、开始事件、成功生产运行证据；未完成及撤销怎样保留 |
| 部署频率 | 向生产或应用商店部署的频度；作者用它作为难以跨情境计量的批大小的代理 | 一次部署怎样识别、观察期间多长、重复控制请求和多个目标怎样归属，哪些变化纳入 |
| 恢复服务时间 | 主要应用或服务中断、受损后恢复所需时间 | 受损开始、恢复条件、受影响范围、未恢复事件，以及采集和通知的延迟 |
| 变更失败率 | 生产变更导致服务降级或随后需要补救的比例 | 纳入哪些生产变更、什么算失败、变更与失败怎样关联、跟进期间及未知结果怎样保留 |

第14章同名 lead time 的终点却是“可部署状态”。可部署与成功生产运行是两件事；本书章节间的差异要随引用保留。若当前问题关心构建与核查准备，可以另报“提交到可部署”；若关心交付到生产，就继续等待成功运行的证据。不能把结束事件换早后沿用原定义名称、趋势和目标。该差异的外部勘误及当前官方定义未在这里核查。来源 ACC-SRC-02。

共同定义至少还要说明：统计单位和分母、窗口归属、数据截至时刻、去重方式、输入与结果缺失、必要分组、来源和定义版本。提交到部署可能是一对多或多对一，不应仅凭数量相近就相互替换；配置变化也未必有对应代码提交。实际关系不清时先核查，不能以空值补零。系统只能记录其采集覆盖的部分，人的回忆也不保证完整；记录与解释发生冲突时，保留冲突并取得能区分它们的证据。关联和对账的投入记入第5.2节的成本。

用户结果则观察用户的一次操作是否取得符合要求的结果。一次部署可能影响很多操作，也可能尚无用户使用；一次用户操作可以包含多次传输尝试。变更失败率的分母是纳入的变化，用户坏结果比例的分母是纳入的操作，两者不能互换。恢复时间也不能直接换算用户受损比例或错误预算。用户目标、联合成功条件、未知数据和行动权限分别见[用户结果方法第1节](user-outcomes-slo-alert-actions.md#1-从用户后果决定目标)、[第2节](user-outcomes-slo-alert-actions.md#2-定义一次可观察的用户结果)、[第4节](user-outcomes-slo-alert-actions.md#4-先判断数据能支持什么结论)和[第7节](user-outcomes-slo-alert-actions.md#7-区分发布止损恢复与目标变更)。

交付变快而用户结果受损、额外支持增加或必要检查被跳过时，不能报告共同结果改善。部署更频繁也不独自证明批次更小、需求更合适或服务更可靠；应取得各自需要的证据，而不是从代理指标推出全部结论。把部署指标按个人拆开排名，还可能掩盖共同交付、支持和交接责任，仍受第5.3节的信息用途限制。

### 5.5 用同一组事件检查终点、分母和未知

下面的“灯片检索服务交付记录”是另一组原创静态题设，与展签预览的 R0/R1 安排分开。所有事件均为给定数据，没有执行部署、用户操作或团队试行。题设时间在同一天，由同一已核对的时钟表示；观察窗口为 `[09:00,13:00)`，数据截至13:00。实际使用时必须重新取得相应环境、记录、时钟与权限事实。

先固定一个提交集合：该窗口内只有 cA、cB、cC 三个纳入的代码提交。它们对应的可部署和成功生产运行事件如下；尚无终点的提交保持未完成，不把耗时写成零。

| 提交 | 提交时刻 | 达到可部署状态 | 成功生产运行 |
|---|---|---|---|
| cA | 09:00 | 09:30 | 10:00 |
| cB | 09:10 | 09:40 | 11:40 |
| cC | 10:10 | 10:40 | 截至13:00尚未发生 |

按第2章的生产终点，cA 已完成耗时60分钟，cB 为150分钟；cC 已等待170分钟，尚无完整前置时间。只列60和150分钟时，必须同时说明它们仅为三个提交中的两个已完成项，另一个仍未完成；不能把未完成项删除后声称全部交付变快。

若改看提交到可部署，三个都是30分钟。这个结果只能说明题设内可部署终点的耗时。把30分钟直接接到原有生产前置时间趋势上，会使 cB 的剩余等待120分钟和 cC 的在途状态消失。正确处理是分别标明两种定义及版本，保持旧结果；确有共同事件可重算时，也要标明重算范围及尚缺记录。不能用文档换名造成的下降批准安排扩大。

再看同窗内的生产变化。题设明确三次不同变化 dA、dB、dC 均已实际生效；配置变更 dC 也在事先确定的纳入范围内。dB 的11:42重复控制回执属于同一次变化，没有新增生效事件。本题把一次变化生效后三十分钟内、由该变化造成的服务降级且需要补救，记为该定义的失败；三十分钟仅为虚构观察边界，更晚影响另行记录，不能据本表排除。

| 变化 | 实际生效 | 与提交或配置的关系 | 三十分钟内结果证据 |
|---|---|---|---|
| dA | 10:00 | cA | 此范围内证据完整，未发生定义中的失败 |
| dB | 11:40 | cB | 11:45发生所定义降级；12:05满足事先规定的服务恢复条件 |
| dC | 12:30 | 配置变化，无本表代码提交 | 截至13:00结果证据缺失，保持未知 |

在这个固定窗口中，三次不同生产变化对应 `3/4 = 0.75` 次每小时。它只是这四小时的观察频度，不是建议目标或长期频度预测。重复回执不把计数变成四次；达到可部署状态的 cC 也不能计入生产变化。部署尝试失败、尚未生效或多个目标部分生效时，应按事先定义另外保存状态，不能套用本题“三次生效已确认”的前提。

三个变化的分母已确认，其中一个失败、一个未失败、一个未知。因此本题变更失败比例只能处于 `1/3` 到 `2/3`，约33.3%到66.7%。这是未知项可能取值形成的范围，不是统计置信区间。把 dC 当作成功会制造未经确认的33.3%；把它删掉再报告 `1/2` 也改变了总体。若连部署采集是否完整都不清楚，这个三次分母和范围同样不再成立，应报告无法计算并核查缺失范围。

dB 的恢复服务时间为 `12:05−11:45=20分钟`。从11:40部署到12:05是25分钟，回答的不是同一个问题；11:42收到回执也不是恢复。这里仅有一个已确认恢复事件，不能据此保证未来事件二十分钟恢复。仍未恢复、仅部分恢复或起点未知的事件必须另列，不能用已恢复事件的平均值遮住它们。

题设还单独给出同窗的用户观察：可信起始集合为200次主动检索，共212次传输尝试，192次取得已授权、版本正确且完整的灯片，并在虚构的三秒内完成；另外8次不满足这个联合条件。自动重试留在原操作内，因此用户坏结果比例是 `8/200=4%`，不是 `8/212`，也不是变更失败比例。三秒只定义一次操作是否及时；题设没有给出获认可的 SLO 比例，不能据此宣称整体服务达标或不达标。记录也没有提供八次坏结果与各部署的完整关联，不能把它们全部归因于 dB。

这组记录目前支持的下一步是：保留 cC 的等待和负责者，核清从可部署到生产仍需要哪些决定；请相应记录负责人补核 dC 的结果；另外按用户影响检查八次坏操作。任何当前严重影响继续按已有响应安排处理，不能为等齐趋势而拖延。记录不足不会自动授权增加采集范围、部署 cC、回退配置或延长协作试行。

### 5.6 引用研究关系时保留对象和分析限制

引用研究可以帮助选择值得调查的假设，但必须说明研究实际比较了什么。Accelerate 第3章和附录B区分四项指标的分群与三项指标的软件交付表现构念。本书的软件交付表现构念是由三项测量共同表示的研究对象；书中作者报告前置时间、发布频率、恢复服务时间组成该构念，并将变更失败率另述为与它高度相关。效度和信度是作者对其测量分析的报告，不能自动成为当前团队新采集数据的性质。来源 ACC-SRC-03。

| 要转述的内容 | 应保留的对象 | 不能直接替换成什么 |
|---|---|---|
| 某一指标与其他变量的关系 | 那个单项、其定义、样本和分析 | 全部四项都已独立检验 |
| 高、中、低表现群体的比较 | 使用四项指标形成的研究分群及年份 | 每个团队必须依次经过的成熟阶段 |
| 与软件交付表现构念的相关或推断预测关系 | 书中三项构念及对应分析 | 某项实践已被证明必然改善变更失败率 |

书中另有单项指标关系，不能把全部分析都说成只用了三项。2016年表2.2及相邻说明还出现中组变更失败率高于低组的例外，作者对其解释保留不确定。它足以限制“组别越高，每个指标必定越好”的笼统推断；不应删掉例外以维持单调故事。书内均值显著差异与表内中位数相同也可以同时成立，不能替换统计量后宣布原结论矛盾。历史分组区间不用于当前目标，群体中速度与稳定性共同改善的报告也不能排除每个项目、每次变化的实际取舍。

研究结论还要保留分析类型和参与者来源。第12章把本书分析归入描述、探索及理论引导的推断预测，并另作分类分析；作者说明缺少其所列后续未来事件预测、因果和机制分析所需的数据。书中 impact、driving 等措辞须放回这个范围，不能直接改写为干预必然造成改善、未来数值保证或已识别的准确机制。理论和回归分析本身不会补出这些证据。来源 ACC-SRC-04。

第15章说明，从2014年起收集四年横截面数据，招募面向熟悉或愿意阅读 DevOps 相关信息的技术人员和组织，通过邮件、社交媒体及转介进行非概率抽样。每年的回答未连接，因此不能把年度差异写成同一批团队的改善轨迹。增加邀请规模、多样性和行业意见是作者所述缓解措施，不会使样本自动获得全行业的概率代表性；招募取向也不是经过验证的技能资格。作者的推广建议仍须与实际样本及未覆盖人群的限制一起表达。来源 ACC-SRC-05。

在本方法中，研究关系只帮助提出“某种安排可能减少重复决定或等待”的候选解释。当前事实、不同解释、允许成本和停止条件仍按第2–6节判断。灯片例子中的30分钟、0.75次每小时、20分钟和4%都是题设计算，不是研究目标；没有比较安排前后，更没有证明干预收益。即使以后取得可比前后记录，也还需考虑工作组成、人员、其他同时变化、采集改变及未观察群体，不能把相关变化写成原因已经确定。

## 6. 给改进期限并按条件停止

改进提议至少说明问题、机制假设、允许范围、负责人、观察窗口、成本、必要条件、复查和到期安排。这里的假设是减少重复决定并由合格人员承接普通问询，可能降低等待与切换；独立检查、紧急支持和可持续投入须同时保留。两天窗口是当前题设，不证明两天足以评估长期效果。来源 L2–L4；适配 A2。

若改进要使用交付观察，提议还应写明所问问题、定义版本、需要的最少事件、记录负责人及补核成本。对灯片题设，可以先在已允许的范围核清 cC 的等待与 dC 的缺失结果；没有依据时不把“提高部署频率”直接写成试行目标。是否缩减重复确认仍需第2–3节的当前输入、能力和授权证据，不能凭研究中表现较好的群体采用过某项实践就作决定。

观察期间定义变化或关键分母不可信时，先停止依赖该数字的改善结论，保留旧定义与未决项，核对能否在剩余批准时间和成本内恢复证据。当前支持、质量或权限条件已被突破时，仍按第6.2节立即处理；不能以等待数据为由继续扩大风险。到期仍无法判断，就报告证据不足，由原负责人决定后续安排，不自动扩大采集、延长或正式采用。

### 6.1 暂时不熟练只是一种待核解释

如果同类工作暂时完成更少，且确有获准培训和交接，必要质量与有效接手条件均保持，可以检查具体哪一步不熟练、说明缺什么，在剩余批准时间和成本内补充说明或练习。但这只支持继续取得有限证据，不证明最终会好转。

同一现象也可能来自输入变复杂、容量不足、责任不清或提议不适用。对方提出的困难应作为待核信息，不能因为“变化都有阵痛”而拒绝检查。原书的变更模型可以帮助提出学习成本假设，不能变成必经阶段、强制坚持或持续恶化的正当理由。

### 6.2 立即停止与到期决定分别处理

| 触发事实 | 立即或到期处理 |
|---|---|
| 使用未批准输入／输出范围，或跳过独立检查 | 停止相应推进，保留已做动作与未决结果，恢复必要核查和决定 |
| 有效紧急接手超过十分钟，或没有合格可用接手者 | 先处理当前请求，暂停依赖该覆盖的保护安排并恢复实际可用路径 |
| 额外投入或持续负担超出批准范围 | 不继续按原可用容量推进；核对必要工作并请求调整范围或资源 |
| 记录被用于个人排名或超出已说明用途 | 停止相关观察用途，处理访问及已产生记录，不能以效果好为由继续 |
| 第二天 11:00 到期 | 丁依据成果、质量、响应、投入和未知，决定保留、缩小范围或停止 |

立即停止条件可以早于到期触发。若证据不足，不自动延长、不扩大范围，也不宣布信任修复或效率成功。正式保留需要明确新的范围和责任；试行批准不会自动变成永久制度。

状态报告、改进提议、试行批准与正式采用分别处理。报告迟到或困难不等于要求上级接管全部工作，更不授权代理调整人员、组织、薪酬或作外部承诺。反馈围绕工作条件和可选动作，不把提出问题的人当成失败原因。

## 7. 恢复安排时保留进行中的责任

恢复旧说明不能撤销已经发生的工作，也不能让新期间的请求消失。停止新保护窗口前后，应逐项保留输入、规则、动作、检查状态、实际结果和剩余责任；详细交接可复用[事件交接与复盘改进方法](incident-handoff-learning.md)。适配 A2、A5。

沿用紧急接手超时分支，请求 Z-17 从 09:45 到达后仍未解决，由丙负责跟进。10:06 请求乙接任，乙在 10:08 明确确认。两分钟的交接不等于此前响应只用了两分钟；从原到达到接任已经二十三分钟，原计时保持。

丙在乙确认前继续承担跟进责任。甲可能已接手技术处理，这也不能代替丙到乙的整体跟进交接；需要明确交的是哪种责任。交接记录应包括输入版本、R1 期间做过什么、实际结果与未知、独立检查状态和下一项工作。发送消息不是接任，没有解决证据就继续报告未解决。

在声称 R0 或旧支持安排已恢复前，还须核实原人员、权限和日历现在仍可用。如果原安排已经无法承担工作，保留当前责任与未完项，请求有权限负责人安排；不能把文档改回旧版就报告恢复。已确认的结果保留其当时版本，未完请求按当前决定继续处理，不清空历史后重新开始计时。

## 8. 使工作经验成为后续可用的知识

经验成为组织可用知识，需要后续工作能找到、理解并采用当前安排。文档页数、会议次数、培训次数或人数保持不变，都不能单独证明这一点。来源 L1、L5；适配 A5。

旧说明 V1 只写“收到问题尽快处理”，读者无法知道哪类输入可以继续、谁有权决定、什么算有效接手。V2 至少应给出 R1 的范围与到期时间、批准文本和模板版本，S／C／未知的判断依据，必要独立检查，以及超出范围时怎样找到负责角色。值守、升级和交接还要绑定当前资格与日历。

丁负责是否保留安排的决定，相关角色维护自己负责的说明和交接。输入、人员、权限或支持类别变化时复查；新成员需要必要的上下文和指导时间，不能只发送链接后视为已经具备能力。不同专长围绕共同成果沟通，资料才能进入实际工作，不必限定某一管理层级或统一组织形式。

一个反例是后续使用者只拿到 V1，或者无法访问最新批准范围，于是把无版本输入当成 S 类处理。V2 文件存在仍没防止错误。下一步应检查当前说明能否找到、旧版是否仍误导、未知分类是否清楚，以及读者是否有足够能力和求助路径。不能只再加一页说明，也不能直接归因于个人不认真。

在后续允许的实际使用中，正确处理新输入、遇到未知能停止相应推进、真正完成接任，才是知识被使用的证据；一次成功也不保证所有变化都已覆盖。当前只给出静态条件和反例，不报告团队已学会或组织学习已有效。

## 9. 输出有限判断与下一项证据

交付内容围绕当前问题，按需要保留以下信息即可，不要求每项任务完成全部流程。

| 输出 | 对本题应说清楚的内容 |
|---|---|
| 事实与未知 | Q1 的确认等待、Q2 的新内容决定、Q3 的缺失版本分别是什么 |
| 解释及反证 | 哪些证据支持有限自主，哪些输入使这一选择不适用 |
| 可选改变 | 范围、能力、保留的检查、支持路径及成本，而非“提高信任”的口号 |
| 决定与责任 | 谁批准、何时到期、哪些还需要决定，当前请求由谁继续跟进 |
| 下一项证据 | 比较哪些同类工作、如何识别投入转移，出现什么立即停止 |
| 知识延续 | 当前说明在哪里、版本和维护责任、后续使用遇到未知怎么办 |

涉及交付测量时，再保留服务与指标定义版本、提交或变化的单位和分母、各终点、观察窗口与数据截至时刻、未完成和未知项，以及用户结果和实际投入的分别判断。引用研究须同时说明单项、分群或构念、分析类型、样本与外推限制。只有当前问题需要时才补这些内容；不要把四项名称变成每次协作报告的固定表格。

对短期变化只给与证据相称的结论。例如可以说“题设下移到下午的培训消除了已列明的一小时冲突”，不能说“该制度已经提升全团队效率”；可以说“已知模板选择获准交给甲”，不能说“信任问题已解决”。来源与静态推导帮助形成待验证方案，当前工作事实才决定采用范围。
