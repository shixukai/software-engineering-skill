## 1. 确定正在审查什么

本方法用于判断一组变更是否引入或暴露可触发的问题，以及现有证据能支持哪种审查结论。审查意见需要连接变更、调用条件和要求；“不符合某本书的建议”本身不能证明当前程序有缺陷。已经发生的异常需要定位原因时，另用[竞争假设、诊断与修复证据](diagnosis-hypotheses-repair.md)。

先取得比较基准、目标版本、完整差异及任务要求。区分“只审这次变更”和“检查整个模块”，并确认配置、生成文件、迁移和调用方是否随同改变。移动或重命名后的行可能保留原行为；新行号不等于新问题。目标版本变化后，旧评论和旧检查结果需要重新关联。

按可能改变的行为追踪必要上下文。删除一次校验时，应查看谁提供输入、校验在哪里发生，以及校验后数据能否改变；修改返回结果时，应查看调用者如何解释结果。先找到这种具体关系，再决定读取哪些文件，不把审查扩大成没有终点的全仓库巡检。

记录实际检查范围及其限制。例如，搜索到了哪些入口，是否检查生成代码、插件注册和配置，是否存在未提供的调用方。搜索没有匹配项不等于入口不存在；类型注解和注释也不等于运行时已经强制满足条件。材料不足时先指出会影响哪条结论，继续完成不依赖该材料的检查。

搜索索引是从源码生成的查询数据；文本索引提供文字匹配，语义引用索引提供分析工具识别出的符号关系。用搜索结果支持审查结论时，分别核对目标源码或工作区、文本索引、语义引用索引对应的版本和更新时间，并确认语义索引依据哪次构建或分析。查询时间不能替代索引更新时间，时间接近也不能证明源码版本相同。能打开目标版本的文件，不表示跳转和引用列表也来自该版本。索引身份未知或与目标错位时，结果仍可帮助定位；所依赖的调用关系须回到对应源码和构建上下文核查，未核实部分保持未知。来源 SG17-V；这里的核对与结论处理是工程适配。

导航是找到足以继续阅读的相关位置；枚举是找全事先限定集合内的匹配。需要据搜索结果判断“全部调用者都经过校验”或“已无旧用法”时，先明确枚举范围，再核对索引包含哪些仓库、版本和文件类型，排除了什么，查询采用哪些匹配条件和过滤，以及返回结果是否经过排名、数量上限、截断或分页。只有确认该查询在已声明范围内没有遗漏返回页或剩余结果，才能说这一范围的匹配已取尽；“全结果”选项的名称本身不是依据。文本命中取尽仍不等于全部符号引用、动态入口或仓库外使用都已覆盖，必要时继续核对构建关系、注册配置或相应运行线索。来源 SG17-R；分页、取尽记录及补证选择是工程适配。

例如，在一个未执行的原创题设中，目标版本新增了调用入口，语义引用列表却来自旧版分析；文本搜索又只返回排名靠前的两个位置。即使这两个调用都安全，也不能据此认定新增入口同样安全或只有这两个调用者。先核对新增入口及索引版本，再确认与结论有关的返回范围；无法取得剩余结果时，报告已查位置和未覆盖部分。仅为导航寻找一个实现时，则不要求先枚举全部使用者。取全结果和维护历史索引都有读取、存储及计算成本，应围绕会改变当前结论的缺口补查，不为一次审查建设搜索平台。

## 2. 把怀疑变成可核查的问题

候选意见是需要验证的解释。先写出“若这些条件成立，变更后的哪一步会违反哪个要求”，然后寻找支持与反对证据。可用下面的关系逐项检查；不要求把每一项都输出成冗长模板。

| 检查对象 | 应取得的具体依据 | 常见跳跃 |
|---|---|---|
| 要求 | 当前需求、接口约定、数据约束或兼容承诺规定的行为 | 从实现或个人风格偏好倒推出要求 |
| 可达条件 | 输入、状态、权限、时序及入口确实能到达被审路径 | 直接构造违反已证明前置条件的内部调用 |
| 行为变化 | 相同相关条件下，基准与目标在何处产生不同结果 | 仅因一行出现在差异中，就把既有问题算作新增 |
| 失败机制 | 调用、分支、状态更新与观察结果之间的具体联系 | 只说“可能出问题”或列出组件名称 |
| 影响 | 哪些调用者或业务结果受影响、何时发生、能否恢复 | 用局部错误推断全局损坏或夸大严重性 |
| 核查方式 | 最小反例、完整静态推导或对应版本的执行证据 | 用所有测试通过代替检查未覆盖的条件 |

缺陷可以通过完整的静态推导得到充分支持，不必强制复现每个问题；但推导所需的运行条件必须有依据。执行失败也需要核对版本、输入和失败原因，不能把环境故障归因给差异。预期结果需要独立依据，见[风险、独立预期与验证层次](test-risk-oracles-layers.md)。

比较基准时分清三种关系：目标新引入错误；目标新增入口使原有潜在错误变得可达；错误在基准中已经存在且本次没有改变它的可达性。前两者可以是本次变更问题，第三种应按任务范围标明既有问题，不能假称由本次引入。若需求也同时改变，分别检查旧版旧要求和新版新要求；行为不同不自动表示回归。

对于并发或异步路径，反例还需包含必要的操作交错、可见状态及确认边界。“两步之间可能发生其他操作”不是充分说明；应证明相关锁、事务或执行模型允许该交错。若关键依赖的实际语义未知，记录缺失证据，不套用另一个技术栈的结论。

## 3. 主动查找能否定怀疑的条件

反证是能否定某条具体缺陷解释的证据。它由已核对的代码、配置、输入范围或需求建立，审阅者用它撤回或缩小意见；它只否定所针对的解释，不认证整个程序。

例如，怀疑空值会进入某函数，就需要核对入口是否强制拒绝空值、所有相关调用是否经过该入口、校验后值是否保持不变。只找到一个安全调用者不够；看到类型名也不能推定外部数据已经验证。怀疑竞争写入时，则应核对保护是否覆盖读、判断、写的完整范围，以及全部相关写入者。

| 取得的证据 | 对原怀疑的处理 |
|---|---|
| 约束确实排除全部相关触发条件 | 撤回该缺陷意见，必要时保存简短依据，避免后来重复误报 |
| 只排除部分输入、入口或时序 | 缩小候选问题范围，继续核查剩余路径 |
| 约束只存在于注释、类型声明或未经核对的说明 | 将它作为待验证前提，指出需要核对的具体执行位置 |
| 新版本新增入口或改变约束 | 重新分析受影响结论；旧版反证不能自动沿用 |
| 支持和反对证据仍矛盾 | 先确认是否来自同一版本、配置与输入，暂不输出确定性缺陷或安全结论 |

寻找反证不等于不断为变更辩护。只要一个满足现行要求且可达的反例已建立，就足以否定相应正确性主张；其他路径工作正常不能推翻它。反过来，一次没观察到错误也不能否定尚未经历的触发条件。

## 4. 原创推演：公告到期与标题处理

### 4.1 题设与两组差异

以下是原创、未执行的静态题设，不来自真实项目或书中示例。它固定一个有限程序 `bulletin-v1`，只包含 `loader.py`、`preview.py` 和 `select.py`。其中所有入口和调用者均已由题设列出；真实审查需要另外取得这种范围依据。

要求是公告仅在 `start <= now < end` 时可见；显示标题为字符串 `title` 去除首尾空白的结果，允许空字符串。三个时间值都是整数，且 `start < end`。调用者提供 `now`，程序不读取系统时钟，不做时区和精度转换。

`loader` 强制检查字段类型与时间范围，不符合者报告输入错误并拒绝交给选择函数；通过者成为不可变记录。`preview` 是唯一调用者，使用这些记录调用 `select_active`；列表和记录不会在校验后被替换或修改。题设没有其他导入调用、插件、反射或反序列化旁路。这些是给定事实，不能由下面几行函数代码单独推出。

基准版本 `select.py`：

```python
def select_active(records, now):
    result = []
    for r in records:
        if r.start <= now < r.end:
            result.append((r.title or "").strip())
    return result
```

候选 D1 的两处差异：

```diff
-        if r.start <= now < r.end:
-            result.append((r.title or "").strip())
+        if r.start <= now <= r.end:
+            result.append(r.title.strip())
```

候选 D2 是另一个待审版本，与基准相比仅删除标题的空值防御；到期判断仍为 `now < r.end`。D2 不是已执行的修复结果。

### 4.2 确认一个可达的边界缺陷

对 D1 建立候选意见：“到期时刻可能仍返回公告。”取记录 `start=10, end=20, title="  通知甲  "`，并令 `now=20`。

该记录满足输入校验，调用者也允许传入整数 20，因此路径可达。基准判断 `10 <= 20 < 20` 为假，结果不含该公告；D1 判断 `10 <= 20 <= 20` 为真，返回列表包含“通知甲”。独立要求规定结束时刻不含在可见区间内，所以这不是单纯的版本差异，而是可达输入下的要求违背。

再尝试否定这条意见：调用者是否保证 `now` 永远小于 `end`，或永远不会等于 `end`？题设没有这些限制，且明确允许上述整数输入。因此不能用“通常不会刚好相等”撤回发现。某些其他输入正常也不影响这个反例成立。

可交付的意见为：

> D1 的 `select.py` 第 4 行把结束条件改成了包含端点。对于 `start=10, end=20, now=20` 的允许输入，公告仍会返回，与结束时刻应隐藏的要求不符。请保留结束时刻不包含在区间内的判断，并在实际修复版本复查该边界。

影响限于等于结束时刻时的展示错误。题设没有提供读者规模或损害后果，不能再推出数据损坏、全站故障或固定最高优先级。上面的输出来自静态推导，没有测试执行记录。

### 4.3 撤回一个看似合理的空值缺陷意见

另一条候选意见是“删除 `or ""` 后，`None.strip()` 会失败”。表达式在空值下失败只说明局部可能性，还要证明空值能到达这里。

本题 `loader` 强制拒绝 `title=None`，全部调用经该入口，校验后记录不可变，其他入口被题设明确排除。因此，构造一个直接把空值交给内部函数的调用，违反已证明的前置条件，不能证明此次变更在本题应用中引入可达回归。

还需检查允许的假值，而非只检查非空标题。对于空字符串，基准的 `(r.title or "").strip()` 与 D1/D2 的 `r.title.strip()` 都得到空字符串；对于非空字符串，两者对同一个字符串调用 `strip()`。题设只允许字符串，且没有自定义类型或副作用。因此删除防御在该输入范围内保持标题行为。

应撤回“空值会使程序崩溃”的缺陷意见，无需为了保留一条评论而要求恢复冗余代码。若任务要求改进接口说明，可以考虑说明已证实的前置条件，但这属于可选改进，不能把它重新命名为已确认运行缺陷。

### 4.4 同一依据支持 D2 的有限结论

对 D2 相对基准的完整差异进行分析：筛选条件不变；输入列表、次序和可变性条件不变；唯一改变是上一节已证明等价的标题表达式。因此在给定输入与调用范围内，未发现有证据支持的变更缺陷。

这里不是因为“没有时间再找”而宣告通过，也不是用 D1 的修复意图推定 D2 正确；依据是实际比较 D2 的全部差异及相关前置条件。结论示例见第 6 节。

### 4.5 新入口使旧反证失效

现在改变一个前提：程序新增插件入口，但插件调用和校验代码没有提供；`preview` 原路径仍保留，其他要求不变。

“所有调用都经过 loader”不再成立，因而不能继续用它证明标题空值风险已经排除。但未知插件也不等于它必定传入空值。正确输出是：标题处理在插件入口下的安全条件尚未核实，需要取得插件注册、调用方式、字段校验以及校验后的数据处理代码。若该函数还承诺直接接受空值，这项接口要求本身也会改变判断。

D1 经原 `preview` 路径到达的结束时刻反例仍成立，因为新增入口没有移除这条允许路径。只撤销失去依据的结论，不把所有已取得证据一并丢弃。

## 5. 区分发现、风险与可选改进

最终意见按证据性质处理，不以发现数量评价审查价值。同一原因导致多个相邻现象时，可以合并为一条有完整影响说明的意见；不同触发和修复责任则应分别表达。

| 结论 | 所需依据 | 如何交付 |
|---|---|---|
| 已确认缺陷 | 要求、可达条件、错误机制及影响已连通 | 给出精确位置和最小解释，指出修复需要保持的行为；严重性依据实际影响与项目规则 |
| 待验证风险 | 有具体可能机制，但关键入口、状态或要求仍未知 | 写清缺什么、如何取得，以及缺证对当前决定的影响；不伪装成确定缺陷 |
| 可选改进 | 可以改善理解或维护，但未证明行为违背要求 | 明确可选及收益代价，按用户审查范围决定是否输出 |
| 已被反证的怀疑 | 对应触发条件被已核对约束排除 | 撤回缺陷意见；只在解释结论或防止重复讨论时保留简短依据 |

确认程度与损害程度是不同问题。缺少证据时不应通过降低优先级来伪装成已确认缺陷；影响可能严重时，也不能因为尚未确认就完全不报告风险。提供具体缺证及其影响，交由任务约定的负责人作是否补查或接受风险的决定。Skill 不自行产生合并许可。

“函数长”“没有采用某模式”“我更喜欢另一种命名”不能独立支撑缺陷。若问题确实妨碍理解，应指出哪个要求、状态或责任难以判断，并按实际任务决定是否建议改进；不要为了显得严格而把风格意见写成运行错误。

## 6. 如何给出未发现缺陷的结论

“未发现有证据支持的缺陷”是对已检查版本和范围的报告，由审阅者依据实际检查形成；接收者据此了解本次工作覆盖了什么。它不等于所有路径已被穷举，也不替代测试、专项证明或审批。

D2 的结论可以写为：

> 在 `bulletin-v1` 题设中，已比较 D2 相对基准的完整差异，并核对 `loader.py`、`preview.py`、`select.py` 的给定输入及调用条件。唯一行为修改是移除在该范围内冗余的标题空值防御，允许的空字符串仍保持相同结果；结束时刻判断未改变。未发现有证据支持的变更缺陷。本次为静态推导，未执行测试；结论不覆盖题设之外的入口或运行环境。

输出深度与任务相称。小变更可以简短说明检查范围和剩余限制，不需要展示每一条已撤回怀疑。若关键路径根本没能检查，应写“该部分尚不能判断”并说明缺什么，不能将“没拿到代码”包装成没有发现缺陷。某一部分未完成，不妨碍报告其他部分已经证实的发现。

## 7. 跟进实际修复并结束审查

对 D1，针对已证实机制的最小修复方向是恢复结束时刻的严格小于判断，保留有依据的标题简化。建议不是执行记录；实际修复提交可能还修改其他行为，因此需要取得新版本和实际差异后复查。

以下只列计划中的检查及独立预期，没有执行结果：

| 条件 | 独立预期 | 所检查的风险 |
|---|---|---|
| 同一记录，`now=9` | 不返回公告 | 不能为修到期问题而扩大开始边界 |
| `now=10` 与 `now=15` | 返回“通知甲” | 起点包含，区间内仍可见 |
| `now=20` 与 `now=21` | 不返回公告 | 原缺陷与到期后的正常隐藏 |
| 可见区间内标题为空字符串 | 返回列表中的空字符串 | 允许输入仍保留，不擅自删除该公告 |
| 标题为 `None` 经 loader 输入 | 输入被拒绝，选择函数不接收该记录 | 原前置条件在实际新版本仍被强制执行 |

在实际获准的验证中，保存运行版本、输入、预期、实际结果及限制；明确检查的是函数、入口还是完整展示路径。对外可见结果需要沿真实连接检查，不能只让替代实现或内部单元通过。已有结果能否复用，见[验收依据与变更影响](acceptance-evidence-change-impact.md)。

修复复查还要看原问题之外的相关影响，但不借机追加无关重构。范围依据实际差异和后果决定；小修复不强制重审全部软件，新增入口或共享约束改变则需扩大相关范围。意见的结束应有证据：实际版本已修复并完成相应复查，或原意见已被可靠依据否定；“作者说已处理”本身不能替代核查。尚未解决或缺证的意见保留明确状态和下一项所需证据。

检查方式也需要反馈。重复误报可指向过宽的检查条目，漏掉的触发条件可用于改善相关检查；只有实际记录才能支持改进有效的判断。不要用评论数、字数或某次模型肯定作为质量指标。
