## 1. 先定义必须完成的效果

适用于一次业务操作经过数据库、消息系统或外部服务，出现“这一步可能已经成功，调用者却不知道”的情况。先列出必须保持的业务事实、每个资源能共同提交的记录，再推导恢复动作。一个函数依次调用了几个系统，不表示这些调用可以共同回滚。

本篇延续[重复、乱序与去重状态](message-idempotency-ordering.md)中的原创文档工作请求，并增加独立检查服务 E。接入程序 S 批准 `CreateAndCheck(A,K1,D1-v7,structure,basic-v3)`：

- A 是接入命名范围，K1 是该业务意图的稳定身份。同一 A/K1 永久最多创建一张工作记录 W1，输入必须与 S 的批准一致。
- D1-v7 是固定文档版本；basic-v3 是批准时固定的不可变检查配置版本。S 保存必要配置内容或可持续取得的不可变引用。重试不能重新解析当前 basic 别名。
- 外部检查步骤 X1 由完整 A/K1 与固定步骤 check 确定，永久最多产生一个外部任务 J1。消息重投、进程重启和人工重试均不能更换 K1 或 X1。
- “检查完成”需要 E 已完成检查，且匹配的实际结果在本地持久保存。S 已批准、Q 已保存消息、W1 已创建和 E 已接受任务，分别是可查询的中间事实，均不能显示为检查完成。
- 已批准工作不能静默丢失。完成依赖所需服务最终可用、输入和历史仍可取得、恢复工作得到调度、存储足够且 E 实际完成任务；永久故障时保持未完成及责任。

S 使用 DB_S；消费者 P 使用 DB_R；Q 是独立的持久消息系统；工作者 H 调用 E。Q 和 E 不参加这两个数据库的事务。本篇题设中的数据库以持久提交后才返回明确成功，已提交事实跨进程重启保留；本地事务明确中止会撤销其全部参与写入。提交响应可以丢失。读取恢复事实必须取得该资源可见的已提交结果；无法确认可见性时保留未知，不能拿陈旧副本的查无记录作为首次执行依据。

所有写路径遵守实际唯一约束与原子条件写。冲突事务整体退出，再读取已提交决定，不继续使用失败事务中的临时状态。这些是推演前提，需要在目标数据库版本、隔离方式与配置中取证，不是所有数据库默认具备的行为。

主线处理进程崩溃、响应丢失、重复交付和旧工作迟到。恢复旧快照、存储损毁和历史删除会破坏上述前提，单独在第 9 节处理。业务身份、消息身份和尝试身份的区别沿用前一篇；新增发送意图 I1、外部步骤 X1、外部任务 J1 及后文撤回操作 C1，不能混用。

## 2. 比较提交次序与较小方案

保持同一个“批准后不得漏做、同一操作不得多做”要求，在每个次序中插入一次崩溃：

| 候选 | 崩溃位置与后果 | 可采用的条件与代价 |
|---|---|---|
| 先保存批准，再发送 | 批准已提交，发送前崩溃；若没有可扫描的待发送事实，恢复者无法可靠找出欠下的工作 | 批准记录自身若带有共同提交、可发现的待发送状态，也是一种发送意图；不能另写一笔事务再声称无遗漏 |
| 先发送，再保存批准 | Q 已保存，批准事务中止；下游可能执行根本没有被批准的工作 | 下游可以拒绝未获批准输入，但这不构成原请求完整恢复方案，也不能把消息收到当成批准证据 |
| 批准与发送意图共同保存 | 提交前明确中止则两者都没有；提交后未发，扫描意图继续 | 增加意图存储、恢复扫描、重复发送及历史保留；仍需下游保护效果 |
| 直接同步调用 E | E 完成而响应丢失时，S 仍不知道结果 | 可省去 Q，但不能省去稳定身份、持久未完成工作和结果核对；是否使用 Q 取决于独立调度与持久交接需要 |
| 实际检查可在同一 DB 内完成 | 确定性检查计算及全部要求的状态写入由一个本地事务完成，恢复读取共同提交结果 | 业务完成要求保持，资源条件改变；确实没有独立 E 效果时优先考虑，不能把远程调用假装移入本地事务 |
| 跨资源原子提交 | 只有参与资源真正支持共同提交，协调决定持久保存且恢复、阻塞等待条件已明确，才有资格比较 | 本题 E 没有 prepare 或共同提交参与能力，因此不能套用两阶段提交解决主线 |

发送意图常被实现为数据库内的待发送记录，但表名或模式名不提供保证。关键是批准与意图确实共同提交，恢复者读得到尚未交接的工作，以及下游能够处理重复。若事务性消息系统在提交后才让消息可见，请求方不能在未提交发送的事务内等待下游应答：下游尚收不到请求，等待会阻止自己的前提成立。请求与结果接收分别保存依据。

## 3. 保存能够恢复的事实

以下是原创协议所需事实，不要求每一行独立建表。合并存储可以，但不得合并不同含义的完成状态。

| 持久事实与保存者 | 最少身份、输入与观察 | 必须共同提交的内容及读取用途 |
|---|---|---|
| S 的批准与 I1，DB_S | A/K1、操作类型、固定输入、I1、待发送状态 | 批准和意图同事务；R 扫描已提交且未取得交接证据的 I1 |
| R 的发送进度，DB_S | I1、领取代数 g、Q 保存证据及观察时间 | 比较当前 g 后保存交接进度；只能证明 Q 这一跳保存，不表示 P 或 E 完成 |
| P 的创建决定，DB_R | A/K1、批准输入、稳定创建结果、W1、X1 | 创建决定、W1、待执行 X1 同事务；重投按原输入复用，冲突不能新建 |
| H 的外部工作，DB_R | X1、完整外部输入、g、待执行/运行观察/未知/确证结果 | 当前 g 条件写保护；完成证据、实际结果和 W1 检查状态共同提交 |
| E 的权威检查记录 | X1、输入、唯一 J1、状态、稳定结果身份及内容 | 是否具备原子重复保护、可查询和保留能力见第 6 节，不能由 DB_R 推断 |
| 撤回批准与工作 | A/C1、X1/J1、原因、IC1、独立 g_C、撤回证据 | DB_S 共同保存批准与 IC1；DB_R 共同保存 C 接手决定、撤回意图和请求状态；完成另按 E 证据保存 |

外部工作至少区分以下含义：待执行表示持久工作仍在；执行中表示曾观察到接受或运行；未知表示尚不能判定是否产生效果；完成需要匹配的最终证据；“确证不会执行”需要 E 的持久拒绝且该 X 以后也不会执行。超时不是拒绝，领取到期不是失败，空 J 字段不是未执行。

检查历史结果与报告当前能否使用分列；撤回请求、撤回执行观察和已证实不可用也分列。原始创建响应始终指向同一 W1；S 按 A/K1 查询另一个检查进度及结果字段，不能重写创建历史来表达检查状态。

## 4. 从批准恢复到持久接手

主线从没有任何相关记录开始。S 在 DB_S 一笔事务内保存批准、固定输入和 I1。

若提交前明确中止，批准与 I1 均未生效，R 不得发送内存中的临时意图。若提交响应丢失，S 保留 A/K1 和输入，重新读取 DB_S 或沿相同身份的唯一保护重试；匹配记录存在则复用，冲突则停止并核对批准。不能因为客户端没收到响应就换 K1。提交后首次发送前崩溃，R 扫描已提交 I1 即可找到责任，不需要原进程还在。

R1 领取 I1 获得 g1，向 Q 发送 M1。Q 实际保存 M1，但保存响应丢失，R1 崩溃。DB_S 尚无 Q 保存证据；恢复的 R2 取得 g2，读取同一 I1，以相同 A/K1 和输入发送 M2。Q 可能拥有两份信封，这是允许的重复交付，后续效果由 DB_R 的唯一保护承担。

再考虑 R1 没有死，只是停顿：R2 已领取 g2 并发送后，R1 又把 M1 发出去。旧 g1 的本地进度更新必须在 DB_S 原子比较中失败，但这个失败不撤销 Q 的 M1。租约只帮助重新分工，不能证明旧网络调用停止。取得 Q 成功响应后、更新 I1 前崩溃，也会重发；只有获得与该意图匹配的 Q 保存证据，当前领取者才可标记这一跳完成。

P1 收到 M1，校验消息的 A/K1 和固定输入确实对应 S 的批准。题设要求它能取得权威批准或等价可验证依据；仅凭“第一条到达的消息”不能建立授权。P1 在 DB_R 同一事务中写入 A/K1 创建决定、W1 及 X1 待外部意图。唯一约束保护所有竞争路径。明确中止时三者均未发生，不确认 Q；响应未知时先读 DB_R，不猜测成功或重新生成 X。

主线中该事务实际已提交，P1 在确认 Q 前崩溃。P2 收到 M2，取得已提交决定、比较完整输入，复用 W1/X1。DB_R 的恢复扫描与实际工作者能够持久承担 X1，P2 才确认 Q 这一跳已接手。若 Q 没收到确认，会继续重投，仍复用同一决定。这时 E 可以完全尚未被调用，S 显示“工作已创建、检查待执行”。

这里的逐项消费进度就是按 A/K1 保存的完整接手决定。Q 中未确认消息由消息交付恢复；Q 已确认后的未完成检查由 DB_R 扫描 X 恢复。只扫描 Q，或只扫描创建状态而漏掉 X，都会遗漏已经转移的责任。

## 5. 连续消费位置不能越过空缺

如果输入改用日志，这是另一个明确条件分支：日志 L、分区 P0 和日志世代稳定，位置不复用，所需输入还在保留范围，并能从指定位置重读。DB_R 的 `Progress(L,P0)` 保存最后连续接手位置 p、版本 v 及当前处理代数 g_L。p=6 表示下一条必须从 7 恢复，不是已见最大位置，也不表示 E 完成到 6。

采用最小的连续串行接手方式。处理位置 n 的事务，必须先原子比较共享 Progress 的当前 g_L、v 和 `p=n-1`，再按 A/K 唯一保护创建该条 W/X，并把 p 改成 n、更新 v。这些写入共同提交。即使不同位置属于不同业务键，也必须竞争同一 Progress 记录；各自业务键唯一不能保护共享位置不倒退或跳过输入。

当 p=6 而位置 8 先到，8 的前置条件不成立。该事务不提交 W/X，也不把 p 设为 8，不确认已连续接手 8。先取回 7，共同保存其 W/X 与 p=7，再处理 8 到 p=8。若 7 提交后响应丢失，新处理者读到共同保存的 p=7 及本地事实，从 8 继续。若 7 明确中止，p 仍为 6，从 7 继续。

两个处理者若同时基于旧 v 写进度，只有满足当前 g_L/v 的一个可提交，另一个整体退出后重读；旧代数不能提交。消息系统观察到的位置即使已经是 8，也不是恢复起点的权威依据。这里仍只证明本地接手，外部 E 依旧独立。输入不可重读、日志世代改变或旧处理者可绕过资源保护时，当前方案不能继续证明正确恢复，不能靠补写位置制造缺失输入。

## 6. 外部能力决定未知后的动作

H 从 DB_R 取得 X1 及固定输入，用本地 g 领取。E+ 和 E- 是两种虚构能力组合，沿用相同业务要求；不是任何真实产品的能力声明。

| 能力 | E+ 题设给定 | E- 题设给定及影响 |
|---|---|---|
| 操作身份及输入 | 按完整 X 保存输入，相同 X 异输入冲突 | 无按 X 保护；每次到达可能创建新 J |
| 并发重复保护 | 所有提交路径在 E 的原子范围内共同保存 X 与唯一 J；重发复用原任务及结果 | 无此能力，客户端本地唯一约束不能替它保护 |
| 结果查询 | 按 X 返回匹配输入、J、执行状态与稳定结果；可区分拒绝、未见和不可得 | 无按 X 权威查询，超时后可能连 J 都不知道 |
| 保留 | 所需身份、输入、决定和结果持续保存，覆盖允许的重试及迟到请求 | 没有支持永久至多一次的保留保证 |
| 拒绝及取消 | 明确持久拒绝可排除该 X 以后执行；取消等待本身没有该含义 | 不提供旧请求不会再执行的证据 |
| 撤回 | 按独立 C 保护并查询，撤回决定与报告不可用共同保存；迟到 X 不清除撤回 | 未给出可安全重复的撤回能力 |
| 共同提交 | 不参加 DB_R 事务，不提供 prepare | 同样不提供，不能由调用顺序补出原子性 |

E+ 下，H1 发送 X1，E 创建 J1 后响应丢失。本地 g1 过期，H2 取得 g2。H1 的旧网络请求仍可能继续；H2 使用相同 X 和相同输入查询或重发，E 的全部路径持久唯一保护才保证仍是 J1。H1 更新 DB_R 时被 g1 条件拒绝，只说明本地旧写未生效，不说明其外部调用未发生。

E- 下有两条对 H 完全相同的历史：第一条，请求未到 E，H 看到超时；第二条，E 已创建 J1，响应丢失，H 同样看到超时。对相同观察作同一重试，会在第二条可能多建任务；直接放弃，会在第一条漏做。因此原“不得漏做且永久最多一个 J”的要求在给定能力下无法同时保证。应记录方案不足，保留 X、批准输入、每次尝试与观察、可能仍在执行的请求、实际责任者及需要取得的证据。停止新的自动调用可以限制新增风险，不能证明旧请求失败或停止；人工接手也不会创造丢失的历史。

只有查询而没有重复写保护的第三种服务也不够：查询说未见 X 时，旧调用可能仍在途中。必须另有原子重复保护，或充分历史及旧调用不会再生效的证据，才可判断重做是否安全。一个已查到的 J 只证明它存在；“只有一个”还依赖覆盖全部写路径的唯一保护。

## 7. 从未知取得结果并完成本地记录

继续第 4 节主线。DB_R 已保存 X1，H 调用 E+，E 已完成 J1，却丢失响应。H 不能写“检查失败”，而是保存 X1 的未知观察。恢复者扫描未完成 X1，先核对 S 批准的 A/K1、D1-v7、structure 和 basic-v3，与 DB_R 的 X1 完整组成、固定输入和最后观察一致，再向 E 按 X1 查询。

| E 的当前有效证据 | 证明的事实 | 当前领取者允许的下一步 |
|---|---|---|
| 匹配 completed | 此 X、输入及 J 有已完成的检查结果 | 校验结果身份与实际内容，持久补记，不再提交新的检查任务 |
| accepted 或 running | E 已接手或仍执行 | 保存观察，继续按同 X 查询；不能标记检查完成或承诺一定成功 |
| 持久 never-execute 拒绝 | 该 X 未执行且以后也不会执行 | 保存拒绝证据及业务未完成结果；任何替代动作需新的业务决定 |
| 当前未见记录 | 这次查询未看到记录 | 保留可能在途；仅凭 E+ 完整重复保护，才可用相同 X/输入重试 |
| 查询不可得或可能陈旧 | 没有足够的当前证据 | 保存未知与复核责任，不能以空结果补成失败或成功 |
| 输入冲突、多个 J、历史缺失 | 原保护假设或身份关系不成立 | 保留冲突原貌并核查，停止自动产生新效果，不覆盖成一致 |

主线取得 E 的匹配 completed，带 X1、规范输入、J1、稳定 result_id 和结果正文。恢复者验证这些字段与批准、DB_R 记录一致，并校验内容。DB_R 一笔事务内比较当前 X1/g，保存外部完成证据、不可变结果正文以及 W1 检查完成状态。也可保存由本地控制并保证持久可取得的内容引用及校验值，但只有 result_id 或外部临时 URL 不足以满足完成要求。

这笔提交响应丢失时，恢复者读取 DB_R 的结果记录；已持久完成则复用，不因自己没收到响应再次产生效果。重复查询或回调仅重复观察，不再次发起检查。没有当前 g 的回调只保存原始观察并唤醒当前领取者，不能直接覆盖完成状态。旧查询结果不能把已完成降回运行，也不能覆盖后续撤回事实。

最后，S 按 A/K1 查询，仍得到原创建结果 W1，并取得已保存的检查结果与检查完成状态。这条路径经过 Q 保存响应丢失、消费提交后未确认、E 完成响应丢失三个断点，每一步都从持久事实恢复；它没有要求原进程存活。

这里的对账是比较三方记录并据证据补记：S 证明批准身份及版本，DB_R 证明已接手的 X 和本地状态，E 证明外部执行与结果。记录证据来源、取得时间及相关版本，判断陈旧性与覆盖范围。迟到的有效匹配结果可补记；缺失不自动允许重做；相互矛盾的证据必须继续核查。修改记录让两侧表面相同，不是恢复正确性。

## 8. 撤回作为独立业务动作恢复

检查已完成后，业务可能批准撤回报告。这是补偿的一种具体含义：让外部权威报告不再可用，不撤销计算成本、已经读到的内容或取得的副本。原检查发生及其结果历史必须保留。若只是补记已发生的检查结果，则是向前修复记录，不需要撤回；不能因为原调用超时就自动做反向动作。

S 在 X1/J1 和匹配结果已经确证后，独立批准 `Withdraw(A,C1,X1,J1,reason)`。C1 是新操作身份，完整输入包括关联的原批准与结果引用。DB_S 同一事务保存撤回批准、完整输入和 IC1。若提交响应未知，仍按同 A/C1 读取或在唯一保护下重试；不能换 C。主线在提交后首次发送前崩溃，R 扫描 IC1 恢复，用原 C 投递 Q。

P 校验 C 的批准输入，在 DB_R 一笔事务中保存 A/C1 接手决定、绑定 X1/J1/原因的 WithdrawIntent 和 `withdraw_requested`。如果创建 A/K1 已经完成，也不能沿创建去重分支直接丢弃这条撤回消息。此事务提交后、Q 确认前崩溃，重投读取匹配 C，复用撤回意图；DB_R 有实际可工作的撤回扫描与责任者后才确认 Q。此刻只有撤回请求已被持久接手，还没有证据显示 E 报告不可用。

H 分别扫描 X 和 C，按 C 的独立领取代数 g_C 执行。E+ 在其原子范围内保存 C 的撤回决定，并将 J1 权威报告标记为不可用，全部报告读取入口遵守该标记。本次响应丢失，H 留下未知。下一领取者从 C 意图及批准恢复，以同 C/输入查询或受保护重试；取得匹配撤回决定后，在 DB_R 比较当前 C/g_C，共同保存撤回结果、证据与报告使用状态。accepted/running 只表示已接手或仍执行，不能提前显示撤回完成。

重复 C 复用决定，异输入 C 冲突。旧 g_C 的本地更新被拒绝，外部重复效果仍由 E 的 C 保护负责。迟到的 Submit(X1) 在 E 只复用原检查历史，不能清除撤回标记；迟到 completed 回调在本地只补检查事实，不覆盖撤回请求、已证实撤回或 C 终态。回调没有当前代数时只保存观察。

若 E 明确撤回失败，保存失败和原因，保留原报告状态；若查询不可得，保存未知；若没有 C 的重复保护，不能规定“一律重试”。新的修复动作取决于具体业务批准与新证据。X 本身仍未知时，不满足本题撤回前提：先查原效果与旧工作是否还可能生效，不能用撤回调用掩盖未知。即使撤回确证完成，也不能把已消耗资源或已泄露的信息恢复为从未发生。

## 9. 历史丢失与恢复旧数据

正常恢复依赖批准、意图、完整输入、决定、X/C 关联及必要结果持续保留。题设没有可信重放截止时间，因此不能从 Q 保留期推出业务去重记录的有限 TTL；人工重试、旧进程和外部在途请求可能晚于 Q 的保留期。复核期限是安排下一次检查，不是到点删除责任。

现在改变条件：DB_R 恢复到没有 W1/X1 的旧快照，但 E 的 J1 仍然存在。此时查无本地记录不表示首次执行。暂停全部受影响效果路径，包括普通消息消费、自动重试、人工入口和直接调用；仅停重放入口不够。暂停新增动作也不能抹去已经在途的 Q/E 调用，要继续保存其未知及责任。

恢复到可继续，至少需要分别取得两类资源证据：

1. 本地批准、操作输入、创建历史、发送与撤回意图、结果及消费进度重新一致。旧本地写者被实际写资源排除，或所有写路径都重新受到已恢复一致历史、唯一约束和条件写保护。只修改一个内存租约值不足以排除仍可写数据库的旧者。
2. 外部旧调用由仍有效的 X/C 持久保护约束，或已有明确证据表明不会再生效。E 只创建一个 J，不能证明本地 W、C、配置版本和消费位置正确；本地写保护也不能证明外部请求停止。

任一证据缺失则不能安全继续，不得通过生成新 X 或 C 绕过历史。如果 E 清除了 X 的去重历史，现存的 J 查询结果也不能自动恢复全部写路径的唯一保护；永久至多一次的原承诺已经失去前提。必须取得可证明的拒收或旧工作排除机制及相容历史，或者继续保持未完成，不能默默改成有限时间保证。

本节只列出该协议继续工作的必要证据，不提供完整快照与日志交接、删除传播、派生重建或其正确性证明；这些属于独立恢复设计，需要另行展开。框架检查点恢复只能回退其实际覆盖的状态，不能撤销已经发送到 E 的动作。

## 10. 责任、成本与停止条件

| 未完成工作 | 持久保存者与恢复触发 | 何时可解除这一跳责任 |
|---|---|---|
| 未发送的 I/IC | DB_S；R 重启及持续扫描已提交意图 | 获得匹配 Q 保存证据并在当前领取下持久记录；没有完成业务的含义 |
| Q 尚未被接手的消息 | Q；重投及消费者恢复 | DB_R 已共同保存对应接手决定及可恢复 X/C，恢复者实际可接手 |
| X 未完成或外部未知 | DB_R；H 扫描、查询及观察唤醒 | 取得匹配最终证据并共同保存实际结果；明确拒绝单独记录未完成业务后果 |
| C 未完成或未知 | DB_R；独立撤回扫描及查询 | 保存匹配撤回决定与报告状态；明确失败单独保留，不能冒充撤回完成 |
| 证据冲突或历史缺失 | 保存原始事实的资源及实际接手的核查者 | 取得可支持下一动作的证据；填入负责人名字不等于实际接手 |

需要具体落实扫描运行、持久容量、工作调度和告警接手。允许重试前检查目标能力、原身份及输入、当前领取和历史是否仍满足条件；未知分支安排有界尝试与下次复核，不能靠无限循环承诺最终成功。异常副本即使另存，也只有真正取得接手证据才可释放原责任，见[消息交付、确认与异常处置](message-delivery-acknowledgment.md)。

相较于单资源方案，本方案多保存批准/意图/接手/外部历史，增加扫描与领取等待、重复网络传输、结果保存及冲突核查成本。容量不足时停止受理无法履行的新承诺，保留已有 I/X/C/Q 责任并安排实际接手；不得为了恢复吞吐清空未知记录。永久不可用或证据已不可恢复时，承认未完成及无法安全自动恢复，不把“等待人工”当成成功路径。

应用本方法的交付应具体写出：要求的效果与稳定身份，各资源共同提交范围，逐个故障窗口的可读事实，未知时下一项证据，历史保留和实际责任，以及仍缺少的平台证明。若所有效果确实在一个可靠的本地事务中，采用第 2 节较小方案即可，不为了展示消息模式增加组件。
