## 1. 何时使用

已有明确行为，但还不能说清“怎样知道做对了”，或需求变化后需要判断哪些说明、实现、检查和既有结论仍适用时，使用本方法。验收依据是**某个版本的要求、它所规定的预期结果，以及判断实际结果时采用的观察方式**。仅列场景名称或取得一次成功响应，还没有形成足够依据。

先取得当前任务范围、行为及其业务理由、适用对象和版本、已知约束、未决项，以及已有检查和结果。没有已有实现或结果时直接记为无，不为填表虚构记录。

同一句话仍可解释成不同结果时，先按[需求澄清方法](requirements-language-behavior.md)解决会改变下一步的歧义。这里不替业务人员选择政策，也不把书中建议当作当前项目事实。当前任务已有明确授权时沿用授权；方案分析本身不产生实施或发布授权。

只修改错别字且含义、用户操作和外部引用都未改变时，核对受影响文字及必要链接即可。需要取消、补偿、兼容或不同版本并存时，展开后续步骤。分析深度由具体影响决定。

## 2. 从行为得到可检查的预期

### 2.1 先确定“依据是什么”

为本次需要追踪的行为保留稳定标识，并说明适用版本。标识连接理由、预期、实现位置和检查记录；编号本身不能证明要求正确。文档可保存完整有效要求，也可保存可还原的版本差异，避免只留零散修改而无法确定当前要求。

把以下判断分开：业务负责人确认的选择是否表达实际需要；文字和示例是否清楚一致；实现是否符合已确认要求。第一项尚待确认时，可以分析候选结果，但不能把候选结果登记为已批准要求。

| 已有依据 | 如何形成预期 | 还不能证明什么 |
| --- | --- | --- |
| 已确认的业务规则、公式或状态变化 | 由规则独立推导结果，保留单位、取值范围、边界包含关系 | 规则符合所有使用者需要，或实现已满足规则 |
| 有效的外部规范或接口约定 | 核实适用版本、对象和例外，再列可观察结果 | 对方真实系统的当前行为必然符合文档 |
| 现有系统行为 | 记录“目前如此”及观察条件，供兼容分析或行为刻画测试使用 | 当前行为就是希望保留的行为 |
| 解释不一或缺少业务决定 | 列能区分解释的输入、不同候选结果和待决定事项 | 任意一个候选结果可以作为通过标准 |

预期值不能直接由待检查的生产函数生成，再用同一个函数的输出验证它自己。根据已确认规则手算、建立简单且规模小的独立参考模型或使用经核对的参考数据；独立方法也须说明假设和局限。没有精确值时，可以检查可靠的关系或性质，但“总数不变”可能只排除一类错误，不能证明每个对象都处理正确。重复运行得到相同结果同样不能证明结果符合需要。

### 2.2 将条件、动作与结果连起来

为每一项必要检查写清：

1. **条件与对象：** 谁、哪一个对象、哪一版规则、什么初始状态；哪些前提已给定，哪些仍未知。
2. **输入与顺序：** 触发事件、取值及单位、发生或接收时间，以及会改变结果的先后顺序。明确使用哪个时间点，不混用客户端点击和系统接收时间。
3. **预期变化：** 允许发生什么、不得改变什么、最终能看见什么。响应文字、持久状态和外部副作用分别列出，不能彼此代替。
4. **依据与范围：** 哪条已确认要求支持该结果；只能判断局部函数、协作过程还是用户可观察的完整行为。

至少检查与当前规则有关的正常情况、阈值前/恰好阈值/阈值后、拒绝条件和结果未知情况。组合数量过大时，按会改变决策的条件划分，并说明未覆盖的组合及原因。不要从“表里没写”直接推断“不允许”：它也可能是遗漏或尚未决定。

让每项重要检查能排除一个具体错误。例如截止要求为 `t < D`，只选很早的时刻无法区分错误实现 `t <= D`；必须保留恰好 `D` 的输入。反例用于核对判别能力，不意味着当前项目已存在这种错误。

## 3. 选择观察方式并约束结论

先确定需要支持的结论，再选择测试、演示、检查或分析。局部计算可用小范围检查；入口到持久状态或外部副作用的结论，需要能观察相应协作的证据。不能用对象级检查通过代替系统协作检查，也不为每个局部判断强制搭建完整系统。

| 记录状态 | 需要的依据 | 可以作出的结论 |
| --- | --- | --- |
| 预期已明确 | 有有效要求、给定条件及可推导结果 | 已知道应当发生什么 |
| 观察方式已准备 | 能设置条件、触发操作并读取所需事实；明确观察时限和失败诊断 | 已具备检查计划或接入能力，尚无执行结论 |
| 已执行、结果可判断 | 保存实际版本、条件、步骤、观察与预期的比较 | 这些条件下符合或不符合要求 |
| 未执行、受阻或无法判断 | 说明未执行原因，或缺失的事实/预期/观察能力 | 当前证据不足；不能登记为通过 |

结果记录至少能回答“检查了什么版本、在什么条件下、实际看到了什么、支持哪个结论”。按需要记录构建、配置、数据、时钟和依赖版本，不要求所有任务填写无关字段。

失败时先定位是否到达目标判断点。编译错误、环境不可用或前置数据错误，不能算业务规则按预期拒绝了请求；“收到非成功响应”也不能证明拒绝原因正确。记录预期原因、实际原因及业务状态，避免通过忽略失败来掩盖未完成工作。

超时或响应丢失只说明调用方尚未得到结果；它既不能证明没有副作用，也不自动允许重试。缺少查询、重复处理或补偿要求时保留未决。要求使用“立即”但没有可测时限时，业务状态规则可能已明确，时间性能仍无法判断；不得擅自填写毫秒数。

“检查通过”“需求范围验收完成”“可以发布”是不同结论。前者只涉及已执行的条件；后两者还分别取决于所声明范围的遗漏与未决项、当前授权以及适用的运行准备。不要自动扩展当前任务。

## 4. 判断变更影响与旧证据的适用性

### 4.1 固定比较对象

先写旧要求、新要求、改变的业务条件与理由、适用对象及生效方式。新建对象、已有对象、在途操作是否用同一规则，须有依据；不能用修改文档的时间替代业务生效规则。尚未接受的建议与已接受修改分别记录，已有授权不必重新请求。

分析者列出工作量、依赖、兼容和时间后果，交给当前有权决定范围的人；缺乏估算依据时说明缺什么，不编造日期。逐项很小的新增要求也应汇总其累计范围影响。保留提出者、决定者、决定内容及其适用范围，累计查看已接受的新增要求。决定接受、拒绝或暂缓后，分别跟踪需要落实的成果或保留未决理由，不能把“已接受”当成“已完成”。

### 4.2 沿具体关系查影响，再反向核对

从改变的条件出发，逐项检查：用户操作和说明、接口语义与消息格式、状态/数据/实现、检查预期及接入、运行观察与切换、以前据此作出的结论。每项写清为什么相连，并登记：

- **需修改：** 哪个行为或解释失效，改成什么，怎样取得新证据。
- **确认不变：** 依据是什么；不变的是业务要求、实现还是某份结果，不能混写。
- **待核实：** 缺少哪个依赖事实，谁或什么材料能补足，阻断哪一步。

沿确定受影响的对象继续查其依赖，直到有依据说明影响不再传播，或将无法判定的范围明确列为待核实。有关联不等于必须修改；没有关联记录也不等于没有影响。挑关键接口、状态变化或检查反向追到业务理由，寻找漏记依赖。无需求依据的设计可能是多余设计，也可能是需求漏写，先查明再决定。

### 4.3 分别判断可复用的东西

| 对象 | 可以复用的条件 | 应做的事 |
| --- | --- | --- |
| 场景数据 | 对象、版本、单位和初始状态仍满足新条件 | 调整适用版本及边界数据；不因记录外形相同就复用 |
| 检查步骤或接入代码 | 仍能设置并观察目标行为 | 接口或观察方式改变时修改接入，业务预期不因此自动改变 |
| 预期结果 | 对应条件下的业务要求未变，推导仍成立 | 保留出处；为改变的条件重新推导预期 |
| 历史通过结果 | 旧结果对应的要求、实现及相关环境/配置/数据仍适用，或有足够依据说明差异不影响所声明结论 | 保留原始版本与范围，写明复用理由；无法说明时重新取得结果 |

预期未变，不代表历史通过结果仍能证明修改后的实现。保留旧结果供追溯，将它对新版本的证明状态记为“不再适用”或“待重新检查”；不要改写历史，使其看起来曾执行过新要求。需求改变的检查重新进入待完成工作，按新要求修订后再取得结果，不批量删除无关回归检查。

## 5. 原创推演：取消截止提前

以下是新写的静态推演，未执行程序或 Skill，也不是实际项目事实。它延续需求澄清方法中的“青岚社区工作坊”，用于展示如何建立依据和影响关系。

### 5.1 题设与适用版本

已有题设：活动容量为 2；本例只考察某场活动中某人的一份有效申请，格式、身份与访问权已核实，重复提交和重复取消不在推演范围。收到申请不占名额，获位才占名额；取消参与与释放名额是两个结果。`S` 为开始时刻，`t` 为系统受理取消事件的时刻。

旧要求 `R-CANCEL@V1`：**名单尚未交付、申请已获位且 `t < S`** 时，接受取消，取消该申请的参与并释放其原占名额一次；`t >= S` 拒绝取消并保留占位。

本节新增的虚构题设：组织者已决定，`R-CANCEL@V2` 仅将上述“名单未交付且已获位”的允许条件改为 `t < D`，其中 `D < S`；从 `D` 起拒绝该分支的取消并保留占位。V2 只适用于采用新规则新建的活动，已有活动继续使用 V1。每个活动保留明确的规则版本及固定 `D`、`S`；本例不包含再次修改活动时间。这些是推演给定条件，不是上一方法已经确认的事实。

为便于读表，取一个虚构 V2 活动：`S = 20:00`、`D = 19:50`，二者在同一天、同一时区。十分钟只是本题数据，不是推荐政策。既有 V1 活动也取 `S = 20:00`，其中 `D` 仅用于对照，不参与其判断。

仍未决定：名单已交付且申请在名单内时，开始前取消与释放怎样处理（`U-LIST`）；名单已交付但申请不在名单内时的开始前政策；竞争最后一个名额的选择规则；重复请求、结果查询与恢复方式；“立即”的可测时限。收到申请但未获位者没有名额可释放，但其撤回政策仍未给定。不能用本次局部修改填补这些空白。

### 5.2 独立推导预期，并指出应观察什么

下表前四行均为名单未交付且已获位；比较时使用各自活动适用的 V1/V2。结果来自上述条件与时间比较，不调用任何生产判断函数。

| 输入或条件 | V1 的静态预期 | V2 的静态预期 | 需要的观察或待决项 |
| --- | --- | --- | --- |
| `t = 19:49:59`，截止前 | 接受；参与取消，原占名额释放一次 | 同左 | 业务结果、参与状态及原占名额变化一致 |
| `t = 19:50:00`，恰好 D | 接受并释放 | 拒绝；参与与占位保持 | 拒绝理由与截止有关；错误的 `t <= D` 会在此暴露 |
| `t = 19:59:59`，D 后且 S 前 | 接受并释放 | 拒绝；参与与占位保持 | 同一输入能区分旧、新规则；不能按客户端显示的旧截止判断 |
| `t = 20:00:00` 或之后 | 拒绝；参与与占位保持 | 同左 | 等于 S 已属于拒绝范围；这不解决名单分支在 S 前的政策 |
| 已收到申请但未获位 | 没有占位可释放；撤回结果未知 | 同左 | 未获位者不能凭取消产生一个新名额；撤回政策待决定 |
| 名单已交付，`t < S` | 在名单内、未在名单内分别待决定 | 同左；不能套用只改名单未交付分支的 D | 交付状态与申请是否在名单内是两个条件 |
| 在允许时刻受理，但调用方未收到响应 | 不能据此认定失败或无副作用 | 同左 | 需取得业务处理事实；查询与重复处理规则未给定，暂不能判断重试结果 |

对于接受分支，观察“处理完成”必须能区分收到请求、取消参与、释放名额。释放生效后原名额即可供后续分配，不以用户收到响应为前提；如何竞争这个名额仍未决。对于拒绝分支，只见状态码不足以证明占位未改变。后续检查者须将处理结果与同一份申请、同一活动及其规则版本对应，并取得参与状态和原占名额事实；本题没有给出查询入口或日志，具体观察接入仍待设计。

若观察通道只能看到“请求已收到”，记录为尚不能判断业务结果；不要通过等待任意时长把它改成通过。若未来建立检查，应能识别环境故障、前置状态错误和业务结果不符。本文没有这样的执行记录，所有行仍是静态预期。

### 5.3 具体影响与反向检查

| 对象及与变更的关系 | 判断 | 需要落实的内容或依据 |
| --- | --- | --- |
| 活动规则：取消允许条件读取活动版本 | 需修改 | V1 按 S；V2 在指定分支按 D；不能用全局新规则覆盖既有活动 |
| 取消入口及客户端：双方解释可取消时间 | 需核实后修改受影响部分 | 即使请求/响应字段不变，业务含义也已变；确认现有入口能否按活动版本给出正确结果，客户端是否自行用 S 开关按钮。是否新增字段取决于现有接口能力 |
| 活动数据：恢复当时适用规则 | 需核实 | 现有数据是否已保存所需版本与时刻；不足才补数据与迁移方案，不能假定必须增加数据库表 |
| 检查预期：D 附近的可取消结果 | 需修改 | 保留 V1 数据与预期，新增 V2 及恰好 D 的拒绝条件；受理时间须可控制或准确观察，尚不具备时记为检查受阻 |
| 开始前很早的允许结果、S 起的拒绝结果 | 预期确认不变；历史结果需重审 | 题设保留这两类结果，但共享判断实现改变后，旧通过记录不能直接证明新构建正确 |
| 名额容量 2、收到申请不占位 | 要求确认不变 | 本次只改取消截止；若实现共享占位处理，仍须检查实现影响，不能由要求不变推断代码无影响 |
| 运行与支持：解释一个活动为何可以或不可以取消 | 需核实 | 是否能识别活动版本、比较的时刻及处理结果，旧客户端和回退版本能否理解 V2；没有这些事实时不能宣布可以切换或回退 |
| 用户说明和客服答复：原先统一说“开始前” | 需修改 | 根据活动版本表达有效截止；不把 V2 说明追溯应用到 V1 |
| 既有结论：“所有活动在名单交付前都可取消至 S” | 对混合版本不再适用 | 缩小为满足 V1 前提的结论；V2 另有依据，历史记录仍保留原适用范围 |

从客户端“在 S 前展示取消按钮”反向追到原 V1 规则，可发现字段未变但界面判断过期的依赖；只搜索接口定义文件会漏掉它。反向检查的对象不是因为在表中相连就必须重写，而是因为它使用了已经改变的条件。

这张表已经指出确定变化、确定保留和未知事实，但不能给出可信工期：现有接口、数据和客户端能力尚未核实。也不能宣布整个报名功能完成；名单相关未决项仍阻断覆盖这些分支的完成声明。当前可完成的只是这一局部修改的预期与影响分析。

## 6. 交付与停止条件

按当前任务留下可用的最小成果：有效要求与版本、必要条件和独立推导的预期、观察方式及其当前状态、影响判断和旧结论适用范围。已有项目记录能表达这些内容时直接更新，不另建重复台账。

本方法的分析完成条件是：他人能知道依据哪个要求、如何判断目标行为、哪里需要修改、哪些证据尚缺、结论适用于哪里。若任务还包括实现或验收，则依相应范围取得执行证据；完成分析不等于完成实现。

以下情况停止依赖相应结论的操作，同时继续不受影响的部分：

- 没有业务依据决定预期，或强制要求互相矛盾：回到需求澄清，保留候选结果和决定事项。
- 关键事实观察不到、未到达目标判断点或结果不确定：登记受阻与缺失证据，不能给出通过结论。
- 变更的对象、生效版本或已有对象处理方式未定：不擅自改变已有对象；先完成不依赖该决定的分析。

小修改在含义、依赖及所需检查均已确认后即可结束；不因使用本方法而启动全部流程。结果明显超出当前任务时，说明需要的下一步，不自动实施、通知他人或发布。
