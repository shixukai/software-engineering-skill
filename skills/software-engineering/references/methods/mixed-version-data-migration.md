## 1. 先确定哪些信息必须保留

数据迁移完成，意味着当前数据和仍会到达的数据能够被相关读写者正确处理，必须保留的信息没有在过渡中丢失，并且有证据支持当前阶段的完成判断。数据库增加了一列、迁移工具返回成功或应用启动正常，都只说明其中一部分。

数据的生命周期往往长于生成它的应用版本。新代码发布后，历史记录、备份、失败消息和未升级客户端仍可能带着旧格式出现。恢复应用文件与恢复业务数据必须分别判断；恢复旧快照可能同时丢掉发布后的新交易。来源 C1、C5–C7、D4。

使用本方法前，从当前任务取得这些信息：

| 要确定的事实 | 它影响什么决定 |
|---|---|
| 字段的业务含义、单位、范围、精度和缺值含义 | 新旧表示能否准确互换，缺值能否补全 |
| 必须保留的已接受数据及其时间范围 | 哪些恢复、删除或转换会违反目标 |
| 当前写入者、读取者、后台任务、客户端和消息通路 | 谁可能继续制造旧格式，谁不能理解新格式 |
| 当前结构、实际数据分布及历史格式 | 是空库初始化，还是有状态升级；哪些记录会违反新约束 |
| 实际存储的原子更新、锁定、版本比较及迁移能力 | 怎样处理并发写、提交未知和中途失败 |
| 可接受的读写暂停、资源使用和操作权限 | 能否分批处理、暂停切换，何时必须停止 |

将“谁是权威值”写清。两列都有值，不等于两列都可以独立修改；两套数据库相互复制，也不等于它们能够同时决定同一业务事实。每个阶段都需要一个可解释的读取和写入规则。来源 C8；具体权威值安排为工程适配 A2。

如果旧数据缺少必要含义，不要为了通过结构校验填写零、空字符串或猜出的平均值。先区分缺失、无效和真正的零，保留异常并取得业务处理依据。新增约束之前检查既有数据和所有写入路径；“只加字段”也可能因默认值、必填要求或旧程序写法而失败。来源 C2–C3、D2。

候选产物与已验证组合先按[同一制品与晋级证据方法](artifact-promotion-evidence.md)核对。部署动作仍在执行或结果未知时，结合[部署中断与收敛方法](deployment-interruption-convergence.md)确认真实执行状态，不能把停止本地脚本当成旧写入已经结束。

## 2. 用同一项变化检查混合读写

### 2.1 原创题设

以下是原创静态题设，未执行迁移或案例。虚构展馆保存播放计划，原来只支持 1 至 120 的整数分钟，现在需要支持 1 至 7,200 的整数秒，包括 90 秒。已接受计划的时长必须准确保留，不允许舍入，也不允许丢失发布后新建的计划。业务允许预定的短时写入暂停；具体时间由任务约束给出，本例不假定统一时限。

权威数据在一个文档存储内，每条记录有不可复用的 `id`、递增的 `revision`、`title` 和 `duration_minutes`，新表示使用 `duration_seconds`。本题没有跨记录业务约束，并明确给定以下能力：

- 可以按 `id` 和已读取的 `expected_revision` 原子地替换一条现存记录；成功后版本号加一，比较失败就不执行该次替换。
- 修改者可以在一次原子替换内更新两种表示并保留其他字段。这不等于两次独立写入，更不等于跨数据库双写。
- 可以阻止新修改，并逐项确认已有写操作已在真正执行的位置结束，再切换规则和应用模式。无法取得这个证据时，后续切换必须停止。
- 可以从一致快照取得回填起点的记录标识集合。扫描期间新记录由受控的新写入者直接生成完整表示，切换前再检查当前完整集合。

这些都是题设能力，实际使用时需要按存储和部署平台的具体版本核实。缺少其中一项，应调整方案或停止相应步骤，不能由 Skill 补出不存在的保证。

### 2.2 三个应用版本

| 版本 | 读取规则 | 写入规则 |
|---|---|---|
| V0 | 只理解整数分钟 | 按记录版本构造整条旧模型并替换，不保留未知字段 |
| V1 | 兼容期以分钟为权威；需要秒数时从当前分钟计算 | 新建和修改时长时一次写入分钟及 `秒 = 60 × 分钟`；修改标题保留其他字段 |
| V2 | 兼容模式与 V1 相同；秒模式只以秒字段为权威 | 兼容模式保持两字段；秒模式写整秒，能准确转换时同步分钟，不能时移除分钟 |

V1 不是支持任意秒值的版本。它只能帮助完成兼容过渡。V2 可以先在兼容模式下部署，等数据、访问者和切换条件满足后再开放新精度。

V0 的问题不仅是“不认识新字段”。它读取含有秒字段的记录，修改标题，再按旧模型写回时，会把秒字段丢掉。即使它没有主动修改时长，读改写仍会破坏新数据。来源 D3；本题的字段和操作为适配 A5。

### 2.3 逐项判断支持关系

| 写入与读取组合 | 本题结果 | 不能省略的条件 |
|---|---|---|
| V0 写分钟，V1 或 V2 兼容模式读 | 可以从当前分钟解释时长 | 仍处于分钟权威阶段，缺少秒字段不被解释成零 |
| V1 写完整两字段，V0 读 | V0 可准确读取分钟 | 仅证明这次读取；V0 随后写回可能删除秒字段 |
| V2 写 120 秒，V0 读 | 若保留分钟为 2，该值可准确读取 | 一个可表达的值不能证明旧版本支持全部秒级记录 |
| V2 写 90 秒，V0 或 V1 读 | 无法准确表示，明确不兼容 | 不得返回 1 分钟、2 分钟、零或过时的旧分钟值 |
| V0 整条替换，新版按秒读取 | 可能丢秒字段或把旧含义写回 | 秒模式前必须终止、隔离或升级真实旧写入路径 |
| V2 修改标题，V2 读 | 可以保持时长和其他字段 | 实际更新保留未知字段，且版本比较在真正写入时成立 |

新代码读旧数据与旧代码读新数据是两个独立方向；读取、修改后写回、转发又是不同路径。来源 D1、D3、D6。实际表格应只列任务涉及的组合，但不能用“解析成功”替代业务含义正确，也不能用一个成功样本覆盖全部数值范围。

若旧客户端不能升级，而业务又要求它准确处理 90 秒，本题的旧整数分钟接口就不能满足要求。必须调整发布顺序、保持原能力或另行设计可接受的接口方案；不能把冲突藏在四舍五入中。

## 3. 分阶段扩展和切换

结构变化、应用发布和新业务能力可以分开进行。原书的过渡应用思路支持先兼容当前与后续结构，再迁移数据库，最后减少旧结构依赖；具体步骤需要根据当前读写语义安排。来源 C8。

### 3.1 各阶段的权威值与进入条件

| 阶段 | 实际状态与行动 | 进入下一阶段需要什么 |
|---|---|---|
| E0：核对旧状态 | 分钟是权威。核对实际数据、访问者、暂停范围和恢复依据 | 分钟含义及范围明确；异常记录有处置，当前访问路径可识别 |
| E1：增加可选表示 | 允许秒字段，分钟仍为权威；部署 V1。V0 与 V1 可短时并存 | 取得 V0 写入者、后台任务及旧在途动作全部退出或受控隔离的实际证据 |
| E1-ready：受控回填 | 只有 V1 兼容写入；分批从当前分钟推导秒。新建及修改一次保持两字段 | 当前集合完整、字段一致；不能只看初次扫描是否结束 |
| E2：固定兼容条件 | 暂停写入并结束在途操作后验证当前数据，再启用两字段及一致性要求；V2 以兼容模式部署 | V1 已退出，当前客户端和消费者能支持后续数据，旧消息有明确解释路径 |
| E3：切换权威与精度 | 再次受控暂停，结束旧模式和回填动作；核对规则与 V2 秒模式一致后开放整秒输入 | 实际秒值有效，当前及恢复路径不再依赖旧分钟表示 |
| E4：收缩旧结构 | 在权限和保留要求满足后删除当前分钟字段与旧规则 | 历史格式解码能力的删除另有依据，不能随当前字段一并去掉 |

E1 中，V0 写回丢秒字段尚未丢失权威分钟值，但会使回填结果无法保持。因此可以逐步部署 V1，却不能把 V0 仍在运行的状态当作回填完成或秒模式的起点。

E2 才要求两字段一致。若 E1 就把秒设为必填，V0 的整条替换会失败；若默认填零，又会把尚未迁移的记录误写成零时长。新增规则必须建立在实际数据与写入者条件之上。

本题使用短时写入暂停取得明确切换点。它的代价是暂停期间的用户影响及协调成本，优点是不用假定复杂的在线并发协议已经存在。如果业务不允许暂停，就要依据平台能力另行证明并发切换的安全性，不能从本例推导出无停机保证。

### 3.2 切换期间失败怎么办

暂停新请求、旧操作已经结束和存储规则已经变更是不同事实。在 E2、E3 的切换窗口内，先记录实际到达哪一步：当前规则是什么、每个实际读写者处于何种模式、是否仍有未知修改。

如果规则更新成功，但某个实例仍在旧模式，保持修改暂停，核对并完成同一阶段的必要步骤，或依据当前数据恢复到先前可用组合。不要让两种权威解释同时对外写入。若旧操作是否结束仍未知，先查原操作、终止依据或实际隔离能力，不能继续冲突修改。

回填工具也属于写入者。切换到秒权威之前，需要确认旧回填已结束；否则一个迟到的“按分钟计算秒”动作可能覆盖新秒值。停止调度新批次不等于已发出的批次停止。

相关应用共用数据库时，还要核查其他应用和后台脚本。代码静态清单可以帮助识别对象，不能独立证明没有临时任务、旧实例或另一个团队的写入者。来源 C4。

## 4. 并发回填、中断与完成检查

### 4.1 从当前权威值推导，写入时再次核对

回填不是把之前读到的值无条件写回。一次安全判断至少包括：该记录仍存在、读取版本仍适用、当前阶段的权威值明确，以及写入不破坏其他字段。以下算法与时间线为工程适配 A1–A2，不是书中已有的执行器。

本题每次读取记录后按当前分钟计算秒；若两字段已经满足当前规则，可以记录已符合，无需重复改变数据。否则携带已读版本执行条件更新。比较失败就重读并重新判断，不去掉条件再次覆盖。

| 连续事实 | 错误做法会发生什么 | 本题处理 |
|---|---|---|
| T0：P 为版本 10、2 分钟、秒缺失；Q 为版本 6、4 分钟、秒缺失 | 假定整批数据在扫描期间不会变化 | 保存起点标识集合，并逐条保留所读版本 |
| T1：回填读到 P 的版本 10，准备写 120 秒；V1 已把 P 改成版本 11、3 分钟、180 秒 | 用旧快照覆盖会把新业务修改退回 120 秒 | `expected_revision=10` 被拒绝；重读后确认当前 180 与 3 一致，不再覆盖 |
| T2：Q 的条件更新成功，成为版本 7、4 分钟、240 秒；检查点未保存时进程退出 | 从旧检查点重跑若再次转换秒，会制造错误数值 | 重读 Q，确认已符合；复用该结果，再推进检查点 |
| T3：扫描期间新建 S，由 V1 写入 5 分钟、300 秒 | 仅检查起点清单，无法说明后来新增记录 | 新写入规则约束 S；切换前仍检查当前完整集合 |

每次都从该阶段的权威分钟值推导，不把已经写好的秒再乘 60。这使已完成记录可以被识别，而不是要求每次重复调用都再产生一次修改。

### 4.2 效果与检查点分别处理

数据更新和检查点是两个独立持久化动作。本题没有声称它们共同提交，因此保存顺序影响恢复方式：

- 先确认记录实际满足目标，再推进对应检查点。进程在两者之间退出，允许重读并复用已完成结果。
- 如果先推进检查点、后写数据，崩溃会留下被跳过的未完成记录。因此不能把“请求已发出”当作可以推进的条件。
- 数据更新响应丢失时，保留未知，检查原操作及当前记录。只有实际结果和操作约束支持时，才能确认该条已处理；不能仅凭超时认定未写入。
- 如果原操作仍可能迟到生效，先处理这个可能性。当前读到一个正确值，不独立证明它稍后不会被旧动作改变。

版本比较必须在真正修改记录时与该次修改原子执行。本题中，旧操作只携带版本 6；若实际记录已经处于版本 7，迟到的版本 6 更新就不能再次生效。若底层只在请求接收时检查版本，或之后又无条件写入，就没有上述依据。

记录删除也要单独处理。扫描清单中的 R 在读取后已被正常删除，条件更新应失败并重新核查，不用 `upsert` 自动复活。这里依赖标识不复用的题设；允许复用的系统还要区分对象的不同生命周期。

### 4.3 什么证据支持回填完成

游标到末尾只说明扫描器处理到了某个位置。它不能证明所有更新成功、之后没有旧格式写入、失败记录已经补齐或切换前没有新的不一致。

本题的覆盖依据由三部分组成：起点一致快照中的标识集合；扫描期间 V1 新建和修改必须保持两字段的规则；切换前暂停修改并核对当前完整集合的结果。三者缺一，完成结论的范围就要缩小。

在暂停窗口内检查每条当前记录：分钟在旧范围内，秒与 `60 × 分钟` 相同，缺项、冲突和异常记录均有结果；核对未知操作、已删除对象、扫描失败和仍可能写入的旧程序。全部符合后才能进入 E2。有限样本可以发现问题，不能独立证明完整集合均已迁移。

实际大数据量任务可能需要分区核验、增量变更追踪或其他覆盖办法。本例没有验证这些机制；应按当前系统提出能解释遗漏、并发新增和迟到写入的方案。资源、锁等待或失败速率超出事先约定的范围时，停止增加批次并保留状态，不为了赶进度取消条件更新。

## 5. API、转发与历史消息

### 5.1 请求与响应分别检查

旧请求明确使用版本 1 和 `duration_minutes`，新请求明确使用版本 2 和 `duration_seconds`。不能保留同一个 `duration` 字段，却悄悄把值从分钟改为秒；双方即使成功解析整数，也会执行不同的业务含义。

新版服务可以把版本 1 的 2 分钟请求准确解释为 120 秒，但旧响应格式无法准确表达 90 秒。因此“服务端先升级”最多是发布安排的一项条件，不能据此推出所有请求和响应都兼容。来源 D5。

本题在开放新精度前，升级或停止当前只支持分钟的客户端。若业务不允许停止且又不能完成升级，就保持整分钟能力，或先评审其他接口安排。不能先接受新值，再让旧客户端静默读取错误结果。

服务独立发布、外部客户自行升级或多个消费者按不同节奏部署时，应分别列出实际支持组合。编码格式的兼容规则需要核对具体版本；字段名不变、默认值存在或解析器忽略未知字段，都不足以证明完整业务兼容。来源 D1–D2、D5–D6。

### 5.2 未知字段能跳过，不代表能保留

两条常见的损失路径需要检查：

1. 旧应用读出含秒字段的记录，只把已知字段装入模型，修改标题后重建整条记录。秒字段随之丢失。
2. 旧消息转发者收到新版消息，重建一个旧格式对象再发送。它自己可能没有报错，但下游需要的新字段已被删除。

修复应针对实际路径。可以采用已验证的局部更新、保留未知字段的编码方式，或者先升级、终止相关旧写入者。只有真实读改写与转发过程保留必要信息，才能支持相应结论。不是所有格式都自动保留未知内容，也不是保留字节就一定保留业务含义。来源 D3、D6。

### 5.3 历史消息能解码，还要判断能否应用

本题的版本 1 消息是完整状态快照，包含计划标识、记录版本和分钟值；版本 2 消息使用秒值。新消费者可以把旧分钟准确转换为秒，但必须先知道消息的格式版本，不能把缺失单位按当前默认解释。

延续前面的时间线：P 在并发修改后为版本 11、180 秒。进入秒模式后将它改为 90 秒，版本成为 12，分钟字段被移除。此时一条历史版本 1 消息带来 P 的版本 10、2 分钟。

这条消息可以解码为 120 秒，但不能覆盖当前版本 12 的 90 秒。只有在“完整状态快照、同一对象版本单调递增、消费者在实际修改时比较版本”的题设下，才可将更旧状态视为不应覆盖当前结果。同版本却有不同内容，应停止并核对来源，不能任选一个。

增量命令、扣减操作或会触发外部效果的消息不能套用上述处理。它们的顺序、重复与结果未知分别参照[重复、乱序与去重状态方法](message-idempotency-ordering.md)和[原子效果、外部结果未知与恢复方法](message-atomic-effect-recovery.md)。本例只说明格式演进中的一个局部判断，不证明完整派生数据恢复已实现。

当前队列为空，也不表示旧格式已经消失。归档、失败保留、延迟重试和备份仍可能再次产生旧消息。删除当前存储中的分钟字段，与删除版本 1 解码器是两个决定；后者需要明确的保留、重放和访问证据。来源 D4；具体退出检查为适配 A6。

## 6. 按当前数据选择恢复方式

### 6.1 回退资格随数据改变

迁移前写下恢复方案，执行中还要根据实际产生的数据重新判断。数据库结构可退回，不等于新写入能够保留；旧二进制还在，也不等于它能够正确处理当前记录。来源 C5–C8。

| 当前阶段 | 可以比较的恢复选项 | 必须先核对什么 |
|---|---|---|
| E0、E1，仍以分钟为权威 | 修复 V1，或受控恢复旧应用 | 数据仍由分钟准确表示；回填和旧动作受控；没有依赖秒字段的当前读取者 |
| E2，要求两字段一致 | 继续修复兼容版本；确需退回时先恢复相应规则组合 | V0 会删除秒字段，不能只替换应用文件；须停写、核对当前数据和权限后安排规则变化 |
| E3 已开放新精度 | 依据实际记录和客户端要求判断 | 不能仅按开关状态或发布时间推断“尚可回退” |
| 已存在 90 秒等值 | 保留数据，选择支持秒格式的兼容版本或向前修复 | V0、V1 无法准确表达当前值，舍入不满足目标 |
| 数据本身损坏 | 控制写入、保全证据，评估可靠数据源和可重现的恢复步骤 | 备份范围、已提交新变更、重放顺序、重复效果和最终业务结果均需证据 |

是否启用新精度与是否已经写入不可由旧格式表达的数据，是不同事实。即使当前值恰好都为整分钟，恢复旧应用还需要检查客户端要求、其他新语义和在途操作；不能只抽样几个值就宣布可回退。

### 6.2 一次新写入改变了恢复选择

继续本题：E3 开放后，P 的 90 秒已被接受，另有新计划 U 为 45 秒、版本 1。此后发现 V2 的显示缺陷，但权威秒值和记录仍准确。

此时有三种提议：

| 提议 | 对已接受数据的影响 | 判断 |
|---|---|---|
| 恢复 V0 或 V1 | 无法准确表达 P 和 U；旧写回还可能删除秒值 | 不满足目标 |
| 恢复迁移前快照 | P 回到更早的值，U 不存在 | 丢失新变更与新记录，不满足目标 |
| 暂停受影响功能，使用已核对的秒级兼容版本或修复 V2 | 可以保留当前数据，再检查新旧记录的显示及写入 | 有条件可行；须核实修复产物、实际状态和权限 |

向前修复不是口号。它需要一个能处理现有秒级数据的具体候选、对应验证结果和执行步骤。若尚无这样的候选，就记录功能暂停和未完成状态，不能把“准备修复”登记为“服务已恢复”。

一旦当前数据已经被错误转换或删除，直接重新运行迁移也可能无法恢复原值。先确定损失来自哪一步、哪些值仍有可靠来源，再判断能否重建。没有来源支持时不要按猜测补数，也不要承诺全部追回。

### 6.3 备份与记录新交易只提供恢复材料

原书讨论了记录新交易、备份副本和重放等方案，但它们都有条件。保存了日志文件，不独立证明所有已提交变更都在其中；能读出事件，也不证明再次应用不会重复副作用。来源 C6–C7。

评估数据恢复时，至少要回答：恢复到哪个一致状态；这个状态之后哪些变更已被接受；它们是否完整、有顺序依据和可重复处理方式；恢复目标能否表达这些数据；用户在恢复过程中还能否继续写；最终怎样核对业务结果。必要外部效果还要另行处理。

若缺少完整的新变更来源或经核实的恢复路径，明确说明无法证明无损恢复，并保留待核范围。为让发布继续而默认丢弃新数据，会改变业务目标；迁移工具和 Skill 均无权自行作出这个决定。

## 7. 何时可以删除旧结构

删除旧字段通常比增加字段更难撤销。先证明它不再是任何当前或承诺保留路径的必要输入，再执行有权限的收缩。来源 C3、C8、D4。

本题进入 E4，需要当前记录的秒值有效、V2 始终按秒读写、旧程序和后台写入已退出、当前客户端与消费者没有分钟依赖，并且拟保留的应用恢复版本也支持秒。删除前仍要核对正在进行的回填、重试和旧操作。

以下事项分别取得依据，不用一项代替其余事项：

- **当前数据**：已完成迁移且通过当前业务条件检查，异常和未处理集合有明确处置。
- **当前访问者**：实际版本、读写路径和后台任务符合，旧实例不能在恢复或重启后重新成为写入者。
- **应用恢复**：需要保留的恢复目标支持当前结构；若仍承诺恢复分钟版本，就不能同时假定秒级数据无须处理。
- **历史输入**：归档消息、备份和重试数据的格式仍能解释，或已有证据支持它们不再进入当前路径。
- **权限和保留要求**：删除范围明确，不扩大到其他应用使用的对象或调查依据。

本题即使删除了当前分钟字段，仍可保留版本 1 消息到秒值的转换器。它不要求当前数据继续存一份分钟值，只要求历史消息带有足够的版本和含义。删除结构、停止接受旧请求和删除历史解码能力可以发生在不同时间。

如果必须长期保留旧客户端或恢复能力，就记录这项维护成本，并相应延后收缩或重新设计接口。不要用一个未经核实的“已过若干天”代替访问和保留证据。

## 8. 输出下一步与停止条件

迁移记录应让下一位负责者知道现在能安全做什么。对小任务用简短表格即可，无需先建立大型迁移平台。

| 输出 | 需要给出的实际内容 |
|---|---|
| 当前阶段 | 实际结构、权威字段、运行版本和当前业务能力 |
| 支持关系 | 当前新旧读写、API、消息与历史格式的允许和不支持组合 |
| 数据处理情况 | 已确认集合、未处理或异常集合、检查点及其代表范围 |
| 未决操作 | 操作身份、输入版本、当前证据和可能的迟到影响 |
| 推进依据 | 写入者退出、数据核对、规则与模式一致、观察范围及权限 |
| 恢复与停止 | 可行恢复候选、信息损失点、时间资源限制、负责者及下一步 |

例如，在 P 的回填发生版本冲突时，可以写：

> 当前仍处于分钟权威的 E1-ready。P 的回填基于版本 10，实际业务已将它改为版本 11、3 分钟和 180 秒；旧回填被拒绝，重读确认当前两字段一致，因此保留业务结果。Q 的更新已确认，但检查点未保存，重启后需重读复用。尚未完成当前完整集合检查，也未确认切读条件，不开放秒级输入。

出现无法解释的字段冲突、未知写入者、未决提交、兼容请求失败或超出约定资源范围时，停止受影响推进，保留已经确认的数据与证据。停止迁移、应用恢复、数据恢复和新版本发布完成分别报告；任何一项都不能由另一个状态自动推出。
