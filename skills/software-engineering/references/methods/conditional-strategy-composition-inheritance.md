## 1. 先说明要隔离哪一种变化

策略是完成同类任务的一种可选择算法。使用者按共同接口调用它；负责选择的一方知道各变体的业务差异，并为本次调用确定所需行为。共同接口只规定怎样调用，输入范围、结果、失败、副作用和寿命还要逐项定义。两个实现都有一个 `select` 方法，不能单独证明它们可以互换。

在已经确认存在两种有用行为，或者已有父类扩展点需要调整时，使用本方法。先说明哪种变化应独立发生、谁使用它、当前结构如何妨碍这次变化。长函数、多个条件和重复语句只是线索。若一个使用点上的两个稳定分支已经清楚，保留小条件就是完整的设计选择。

《从结构问题到候选变换》用不同变化原因比较保留、局部提取、搬移及策略入围；这里接续“确有算法变体”的判断，展开如何表达和连接这些变体。《从变化需求到模块职责与接口契约》提供完整输入、失败、拥有与借用、行为替换的分析；《从行为保护到渐进重构》提供观察点、接缝、小步提取和旧入口接线。本方法复用这些责任，补足同一要求下的正向比较。

条件、表、函数和对象不构成互斥的模式排行榜。条件或表可以选择一个函数；对象可以持有该函数；子类也可以通过窄接口调用协作者。策略描述算法变化的组织方式，组合描述对象之间如何合作，继承描述父子类型及实现关系。先看责任是否完整，再看形式能否降低修改和理解成本。

GoF《设计模式》1.6.4–1.6.6区分接口角色、实现复用及运行时协作；5.9说明算法独立变化的价值，也保留客户选择、通信和对象数量的成本。《A Philosophy of Software Design》第7章提醒相同签名的浅转发可能只增加接口，却允许有实际选择责任的共同接口。《重构》8.1又允许搬移时暂留原入口转发。这些观点可以共同指导调查，不能合成“一律组合”或“一律删除转发”的命令。

## 2. 固定客户能依赖的输入和结果

### 2.1 共同的纸鸢样卡准备器

“纸鸢样卡准备器”是虚构静态场景。所有候选都提供同一个公开入口 `prepare(cards, requestChoice, fixedProfile)`，返回完整的 `Prepared` 或明确失败。下面的输入、错误和资源约定是场景给定的工程选择，不是任何书中的现成程序。

`cards` 是本次调用期间值固定的有限有序序列。每项包含非空字符串 `code`、取值为 `warm` 或 `cool` 的 `tone`、1至9的整数 `width`。输入允许重复和空序列。准备器不修改输入，不读时钟、文件或可变全局值，不在下一请求中继续使用上一请求的数据。

入口先按原序检查卡项，首个无效项使整次调用返回 `InvalidCard(原始位置)`，位置从1开始。此时不处理选择，不筛选，不装配本次运行器，也不获取输出资源。全部卡项有效之后，后续步骤才接收带原始位置的有效记录。

| 原始位置 | code | tone | width |
|---|---|---|---|
| 1 | k09 | cool | 2 |
| 2 | w08 | warm | 3 |
| 3 | k02 | cool | 1 |
| 4 | w01 | warm | 2 |
| 5 | w08 | warm | 3 |

实际变体只有两个：`all` 保留全部记录；`only` 保留 `tone` 属于所给 `tones` 集合的记录。两者都保持原顺序、每次重复出现、原始位置及全部字段。每个入选项形成 `code:tone:width` 字符串；行表示不排序、不去重，也不改变卡项值。

对上表，`all` 的行依次是 `k09:cool:2`、`w08:warm:3`、`k02:cool:1`、`w01:warm:2`、`w08:warm:3`。`only` 配合 `{warm}` 取得原位置2、4、5，行依次是 `w08:warm:3`、`w01:warm:2`、`w08:warm:3`。这个输入能够区分错误排序和去重：把编号升序排列会把 `w01` 移到前面，按编号唯一存储会丢掉一次 `w08`。

成功值 `Prepared(profileVersion, rows)` 保存本次配置版本和完整、独立的行值。生成过程只写私有草稿，不发布文件或消息。任何失败都不向客户返回部分行；释放失败也阻止返回 `Prepared`。这些完成条件在第6、8节具体展开，不能由某一候选自行简化。

### 2.2 默认、未知选择与缺配置分别处理

`Profile(version, defaultChoice, defaultTones)` 是装配位置先校验并固定的完整配置。默认若为 `only`，必须具有有效集合；当前配置 `p1` 的默认是 `all`。固定配置与请求中的显式选择分开：省略整个选择才采用完整默认；显式选择连同它自己的参数一起覆盖默认。

| 输入或装配状态 | 明确含义和处理 |
|---|---|
| 在有效 `p1` 下完全省略 `requestChoice` | 采用 `all`，返回全部五行并标记 `p1` |
| 显式 `all`，没有 `tones` | 采用全部记录；不从默认 `only` 拼入任何集合 |
| 显式 `only`，有 `{warm}` | 采用暖色子序列 |
| 显式 `only`，有空集合 | 有效的“没有颜色入选”，最终返回空行成功 |
| `"All"`、空字符串或未知名称 | `UnknownChoice`；不改大小写、不去空格、不猜测用户意图 |
| 显式 `only` 缺少集合 | `MissingTones`；不取默认集合或上一请求的集合 |
| 集合含 `other` 等不允许值 | `InvalidTones`；不删除错误值后继续 |
| 显式 `all` 又带 `tones` | `UnexpectedTones`；不忽略冲突参数 |
| 装配缺完整配置、配置校验失败或新运行器创建失败 | `ConfigurationFailed`，没有可调用的新实例；不能以默认算法掩盖 |

对已经取得有效固定配置的公开调用，卡项校验先于请求选择。第1项宽度为0、第2项宽度为10且选择名未知时，返回 `InvalidCard(1)`，尚未解析选择。只给 `only` 的集合为空不是卡项错误，也不是缺参；应在卡项全部有效后正常得到空结果。

“配置无法建立”属于装配边界；公开调用的前提则是已取得有效 `fixedProfile`。这两种失败不能混为“没有选择”。若实际入口允许无效配置与原始卡项同时进入，必须另定义错误优先级，不能从本例推断。已有旧版本能继续服务在途调用，也不自动允许把新请求的配置错误偷偷改用旧版。

GoF 5.9允许在没有额外策略对象仍有明确意义时提供缺省行为。本例把完全省略定义为默认，把未知名称、缺参、配置和创建失败定义为各自错误；后几项是明确的工程政策，不是原书授予的任意回退许可。

### 2.3 先区分换行为与换实现

入口解析得到完整的 `Selection(kind, tones可选, profileVersion)`，随后装配已绑定该选择的运行器。运行器公开它绑定的选择，一轮 `run(validCards)` 期间选择和算法固定。客户可依赖的输入仍是全部有效卡序列，包括空序列和宽度9的卡项。

从 `all` 改选 `only {warm}` 是有意改变结果；两者不应返回相同行。比较保行为替代时，必须固定同一 `Selection`、同一输入、同一完成与失败要求，再把条件实现换成函数、对象或子类。仅有同名方法或父类型，不能代替这个比较。

一个替代函数只接受非空输入，或某子类把宽度上限收为5，都收紧了旧允许范围。一个替代对象返回相同行却关闭借入的写入器，也破坏了后续操作。真实替换要求同时保持允许输入、完整结果、错误含义、外部效果和资源责任；它不要求两个不同业务选择的结果彼此相等。

## 3. 从最小实现开始比较

先把第2节的行为要求固定，再改变使用点、复用和独立变化这些结构事实。下表中的事实组分别成立，不是项目必须依次升级的阶段。所有方案仍承担相同的校验、选择、行结果和第8节失败要求。

| 已确认的事实 | 合理的最小方案 | 收益和必须承担的成本 | 什么变化会使选择翻转 |
|---|---|---|---|
| 一个使用点，两个稳定算法，选择紧邻使用 | 小条件加清楚的局部计算 | 装配少，读一处即可理解；以后多处复制选择会增加同步修改成本 | 出现独立变化、真正复用或难以理解的重复选择时，再提取函数 |
| 两入口复用同一筛选，变体由明确值计算，无独立寿命 | 直接函数；需要查找时使用有限函数表 | 共享完整计算而没有对象寿命；仍须明确选择者和参数 | 配置要与多个操作共同固定，或新职责无法由这组函数清楚表达时，再比较对象 |
| 多个运行器使用相同版本的固定算法配置 | 小策略对象，或者捕获同样固定值的函数 | 装配后少传重复参数；增加创建、接口、捕获状态检查和诊断跳转 | 若对象只为一个操作藏两项简单值，直接函数更容易说明时，应保留函数 |
| 已有稳定父流程，明确开放 `select`，实例固定选择，无同实例换算法要求 | 保留只覆写 `select` 的子类 | 直接使用已有流程，少一个协作者连接；依赖父类扩展和调用约定 | 父类内部依赖增多、算法要跨运行器复用或独立更换时，比较组合 |
| 多个运行器独立复用筛选，后续运行需要换一份完整选择 | 持有窄筛选协作者；需要父类型时加薄子类适配 | 算法与运行编排可以分别变化；多出对象关系、装配和寿命判断 | 没有独立变化且每层只原样转交时，比较直达、合并或保留继承 |
| 父类自调用、构造、关闭或第三方客户尚不明确 | 保留依赖未知关系的结构，先核这些关系 | 避免把未知当成等价；暂不能取得预计的结构收益 | 得到扩展点、客户和资源证据后，按相同要求继续比较 |

表驱动还要分清两件事。`tones` 集合用于回答“这一颜色是否入选”；`choice` 到函数的表用于回答“哪个已知算法处理本次选择”。前者保存数据，后者保存动作引用。两种表都不替代完整记录序列，也不自动提供校验、默认或失败处理。Code Complete 18.1要求先说明如何找到条目、条目保存什么；简单逻辑仍可以直接写条件。

若以 `code` 为唯一键保存共同输入，再把它当作筛选结果，其中两次 `w08` 会被合成一项。问题在于把重复出现改成唯一身份，不在于某种表语法优劣。成员表可以辅助逐项筛选，但完整输出仍按每次出现及原序形成。

函数表只需要一个由 `all`、`only` 到已知能力的有限映射时，不必建立可动态注册的插件框架。检查表的完整性、重复项处理和所指能力是否存在，仍是装配责任。查找失败必须回到已经定义的选择或配置错误，不能调用一个空函数后假装成功。函数引用、闭包及查找的具体语法和效率需要当前语言证据；书中的表驱动观点不证明这些实现细节。

比较包装层时，先逐项删除想象中的职责，再看还有什么实际责任。一个运行器负责验证完整结果、拥有草稿和解释清理失败，即使内部调用一次 `select`，也不是只有转发。相反，多加一层只是把同一参数和返回值逐字转交，未隔离变化、选择实现或维持必要兼容，其接口和签名维护成本可能没有收益。必要的过渡转发也应有已知客户和退出条件，不以永久多层间接调用为默认。

## 4. 明确选择责任和数据通信

### 4.1 走完两种算法的共同调用

调用者提交业务选择；应用入口检查它的名称和参数；装配位置据完整选择创建或取得相应能力；运行器调用该能力并消费它的完整结果。算法本身不决定“用户其实想选什么”，也不重新读取最新默认。

在条件方案中，入口完成校验和解析后，在唯一选择位置分两支：`all` 返回全部有效记录，`only` 按原序逐项检查颜色成员关系。之后两支共同进入行生成和资源流程。不能把卡项校验藏进 `only` 的入选分支，否则本会被过滤掉的错误卡项就逃过检查。

在函数方案中，装配位置选择 `selectAll` 或 `selectOnly`。前者只需要有效记录；后者还需要本次有效集合。若为统一调用采用 `select(validCards, selection)` 形状，`all` 不使用集合是一个明确的接口成本，而不是隐藏缺参的理由。也可在装配时绑定完整选择，再暴露只接收有效记录的调用能力；绑定值的保存期限随第5节确定。

在对象方案中，小对象对外说明所绑定的选择，运行器调用其 `select`。对象只决定筛选，不生成行、不打开草稿，也不把原运行器的全部字段带进算法。若一次调用无法形成完整子序列，返回 `SelectionFailed`，共同流程不开始打开草稿。正常空子序列则继续完成空行的草稿生命周期。

这三种写法改变的是责任所在和通信方式。同一有效选择下，都应得到同一原位置子序列。结果之外，还应追踪“原入口是否真的使用了返回值”：新函数选出2、4、5，旧入口却仍写全部五项，算法局部正确也没有完成接线。

### 4.2 优先传必要值，确有需要才提供窄上下文

上下文是算法能够读取的一组约定信息或调用能力，由使用者在一次操作开始时提供。本例最小输入是有效记录、完整选择及其版本；有这些固定值就足够计算，不需要传应用对象、服务定位器、草稿工厂或写入器。

当算法真的需要按需读取时，可以提供窄 `Context`，但必须把它能读什么、何时读、失败怎样返回写清楚。少几个显式参数换来的代价，是算法依赖另一接口及其时间行为。下表既适用于对象，也适用于捕获上下文的函数。

| 通信内容 | 本例可接受的约定 | 不满足时如何处理 |
|---|---|---|
| 颜色集合和版本 | 同一次选择解析取得完整值；集合及其成员在本轮固定 | 缺集合按选择错误处理，不能沿全局链补值 |
| 窄读取能力 | 只返回本轮固定选择所需信息，不能途中换成最新版 | 无法给出一致值时，先补取得协议，不能宣称本轮已固定 |
| 可写性和权限 | 算法没有修改配置、输入或草稿的能力；返回值也不能泄漏可写内部集合 | 只读外壳仍暴露可变别名时，落实复制或实际所有权后再使用 |
| 保存期限 | 本轮借入的上下文或回调只在本轮同步筛选中使用，不保存、不异步调用 | 需要延期使用时，另定义拥有者、结束条件和失败责任 |
| 读取或回调失败 | 保留主要原因，作为本轮 `SelectionFailed` 返回；不打开草稿 | 不转换为空子序列、另一算法或默认成功 |

统一接口可能让某个算法收到用不上的参数，这是 GoF 5.9明确指出的成本。不要为消除一个未使用参数而让所有算法拿到整个应用；也不要因“解耦”机械拆散本来需要一起解释的完整选择。应让调用者能从接口知道本次需要什么，并能在一个有限位置追到这些值的来源。

如果两个算法需要根本不同且无法共同说明的输入、成功保证或失败恢复，先重审它们是否属于同一替换关系。用一个巨大 `Context` 把差异全部藏住，只统一了外形，没有得到可用的共同接口。

## 5. 约束共享状态和版本更换

### 5.1 无状态共享与固定配置共享是两种条件

无状态算法不在调用之间保存输入、集合、中间行或“最近一次选择”。所有本次所需值逐次传入，因此两个运行器可在满足实际调用安全条件时共享这项算法能力。GoF 5.9为减少对象开销提出的共享，正是这种不保留调用间状态的有限方案；不能直接推广为任何对象都能安全共享。

假设请求A选择暖色，请求B随后选择冷色。B必须得到 `k09:cool:2`、`k02:cool:1`。若共享对象把A的集合存在可写字段里，B省略传递或错误读取该字段，就发生请求污染；即使完全串行也会出错。闭包捕获了同一个可变集合时同样存在问题，写成函数不会自动消除状态。

另一种工程选择是共享真正不可变、固定配置的能力。例如多个运行器都使用同一个版本及同一份固定暖色选择，可以复用这一对象或绑定函数；它的公开配置必须与调用者要求一致。冷色请求不能复用暖色实例后改写它的字段。需要不同选择时，另取匹配的实例，或改用逐次传值的无状态算法。

共享前检查整个可达配置是否实际不可变，是否还有可写别名、惰性初始化、内部缓存、诊断计数或有独立寿命的依赖。`readonly` 名称、私有字段、浅副本和类图都不提供这些保证。固定配置共享、闭包捕获及安全发布是工程适配，必须按当前语言和使用方式核实；没有相关实现证据时只能给出设计条件。

### 5.2 一次调用只使用一个完整版本

管理方提供新配置 `p2`，默认改为 `only {cool}`。请求A已经取得 `p1`，请求B在更换后取得 `p2`。两者都省略选择时，A仍用 `p1` 返回全部五行；B用 `p2` 返回两条冷色行。A不能解析选择时用 `p1`，筛选时读取 `p2`，最后又把结果标成 `p1`。

因此，开始时取得的必须是互相一致的配置、完整选择和实现引用，并在本轮保持。管理方更换的是后续调用可取得的版本，不是向在途实例写入几个新字段。如何原子地取得和发布这组信息、怎样保护引用及不可变值，取决于实际实现；本例只定义应达到的结果。

显式 `all` 在 `p2` 下仍返回全部五行并标记 `p2`。默认的冷色集合不应拼入显式选择。新配置校验或新筛选能力构造失败时，报告 `ConfigurationFailed`；已经固定旧版本的调用可按原要求结束。是否允许后续新请求继续使用旧版，需要明确政策与可观察版本，不由“还有旧对象”自动决定。

### 5.3 资源型策略要重新定义退出责任

本例筛选能力没有需关闭的资源，因此丢弃一个不再需要的选择绑定，不等于执行资源清理。若以后策略持有文件、线程、连接或需要关闭的缓存，已经改变了寿命假设，不能简单把字段换成新对象后立刻关闭旧对象。

需要先定义谁拥有该资源、谁仅借用、何时停止新借用、在途调用保留哪一引用、怎样确认最后一次借用结束，以及关闭失败后由谁继续处理。一个可行的条件顺序是：停止给旧版本分配新调用，保留已有调用的完整引用，等所有借用结束，再由唯一拥有者关闭。关闭失败保留残留资源身份和责任，不能登记为退出完成。

这不是任意语言的引用计数、析构、内存回收或并发机制保证。如果无法证明旧对象仍被谁使用，就停止依赖“现在可以关闭”的更换步骤，继续核查寿命。函数捕获一个有资源的对象也承担相同义务，不因没有显式策略类而例外。

## 6. 在同一父类约定下比较继承和组合

### 6.1 把允许的扩展点和共同流程写具体

为比较已有框架扩展，另明确一个虚构父类 `PreviewRunner`。它公开绑定的 `Selection`，`run(validCards)` 接收全部有效卡序列。共同 `prepare` 负责原输入校验、选择解析和装配；父类 `run` 负责筛选后的行格式与私有资源。这里只允许改变 `select(validCards)`，不允许覆写 `run`。

父类扩展说明明确要求：`run` 恰好调用一次 `select`；这个调用到达装配时支持的覆写点。`select` 返回本次完整子序列或 `SelectionFailed`，不能收紧有效输入，也不取得资源或保存异步工作。父类构造与关闭不调用此钩子；构造只绑定完整配置、选择和 `DraftFactory`，不打开草稿。这里的调用规则是题设给定的扩展说明，不能当作真实语言的默认动态绑定行为。

`Draft` 是一次运行独占的私有草稿资源。`DraftFactory.open` 成功返回资源，运行器才取得释放责任；获取失败不留下已交付给运行器的资源。固定 `appendRows` 借用写入器生成行，不关闭、不保存，也不异步使用它。`select` 根本不接收写入器。草稿的 `freeze` 复制出独立候选行值，运行器确认 `release` 成功后才向客户交付 `Prepared`。

共同顺序为：原序校验卡项、解析完整选择、装配运行器、调用一次筛选、获取独占草稿、写入入选行、复制候选行、释放草稿、返回完整结果。空输入或空入选仍调用一次筛选，仍打开、冻结并释放一次草稿；不能在某个候选里悄悄跳过这些完成义务。

### 6.2 正向继承：只实现已经支持的筛选钩子

假定稳定框架已经提供上述父流程，当前客户接受 `PreviewRunner`，没有同一个实例运行期间更换算法的要求。装配位置根据完整选择创建或复用匹配的 `AllRunner`、`OnlyRunner`。两个子类都沿用父 `run`，只提供自身 `select`；实例固定选择，不通过修改父类内部字段切换模式。

取暖色请求走正常路径：`prepare` 原序校验五项，再形成 `Selection(only,{warm},p1)`；装配 `OnlyRunner`，构造阶段不调用筛选、不取得草稿；客户调用继承的 `run`，父流程调用子类 `select` 一次，取得原位置2、4、5；父流程打开草稿，按这一次序借用写入器追加三行，冻结独立值，确认释放后返回 `Prepared(p1,三行)`。`AllRunner` 同样走父流程，只在筛选结果上保留全部五项。

失败也走同一父流程。子类筛选失败时，父流程在打开草稿前返回 `SelectionFailed`；第二行写入失败时，子类没有额外清理权，父流程放弃私有前缀并尝试释放一次，返回写入失败；若释放也失败，同时保留清理失败与残留资源身份。构造失败没有可调用新运行器；冻结或最终释放失败按第8节返回，不能由子类改为空成功。

在这些事实下，保留继承有正向理由：既有父类型已经是客户所需接口，受支持钩子与变化恰好一致，固定算法无需额外更换协议，构造和资源逻辑无需再复制。另加一个只转交同一筛选的对象，可能只增加装配和跳转成本。

代价是对子类扩展约定和父类调用关系的依赖。父流程以后改变钩子的次数、允许阶段或失败处理时，须评估对子类的实际影响；这不等于父类任何改动必然修改所有子类。若子类覆写 `run` 跳过释放、在构造阶段调用钩子，或要求输入不能为空，它直接违反本题扩展要求，不能用“语言允许”合理化。

### 6.3 正向组合：让筛选协作者独立变化

现在换一组结构事实：多个运行器确实复用同一筛选算法，后续运行可能选择另一完整配置，算法与运行编排需要独立维护。可以令运行器持有窄 `Select` 协作者，`select` 只把有效记录交给本轮已经绑定的能力。每轮开始先固定协作者及选择；本轮中途不重新读取可变字段。

若客户必须接收原父类型，保留一个仅实现 `select` 的薄子类适配，由它转交 `Select`，其余仍使用同一父 `run`。若客户只需要共同运行接口，可以在该接口下用组合运行器，但它必须明确兑现相同的行生成、完成和资源要求。不能把不属于父类型的对象硬塞给要求父类型的客户，也不能为了显示“纯组合”暗中减少义务。

取同一暖色请求走正常路径：共同入口校验五项并形成同一选择；装配位置取得对应 `Select`，连接运行器及同一类草稿工厂；构造不调用算法、不取得草稿；运行器的共同流程调用窄协作者一次，得到原位置2、4、5；运行器打开草稿、借用写入器写三行、冻结、释放，最后返回同样的完整结果。选择业务行为与连接实现仍由入口和装配位置负责，协作者不自行更换默认。

取同样失败路径：协作者创建失败产生 `ConfigurationFailed`，没有新运行器；筛选失败产生 `SelectionFailed`，未打开草稿；第二行写入失败由运行器放弃前缀并释放，`Select` 不关闭它未拥有的草稿；写入后释放再失败时，运行器保留同样的主次错误和残留身份。冻结成功但释放失败仍不交付行。组合并没有把这些责任委托给垃圾回收或对象关系图。

组合的收益来自独立复用和更换的事实；成本是更多对象、装配关系、转交和寿命检查。后续运行换协作者可以满足新选择，但当前运行仍固定旧引用。框架薄适配负责实际类型兼容，运行器负责草稿，筛选对象负责算法；每层都有可说明的工作时，间接性才有价值。若现实中既无独立复用也无更换需求，应回到保留继承或直接函数重新比较。

## 7. 搬移后保持原接收者的含义

普通转发把一次调用交给另一个对象，受调用的方法通常使用接收它的那个对象。严格委托还要求受托操作能够引用原请求接收者，以保留原先依赖该身份的行为。GoF 1.6.5.2用文字讨论传递原接收者；其中 Window/Rectangle 图只画面积转发，图本身没有画回调，不能从那条箭头补出原对象身份已经保留。

考虑一个独立于第6节基线的扩展条件：实际父流程明确支持原接收者上的只读 `acceptTone`，它表达已固定配置的颜色判断。某段被搬移的筛选会调用这个钩子。基线只有 `select`，不能因为现在讨论这个条件，就假定基线父类一直还有第二个隐藏钩子。

旧路径中的筛选使用原接收者的 `acceptTone`。搬到 `Select` 对象后，如果直接调用新对象自己的同名方法，名称虽然相同，决定颜色的对象却变了。原接收者有客户专属覆写而新对象使用自己的默认时，结果可能不同。这里没有给出新旧方法具体返回值，因此只能指出一个可使行为改变的关系，不能捏造某组错误行或声称已经观察到差异。

先判断这项依赖是否能改为完整固定值。若原钩子只查询本轮固定的颜色集合，把该值和版本明确传入即可，算法无需保留原对象身份。若客户必须保留原接收者提供的行为，则传入绑定原接收者的窄只读 `acceptTone` 回调，或者只暴露这一能力的上下文；不能替换成新协作者的同名方法，也不需要传整个应用对象。

窄回调的约定仍须具体：它与本轮同一配置绑定，不改输入和原对象状态，不重入 `run` 或取得草稿，只在本轮同步筛选期间调用，结束后不得保存或异步使用。读取失败使筛选失败，并保留原因；不能返回“拒绝所有颜色”掩盖故障。原接收者须在所有允许回调结束前有效，任何并发修改、实际方法绑定和释放都需要当前平台证据。

这种方式增加了双向理解负担：读筛选时还要追到原对象，原对象也必须满足回调寿命。只有这项身份依赖确有业务意义，才值得保留。若传固定值已经完整表达行为，就不必为了使用“委托”一词创建回调。若父类的自调用关系未知，先调查父类、覆写与客户，再决定搬移；普通转发不能自动补足它们。

## 8. 逐项解释失败和资源责任

第6节两案使用同一资源协议。下表以失败发生的阶段区分返回结果；它也约束条件、表、函数和对象方案，不能把简单实现的失败责任从比较中删掉。

| 退出位置 | 已有责任与处理 | 客户得到什么 |
|---|---|---|
| 卡项校验失败 | 尚未处理选择、筛选或资源；按原序首错停止 | `InvalidCard(原始位置)`，没有行 |
| 请求选择错误 | 卡项有效，但没有完整可用选择；不筛选、不开草稿 | 对应的 `UnknownChoice`、`MissingTones`、`InvalidTones` 或 `UnexpectedTones` |
| 配置或运行器装配失败 | 不交出半构造的新运行器；本题构造没有取得草稿 | `ConfigurationFailed`；不静默默认 |
| 筛选或必要回调失败 | 没有完整子序列，草稿尚未打开 | `SelectionFailed`，保留主要原因 |
| `open` 失败 | 没有交付已取得资源，不释放从未取得的草稿 | `DraftOpenFailed` |
| 第二行等任意写入失败 | 已取得草稿，运行器作为唯一拥有者尝试释放一次；私有前缀不返回 | `DraftWriteFailed`；释放也失败时附 `cleanupFailure` 和残留资源身份 |
| `freeze` 失败 | 没有完整候选行值，仍尝试释放已取得草稿一次 | `DraftFreezeFailed`；清理失败另附，不覆盖主因 |
| 冻结成功，`release` 失败 | 候选行仍不能交付；残留资源继续由拥有者负责 | `DraftReleaseFailed` 与资源身份，不返回 `Prepared` |
| 筛选、写入、冻结和释放均成功 | 完整独立值已形成，必要释放得到确认 | `Prepared(本轮版本,完整行)`；空输入或空入选时行为空 |

失败结果保存失败阶段、主要原因、可选清理失败及尚待释放资源身份。写入先失败、释放后失败时，主要失败仍是写入；只报告最后一个错误会掩盖起因。仅调用过 `release` 不能宣布清理完成，失败后剩余责任应由原拥有者继续处理。表中的一次释放尝试指本轮清理步骤，不授权在未知状态下盲目重复关闭；后续处置需资源自己的协议。

固定 `appendRows` 只是借用写入器。若它或筛选协作者私自关闭、保存或异步使用写入器，就破坏了运行器后续 `freeze/release` 的条件。即使行文字看起来正确，也不满足替换。若另一个接口确实要转移拥有权，应明确定义何时转移、拒收时谁释放及之后谁还能使用，不能把它当作本题借用接口的等价实现。

本题的“失败不返回部分行”来自所有写入都留在私有草稿、冻结产生独立候选值、成功还需确认释放这些明确前提。它不是文件替换的原子性、数据库事务或外部发布保证。实际流程若逐行写外部目标，或者关闭才触发发布，就须另外定义部分效果、结果未知和恢复；不能照搬 `DraftWriteFailed` 就声称外部没有改变。

空结果也有独立含义。有效空集合使每项成员判断都为否，仍是一份完整结果；算法或回调未能完成不是空结果。空输入下资源仍可能获取、冻结或释放失败，应保留这些失败，不通过提前返回空数组掩盖它们。

## 9. 用反例保护选择并交给实施

### 9.1 让观察能够区分错误

检查应从既定要求推导预期，再选择能区别错误实现的输入及观察。下面是静态反例，不是运行结果；只看返回行数、方法名称或检查数量不足以保护这些差异。

| 变化或错误实现 | 从共同要求推出的观察 | 判断能支持的范围 |
|---|---|---|
| 暖色选择被排序或去重 | 依次保留 `w08,w01,w08`，原位置2、4、5 | 排除这两种错误，不能证明所有输入都正确 |
| 原第1项颜色改为 `other`，仍选暖色 | `InvalidCard(1)`，未筛选、未打开草稿 | 不能因错误项本会被过滤而跳过校验 |
| 原第3项冷色卡宽度改为10，仍选暖色 | `InvalidCard(3)` | 过滤在后，冷色的错误也必须拒绝 |
| 原第1项宽度0、第2项宽度10且名称未知 | `InvalidCard(1)` 优先 | 区分原序首错与提前解析选择 |
| 单项宽度1或9，对照0或10 | 前两项允许，后两项在原位置失败 | 防止新函数或子类收紧输入范围 |
| `only` 空集合，对照缺集合 | 前者完整空成功，后者 `MissingTones` | 防止用真假值判断把空集合当未提供 |
| 空卡序列且有效 `all` | 筛选一次，打开、冻结和释放各一次后空成功 | 防止某个候选跳过必要完成流程 |
| 暖色请求之后是冷色请求 | 冷色结果为原1、3，不能包含暖色残留 | 串行请求也能揭露共享可变状态，不等于并发已经安全 |
| A固定 `p1` 后更换为默认冷色的 `p2` | A仍五行且标 `p1`；B省略时两条冷色且标 `p2` | 区分整轮固定与读取混合版本 |
| `p2` 下显式 `all` | 全五行且标 `p2` | 明确选择完整覆盖默认，不逐字段拼接 |
| 写入失败后释放再失败 | 没有部分行，主要写入失败和附加清理失败都在 | 不能只断言“失败”而丢掉资源及起因 |
| 冻结成功但释放失败 | 没有 `Prepared`，残留身份可追踪 | 候选值存在不等于达到本题成功条件 |
| 新筛选正确，原入口继续消费旧列表 | 公开入口的实际行与选择不符 | 需要追返回值接线，局部算法结果不足 |

再核对三个关系反例：子类绕过 `run` 的资源流程，违反受支持扩展；普通转发丢掉原接收者回调，可能改变行为；借入写入器被保存或关闭，破坏拥有者后续操作。这些都可能在少量正常结果相同的情况下存在，因此必须同时观察调用、失败和寿命要求。

### 9.2 采用足够小的过渡步骤

先保留公开入口，把本次完整选择和必要值显式传到计算位置，再替换一段算法责任。沿《从行为保护到渐进重构》的方法检查已有观察点和接缝；找不到保护时，限制首次解依赖编辑并说明尚未保护的范围。未来建立的检查不能倒推证明第一个编辑已经等价。

如果把覆写搬到协作者，先查源与目标环境、被调用数据、所有相关调用者及父子覆写。可让旧 `select` 暂时转交新能力，同时保持原返回、主要错误和必要原接收者关系。逐一确认客户使用新返回值、装配没有覆盖传入能力、每轮仍固定同一选择、草稿只有一个拥有者；确认已知客户迁移后再考虑删除过渡入口。《重构》8.1支持这个调查和过渡方向，书中步骤本身不证明当前语言绑定或客户清单完整。

采用新业务选择要有独立预期。把默认由 `all` 改为 `only` 不属于同一选择下的保行为重构；不要同时改实现和期待，使意外差异消失。回退也要检查旧实现是否仍支持已经承诺的选择、输入及完成条件，不能为了恢复代码而悄悄退回旧业务行为。

当实际路径包含外部效果时，比较新旧实现不得各产生一次效果。先确定可隔离的计算与观察范围，并在具体授权下选择验证方法。模块方法对已发布、未发布和结果未知的区分继续适用，代码回退或释放资源不能撤销外部效果。

本篇的两种对象协作只展示一个明确父流程与有限选择。实际变化若经多个客户、共享对象、返回值和继承关系继续分叉，须另完成影响路径及观察点收敛；难构造旧类时，新生方法/类和外覆方法/类也需要自己的正向中间状态与旧入口失败分析。这里的薄适配或一条“检查调用者”提醒不能替代这些工作。

### 9.3 给出有条件的决定并停止扩展

交付当前任务需要的结论：固定的客户要求、真实变体和选择者，选中的最小表达方式，正常及失败协作，新增成本，拒用的替代，以及会改变选择的事实。简单变化可以只用一段说明；不必为了使用本方法新建全部对象或文档。

若一个使用点、两稳定分支成立，保留条件；若纯计算共享且无独立寿命，函数足够；若固定配置与能力共同变化使装配更清楚，再比较小对象；若稳定父类的受支持钩子正好满足变化，继承可以胜出；若算法与使用者确有独立复用和更换，组合更值得承担。实际证据变化后重新比较，不把这几个结论变成固定技术偏好。

决定性输入、父类扩展或寿命未知时，停止依赖它们的迁移，列出能恢复判断的最小证据。没有额外变化需要保护时，停止增加接口和模式。来源支持、静态推导、代码检查和实际行为观察分别说明范围；任何一种局部证据都不能单独证明工程效果。
