## 1. 要作出的决定

发布候选是一份准备进入下一阶段的确定产物及其配套运行条件。交付负责人依据构建记录、配置、部署步骤和目标环境信息识别它，再把检查结果与这份候选关联。候选可以进入后续测试环境，也可以等待目标环境发布；这两种决定需要的证据和权限不同。

晋级是选择这份候选进入明确的下一阶段。先写出“哪个候选、进入哪里、为了取得什么反馈或提供什么能力”，再判断已有证据是否够用。例如，允许进入隔离测试环境以调查未知，并不表示允许给用户提供服务。不要用一个没有目标的“可以发布”掩盖差异。

本方法适用于交付路径尚未贯通、准备选择发布候选、检查结果和部署对象可能不一致，或配置及环境变化后需要判断证据能否复用的任务。只修改一段与交付无关的文字时，无需启动完整发布分析。

先取得当前任务允许的材料：变更目的与验收依据、候选所在位置、构建和部署记录、配置与环境版本、已有检查结果、当前发布要求。读取记录不等于执行部署。缺少候选内容身份时，下一步是补足身份与来源；缺少目标环境信息时，可以给出条件性分析，但不能宣布目标环境已验证。

本方法形成候选选择和证据判断。若还涉及部分实例更新、部署中断或持久数据迁移，需另行展开过渡状态、混合版本读写和恢复步骤。清单中的“无迁移”必须来自变更范围核查，不能因为没有看到脚本就默认没有数据影响。

## 2. 从最薄的交付路径开始

最薄的交付路径是一项足够小、但从构建一直到部署后业务结果都能观察的功能。团队从第一批实际需求中选择它，用这条路径暴露工具、环境、权限和协作上的未知，再逐步增加功能。仅有进程能启动，无法回答应用是否使用了正确配置、是否接通必要依赖、是否产生用户需要的结果。来源 G1–G4。

选择路径时，比较几个候选功能。优先选择能穿过当前最不确定边界、结果容易独立判断、失败影响可控制的一个。不要为了“端到端”一次引入全部子系统；也不要选择绕过主要依赖的假成功路径，使最重要的未知继续隐藏。

一条有用路径通常能回答下表的问题。具体工具由项目现状决定。

| 环节 | 要取得的证据 | 常见的错误完成判断 |
|---|---|---|
| 获取输入并构建 | 输入版本可取得，实际依赖和工具版本可查，构建过程能产生可保存的产物 | 开发者机器上能运行，就认为其他环境能够复现 |
| 保存和部署 | 部署选择了这份产物；所用步骤和参数可查，运行对象与计划一致 | 部署命令退出成功，就认为正确版本已接收请求 |
| 配置与接入 | 已部署入口加载了指定配置，并使用需要验证的真实适配器与依赖 | 本地测试直接调用内部函数或固定成功替身 |
| 业务结果 | 从部署后的入口取得结果，并按独立需求判断内容或状态 | 健康检查返回成功，就认为用户功能正确 |
| 协作与环境 | 需要他人提供的地址、访问条件和环境支持有负责者、预计取得时间及未验证项 | 请求已经发送，就认为跨团队依赖已解决 |

外部服务暂不可用时，可以用临时替代推进构建、部署和一部分应用反馈。记录替代了什么、哪些错误它无法暴露，以及什么时候由谁补足真实连接证据。替代路径通过支持的是已包含范围，不能在汇报中改名为“真实集成已通过”。是否足以进入下一阶段取决于该阶段的目的。

环境代表性也要具体说明。运行软件版本、配置加载方式、身份与权限、网络路径、外部接口和必要数据状态中，哪些与目标一致，哪些不同？缩小数据量可以降低成本，但不足以支持目标负载能力；试验凭据能够访问一份样本，也不证明目标凭据能访问全部需要的数据。把差异连接到待补的观察，而不是写一个没有内容的“环境基本一致”。

当一项业务行为已经贯通构建、部署、接入和结果检查，下一批未知有明确处理路径时，就应把反馈用于后续功能。除非有具体风险或重复成本依据，不继续为首条路径建设通用流水线平台、多区域编排或完整监控产品。初期耗时常受未知影响，先根据发现更新计划，不把这段时间机械外推为全部功能的稳定速度。

已有系统通常已有构建和部署入口。先沿当前最简单路径确认实际行为，增加将修改部分的保护，再调整实现；不要求为了取得第一条可信反馈先重写系统。需要建立行为保护时，衔接[行为保护与渐进重构方法](refactoring-legacy-safety.md)。

## 3. 确定候选及其运行条件

### 3.1 一份候选清单需要记录什么

清单的作用是使别人能够确认“当时验证的是什么、现在准备使用什么、哪里发生了变化”。优先引用现有可查记录，不为每次变更复制一套大型表单。来源 B1–B4、P1–P2、ACC1、SG18、SG23；下面的字段组合是工程适配 A1。

| 对象 | 至少保存能够判断差异的信息 | 它支持的判断 |
|---|---|---|
| 源码与依赖 | 提交或受控版本、实际解析到的依赖版本、可取得的位置 | 是否使用预期输入，是否引入依赖变化 |
| 构建过程 | 构建步骤版本、工具链、会影响产物的参数和记录 | 相同提交的两次构建是否实际采用相同条件 |
| 产物 | 不可变引用、完整内容摘要值、保存位置及取得方式 | 后续取用的字节是否与已验证产物一致 |
| 配置 | 版本或内容摘要值、环境差异、加载与覆盖顺序 | 实际行为是否受不同开关、地址或默认值影响 |
| 秘密引用 | 安全存储中的引用和适用版本、需要的权限范围 | 是否存在身份或权限变化；不在 Git 和普通报告中保存秘密值 |
| 部署步骤 | 脚本或配置版本、参数、目标选择和执行记录 | 环境变化是否同时引入过程变化 |
| 环境 | 运行软件、网络、外部服务版本及相关实际状态 | 声明的环境基线是否与当前观察一致 |
| 数据和迁移 | 相关模式、必要初始状态、迁移版本及执行状态；确实无影响时说明依据 | 代码与环境一致时，是否仍有状态或兼容性差异 |
| 检查依据 | 测试版本、独立预期或需求版本、数据范围、环境条件和结果 | 结果是否回答当前候选的实际风险 |

配置会改变行为，不能按“只改配置”自动降低检查要求。数据、外部服务和运行环境也可能在产物未变时改变。对实际决策没有影响的系统信息无需全部收集；对所依赖结论有影响的信息缺失，则必须明确限制。

受控范围包括代码、系统与应用配置，以及构建和配置脚本。版本可查只是核对输入的一项条件，不证明内容正确、能够运行或能够恢复。秘密值和生产个人数据不能因“全部入库”的要求进入普通版本库；配置与秘密管理各有维护成本，数据恢复仍需单独证据。来源 ACC1；数据与秘密的处理边界属于工程适配。

需要跨机器重复构建或复用先前结果时，构建负责人还应说明每项构建动作读取哪些源码、工具、依赖及必要环境，产生哪些输出，会修改哪些共享状态。复用依赖于输入声明完整、动作遵守声明且输出确定；未声明的环境读取、随机输出或共享副作用会使这项依据不足。补齐相关边界前，不能只凭同一构建步骤版本认定结果可复用。来源 SG18；隔离能力须按实际平台确认，自定义动作仍可能带来不确定性。小任务或现有构建已足够时，新增规则和迁移工具链的成本可能超过收益。

检查构建依赖时，形成一份小清单：当前代码实际使用哪些外部能力；每项能力由哪条已声明的依赖或明确支持的重导出约定提供；变更后该约定是否仍成立。把“本次环境中可以访问”和“项目保证可以依赖”分别记录。缺少声明或支持依据时，先补证据，再决定修改构建定义、调整调用或保留当前边界；不要仅凭一次成功构建结束核对。这里是本方法的原创检查清单，来源 SG18-D仅供背景定位。

如果A只使用B的接口，C只是B的内部实现，就不能仅因C出现在传递依赖中要求A直接声明C。若构建或模块约定明确支持B向A重导出C，则先确认A的用法在承诺范围内、谁维护这项依赖，以及B变动会不会破坏可得性；按该工具的实际表达方式核对，而不以是否手写同一条依赖边作统一判断。这些分支属于工程适配，明确支持的传递关系与偶然可得应分别记录。工具能否发现或强制声明责任须按具体版本取证；补声明仍有维护成本，也不证明清理完成或支持任意细分构建目标。

### 3.2 保存同一份产物和重新构建是不同能力

一次构建得到的产物通过检查后，后续阶段应取得保存的同一份内容。部署前校验取用的内容摘要值，并在能够观察时确认当前运行对象。产物仓库和部署记录应保持可信关联；只有一张人工填写的摘要值清单，不能证明实际部署了对应内容。来源 P1。

同一提交不保证相同产物：依赖、编译器、参数或打包过程都可能不同。重新构建生成不同字节时，应作为另一份产物处理。差异本身不证明业务有缺陷，但原产物的整体检查结果不能直接绑定给它。是否可复用某个局部结论，仍须证明那个结论依赖的输入没有变。

可重建表示受控输入和过程能够再次产生所需产物；字节可复现还需更强的条件和验证。两者都不能只凭“有源码”推定。已验证产物若丢失，历史报告不能用来部署；重新构建后要重新识别候选和适用证据。产物、依赖副本和相关记录保留多久，应服务恢复、复查和存储成本的实际需要，不照搬“总能重建，所以无需保留”的绝对说法。

配置外置有助于同一产物用于不同环境，但外置不意味着配置不属于验证对象。如果必须为不同目标产生不同包，就明确承认它们是不同产物，分别保存身份与所需证据，不在发布阶段静默重新打包后仍沿用旧身份。

### 3.3 声明状态和观察状态分别记录

源码 head 是代码库当前指向的提交；green head 是检查系统在所记录条件和检查范围内标为通过的提交。发布候选 RC 是负责人实际选定、准备晋级的产物及配套条件；部署对象则是环境实际取得或运行的内容。四者应通过实际记录核对，不能按名称互相替代。尤其是从通过的提交重新构建、另切候选或挑选提交形成 RC 后，仍须核对新对象与旧证据的关系；green 不涵盖未执行的检查，也不证明已部署。来源 SG23，具体记录方式沿用本节清单。

部署计划中的 A1、配置库中的 C1 和环境说明中的 E2，首先是预期。需要能支持当前决定的读回或执行记录，才能说明实际使用了它们。若读回不完整，就把对应部分写成未知。

读回也有范围：某个实例的版本不证明全部实例完成；取到配置文件不证明进程已经加载；命令返回接受不证明部署完成。部分更新和执行中状态须进入专门的部署状态分析，不能由候选清单直接宣布收敛。

## 4. 从失败风险选择必要证据

先写“可能发生什么错误、影响谁、哪些观察能区分正确和错误”，再选择检查。风险决定证据，流水线现有按钮不决定什么算完成。详细层次选择见[风险、独立预期与验证层次方法](test-risk-oracles-layers.md)。来源 P3–P6。

| 当前风险 | 较早、较便宜的反馈 | 还需要的大范围证据 | 不能据此推出 |
|---|---|---|---|
| 局部计算或分支错误 | 独立预期下的局部检查 | 少量关键路径经过实际接线后的结果 | 局部通过不证明配置、网络和依赖正确 |
| 取错包或配置 | 比较实际产物、配置和部署步骤身份 | 部署后观察实际加载与关键业务结果 | 内容相同不证明业务行为符合需求 |
| 外部依赖接入错误 | 格式、解析和错误处理的局部或接口检查 | 代表环境中的真实连接及目标差异检查 | 替身成功不证明权限、网络及真实服务行为 |
| 展示方式不符合用户需要 | 可自动判断的内容约束 | 仍需人的判断时安排有限人工反馈 | 自动验收通过不覆盖尚未表达的可用性问题 |
| 容量、恢复或安全方面的特定变化 | 与变化直接相关的快速检查 | 按该风险准备必要的负载、故障或安全证据 | 每次全跑所有昂贵检查不自动提高有效覆盖 |

把便宜且能快速定位常见错误的检查放在前面；慢检查可以在条件允许时并行，目标环境检查在相应对象可用时进行。检查依赖关系和成本决定顺序，不预设统一阶段数或固定分钟阈值。自动化收益需与维护成本比较；大量脆弱的端到端检查会拖慢反馈，仍不能替代缺少的独立预期。

某项检查是否阻止当前晋级，要在读取本次结果前按阶段目的和影响明确。例如，进入隔离测试环境的目的可能就是取得尚缺的集成证据；给用户提供新功能则不能把这份必需证据继续留空。人工反馈只有在本次需要它回答一个必要问题时才成为条件；不要将所有人员审阅固定到每次发布。

给定时间限制时，比较三种选择：缩小候选范围以减少未知；补做最能区分风险的检查；沿已授权的例外路径接受明确风险。遗漏一项必要检查的成本不能用“其他检查很多”抵销，未经授权的风险接受也不是交付负责人或代理可自行选择的捷径。

## 5. 判断结果能否支持当前候选

一条证据记录某次检查实际包含的对象和观察结果。检查执行者或工具在执行时保存记录，评审者据此判断它是否适用于当前候选。字段至少覆盖实际产物、相关配置和环境、测试与独立预期版本、数据条件、执行时间及结果位置；只有与该检查有关的维度才需要绑定。字段和以下结果划分属于工程适配 A1–A2。

| 观察或状态 | 对当前候选能说明什么 | 下一步 |
|---|---|---|
| 通过，且对象与必要条件匹配 | 在记录的输入、观察范围和时间内满足预期 | 保留范围限制，继续核对其他必要证据 |
| 观察结果不符合有效预期 | 被检查行为存在不符，或检查本身有问题 | 先区分产品、预期变化、测试和运行条件 |
| 执行设施错误 | 没有取得所需观察；若应用已经开始执行，还需辨明实际范围 | 修复设施后新增尝试，保留旧记录；不标为产品通过 |
| 未运行或被跳过 | 没有该项证据 | 说明是否仍为必要条件；必要时补做或走已有例外路径 |
| 曾通过，但相关输入已变 | 历史结果仍有效地描述旧对象，不足以支持新对象 | 按变化影响补证，不改写历史结果 |
| 报告对象不明或身份错绑 | 不能确认其对当前候选的适用性 | 找实际执行记录；不能只改文件名或标签 |

过期在这里指支持结论所需的条件已经改变，不是所有结果超过固定天数就一律失效。外部服务、权限、数据和时间相关条件可能变化，是否需重新观察取决于这些条件对结论的影响。

复用证据时，沿输入到结果的依赖关系逐项判断。例如，前缀配置变化不影响完全不读取配置的字符编码函数，却影响最终标签文本。复用前者的结果，需要确认产物中的对应代码、输入、测试和预期没有变化；后者应在新配置下重新检查。不能因为一项受影响就机械重跑所有检查，也不能仅凭测试名称相同宣布结果仍可用。更细的变化关系见[验收依据与变更影响方法](acceptance-evidence-change-impact.md)。

重复执行要保留尝试身份和条件。一次不符合后又一次通过，可能来自间歇问题、状态污染、设施变化或测试错误；最后一次绿色不能独立解释第一次失败。需要查明差异并评估它对当前风险的影响。涉及夹具和异步结果时，读取[夹具、替身与异步观察方法](fixtures-doubles-async-observation.md)。

## 6. 同一条交付路径的连续推演

### 6.1 给定事实与第一条路径

以下是原创静态题设，不是实际运行记录。一个只读的展品标签服务接收编号，向目录服务查询名称，再加上配置前缀返回纯文本。独立需求 R1 规定：目标前缀为“展品：”；M7 的名称为“月舟”，因此结果应为“展品：月舟”；未知编号返回“未找到展品”。它不写目录、不创建用户数据、不执行迁移。

A0、A1、A2 是不同的不可变产物；h0、h1、h2 是题设给定的不同完整内容摘要值别名，未在本项目计算。D1 是部署步骤，Q1 是验收检查。C1 的前缀正确，C2 将它误写为“展品-”。K1、K2 是秘密版本引用，报告不包含其值。

最初 A0 只实现 M7 路径，目录试验服务尚不可访问，临时替代 S1 返回“月舟”。团队能够构建、保存 A0，用 D1 部署，加载 C1，再从部署后的入口取得“展品：月舟”。这一结果说明已包含的交付路径能工作，尚不说明真实目录接入或未知编号行为正确。

交付负责人甲协调目录负责人乙取得试验地址和访问权限，记录需要的条件、预计时间及未验证项。此时继续完成未知编号行为和真实连接，优于立即建设通用部署平台：前者直接减少当前交付未知，后者尚无必要性依据。

### 6.2 建立 A1 的候选清单

团队在 A0 的基础上增加未知编号处理，形成提交 s7，构建新的 A1/h1；A0 保持原内容。A1 的实际依赖为 L4，工具链为 T1，构建过程为 B1。E2 使用目标版本的运行软件和相同配置加载方式，接入目录试验实例；静态目录数据 Z1 包含 M7=月舟。小规模试验不证明目标负载能力，也不覆盖目标的全部数据和权限。

| 项目 | A1 的确定记录 | 本题中的作用 |
|---|---|---|
| 输入与构建 | s7、L4、T1、B1及构建记录 | 区分后续同提交重建是否改变条件 |
| 产物 | A1/h1，字节已保存并能取得 | 后续直接使用这份内容 |
| 部署与配置 | D1、C1，目录地址按环境引用 | 区分代码不变时的行为变化 |
| 身份和环境 | K1、E2及实际配置读回记录 | 限定已经验证的连接和权限范围 |
| 数据与迁移 | Z1；已核查为只读变更，无迁移 | 限定检查样本，避免把无迁移假设外推到其他候选 |
| 验收 | Q1/R1，对已知与未知编号取得符合结果 | 支持这份候选在该范围内的行为 |

### 6.3 每次变化怎样改变决定

| 新事实 | 推理与决定 | 需要保存的下一项证据 |
|---|---|---|
| 源码 head 已到 s8，green head 仍指向 s7，其通过记录实际绑定 A1/h1。团队为 RC 从同一 s7 另一次构建，实际解析到 L5并生成 A2/h2；h2 与 h1 不同，部署读回仍为 A0/h0 | 这次构建没有保持 A1 的 L4 输入条件。green head 不能把 A1 的整体验收转给 A2，也不能证明 s8 通过或 A2 已部署。优先选择可取得且已有证据的 A1，或说明为何选择 A2；选择 A2时，只保留经核对不依赖变化且其他条件未变的局部证据，补齐受影响检查。本次目标要求的证据未齐前停止晋级 | 所选产物的真实构建输入与内容身份；A2 的适用检查结果；实际部署对象仍单独核对 |
| 计划仍部署 A1，却取到 C2。任意前缀拼接的局部测试通过；R1 检查得到“展品-月舟” | 局部测试没有验证目标前缀。A1 字节相同仍不满足目标行为；保留 C2 不符记录，更正配置，补验受影响的最终结果 | C1 实际加载记录及 Q1/R1 下新结果；无关局部检查复用的依据 |
| 更正配置后，尝试 J1 未获得运行资源，应用和测试均未启动 | 没有业务观察，所以不判断产品失败或通过；先恢复设施，再创建新尝试。将检查设为跳过也没有补出证据 | 设施错误、跳过动作及后续尝试分别保存；必要检查未取得前保持缺口 |
| 后续 J2 在 A1/C1/E2/D1/K1/Z1、Q1/R1 下两项通过；另有旧报告 J0，实际对象是 A0/h0 | J2 的绑定支持它实际检查的范围。仅把 J0 标签改成 A1，不能让旧产物的结果变成 A1 证据 | 使用 J2 的原始执行关联；J0 继续保留为旧对象的记录 |
| 目标 E3 读回发现 K2 和另一目录软件版本，尚无对应检查；人工可读性确认也未取得 | E2 通过不涵盖新增环境差异。保留不依赖目录或环境、且其他输入未变的局部证据；补齐目标连接、权限和结果观察。若人工确认是本次已约定必要条件，它仍是缺口 | 差异对应的观察范围与结果，以及确有必要的人工确认 |
| 后续给定记录补足已确认目标条件下的连接、两类编号、权限检查与人工确认，但负责人丙尚未批准目标环境操作 | 可在本题已约定范围内报告技术证据齐备；当前仍不能执行目标发布。通过不保证所有数据、未来运行或负载可靠 | 丙的有效授权，以及实际执行时需要再次确认的状态 |

这组推演没有因为某个绿色汇总增加就自动推进候选。每一步都先确定结果支持哪个对象、还有哪个必要问题未回答，再决定保留、补证、更换候选或等待授权。

### 6.4 反例：产物丢失后只剩报告

如果 A1 字节已从存储丢失，只剩 s7 和通过报告，而重建只能取得 A2，则“之前通过过”仍不足以交付 A1。可选择恢复保存的 A1，或者把 A2 作为新候选建立所需证据。不能把重建成功写成取得同一份产物。该反例也说明产物保留与源码版本控制解决的是不同问题。

## 7. 处理失败与变化

来源 P4–P6 要求重视阶段失败并区分原因；具体记录和复用步骤属于工程适配。失败后的第一步是确认有效预期、实际对象和执行条件，不能先决定“产品坏了”或“测试不稳定”。

| 新的依据 | 应作出的处理 | 错误处理 |
|---|---|---|
| R1 仍有效，实际 A1/C2 结果为“展品-月舟” | 保留不符事实，修正配置或实现，识别新候选条件并重新验证受影响路径 | 只修改期望字符串让 C2 通过 |
| 业务负责人正式将未知编号预期改为 R2 的“无此编号” | R1 历史结果继续保留；按独立 R2 修改检查和实现，新结果绑定新预期。若改代码，生成新产物 | 将 A1 的旧结果重新标记为满足 R2 |
| R1 正确要求“展品：月舟”，Qbad 却误写成“展品-月舟”；实际结果符合 R1 | 依据独立需求确认测试错误，审阅修正后的检查，再生成绑定新测试版本的结果 | 因为想发布就认定任何失败都是测试问题 |
| 应用未启动，运行资源分配失败 | 修复设施，新增尝试并保留 J1；尚无业务结论 | 把设施错误归为产品失败，或忽略它后标为全部通过 |
| 一次失败后偶然通过，原因不明 | 追踪条件差异、隔离性和实际风险；未解释的相关失败仍进入决定 | 重跑到绿色，隐藏其他尝试 |

流水线中断应使相关负责者及时处理，避免将不满足条件的候选继续当作正常候选。处理可以是纠正输入、修复设施、修复产品、修复检查，或按既有制度进行有依据的范围调整。不要把这一原则机械扩大成任何检查失败都让整个组织停止工作，也不要让 Skill 自动撤销提交或回退环境。

## 8. 区分技术条件与操作授权

技术就绪说明针对当前目标约定的必要证据已经取得，并且仍适用于这个候选。操作授权说明谁允许在什么对象、时间和范围执行动作。两者分别记录；来源 P6 提供按证据选择候选和人工判断的依据，以下具体授权与例外记录属于工程适配 A3。

常规决定至少回答：候选身份是否确定，必要证据是否适用，未解决风险是否仍阻止该阶段，授权是否覆盖准备执行的动作，以及当前状态是否仍与计划一致。候选有可查的通过结果，却缺少授权时，输出待授权状态和具体缺项；不要直接发布。

紧急修复可以有不同的检查顺序和风险接受方式，但应来自已有应急规则和负责者的有效决定。先识别紧急条件是否成立，写清要略过的检查、可能后果、候选范围、观察与停止条件、负责者及之后补证安排。缩小变更或选择已有证据的产物，可能比在信息不足时扩大修改更合适。

如果既有规则允许且有效授权已经取得，可按该例外范围处理；记录为“接受明确风险的例外决定”。原有产品失败、未运行或证据缺失状态继续保留。没有规则或授权时，不由代理自行创造例外；给出已能完成的准备及缺少的决定依据。

恢复方案也必须说明对象。取得旧产物只说明代码内容有机会恢复；旧配置可能与当前代码或服务不匹配，旧代码也不能自动撤销已写入的数据、已发出的消息或外部效果。若存在这些变化，须在执行前另行分析兼容性、停止、前向修复和恢复步骤。不要用“可以回滚”三个字替代实际恢复依据。

## 9. 形成可执行的下一步

输出应让接手者知道现在可以决定什么、还缺什么，以及下一步为什么值得做。按任务规模给出简短段落或表格即可，不要求每项任务填满所有字段。

| 输出 | 需要回答的内容 |
|---|---|
| 目标与候选 | 进入哪个阶段、为了什么，使用哪份产物和配套条件 |
| 已有依据 | 哪些结果确实绑定当前对象，覆盖什么范围，哪些结果经影响分析可以复用 |
| 缺口与冲突 | 哪些是产品不符、设施错误、未运行、跳过、条件变化或对象不明；是否仍阻止当前目标 |
| 最小必要下一步 | 谁补什么观察或修复，预期区分什么风险，完成后怎样改变当前决定 |
| 技术与授权状态 | 技术条件齐备、尚有缺口或采用已授权例外；操作是否获准，以及限制条件 |
| 执行后的观察 | 当前任务允许实施时，核对实际运行对象、配置、必要业务结果及停止条件；未实施时明确这些仍是计划 |

例如，在第 6 节 E3 差异刚被发现时，可写：

> 当前选择已保存的 A1/h1。Q1/R1 在 E2、C1、K1、Z1 下的结果支持该范围；不涉及目录或环境的局部结果在其输入未变的条件下保留。E3 的 K2 与目录版本尚无对应连接、权限及结果证据，必要人工确认也未取得，因此尚不满足本次目标发布要求。甲协调乙补足差异对应检查并登记实际对象；丙的发布授权单独确认。目前没有目标环境发布结果。

这个记录把缺口转成具体工作，也避免要求不受影响的检查无条件全部重跑。与下一阶段衔接时，使用[交付流程](../workflows/delivery.md)继续处理实际任务；本方法不以来源核查或静态示例代替项目运行证据。
