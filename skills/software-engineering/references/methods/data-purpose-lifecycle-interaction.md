## 1. 从本次变化确定检查范围

数据生命周期定义一项信息从收集、使用和传播，到停止访问、受控恢复及最终处置的条件。团队依据已确认目的和适用要求确定这些条件，工程师把它们落实到字段、接收者、实际副本和用户操作。一个“已删除”标志不能同时证明所有阶段都已完成。

本次变化涉及个人信息的新用途、新接收者、字段组合、保存要求、删除或恢复入口时，采用本文。先说明谁希望完成什么，哪一项变化可能改变结果，再沿相关数据和任务路径展开。只修改帮助文字的标点，且处理含义、数据流、操作路径和原证据适用性均未变时，核对受影响文字及链接即可。若把“移出”改成“删除”，其含义可能变成不可恢复，应重新核对承诺，不能当作纯编辑。来源T6-CHANGE、T6-LIMIT；裁剪步骤为工程适配。

既有[数据用途与最小化规则](../rules/se-pro-data-minimum.md)和[关键交互初查规则](../rules/se-quality-access.md)已提供简短入口。本文补足从目的到具体结果的连续推导。遇到含义未决，复用[需求澄清方法第2、4–6节](requirements-language-behavior.md#2-把原话分成竞争解释)；结果证据和变更影响复用[验收依据方法第2–4节](acceptance-evidence-change-impact.md#2-从行为得到可检查的预期)。消息身份、派生删除和恢复继续由对应方法承担，本文给出需要交接的输入与判断。

采用本方法不会取得额外操作权限。设计审查可以给出条件和选择；收集、改权限、删除、恢复、外发及生产修改分别沿用当前任务授权。隐私初查和交互初查保留各自证据范围；专业判断的边界不能成为省略日常字段分析、状态设计和可操作检查的理由。

## 2. 把目的、对象和决定责任连起来

### 2.1 固定一个连续的虚构题设

“苔岚拼贴室”是一套虚构私人卡片服务。本文复用2026-10-01形成并修订过端点说明的原创题设；以下是本次静态推导的给定条件，没有运行服务、用户研究、恢复操作或Skill行为。卡片、角色和事件均不对应真实项目。

| 给定事实 | 它允许推导什么 |
|---|---|
| 本人建立卡片；主存储保存卡片号、生命周期号、所属账户、正文和本人选择的主题 | 本人查看、编辑有效卡片是已确认目的；所属账户用于当前本人关系判断 |
| 私人列表按账户读取；搜索索引保存卡片号、生命周期号、主题和必要摘要 | 索引是内容的派生表示，不能在主存储删除后自动视为消失 |
| 编辑原文会进入短期撤销副本；本人在获准范围恢复自己的内容是已确认用途 | 撤销副本有独立恢复目的，需要自己的访问、期限和处置条件 |
| 候选推荐组件拟接收稳定账户号、主题、访问时刻、卡片摘要，用于不同活动中的个人偏好分析 | 接收者、字段组合和用途都发生变化；产品负责人支持方案，但本人对新用途的同意未给定 |
| 用户需要区分“移出当前列表并可恢复”和“最终删除内容” | 两项操作的后果必须分别表达；相似名字不能合并其状态 |
| 移出后停止通常访问；本人只能在截止点D之前通过获准恢复入口读取隔离内容 | 恢复条件为实际判断时刻t满足t＜D；t＝D或t＞D不在该恢复承诺内 |
| 最终删除须不晚于完成点X，含X时点，清除运营方控制范围内该卡片的内容；X以后不再承诺原文恢复 | 完成判断要覆盖在线存储、索引摘要、短期撤销副本、备份和待处理更新内实际保有的内容，并防止旧输入或恢复重新暴露 |
| 经题设确认足够的最小操作记录含操作号、卡片/生命周期号、操作种类、受理时刻、各路径状态及最终结果 | 它不含正文、主题、稳定账户号或可还原内容，但仍可能关联对象；读取者和保留结束条件E须单独确定 |
| 范围只有上述五条内容路径及最小操作记录，没有用户导出副本 | 推导可以在这个范围闭合；真实工程仍须查实际副本与接收者，不能照抄“没有导出” |
| 候选接口可返回可信操作号，并允许按同一操作号查询 | 回执不证明全部路径完成；发送前是否已有可恢复的请求身份、响应丢失时如何找回操作号仍需设计 |

D、X的具体时刻及其确定依据，E的结束条件，备份能否逐项清除，删除控制如何抵抗旧输入，界面和平台实际能力都未给定。团队可以推导条件分支，不能填入经验天数或宣布已经满足要求。卡片号加生命周期号用于区分同名卡片的不同存在期间；后续新建卡片不能继承旧卡片的迟到更新或删除决定。

### 2.2 五类问题分别取得依据

目的说明应使读者知道使用哪些信息、对谁产生什么结果，以及信息会到谁手里。例如“分析偏好”仍不足以判断摘要和访问时刻是否必要；数据负责人须确认需要跨哪些活动关联、输出给谁及何时结束。用目的、信息主体、发送者、接收者、信息属性和传播限制描述变化，来源为T6-CONTEXT；以下责任划分是工程综合。

| 问题 | 本题由谁提供什么依据 | 缺少依据时保留什么 |
|---|---|---|
| 本人是否同意特定个人信息改作新用途 | 信息主体对明确新用途的同意依据；ACM 2018第1.6条把它作为独立职业伦理前提 | 新用途未决；不启动其收集、跨活动关联或交付，不影响已有明确目的内可继续的工作 |
| 组织是否决定承担该功能的收益、风险和成本 | 数据负责人确认目的、字段、保存及传播要求；产品负责人作职责内的功能选择 | 方案与决定者分列，不能把产品支持冒充本人同意 |
| 谁可以读取、修改和恢复哪张卡片 | 控制维护者核实当前身份、所属关系、入口及实际执行限制 | 缺少当前关系或控制证据时，不开放相应访问；曾经能读不表示现在仍能读 |
| 执行代理可实际做哪些动作 | 当前用户任务对目标、动作与范围的授权 | 只形成当前获准产物；角色称谓、登录状态和方法建议均不增加权限 |
| 当前法律允许或要求什么 | 针对实际地区、主体、信息种类及时间的有效规范和具备相应职责者的判断 | 保存具体法律问题与影响，停止依赖未定法律结论的承诺；本文不作法律认证 |

因此，产品负责人批准推荐组件、运维人员能读主库、内容已加密，仍不足以跨过新用途同意未给定的分支。若后续另行给定本人对明确新用途的同意，也须继续比较必要字段，核对组织决定和技术控制。一次勾选只证明某个界面动作；同意内容、适用版本、主动决定和背景是否足够，需要自己的证据。来源A1.6、ACM-PREAMBLE、T8-POLICY、T8-INTENT。

保密责任也不能被用途变化绕过。ACM 2018第1.7条的有限例外须连读文件页8、9：它同时限制披露对象为适当主管方并要求审慎判断。本文未指定任何真实主管方，也不从该例外产生外发许可。

## 3. 从必要结果比较收集方案

### 3.1 先问每个字段怎样改变目标结果

沿用本人卡片主线：本人需要打开自己的指定卡片，故当前请求需要能找到卡片并检查本人关系；正文用于展示，主题用于本人分类。把这些用途转交推荐组件时，要逐字段重新说明必要性。主存储需要账户关系，不等于推荐组件也必须得到稳定账户号。

| 拟交付字段 | 对跨活动偏好候选的可能作用 | 改成只给本人当次主题建议后的判断 |
|---|---|---|
| 本次主题 | 形成主题偏好输入 | 可能已经足够，先确认建议能否只依赖它 |
| 稳定账户号 | 把多个活动连接为同一个人 | 当次建议没有跨活动目的时，不因现有字段方便而继续传递 |
| 访问时刻 | 排序、频率或时段分析 | 当次建议若不依赖时间，这一字段缺少必要性；粗化时间也须说明用途 |
| 卡片摘要 | 从正文提取更丰富偏好 | 若主题已经足够，摘要增加内容暴露而不支持额外必要结果；有明确语义需求后才重新比较 |
| 正文 | 支持内容理解 | 本候选原本只提摘要，不能为方便调试额外发送正文 |

最后一列是另行给定“只需当次主题建议”的条件分支，改变了原跨活动功能目标；它不声称较少数据能够实现同样完整的跨活动分析。数据负责人先确认真正需要的结果，再由工程师选方案。来源T8-MIN、A1.6；字段分析为本题适配。

### 3.2 比较能改变选择的候选

| 候选 | 功能收益和损失 | 工程代价及反例 | 选择反转条件 |
|---|---|---|---|
| 不启动新增收集或推荐传递 | 保留已有私人功能，失去新增个性化推荐 | 不需要新关联存储；但不能假装已实现推荐目标 | 新用途依据齐备且确有必要结果后，再比较其他方案 |
| 只传当次主题，去掉稳定关联、时间和摘要 | 可支持已确认的当次建议；不能形成跨活动个人历史 | 可能降低建议细致程度；即使不带姓名也不自动匿名 | 明确目标确需跨活动结果，且更窄信息不能满足时，才比较额外字段及关联 |
| 保留经论证的字段，限制接收者和读取 | 指定组件仍能计算所需结果，减少其他读取者 | 必须维护每个读取与转送入口、故障和离职等变化；有权限的组件仍可关联内容 | 当前用途可用更少字段满足时，应回到更窄方案；控制覆盖无法证明时，不能承诺相应保护 |
| 为必要信息设置有依据的受限保留 | 让一段必要历史可用，减少以后持续暴露 | 需要到期处理、派生清理、备份和迟到输入安排；仅删主表可能留下摘要 | 结束条件不能覆盖恢复或既定结果时，重新决定对象和能力；不能默默延长期限 |

这些选择可以组合。当前主线因新用途同意未给定，停在第一行；没有必要先建一个“以后再启用”的个人偏好库。假设同意等条件后来成立、目标收窄为当次建议，第二行就比保留整个历史再限制读取更直接。若证据反而证明必须跨活动，第二行的功能损失便不可接受，但第三、四行仍须证明必要性和可实施性。

一个反例是删除姓名后仍传稳定账户号、精确访问时刻及丰富摘要。组件仍能把多次行为连在一起，甚至与其他信息组合；因此不能把它描述为匿名数据。加密可以保护特定传输或存储环节，不能决定该组件是否应取得这些字段。来源T6-LINK、T8-POLICY。

### 3.3 为结果留证，也要论证最少必要

本题的操作记录用于说明某次删除是否受理、哪些路径完成及哪些未完成。题设已确认最小操作记录足够支持这些结果核查，因此不把完整卡片正文、摘要和主题写入操作日志。当前本人关系和权限由现有控制承担；仅凭上述最小字段不能独立重建全部身份与授权事实。确有额外核查需要时，先说明必要依据和受控关联，不能把所有认证信息复制到日志中。

T8-LOG是在不可抵赖性控制中提出较多记录的建议，原文已要求按需要确定保留时长，并核查日志或信息传递与隐私政策的关系。本文不采纳“存储便宜便可无条件多收集或无限保留”的外推。当同一份个人信息、同一目的和同一保存范围同时涉及证据需求与最小化时，团队须比较字段是否真的改变待证明结论。目的不同、对象不同的段落不自动构成书间矛盾。

若团队认为上述最小记录不能判断一次失败，应指出缺少哪项事实，并比较增加一个受限状态、修复结果查询或保留完整内容等方案的收益和代价。没有这项证明，不能以“有日志价值”保留正文。换名为审计证据或只存可关联摘要，也不使信息脱离隐私责任。证据身份、关联方式、接收者和结束条件E仍由下一节处理。

## 4. 分别定义内容、证据与副本的期限

### 4.1 将四种动作分别绑定对象和结果

使用是为已确认目的读取或处理；停止通常访问是让日常列表、搜索和其他已纳入入口不再暴露内容；误删恢复是在仍有效的恢复要求和当前权限下重建允许使用的内容；最终处置是按指定范围和期限移除应当消失的内容。团队先定义用户后果，再确认存储如何实现，不能从数据库字段名倒推承诺。来源S26-SOFT、S26-RETENTION、S26-RECOVERY、A1.6。

| 对象 | 使用与停止访问 | 误删恢复 | 最终处置和应取证据 |
|---|---|---|---|
| 主存储中的指定卡片/生命周期 | 本人关系和当前状态允许时展示；移出后日常列表及直接读取均受当前限制 | t＜D且本人当前有权、没有更晚有效删除限制时，才可从隔离内容恢复 | 最终删除范围内不晚于X移除正文等指定内容；核对对象、版本、实际存储及读取入口 |
| 索引摘要和主题贡献 | 仅支持已确认搜索；移出后搜索结果及摘要预览不能绕过限制 | 必须从获准版本重新建立相应贡献，不能恢复已被更晚删除的内容 | 对照卡片/生命周期查全部摘要和关联贡献，并取得删除已应用与查询不可见的证据 |
| 短期撤销副本 | 只用于已确认恢复，普通列表无权读取 | 核对副本对应版本、t＜D、当前权限及后续修改，不能用旧文覆盖正确新文 | 最终删除要求覆盖实际保有内容；核对副本清单和清除结果 |
| 备份 | 只在明确恢复职责下访问；普通界面关闭不说明备份销毁 | 在隔离目标恢复并先应用当前控制；原格式、代码和依赖须可用 | 有逐项删除能力则取得覆盖证据；否则按最晚仍可恢复内容的清除点B与X比较 |
| 待处理更新 | 按原允许目的处理；移出或删除后的旧输入不再取得相应曝光资格 | 恢复也须核对输入所属生命周期和当前允许状态 | 若载荷实际含内容，也属于不晚于X清除范围；还须证明迟到写入不能复活内容 |
| 最小操作记录 | 供获准结果查询及必要核查者使用，另限关联和读取 | 它只能恢复操作结果，不足以恢复卡片正文 | 按独立结束条件E清除或退出关联，并满足结果查询、重复保护和当前删除控制的责任；E未定则此设计未完成 |

“移出后停止访问”仍须确定限制在哪个时点生效、如何处理已发出的读取和响应。若产品要求受理时立即停止，接入点须能证明所有相关入口在该时点受控；若方案只能逐步传播，应取得明确的较晚生效约定，不能把受理时刻偷换成生效时刻。本文没有给出通用延迟数值，界面也不能无依据显示“已经隐藏”。

### 4.2 端点、未知与真正冲突

本题D使用严格边界：t＜D才可能允许误删恢复；等于D不允许沿这项承诺继续。X包含端点：证据若证明相关内容恰在X清除，时间条件仍满足。实际工程还要核实谁记录时间、时区、时钟误差、触发点和最终完成点；无法确定先后时，保持该时间结论未知，而不是按客户端倒计时猜测。

假设某备份不能逐项清除，最后可恢复内容只会在B消失。B≤X只是满足一个必要条件：还须核对全部备份成员、撤销副本、索引、待处理内容及旧恢复路径。B＞X则当前能力不能履行内容清除承诺。存储负责人可比较有证据的逐项清除能力、退出相应备份内容或改变保存结构；有权决定要求者可以考虑改变尚可修改的承诺及相应告知。工程师不能自行推迟X，也不能把备份里的内容改称“技术副本”排除。

恢复与销毁只有在同对象、同范围、同时间和同要求真正互斥时才冲突。例如对同一可恢复内容，仍有效要求在某一时刻必须可恢复，另一有效要求却要求同一时刻已经不可恢复，两者不能同时满足。若前者只适用于选择“移出”的卡片，后者适用于另行选择“最终删除”的卡片，应先确定操作之间的有效关系；不凭两个按钮并列就捏造冲突。不同时间先恢复、后处置也可共存。来源S26-SOFT、S26-RECOVERY；具体判断为工程适配。

E未定不能被写成“无限保留”。数据负责人须确认操作结果需查询至何时、哪些旧请求仍可能进入、删除控制还承担什么责任；存储负责人证明相应保留与容量。缺少结束条件时，继续设计比较，暂停依赖该留证方案的新上线承诺。对已承担的请求，不能为腾空间删除必要证据；按原权限限制新增负载并交接待定责任。内容清除证据可以单独成立，但不能据此声称连同最小记录在内的全生命周期已经完成。

## 5. 把删除要求交给每条派生与恢复路径

### 5.1 用一个对象贯通，而不是各报一个成功

本人选择最终删除卡片C@L。数据负责人把确认的范围、X、允许保留的最小记录及待定E交给各路径负责人。控制维护者确认当前本人关系和执行权限，存储负责人列出该对象确实存在的副本；索引负责人列出摘要、主题关联和可能的缓存贡献。题设未给缓存实例，真实清单若发现额外缓存，就扩大实际对象清单并重核原承诺，不能悄悄漏掉。

主存储报告C@L正文已清除，索引却仍有同生命周期摘要，这是明确的未完成。索引删除后，还要区分“已应用删除”和“查询入口不再提供内容”。复用[派生更新方法第3、5节](data-derived-state-rebuild-reconciliation.md#5-把删除与旧贡献纳入恢复)，向下游交接对象/生命周期、删除版本、旧贡献、必要来源范围及查询要求。不要另写一个仅按卡片号删除的算法，使旧C@L删除误伤后来C@L2。

迟到编辑若仍携带C@L旧正文，查询主库为空不足以证明它不会重新写入。各写入及派生入口必须依据当前删除或生命周期限制拒绝旧效果，并取得这些限制实际作用于提交位置的证据。只在接收时查过一次状态，随后无保护地写入，会留下删除和旧写交错窗口；租约过期和进程自报停止也不足以关闭窗口。具体版本、共同提交或目标资源隔离复用[派生更新方法第9节](data-derived-state-rebuild-reconciliation.md#9-在实际读写位置启用新结果)。平台不能提供所需保护时，比较在已获授权范围内受控停止并确证在途工作结束的方案；仍不能证明时保留未完成。

### 5.2 内容清除与防复活证据分别收集

| 路径 | 负责人应取得的具体事实 | 不足时如何继续 |
|---|---|---|
| 主存储与撤销副本 | C@L、应清除字段、相关版本和副本范围均相符；实际结果满足定义的内容处置要求 | 保存已证实范围，查缺失副本或存储能力，不凭删除请求返回成功补齐 |
| 搜索索引 | 原摘要及相关贡献已移除，所用索引版本与查询入口一致；必要输入覆盖已核实 | 继续对应删除或有依据重建；不能用总条数相等证明特定卡片已消失 |
| 待处理更新及在途写者 | 实际载荷是否仍含内容；保留与清理范围；每条效果入口对C@L的当前限制；旧工作结束或受保护拒绝的证据 | 约束有关入口并核查原工作；“队列空”不能代表离线重投、其他副本或已取走工作消失 |
| 备份和恢复 | 清单覆盖实际可恢复内容；B和处置结果可信；旧恢复受当前限制约束 | B未知则期限结论未知；B＞X则报告无法满足要求；缺当前控制时保持隔离 |
| 最小记录及删除控制 | 能关联原操作、对象、结果和所需拒收边界；有当前读取限制、结束条件及清理依据 | E未定或去重/拒收证据不足时，保留具体缺口并限制无法履行的新承诺 |

这些路径不默认共享事务。一个协调任务“已完成”不能代替每个资源的范围证据；若只完成四条，就明确列出第五条未完成或未知。最终处置也要定义是否要求无法恢复原内容，并据实际存储、快照、日志及密钥能力取证；普通业务查无记录和操作系统空间已释放都不能自动证明它。本文不提供通用物理介质销毁认证。

### 5.3 恢复旧备份时先恢复当前限制

继续同一C@L：当前已经接受最终删除，旧备份仍含其正文和“有效”状态。恢复负责人先把备份加载到隔离目标，取得独立于这份旧副本且可证明为当前的删除、访问和执行控制，核对生命周期、备份切点、兼容代码、必要依赖和恢复范围，再决定哪些数据可以开放。不能直接用备份中的旧“有效”状态覆盖现行删除决定。

复用[保留与恢复方法第8、10节](resource-retention-cleanup-recovery.md#10-恢复旧数据前取得当前控制)和[派生更新方法第10节](data-derived-state-rebuild-reconciliation.md#10-联合判断恢复材料容量与保留)。当前控制无法取得时，仍可在获准隔离范围检查字节与结构，相关读取、业务写入和外部效果保持关闭。把控制文件放在另一目录，不证明它不会随同一故障丢失或回滚。

相反，C@L仅被移出、t＜D、本人仍有权、没有更晚删除限制且内容和依赖完整时，可以设计受控恢复。恢复者核对当前内容是否已有后续正确编辑，选择需要恢复的版本或子集，避免整份旧备份覆盖新状态。恢复结果还要证明本人能取得正确卡片、索引对应且无越界暴露；备份作业曾运行不是这项结果。来源S26-RETENTION、S26-RECOVERY、S26-EVIDENCE。

删除标记和操作记录的保留不能只取一个方便的TTL。全部重放路径、允许查询、在途提交和恢复依据共同决定退出条件，复用[保留方法第5–6节](resource-retention-cleanup-recovery.md#5-从所有重放路径推导保留条件)及[去重方法第7节](message-idempotency-ordering.md#7-推导历史保留与清理条件)。若要求永久阻止复活却又要求清除所有识别依据，应指出能力与要求之间的具体矛盾，比较可靠拒收边界或其他有证据的方案；不能同时声称永久保护和无条件清空历史。

## 6. 让同一关键任务具有明确结果

### 6.1 从目标进入，先让人能作出决定

本人目标是“这张卡片暂时不出现在通常入口，保留有限恢复机会”，或“这张卡片内容最终从已声明范围清除”。交互负责人从私人卡片列表开始设计入口和说明，不直接把检查者放进删除面板。否则只检查到面板内部可用，未检查用户能否找到入口。来源T15-CONFIG、T15-GOALS。

候选面板显示可识别的卡片身份及两项清楚命名的操作，说明各自影响、D或X的含义、备份是否仍待处置、最小记录的范围及已确定的结束条件。说明须在决定前可取得，不能藏在操作完成后的提示。D、X或必要保留条件尚未决定时，设计者保留未决说明，不用“立即、彻底、永久”替代缺失要求，也不发布依赖这些承诺的操作。

候选交互要求本人主动选择操作，并在提交前能复核对象、范围和后果。取消或返回卡片应明确可用；最终删除的说明不能只有威吓，也不能迫使用户批准与目的无关的新用途。警告的必要性、解释、可行动选择和验证，分别对应T15-WARN中的NEAT；来源、步骤、风险、用户知识、选项和证据对应SPRUCE。本文把这些原则用于该面板，未声称警告已经证明理解或有效同意。

当关键任务从账号变化、风险通知或支持回访开始时，交互负责人应让接收者能从已知可信入口独立找到同一通知，核对所指对象、动作及当前资源状态。昵称、来电显示或不明链接不能成为唯一可信依据；通知声称操作完成，也不能代替资源上的结果。可信入口查不到对应信息、状态冲突或证据过期时，保留无法核实的结果，不能据此直接认定通知真实、通知虚假或操作未发生。[原文支持：T15-NOTICE；工程适配：通知与资源对应及未决判断]

交互同时说明哪些动作可暂停或取消、何时生效，以及已经发生的效果如何核对；具体结果沿用第6.3–6.4节，关闭通知不等于撤回后台操作。缺证时暂停依赖该通知可信性的动作，并交给明确负责人核实。确有紧急要求时须说明当前依据，按实际权限和后果选择处置，不能笼统保证可延迟或可撤回。维护独立入口、通知与状态对应关系会增加产品和维护成本；是否发送、发给谁及采用何种渠道仍由当前要求与授权决定，人的实际理解与效果另取证据。

### 6.2 先解决响应丢失时如何找到原操作

操作身份指同一次业务意图在发送、查询、重试和结果记录间保持的关联。发送前若只有卡片号，而服务器操作号O要等响应才得到，响应丢失后就可能无从查询；“按O查询”不能解决调用方根本不知道O的分支。

候选方案在发送前保存关联K及固定的卡片/生命周期、操作种类和适用要求版本。服务器若使用同一K作为操作号，须核实身份范围和输入绑定；若另发O，须提供经当前身份授权、能按K查回O和对应请求的可靠关联。K本身不授予读取权限，也不能作为任何人可查对象的公开凭证。保存关系所需的最少信息和期限仍受第3、4节约束。

这些是待验证的接入条件。须分别核查：相同K异输入如何拒绝或报告、多个写入口如何保护重复、关联保存到何时、查询看见什么版本、受理责任保存在哪种故障范围内。复用[操作身份方法第2–5节](message-idempotency-ordering.md#2-定义操作身份输入与存储前提)及[未知效果方法第6–7节](message-atomic-effect-recovery.md#6-外部能力决定未知后的动作)。不能照搬相邻题设的本地事务来保证跨主存储、索引和备份原子删除。

若目标环境不能提供发送前身份及找回关系，提交后无响应只能保留未知，交给明确的接入负责人核查原请求、已发生效果和剩余尝试；停止自动重做。该设计仍缺可靠自助恢复，不能宣称完整交互已可交付。若只有查询而没有重复保护，查无记录仍可能是旧请求在途，也不能换号重发。

### 6.3 把请求事实、后台进度与观察状态分开

下表定义候选界面怎样表达证据。受理和处理进度描述后台已知事实；未知描述当前观察不足，可以叠加“上次已知受理”。它们不必挤进一个互斥数据库枚举。来源只支持目标与证据原则；这份状态约定是本题工程适配。

| 可显示状态 | 进入该状态需要的证据 | 本人看到什么、可以做什么 | 不能据此推导什么 |
|---|---|---|---|
| 尚未提交 | 操作选择仍在本地，发送未发生且没有同次其他尝试 | 可修改选择或取消；取消后返回有意义的卡片位置 | 仅关闭界面不证明系统没有此前其他操作 |
| 提交后待确认／受理未知 | 请求已发出，尚无充分受理或拒绝依据 | 显示“尚未确认是否受理”，保留原K和查询/核查入口 | 无响应不等于未受理、未删除或可再建操作 |
| 已受理 | 取得匹配K/O、对象和种类的可信回执，并证明其承诺的保存及处理责任 | 显示请求已接手及后续查询方式；允许离开页面 | 回执、队列保存、操作者勾选均不证明内容清除或访问停止 |
| 处理中 | 当前可靠观察说明仍有必需路径未完成且责任在执行或等待 | 显示已经完成与仍待完成的范围及最近观察；可查询状态 | 不用虚构百分比或未经证实时间承诺掩盖等待 |
| 结果未知 | 查询不可得、证据陈旧或缺失、原身份无法找回、提交响应无法判断 | 保留“上次已知”及未知范围；继续原操作查询或交接核查 | 不把曾经处理中改成确定失败；也不把空查询改成从未发生 |
| 完成 | 对指定操作取得与第4、5节范围一致的最终结果；各必需路径和当前限制均有证据 | 移出完成说明停止访问及有效恢复条件；最终内容删除完成说明清除范围、时间及仍保留的最小记录 | 移出完成不等于销毁；内容清除完成不等于全部记录已消失或所有生命周期问题已解决 |
| 失败／明确拒绝 | 有具体持久拒绝或实际失败证据，说明失败步骤、已发生效果和剩余责任 | 若确证未受理且不会执行，说明本次未生效；若部分清除后失败，保留已清除范围及待修复路径 | 技术失败不能抹去已经发生的删除；失败标签本身不允许重做或恢复 |

受理含义沿用[消息确认方法第4、6节](message-delivery-acknowledgment.md#4-定义确认故障与责任)：只有接收方承诺并实际保存的责任才是该跳受理，不把网络响应码等同持久业务结果。负责人下一次复核时间用来追查，不是自动失败、销毁或无限等待的依据。

### 6.4 连续推导正常、中断与反例

本人从列表进入C@L的操作面板，读到两种后果，选择最终删除。假设本分支已补齐D/X/E中与该操作有关的要求、当前授权、K/O关联、各资源处理能力和查询依据，才允许提交。接入方保存K和固定输入，服务器返回匹配受理。此时界面显示“已受理”，负责人继续完成主存储、索引、撤销副本、备份及待处理更新的工作。

随后主存储和索引已有证据，备份仍未到已验证的B。界面应显示处理中并说明剩余范围，不能因本人列表已空显示“全部内容已清除”。当B≤X、其他必需内容都已清除、旧输入和恢复路径都受当前控制约束，且取得全部相符证据时，才形成该范围内容删除完成记录。若某项只能确认“请求已发送”，它仍未完成；即使时间越过X也不能自动变成成功，此时还须报告未履行时间要求及处置责任。

改变一个事件即可区分错误设计：

- 本人在尚未发送时取消：候选要求不发出请求，关闭面板后焦点回到原入口；原入口消失时回到相关卡片列表位置。后续操作检查需要证明没有该次受理，并观察焦点，不能从面板消失猜测二者成立。
- 本人在已经受理后关闭面板：关闭只结束当前视图，后台责任继续；重新进入时按原K/O查询。界面不能显示“删除已取消”。若业务另需撤回请求，必须定义独立操作、能否中止、已发生删除的后果和对应证据；本文题设没有提供此能力。
- 提交响应丢失：至少可能未到服务，也可能已经受理；前端保留未知。查回匹配受理后显示已受理或当前进度；查询为空仍不证明无效果，不能自动换号再删。
- 内容已部分清除后某路径明确失败：保存各路径结果和原操作身份，交由对应负责人修复或补证；已经销毁的正文不能凭“重试”或“回滚”重新产生。
- 旧查询响应晚于新完成结果到达：核对同一K/O及可靠版本或观察顺序，避免把已证实完成降回处理中。没有可证明的顺序关系时并列保存矛盾观察并核查，不能仅按到达先后覆盖。

同样的判断用于“移出”与“恢复”：本人按恢复按钮是请求，恢复已受理是责任接手，正确内容在当前权限下重新可用才是恢复结果。读回一条成功日志只证明该记录存在；交付证据还需核对同一对象、生命周期、操作、内容版本及允许查询路径。

## 7. 在指定环境初查键盘与辅助技术

### 7.1 先固定环境和本次要观察的任务

以下是待执行的工程检查方案，不是执行报告。示例目标为Windows 11桌面、Google Chrome桌面、简体中文页面、NVDA 2026.2及桌面键盘布局；这不是对使用者当前电脑的描述。开始实际检查前记录操作系统构建、浏览器和NVDA实际版本、键盘布局、语言、页面构建、缩放、当前权限、对象初始状态及选中的分支。版本不符时先核对对应官方操作说明，再调整步骤，不能直接继承这里的命令或结果。

检查对象为同一C@L的入口、移出、有限恢复、最终删除、取消、返回与状态查询。每个分支都须有可观察的后台预置或获准隔离条件；若不能形成受理、处理中、未知和失败等情况，明确记下未检查分支，不把正常路径扩展为全部通过。本项目正文建设阶段不执行本方案；未来实施同样按其任务权限使用合适的隔离材料。

键盘、标签、说明和错误的基础来自W3C Easy Checks冻结页；该页只支持有限初查。NVDA基本命令另据2026-10-02取得的官方2026.2手册，补充范围见第9节；它没有证明目标页面行为或全面可访问性。

### 7.2 先用键盘完成同一任务

交互负责人逐步记录按键、到达位置、可见内容和后台结果关联。不要先用鼠标替自己定位目标，再声称键盘已找到入口。

| 操作步骤 | 应观察和保留的具体事实 | 不满足时的分支 |
|---|---|---|
| 从私人列表开始，用Tab和Shift+Tab逐项前进、返回，找到C@L及操作入口 | 顺序符合任务阅读关系；每一步焦点可见；相似卡片入口能辨认对象；进入后仍能离开 | 记录最后可到达控件及下一预期位置，区分入口找不到、焦点不可见和被困；不能用鼠标完成来补记通过 |
| 用键盘激活入口，遍历两项操作、说明、取消和提交 | 面板出现后焦点落到能理解上下文的位置；静态说明可阅读，动作可到达；关键功能没有只在悬停时出现 | 修正对应入口、顺序或信息呈现；静态说明无需都成为Tab停靠点，另查其阅读可达性 |
| 在操作选项之间移动，核对对象与后果；使用该控件定义的键盘动作选择 | 浏览选项不会意外提交或跳离；选择与提交可区分；名称明确区分移出和最终删除 | 若一移动就产生效果，检查控件和提交关系；具体自定义控件按已确定的按键约定检查，不臆造统一键位 |
| 在未提交分支激活取消，再从原处重新进入 | 本次没有发出请求；焦点回到原入口或有意义替代位置，用户可继续任务 | 页面关闭和后台无请求分别取证；缺任一证据保留未判定 |
| 选择操作并提交；然后关闭、重新进入状态查询 | 能用键盘找到原操作状态；受理后关闭不被显示为撤销；焦点没有因进度刷新反复跳走 | 记录找不到的入口或被打断动作；仍用同一K/O核对后台，禁止另建请求作为检查捷径 |
| 在受控错误分支不选择必需操作就提交，再按提示修正 | 错误说明具体指出需要选择的组，提示在需要时可找到；不只靠颜色；修正后可继续且对象不被换掉 | 记录错误文字、位置及关联；若实际设计没有该必填选择条件，换成真实已定义的可修正输入错误，不凭空要求新增字段 |

Enter或空格能否激活，取决于控件的实际类型和已定义行为；普通链接和按钮应按各自类型检查。若采用模态面板，焦点循环留在面板内可以是有意设计，但必须能到达并执行明确的关闭或取消，使用户返回任务；不能把任何焦点限制都判为陷阱。Esc是否关闭面板须由产品定义并实测，也要与下一节NVDA切换模式的含义区分。

### 7.3 用NVDA核对名称、说明、错误和状态

先使用已安装NVDA的开始菜单入口启动，核对实际版本和配置。NVDA修饰键默认可用Insert或关闭Num Lock后的数字键盘0，也可配置Caps Lock；本方案以当前已记录的配置为准。按NVDA+1检查键位帮助，再按一次退出，避免把帮助模式中按键未执行误判为页面失败。以下命令据官方手册的限定章节；步骤和判断是本题工程适配。

1. 回到列表，使用Tab与Shift+Tab移动实际系统焦点；在卡片入口、选项、取消、提交和状态查询处按NVDA+Tab读取当前焦点。记录实际读出的名称、类型、值和状态，核对能否区分对象与两种删除后果。控件外观有文字而读出名称为空或错误时，记录具体控件，检查可访问名称的实际关联。
2. 在浏览模式下用方向键阅读面板标题、对象、D/X说明、备份范围和必要记录说明；需要直接操作表单控件时检查焦点模式，必要时按NVDA+空格切换。先确认当前模式，再判断按键被页面处理还是被阅读器处理。自动进入的焦点模式下Esc可回到浏览模式，不能仅凭一次Esc未关闭面板判定面板故障。
3. 用键盘进入必需选择组，记录名称、选项、已选状态及必填说明是否在决定前可取得。把实际朗读和页面标记中的标签/描述关联对应起来。HTML的label/for/id是常用方式，其他正确关联也可能成立；检查结果按实际名称和关系判断，不强制所有控件用同一种写法。
4. 在同一已定义的可修正错误分支提交，保持对错误出现时的朗读和焦点位置的记录；随后用浏览模式或正常导航找到完整错误、关联选项及可做修正。记录错误是否被及时告知、是否能定位并纠正，不能只保存一张红框截图。无错且可安全保留的输入应仍在，敏感输入的保留另按实际要求判断。
5. 在已准备的受理、处理中、未知、完成和失败分支，分别观察状态改变时实际听到什么，再从状态查询入口读回完整文字与对象关联。比较语音、视觉文字、查询响应与第6节的含义。若视觉变了却没有及时可感知反馈，或只有短暂提示且无法重读，登记该分支的障碍；即使读出“完成”，仍须核对第5节后台证据。
6. 在未提交取消与已受理关闭两个分支，记录关闭后的实际焦点名称、用户能否继续阅读，以及再次进入是否仍查到原操作。阅读器能读到文字不证明用户理解了后果；理解性检查需要另外取得合适使用者、任务和观察依据。

可访问名称描述控件是什么，说明帮助理解当前选择，状态表达当前证据；三者各有检查对象。不要让所有静态文字都抢占键盘焦点来“解决”读不到状态。具体通知实现须在目标版本下验证，本文不规定某个属性一加就必然正确。

### 7.4 让一次初查的结论可复查

每条实际记录应包含环境与页面版本、对象/生命周期、分支初态、按键和模式、预期依据、实际焦点/名称/说明/错误/朗读、同一操作的后台结果，以及未执行或无法判断的部分。发现问题时保存最短可重现路径和具体阻碍，不编造缺陷根因；环境没有启动、键位配置不明和产品实际障碍分别记录。

本方法目前只有这些步骤和预期，实际观察均为未执行。W3C冻结页的两张标签示意图没有恢复或查看，本文只使用文字自足的关联与一般位置建议，不给出图像质量结论。即使以后本表各项实际通过，也只支持该构建、环境和已走任务的有限结论；全面可访问性评价仍需更广的用户、技术和标准范围。

## 8. 交付可判断的结论与后续证据

一项小任务可以在现有记录中留下几段说明；多路径删除才需要较完整的关系和状态表。交付者应让下一位工程师能够回答：当前允许什么，哪项条件尚缺，什么观察能改变决定，以及谁接手相应责任。

本题的当前结论是：私人查看、编辑和有限恢复目的已有题设依据；新增跨活动推荐仍缺本人新用途同意，停止相应收集和交付承诺。窄化为当次建议只有在目的另行确认后才进入选择。移出、最终内容删除和最小操作记录的退出分别定义；D/X具体依据、E、备份清除与接入能力仍需给定，不能宣布功能上线或全生命周期完成。

交付中保留以下相互衔接的内容：

| 交付部分 | 沿C@L应交给下一位什么 |
|---|---|
| 目的与决定 | 已确认私人目的、新用途未决、五类不同依据、决定者和未决影响 |
| 信息与接收者 | 必需字段、拒绝的额外字段、可替代方案、实际接收者及传播限制 |
| 生命周期 | 内容/最小记录/各副本，停止访问、恢复、处置的触发与端点，D/X/E及其依据 |
| 派生与恢复 | C@L及版本、全部贡献和载荷范围、旧输入与当前控制、B和X关系、各路径证据 |
| 关键交互 | 从列表到结果的任务，发送前身份和K/O关系，受理/处理中/未知/完成/失败，取消与关闭的差别 |
| 初查与实际结果 | 指定环境、键盘与NVDA步骤、各分支实际观察及后台依据；未执行项明确保留 |

停止条件必须指向具体工作：用途或同意未定时停止依赖它的新处理；同对象同时间要求互斥时停止承诺两者兼得；无法证明清除或防复活时停止宣布相应完成；结果未知时停止未经保护的重做；目标环境未检查时停止声称交互通过。已确认事实与可独立进行的分析仍可继续。

本方法的写作与来源核查不能代替实现验证。后续取得真实观察前，分别保留来源支持、工程推导、准备中的检查及实际执行结果；独立审阅也须绑定当前正文和实际证据。不能用词语命中、格式正确或一份自评，把未运行的删除、恢复或辅助技术检查变成通过。
