## 1. 把问题报告变成可检查的问题

适用于已经观察到行为不符，需要查明可能原因、选择下一项检查并判断修复是否针对原因的任务。先写预期与实际的差别、受影响范围和证据来源，不把“看起来像缓存问题”写成事实。若只是审查尚未运行的差异，需要先证明触发路径和影响，不能把本方法的虚构故障当成代码存在缺陷的证据。

以下是原创静态题设。所有表中结果均为给定观察，用于推导下一步，不是执行记录，也不来自真实项目或书中案例。

一个工作区的文档预览接收 `Preview(D-v4,C1)` 或 `Preview(D-v4,C2)`。D-v4 是不可变文档版本，C1/C2 是不可变配置版本；独立配置表规定 C1 的页脚为“甲”，C2 为“乙”。配置按明确身份读取，不解析 current 别名。预览只产生文本，没有业务写入或外部副作用。主线中，结果仅取决于文档版本、配置版本与固定渲染规则版本。

最初报告只有：“选择 C2，界面却显示甲。”这证明有一次报告的预期与显示不符，尚不知道服务器实际返回了什么、请求是否重叠、缓存是否已有内容。报告不能直接支持“清缓存即可修复”。

最小调查记录应补齐：请求身份、文档与配置版本、程序版本、请求及响应关联、缓存初始状态、发生时间和影响。时间用于定位，不能单凭相近时间建立跨进程因果顺序。预期必须来自需求或独立配置表，不从当前错误输出倒推；需求本身未确定时，先澄清预期，见[验收依据与变更影响](acceptance-evidence-change-impact.md)。

本题后续隔离观察使用固定程序 B7、同一实例和串行请求，每次等前一请求结束。保留服务器原始响应，并另外关联界面显示。缓存是该实例可重置的内存数据，重置不影响业务记录。这些条件只属于题设；不能据此认为真实缓存都可以直接清空。

## 2. 先决定是否需要缓解影响

诊断目标是解释原因，缓解目标是降低当前损害。两者可以并行安排，但不能为了得到更漂亮的原因证明，让持续损害继续扩大。

若实际任务只是隔离环境中的偶发现象，可以先收集现有观察再设计实验。若错误结果正在影响用户或破坏数据，应先按影响选择已获授权且后果可控的缓解动作，同时尽量保留定位所需的版本、输入及状态。事故响应角色、升级和交接需另外落实；本篇不替代完整事件管理。

对本题的预览错误，有三个候选，而非一条默认命令：

| 候选 | 可能收益 | 动作前所需证据与代价 |
|---|---|---|
| 暂时返回明确不可用 | 避免继续展示错误预览 | 确认调用者能区分不可用与正确结果，评估被中断的业务并取得对应授权 |
| 临时绕过缓存 | 直接重新生成结果，可能减少错误复用 | 需确认该路径没有隐藏写入、容量可承受、配置和文档仍固定；否则可能扩大负载或触发其他后果 |
| 清理特定缓存记录 | 移除已知错误结果 | 需知道完整范围、在途写入和重建成本；清空后旧程序仍可能再次写入错误项，不能当永久修复 |

题设没有给出生产容量或操作权限，因此不执行这些生产动作。现实任务里缺证时应取得相应事实或交给实际负责人，不能由 Skill 自行扩大权限。若采取缓解，记录生效范围、时间、版本、实际观察和撤销条件；“用户暂时看不到错误”与“原因已确认”分别报告。

## 3. 为竞争解释写出不同预测

候选解释要能产生不同的可观察结果。仅列出“网络、数据库、缓存、前端”只是组件名单，不能指导下一项检查。

| 解释 | 在本题中的具体预测 | 能否定什么、不能否定什么 |
|---|---|---|
| H1：C2 总被解析或呈现为 C1 | 独立空缓存下请求 C2，仍返回甲 | 若返回乙，可否定“总是错误”的版本；不能排除只在特定状态下发生的配置问题 |
| H2：缓存把不同配置当成可复用结果 | 同一 D 先请求 C1 再 C2，第二次复用甲；反向顺序可能复用乙 | 顺序相关只支持缓存范围问题；缺少键字段、错误归并配置或其他共享状态仍可能造成相似现象 |
| H3：界面使用了旧请求响应 | 服务器对当前 C2 返回乙，界面却显示旧 C1 的甲 | 若当前请求关联的原始响应本身就是甲，单纯界面乱序不能解释这条观察；不能因此证明所有前端逻辑正确 |

这些解释不是穷举，也不必互斥。可能同时存在键错误和界面关联错误；应按每条观察限定结论，而不是选中一个解释后删除其他证据。

下一项检查先选“空缓存下独立请求 C1/C2”：它能低成本否定 H1 的强版本，且有明确初始状态。全量日志或更复杂的负载实验此时没有必要。检查的优先级由区分能力、代价和风险共同决定，不由工具是否熟悉决定。

## 4. 逐步取得区分证据

### 4.1 空缓存结果改变了第一种解释

给定观察 A：在隔离实例，固定 B7、D-v4 和渲染规则，独立清空后请求 C1 得到甲；再次独立清空后请求 C2 得到乙。每次记录请求身份及实际配置身份。

这否定了“H1：C2 总被处理成 C1”。如果只做 C2 且成功，仍不足以检查 C1 的独立基线；两个明确预期一起保留。不能把结果写成“配置处理没有任何缺陷”，因为还没检查带历史状态、并发或其他配置。

下一步不是继续重复同一个空缓存成功结果，而是保持输入和程序不变，改变缓存已有状态，检验 H2。

### 4.2 改变请求顺序，只能缩小范围

给定观察 B：

| 初始状态与次序 | 第一次响应 | 第二次响应 | 独立预期 |
|---|---|---|---|
| 空缓存，C1 后 C2 | 甲 | 甲 | 甲、乙 |
| 重新空缓存，C2 后 C1 | 乙 | 乙 | 乙、甲 |

两组均为串行调用，前一请求已经结束；服务器原始响应中的请求身份分别与当前调用匹配，界面显示与对应原始响应一致。因此，单纯 H3 的“旧响应在界面覆盖新响应”不能解释本组错误。这里排除的是该条因果解释，不是给整个界面做正确性认证。

相同文档下，后一次结果跟随第一次配置，而非后一次实际要求。这支持缓存或共享状态中的错误复用，但还不能确定是哪一行代码。若此时直接修改缓存键，可能碰巧掩盖配置归并或可变对象污染。

下一检查针对一个具体未知：不同的实际配置，在结果复用之前是否仍保持不同身份？如果它们早已被错误解析为同一版本，应回到配置路径；如果配置仍不同而实际缓存键相同，再检查键的构造与命中返回路径。

### 4.3 组件边界与实现共同说明机制

给定观察 C：在相同 B7 的边界记录和代码检查中，可以确认：

1. 两个请求进入缓存边界时分别携带不可变的 C1 与 C2，没有在此之前被归并。
2. B7 的键构造函数只接收 D-v4，实际键不含配置身份；两次得到同一个键。
3. 第一条缓存项保留其配置身份和已生成的页脚。第二次命中该项后直接返回，未调用渲染器。
4. 未命中路径把实际请求配置传给渲染器，与观察 A 的空缓存结果相容。

现在可以连接因果步骤：第一次请求把某配置的结果写入文档键；第二次不同配置映射到同一键；命中路径跳过重新生成，返回了先前结果。反向填充时错误结果随之反向变化，也由同一机制解释。

在这个有明确资源与实现条件的模型中，可以确认“缓存复用缺少结果所依赖的配置版本”是所示失败的原因。结论范围限于这些路径与输入，不证明其他缺陷不存在，更不等于真实部署已经复现或修复。

如果实际只拿到观察 B，没有边界或实现证据，应写“缓存/共享状态复用有较强支持，具体机制未确认”，而不是借用本题的观察 C 填补事实。

## 5. 控制实验条件与观察范围

一次阴性结果只在实际覆盖范围内排除预测。保持相同版本、输入、前置状态和关联方式，才能比较结果差异。缩减请求数量、替换组件、删除代码或清理状态时，需要检查原触发条件是否仍在；失败消失可能意味着移除了必要条件，也可能只是没有再经历所需交错。

本题需要区分的状态至少包括：B7 程序版本、D-v4 内容、C1/C2 内容、渲染规则版本、实例身份、缓存重置范围、调用次序及实际原始响应。配置内容不可变只是题设保证；实际使用可变别名时，要记录解析后的版本，不能只记录别名。

观察也有成本和缺口。只记录缓存命中次数，不能判断命中的是哪个配置；只保存界面截图，不能区分服务返回和显示选择；采样日志没有某条事件，不能证明事件没发生。请求身份应贯穿相关边界，并说明一个请求中的多次尝试怎样区分。跨进程时钟未校准时，不用显示时间强行排序。

增加详细日志可能改变时序、资源占用或数据暴露范围。优先使用已有的、能回答当前问题的观察；新增观察要限定字段和时间，并保存开启前后的配置。若实验本身改变现象，应把这一点作为结果，而不是当噪声删掉。恢复实验前配置也要核对期间状态变化，不能假设关闭日志就恢复全部初始条件。

一个重要变体是：错误只在并发调用时出现，而串行路径始终正确。这时本题串行结论不能沿用。可能存在共享可变配置、回调关联或缓存写竞争，应取得实际交错、请求输入在何处被修改和结果写回的证据。串行成功不能排除并发原因；增加延迟后不再失败也不能证明修复。若无法安全复现，只能保存支持程度和下一项必要证据。

## 6. 从机制推导修复与验证

### 6.1 修复结果复用条件

主线的错误来自不同结果影响条件复用了同一条缓存项。因此，修复目标是让缓存身份与实际计算输入一致，而非强制每次清空或对“C2 返回甲”加特判。

在本题限定条件下，候选键为完整的 `(文档版本, 配置版本, 渲染规则版本)` 元组。键构造与渲染都从同一个固定请求上下文取得输入，避免键按 C2 生成而计算时读取了后来变化的 C1。元组应有无歧义编码，不能靠可能碰撞的字符串拼接建立身份。

真实系统的结果可能还取决于工作区、权限、语言或其他状态。应按实际计算与访问约束核对这些因素，不能把本题的三个字段当通用完整键，也不应不加判断地把所有可见字段塞进缓存键。若无法给出可安全复用的条件，考虑禁用该处复用，但须重新评估成本。

### 6.2 用同一独立预期检验修复

保留 B7 和其可观察失败条件，再检查修改版本。下表是待执行的验证预期，本篇没有运行这些检查：

| 检查 | 修改前可暴露什么 | 修改后应取得什么证据 |
|---|---|---|
| 空缓存独立 C1/C2 | 原本正常的生成路径 | 仍分别为甲、乙，避免修复损坏原成功路径 |
| C1 后 C2、C2 后 C1 | 已固定的错误复用机制 | 每个请求都符合独立配置表，不依赖第一次填充者 |
| 相同完整键再次请求 | 复用是否存在及其含义 | 可复用原正确结果，不能只靠永远未命中让用例变绿 |
| 不同文档版本或渲染规则版本 | 相邻身份碰撞 | 不复用错误版本；测试数据应让版本差异产生可区分结果 |
| 有缓存与明确绕过缓存 | 两条路径的语义差异 | 相同固定输入下业务输出一致；耗时差异不作为语义错误 |

预期来自配置与行为要求，不调用被修复函数自己计算“正确答案”。既检查错误情形，也保留原来应成功的情形；检查层次和观察对象按[风险、独立预期与验证层次](test-risk-oracles-layers.md)选择。只检查键字符串出现了 C2，不证明实际运行入口使用了该键，也不证明输出正确。

复现用例在修改前失败、修改后通过，可以支持本机制的修复；还需检查相关调用路径和副作用。不能在修改后同时清空全部状态、换配置、替换版本并改变请求顺序，再将成功全部归因于键修复。

### 6.3 旧状态和实际恢复另有责任

即使新键正确，旧缓存和旧处理者仍可能存在。主线候选采用新的键格式命名范围，使新程序不再读旧格式；并确保旧 B7 无法把旧格式结果写入新范围。若只是复用旧键并清一次缓存，旧工作仍可能重新污染结果。

采用新范围会降低初期命中率并增加重算与内存需求，需要容量依据。若多个版本并存，要说明各版本读写哪个范围、何时可清旧项，以及撤销变更后读到什么。回退到 B7 并恢复旧缓存可能把同一故障带回来，回退动作不能自动称为安全恢复。

这里列出修复所依赖的旧状态处理条件，不声称完成全套混合版本发布协议。实际部署、清理或回退仍按任务授权和交付流程开展；本方法的静态题设不提供生产操作许可，也没有上线成功的证据。

## 7. 证据不足时怎样继续或停止

调查应随证据改变方向，而非无限增加日志。一次检查前写出要区分什么、什么观察会改变决定以及代价；结果不能区分候选时，说明为什么，并选择更有区分力的检查。

可以结束当前定位阶段的条件是：已确认或有充分支持的机制与已观察事实相容，剩余不确定性明确，下一修复或缓解有与后果相称的依据。不要求证明整个系统不存在其他原因。高风险动作不能仅靠“较有可能”自动执行；需要补证或由具备权限与责任的人决定可接受的处置。

若没有原始响应、无法关联请求与配置，先取得这些必要观察；若现场条件不可安全重建，保留候选与不足结论；若当前权限不能检查某组件，把所需字段、访问目的和阻断判断的原因交接给实际负责人。不要把“有人负责”当成对方已经接手。

交付至少区分三层：

- **观察事实**：来源、身份、版本、时间范围、检查条件、实际结果及缺失项。
- **解释与依据**：支持或反驳哪个预测，适用范围，多因或未排除分支，为什么下一项检查有价值。
- **动作与验证**：已经执行的缓解、候选修复、验证对象和预期、尚未执行事项及责任。无实际执行时明确写待执行。

定位相同机制的其他入口具有价值，但搜索应围绕同类键构造、上下文绑定或复用路径，不能把一次缺陷变成未经授权的全库重写。改进清单、事件时间线及长期责任跟踪属于后续复盘方法，不能由本篇的一份诊断说明替代。

## 8. 来源与采用边界

| 来源与定位 | 采用原则 | 限定范围 |
|---|---|---|
| Code Complete，23.2 Finding a Defect，`OEBPS/ch23s02.html#scientific_method_of_debugging` | 数据、假设、区分检查与反例；稳定及缩减触发；检查最近变更和调整搜索范围 | 不采用历史比例和对高发原因的强断言；删代码后失败消失不是无条件因果证明 |
| Code Complete，23.3 Fixing a Defect，`OEBPS/ch23s03.html#fixing_a_defect` | 理解机制、确认竞争解释、保留原版、逐项修改、修复验证及相关回归 | 不把短程序研究推广成修改前必须读完整大系统；不默认全库修改 |
